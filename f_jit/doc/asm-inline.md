# f_jit 内联汇编可行性分析（JIT lambda 内）

> 状态：**仅可行性分析，未开发、未立规格**。本文不改变任何既有语义与格式。
> 分析对象：在 f_jit 方言（lambda 源码，`.fbc` 字节码）中书写内联汇编，经 JIT 直接进入机器码执行。
> 平台边界：**仅 Linux x86_64 与 Linux aarch64**（其余 OS/架构一律不支持，见 §4.8）。
> 依据规格：`jit-bytecode-m1.md`（v0.18.36）、`jit-bytecode-m2.md`、`jit-bytecode-m3.md`、`design-m1/m2/m3.md`、`plan-m1.md`。

---

## §0 结论摘要

**技术上可行**——三条路都有明确落点，且不需要仓颉编译器提供内联汇编能力（方言是 f_jit 自己的语言）：

| 判定项 | 结论 |
|---|---|
| 语言前端 | ✅ 可做：方言词法/语法/降低全在 `compiler/` 内，扩展语法无外部依赖 |
| 字节码表示 | ✅ 可做：新常量 kind（推荐）或新 opcode（0x08–0x0F/0x1D–0x1F/…/0xC0–0xFF 仍有 RSVD 槽） |
| 机器码发射 | ✅ 可做：`CodeBuffer.write(bytes, off)` / `patch` / `seal` 已支持整段字节写入与 W^X |
| ABI 契约 | ⚠️ 有明确约束：`r15`/`x19` 持 ctx、帧 16 B 对齐、实参 `[rsi-8i]`/`[x1-8i]`、callee-saved 集合 |
| **三引擎一致性（I7）** | ❌ **会被打破**：解释器无法执行机器码 ⇒ 含汇编的单元必须**排除在解释器与差分之外** |
| **deopt 重放** | ❌ **会被打破**：`-1 → Interp.run 重跑` 对汇编单元不可用 ⇒ 必须**禁 deopt**（强制 `JitMode.Force`） |
| 安全模型 | ⚠️ 本质是**进程内任意代码执行**：无法沙箱化，只能 `unsafe` + 显式 opt-in + 信任边界文档化 |

**推荐形态**：**B（原始机器码字节 + 声明式契约）先行**；A（汇编文本前端）作为 B 之上的二期可选层；**不建议**把内联汇编做成"普通能力"（会持续破坏 I7 与安全模型，见 §4.1/§4.6）。

**三条硬代价**（立项必须先接受）：
1. 含汇编的单元成为 **JIT-only 单元**（解释器拒绝、差分测试排除、改用金样对拍）；
2. 含汇编的函数 **禁 deopt**（不得触发 `-1` 重放），因此也**禁**变更型指令（沿 `§9.15` 同型禁令模式）；
3. 汇编块 **不得触碰** helper/句柄表/窗口/GC/ctx（否则窗口账目、GC 安全与错误归因无法证明）。

## §1 命题与范围

**命题**：在 f_jit 编译的 lambda 中，允许书写内联汇编；该汇编在 `JitMode.Auto/Force` 下由对应后端原样落入 code buffer 并执行。

**范围**：
- 仅 Linux x86_64 / Linux aarch64（`f_base.OS.Arch` 判定 + 加载期双重门禁）；
- 仅分析可行性、代价、方案与工作量；**不含实现**；
- 不评估"通过内联汇编调用宿主仓颉 API"（既有封闭白名单明确禁止，见 §4.5）。

**非目标**：跨平台可移植的汇编抽象、汇编级调试器、汇编与解释器语义等价。

## §2 调研事实

### 2.1 仓颉语言层：**没有内联汇编**

- 语言特性文档（`cangjie_docs/docs/dev-guide/source_zh_cn`）检索 `内联汇编|汇编|asm`：**0 命中**；
- 全量文档仅两处出现"汇编"字样，且均与语言能力无关（`cmd-tools/cjdb_manual.md` 的调试器说明、`central-repo/agreement/agreement.md` 的条款文本）；
- 结论：**不能依赖 `cjc` 提供 `asm` 语法**；方言要支持内联汇编，只能由 f_jit 自己定义语法并自行编码（这反而是可控的——方言本就是我们自己的语言）。

### 2.2 f_jit 现有能力（可直接复用）

| 能力 | 位置 | 对内联汇编的意义 |
|---|---|---|
| `CodeBuffer.write(bytes, off)` / `patch(pos, bytes)` / `read` | `src/backend/CodeBuffer.cj:99/112/117` | **整段字节写入**已有原语，形态 B 零新增底层能力 |
| `CodeBuffer.seal()`（W^X）/ `flushICache()` | `src/backend/CodeBuffer.cj:131/149` | 汇编写入必须在 seal 前完成；指令缓存刷新已有 |
| 两后端 lowering（157 opcode 全覆盖，`verify.md:69` 核对） | `src/backend/X86Lower.cj`、`A64Lower.cj` | 只需为 ASM 指令加一条"拷贝字节"分支 |
| **原样写字节的现成原语** | `src/backend/X86Lower.cj:68 func appendBytes(bs: Array<UInt8>)`（`:101 finish()`；`X86Compiler.cj:46/49` 已用它拼接序言/尾声） | **x86 侧形态 B 几乎零底层成本**；aarch64 侧需给 `A64Emitter` 补一个"写字节"入口（`A64Emitter.cj:118 finish()` 已有） |
| 帧与 ABI（`r15`/`x19` 持 ctx；`rsp`/`sp` 16 B 对齐；实参 `[rsi-8i]`/`[x1-8i]`） | `jit-bytecode-m1.md` §12.2/§12.3 | 汇编契约必须声明并保留这些寄存器/布局 |
| 收敛块（`SET_SITE` 写 `[r15+8]`；`CHECK_ERR` 比较 `[r15+0]`；`BAIL`/`jit_dump`） | `jit-bytecode-m1.md` §12.4 | 汇编块内出错无法归因 ⇒ 契约要求"块内不失败" |
| opcode 表与 RSVD 槽 | `jit-bytecode-m1.md` §5（`OP_RSVD`：0x08–0x0F、0x1D–0x1F、0x27–0x2F、0x3C–0x3F、0x4E–0x4F、0x6F、0x73、0x8A–0x8F、0x9F，另 0xC0–0xFF 为 M2 预留区） | 有充足空槽新增 `ASM` 指令 |
| 常量 kind（10 = Regex、11 = JSON 均"加载期一次实例化、跨调用复用"） | `jit-bytecode-m1.md` §11.5、`jit-bytecode-m3.md` §11 | **形态 B 的最佳载体**：kind 12 存机器码字节 |
| `verMinor` 规则：新增 opcode / 新 helper / 类型表变更等须递增；**加载器接受 ≤ 自身版本的 verMinor** | `jit-bytecode-m1.md` §11.6（当前 14） | 新 opcode/kind ⇒ **verMinor 15**；旧加载器按既有规则拒绝 |
| `flags.bit1 = 需要 JIT（必须为 0）` | `jit-bytecode-m1.md` §11.6 | 可复用为 **"JIT-only 单元"标记**（需改口径，见 §5.2） |
| `Assembler` 11 项静态校验（栈平衡、PUSH_KH 越界、deopt 模式等） | `plan-m1.md` S3.20 | 原始字节不可静态验证 ⇒ 需新增**声明式契约**校验 |
| `JitExecutor.create` 失败 ⇒ 静默退回解释器 | `design-m1`/verify.md CRITICAL-01 | **对汇编单元必须禁止静默回退**（否则变成 15/19 一类硬错误） |

### 2.3 关键 ABI 常量（汇编契约的输入）

| 项 | x86_64 | aarch64 |
|---|---|---|
| ctx 寄存器 | `r15`（callee-saved，全程持有；**禁** `rdx`/`rcx`） | `x19` |
| 帧寄存器 | `rbp`（+`[rbp-8]` 存调用方 `r15`） | `x29`（+`x30` 返回地址） |
| 栈对齐 | `rsp` 16 B 对齐 | `sp` 16 B 对齐 |
| 实参基址 | `rsi` 指最深实参，第 i 个在 `[rsi-8i]` | `x1` 同构，`[x1-8i]` |
| 返回值 | `rax` | `x0` |
| ctx 字段 | `[r15+0]=errCode`、`[r15+8]=site`、`[r15+16]=hwTop`、`[r15+40]=fnId` | `[x19+…]` 同布局 |
| IBT | 间接调用目标需 `endbr64` | 间接调用目标需 `bti c` |

## §3 三种实现形态

### A. 汇编文本 + 内置汇编器

方言接受 `asm "...Intel/AT&T 语法..."`，由 f_jit 自带汇编器编码为机器码。

- **优点**：可读性最好，贴近用户对"内联汇编"的预期；可支持标签/局部跳转/常量引用。
- **缺点**：**工作量最大**——两套指令编码表（x86 变长编码、aarch64 定长）、伪指令、标签与重定位、寄存器语法差异、错误诊断（列号/建议）；且仍需全部契约校验（§4.7）。
- **风险**：汇编器自身就是新的缺陷面（编码错 ⇒ 静默错值），且要两架构各写一遍。

### B. 原始机器码字节 + 声明式契约

方言接受字节串（如 `asm x86_64 "48 89 C3 ..."` 或 `asm { bytes: [0x48, 0x89, 0xC3], ... }`），JIT 原样写入。

- **优点**：实现最小（`CodeBuffer.write` 已有）、语义**完全可预测**（写什么执行什么）、平台分叉天然（字节按架构绑定）。
- **缺点**：可读性差；无标签/重定位 ⇒ 只能做**位置无关、块内自足**的代码；用户需自备编码器。
- **适用**：特殊指令（`rdtsc`、SIMD、原子操作、`pause`/`yield`）、极致热点手工优化、验证性实验。

### C. 白名单指令 intrinsic

如 `asim("add", r1, r2)` / `@asm(SIMD_ADD, ...)`，编译器负责编码与寄存器分配。

- **优点**：安全可控、可静态验证、与 I7 冲突最小（可让解释器也实现同一 intrinsic 的语义）。
- **缺点**：不是"内联汇编"而是"内建指令"；表达能力受限（无法写任意序列）；新增指令要三引擎同时实现。
- **适用**：目标只是"让方言能用某几条特殊指令"，而非开放汇编。

### 对比

| 维度 | A 汇编文本 | **B 原始字节** | C intrinsic |
|---|---|---|---|
| 实现工作量 | 大（+20–30 人日） | **小（最小子集）** | 中（每指令三引擎） |
| 可读性 | 高 | 低 | 中 |
| 可静态验证 | 中（编码后可验） | **低（只能验契约）** | **高** |
| 标签/重定位 | 支持 | **不支持（需限制）** | 不适用 |
| 与 I7 冲突 | 高 | 高（但可隔离） | **低（可解释器同实现）** |
| 静默错值风险 | 中（汇编器 bug） | 低（字节即真值） | 低 |
| 建议定位 | 二期可选前端 | **一期最小可行** | 若要长期开放"特殊指令"，优先 |

**推荐**：**B 先行**（唯一能以最小代价验证 ABI 契约与门禁模型）；A 作为 B 的**前端**（A 产出 B 的字节，契约层不变）；C 留给"只需要少数特殊指令"的场景，长期更划算。

## §4 与既有不变量的冲突（逐条）

### 4.1 I7「同一字节码三引擎逐位一致」——**硬冲突**

现状：`Interp` / `BackendX86_64` / `BackendAArch64` 对同一单元结果/错误码/site/报告文本**逐位一致**（`§13.2` 差分，`RealRunners` 四元组）。

含汇编的单元：
- 解释器**无法执行**机器码（也不应模拟）⇒ 只能**拒绝**；
- 差分测试**不能纳入**（没有第三侧）；
- 替代验收：**金样对拍**（JIT 结果 vs 源码内期望值/宿主侧同逻辑函数），并显式记录"该单元不参与 I7"。

**要求**：确立"**JIT-only 单元**"这一新类别（§5.2），在规格中把 I7 的适用范围改为"不含内联汇编的单元"，并新增对应测试门类。

### 4.2 deopt 重放 `-1 → Interp.run 重跑`——**硬冲突**

`JitReport` 的 `-1` 语义是"退回解释器透明重跑"（`S6.4`）。汇编单元无解释器路径 ⇒ 一旦 `-1`，**无法重放**。

**要求**：汇编单元内**禁止** deopt：
- 编译期：汇编函数的 `flags.bit0`（变更型）互斥检查（沿 `§9.15` 变更型 deopt 禁令同型）；
- 运行期：`JitMode.Off` ⇒ 直接拒绝编译/装载（不得静默回退）；
- 失败面：`JitExecutor.create` 失败 ⇒ **硬错误**（15/19 一类），不退回解释器。

### 4.3 fail-fast 与错误归因

现有模型：`SET_SITE` 前置写 site、`CHECK_ERR` 比对 `ctx.errCode`、`BAIL` 收敛并单次转储（`§9.16`）。

汇编块内：
- **无法**自动插入 `SET_SITE`/`CHECK_ERR`（字节不透明）；
- 若汇编崩溃（非法指令/访问违例）⇒ 进程级信号，**不是** `JitException`。

**要求**：契约声明"**块内不失败**"——不得访问可能失效的内存、不得执行可能 fault 的指令（除用户显式承担风险）；失败归因记为"不可用"，不做部分保证。文档必须写明：**汇编块内的错误不在 f_jit 错误模型内**。

### 4.4 帧与 ABI

汇编块必须：
- **保留** callee-saved 寄存器（x86：`rbx/rbp/r12–r15`；aarch64：`x19–x28/x29/x30`）；
- **不得改写** `r15`/`x19`（ctx）与 `rsp`/`sp`（栈平衡）；
- 若调用外部函数：栈 16 B 对齐、遵守 SysV/AAPCS64；
- **不得**构建/破坏帧布局（`[rbp-8]` 存调用方 `r15` 等）。

**要求**：契约字段 `clobbers`（声明破坏的 caller-saved 集合）+ `stackDelta`（块内净栈变化，要求恒 0 或由加载器校验）+ `preservesCtx`（恒真）。

### 4.5 句柄表 / 窗口 / GC

现有模型：句柄以 Int64 ID 存在，窗口登记 `hwTop`，引用型返回登记 1 槽，GC 只发生在 helper 边界（`§8.1`/`§9.6`）。

汇编块：
- **不得**调用 helper（H01–H75）——否则窗口账目/错误码/GC 都无法保证；
- **不得**触碰句柄表或窗口（`ctx.hwTop`）；
- **不得**触发分配/GC（进程内 GC 中断汇编执行会破坏假设）。

**要求**：契约声明"块内无 helper 调用、无分配、无 GC 点"；加载器按声明校验（无法从字节验证，只能**信任声明 + 负向测试**）。

### 4.6 安全模型——**本质性代价**

既有模型：封闭白名单（无宿主指针、无任意 API 调用、W^X、IBT），错误可枚举。

内联汇编 = **进程内任意代码执行**（可读写任意内存、可 `int3`/`ud2`、可跳任意地址）。**无法沙箱化**（同进程、同地址空间）。

**要求**：
- 语法必须置于 `unsafe` 语义之下（与仓颉 `unsafe` 概念对齐：显式承担风险）；
- `CompileOptions.allowInlineAsm: Bool`（默认 **false**）+ 每单元 `flags` 标记；
- 文档化信任边界："允许内联汇编 = 允许宿主进程内任意代码执行"，不承诺隔离；
- 运维建议：生产环境默认关闭，仅对可信源码开启。

### 4.7 可验证性（Assembler 11 项校验）

`Assembler` 现有校验（栈平衡、`PUSH_KH` 越界、deopt 模式、类型表、site 覆盖等，`S3.20`）对**不透明字节**失效。

**要求（保守校验）**：
- `stackDelta == 0`（块内净栈不变）；
- `clobbers ⊆ caller-saved`（且不含 ctx 寄存器）；
- `size ≤ 256 B`（上限，防止误用）；
- 架构标签与后端一致（`asm x86_64` 在 aarch64 上 ⇒ 编译期拒绝）；
- 可选：**字节级操作码白名单扫描**（x86 变长编码下不可靠，只能作 `diagnostics` 提示，不作安全保证）。

### 4.8 平台门禁（仅 Linux x86_64 / aarch64）

- **编译期**：`f_base.OS`/`Arch` 判定；非目标平台 ⇒ `SourceCompileException`（明确"内联汇编仅支持 Linux x86_64/aarch64"）；
- **装载期**：`flags`（JIT-only）+ `verMinor`（≥15）⇒ 旧加载器/非 JIT 环境拒绝；
- **运行期**：`JitMode.Off` 或后端不可用（非 Linux 恒 Interp）⇒ 拒绝执行，**不得静默回退**（§4.2）。

### 4.9 报告（DbgDump）与诊断

汇编可能写坏局部变量 ⇒ 转储内容不可信。

**要求**：含汇编的帧在报告中标注"**含内联汇编，变量转储不可信**"；或直接禁止该帧转储（更保守）。`site` 仍可标注块入口偏移（可归因到"哪一块汇编"）。

## §5 推荐方案草案（若立项；本文不实现）

### 5.1 语法草案（方言层）

```cangjie
// 形态 B：原始字节 + 契约（最小可行）
let t = unsafe asm x86_64 {
    bytes:   "0F 31",            // rdtsc → edx:eax
    clobbers: ["rax", "rdx"],    // 破坏的 caller-saved
    stack:   0,                  // 块内净栈变化（必须 0）
}

// 形态 A（二期）：汇编文本，由 A 前端编码为 B 的字节
let s = unsafe asm x86_64 "mov rax, [rsi-8]; add rax, 1"
```

约束：`asm` 只能出现在**表达式**位置；其类型由 `ret` 声明（默认 `Unit`，或 `Int64` 取 `rax`/`x0`）；块内**不可**引用局部变量（除实参寄存器约定）。

### 5.2 字节码表示（推荐：常量 kind 12 + 单条 `ASM` opcode）

| 方案 | 内容 | 评价 |
|---|---|---|
| **kind 12（推荐）** | `ConstPayload.PAsm(arch: u8, len: u32, bytes, clobbers, stackDelta)`；`FbcReader` 加载期校验一次、跨调用复用；`ASM` 指令仅带 `constIndex`（u16） | 与 kind 10/11 同模式；字节不进 code 段、不重复；校验集中 |
| 新 opcode 内联载荷 | `ASM arch u32len [bytes]` | code 段变长指令、校验分散、不推荐 |
| 复用 kind 11 JSON | — | 语义错位，禁止 |

配套：
- **新 opcode `ASM`**（占一个 RSVD 槽，如 `0x4F`），fmt = `u16`（const 索引）；
- **`verMinor` 14 → 15**（新增 opcode + 新 kind，符合 §11.6 递增原因）；
- **`flags.bit1` 语义改写**：由"必须为 0"改为"1 = 含内联汇编（JIT-only）"（需规格同步，属**兼容性变更**：旧加载器会拒绝 ⇒ 正是期望行为）。

### 5.3 发射流程

1. `FbcReader` 装载：校验 arch/长度/clobbers/stackDelta；登记常量；
2. `X86Lower`/`A64Lower`：遇到 `ASM` ⇒ **原样拷贝**字节到 code buffer（记录起止偏移，供转储归因）；
3. 若块作为**间接调用目标**（当前不支持）⇒ 需前置 `endbr64`/`bti c`；
4. `seal()` + `flushICache()` 沿用既有流程；
5. 契约校验失败 ⇒ 加载期拒绝（14/18 语义），运行期不出现。

### 5.4 测试策略（替代 I7 差分）

| 测试 | 内容 |
|---|---|
| 金样 | 每个汇编块：JIT 结果 vs 期望常量/宿主同逻辑函数（x86 与 aarch64 各一份金样） |
| 契约负向 | 错架构、超长、`clobbers` 含 ctx、`stackDelta≠0`、非法 kind ⇒ 加载期拒绝 |
| ABI 韧性 | 块前后局部变量值不变、`hwTop` 不变、`errCode/site` 不变（汇编不触碰时） |
| 回归 | 不含汇编的 560 例全量绿（零回归门槛不变） |
| 平台门禁 | 非 Linux/非目标架构：编译期拒绝 + 加载期拒绝 双层用例 |

## §7 风险清单

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 汇编块写坏 ctx / 栈 | 进程崩溃或静默错值 | 契约校验 + 负向用例 + 文档警示（无法根治） |
| R2 | 用户编码错误（字节即真值） | 非法指令 `SIGILL` | `size` 上限 + 可选操作码扫描 + 金样 |
| R3 | 与 I7 永久分叉 | 差分体系出现"例外单元" | 明确 JIT-only 类别、门禁、测试替代（§4.1） |
| R4 | deopt/回退路径漏网 | 运行期"透明回退"变成崩溃 | 编译期 + 装载期 + 运行期三层禁回退（§4.2） |
| R5 | 跨架构语义分叉 | 同一源码两架构结果不同 | 语法强制架构标签；不提供跨架构汇编抽象 |
| R6 | 安全边界被误读为"沙箱" | 安全事故 | 文档硬性声明"进程内任意代码执行"+ 默认关闭 |
| R7 | 汇编器（形态 A）自身缺陷 | 静默错值 | A 仅作前端、产物仍走 B 的字节与契约，可逐字节对拍 |

## §8 结论与建议

| 档位 | 内容 | 建议 |
|---|---|---|
| **D0 不做** | 维持现状：需要特殊指令时走 helper 扩展（受白名单约束，I7 不破） | **默认推荐**——除非确有"必须任意指令"的场景 |
| **D1 最小子集** | 形态 B：kind 12 + `ASM` opcode + JIT-only + 禁 deopt + 契约声明 + 金样测试 | 若确需，**从这里起步**（24–36 人日） |
| **D2 完整** | D1 + 形态 A（汇编文本前端）/ 可选 D1+C（intrinsic） | 仅当有真实用户需求与长期维护投入 |

**关键判断**：内联汇编在 f_jit 里不是一个"编码问题"，而是一个**语义契约问题**——它必然打破 I7、deopt 重放与安全白名单这三条现成立柱。若接受隔离（JIT-only + 禁回退 + 契约声明），技术可行；若不接受，则应选择 **D0/C**。

## §9 开放问题（需拍板）

1. **形态选择**：B（原始字节）先行，还是直接做 A（汇编文本）？
2. **隔离口径**：JIT-only 单元允许存在（I7 例外），还是要求"汇编单元也必须有解释器等价实现"（则需 C 形态）？
3. **`flags.bit1` 是否复用**为 JIT-only 标记（改口径），还是新增 flags 位？
4. **错误模型**：汇编块内 fault 是否一律视为"不可归因"（不做 `JitException` 包装）？
5. **默认开关**：`allowInlineAsm` 默认 false（安全）还是 true（便利）？
6. **上限**：单块字节数上限（建议 256 B）、每单元块数上限（建议 8）？
7. **是否允许 `asm` 作为间接调用目标**（决定是否强制 `endbr64`/`bti c` 与重定位需求）？
