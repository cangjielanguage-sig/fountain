> `2026-11-27-optimize-call-path-phase2`。

## 0. 一句话结论

并行执行本身已无全局锁；剩余的是**每次调用路径上的若干短临界区**。本方案按「先测量、再改一步、
用数据决定去留」的方式逐项验证，**没有数据支撑的改动一律回滚**。

## 1. 硬规则（不可协商）

1. **先基线后改码**：每一项改动动手前，必须先在当前 commit 上采集同一指标至少 5 次。
2. **一次只改一项**（或其不可分割的组合），单独提交，保证可 `git revert`。
3. **保留条件**（三项同时满足）：
   - 目标指标中位数提升 ≥ 本文给出的最小可观测收益（MOV）；
   - 其它指标中位数回退 ≤ 2%；
   - 全量测试零失败（`PerfOverride_test` 已知高负载假失败除外，单跑 3 次至少 2 次通过）。
4. **达不到就回滚**，并在 §7 决策日志记录「无效 + 数据」，不保留"看起来更优雅"的代码。
5. **共享构建机**（7 核 Cortex-A53、常驻负载 3+）只做初筛；`8 线程 ≥5×` 的达标结论必须在
   专用 ≥8 物理核机器上复测。
6. 任何改变**可观察语义**的改动（计数口径、错误码、API）必须先走 OpenSpec 变更，不能以
   "性能优化"名义直接改。
7. **前置项单独无收益时先回滚**；若后续项依赖它，则把两者合成一个实验重新判定——
   组合收益必须覆盖两项成本，否则两项都不保留。

### 2.1 指标

| 代号 | 定义 | 采集方式 |

| `S2/S4/S8` | N 线程加速比 = `N × T1 / wallN` | `ParallelThroughput_test`（现有） |

> `T1` = 单线程一次长调用的墙钟；`wallN` = N 线程各调用一次的墙钟。
> 所有指标都同时记录**原始 5 次值 + 中位数**，不只记一个数。

### 2.2 测量协议

```text
# T0 先补测量工具（不改产品代码）
cjpm test --filter CallPathBench_test --parallel 1 --show-all-output
cjpm test --filter ParallelThroughput_test --parallel 1 --show-all-output

# 每轮 5 次，取中位数；机器空闲（load < 0.5）、绑核、固定调频
for i in 1 2 3 4 5; do ...; done
```

- 场景 B1–B4 放在**同一个非门槛测试类**里，只打印 `CP-BENCH ...`，不做时序断言；
- `ParallelThroughput_test` 补 `@Assert(f.isJitBacked(), true)`——当前 734 ms / 2M 次循环
  很可能走解释器，若属实，`S4/S8` 反映的是解释器并行度，不能代表机器码路径；
- 噪声门槛：基线 5 次的中位数 `M` 与相对离散度 `d = max|xi-M|/M`；
  **MOV = max(3%, 2d)**。低于 MOV 的变化视为噪声，不保留。

每个候选改动都要跑：

`ParallelThroughput_test`（2M 次循环单元，单次约 734 ms）：

| --- | --- | --- |
| 1 | 733 847 µs | 1.00× |
| 2 | 1 153 839 µs | 1.27× |

**基线解读**：

- `Q4/Q1 = 195595/180681 = **1.08×**`：4 线程短调用几乎不扩展 —— 调用路径上的三把锁把 4 线程压成 1 线程；
- `F4/F1 = 1738/868`：4 线程字段查找单次成本翻倍 —— 每次 `find` 的全局锁 + bucket 拷贝在并发下直接互相排队；
- `S4 = 2.22×`：长调用仍能扩展（执行本身无锁），说明瓶颈在**每次调用的簿记**，不在执行；
- `jitBacked=1`：B1/B3 与 `ParallelThroughput` 的单元都由机器码承载，基线不是解释器数据；
- **A4 不稳定（0.78–1.11×），暂不作为 Phase 1 指标**：B3 受 §10 的 gen 阻断限制，只能测 25k 次复用，样本太短；A4 留到 Phase 2 修复 gen 后重测。

## 4. 实验卡

每张卡的结构：假设 → 改动 → 指标与预期 → 保留门槛 → 回滚条件 → 前提/冲突。

### T0 建立测量工具与基线（不改产品代码）

- **改动**：新增 `CallPathBench_test`（B1 短调用、B2 字段循环、B3 分配型、B4 ctx 创建/释放）；
  `ParallelThroughput_test` 增加 `isJitBacked` 断言与打印。
- **产出**：上述 6 个指标的基线中位数与离散度；写入 §7。
- **保留条件**：工具能稳定打印、5 次离散度 < 10%；否则先修工具，不进入任何优化。
- **注意**：这是测量基础设施，不参与 keep/revert 判定；没有它，后续任何收益都不成立。

### P1.1 HostFault 改线程本地

- **现状**：`HostFault` 全局 `mtx` + 两张 `HashMap`；`JitContext.free` 每次调用都 `clear`，
  即使无异常也抢一次全局锁（`runtime/HostCall.cj`、`JitContext.cj`）。
- **改动**：改为 `ThreadLocal<HashMap<UInt64, FaultEntry>>`；ctx 仅在调用线程读写，
  `record/causeOf/takeCause/clear` 全走本地表。
- **指标**：`L1`、`Q1`、`Q4`；辅助 `C1`。
- **预期**：短调用每次少 1 次全局锁；长调用（B0）可能落在噪声内。
- **保留门槛**：`Q4` 提升 ≥ MOV，或 `L1` 下降 ≥ MOV；且 `Q4` 回退 ≤ 2%。
- **回滚条件**：无指标达到 MOV，或异常 cause 用例出现跨线程串味。
- **前提**：无。与 P3.1 的顺序约束：**必须先于 ctx 池**（池复用 ctx 指针，旧 fault 必须先清）。

### P1.2 HostFieldTable 改不可变快照 + 无锁读

- **现状**：每次 H64/H65 字段访问都在全局锁内拷贝 bucket 到新 `ArrayList`，
  再锁外匹配（`runtime/HostField.cj`）——一次访问 = 一次锁 + 一次分配。
- **改动**：注册时在写锁内构建不可变快照，`AtomicReference<Snapshot>` 发布；
  `find` 只 `load()` + 数组遍历，不拷贝。
- **指标**：`F1`、`F4`；辅助 `Q1/Q4`。
- **预期**：字段循环应有明显收益（去锁 + 去分配）；普通调用（不访问字段）不受影响。
- **保留门槛**：`F1` 或 `F4` 提升 ≥ 10%（此项预期收益大，门槛高于 MOV）。
- **回滚条件**：`F1/F4` 提升 < 10%，或字段访问用例/注册期用例失败。
- **前提**：`accepts` 仍在锁外求值（可重入注册）；快照只增不删（`resetForTest` 除外）。

### P1.3 JitFunction / EscapedClosure 的 state/active 原子化

- **现状**：`enter/exit` 每次调用各进一次单元 `mtx`（`JitFunction.cj`），包装实例还要进
  `EscapedClosure` 的状态机；这是执行路径上最后一把"整调用级"的锁。
- **改动**：
  - `state: AtomicInt64`、`active: AtomicInt64`；
  - `enterUnit`：读 state → `active+1` → 复读 state；变 1/2 则 `active-1` 并抛 19；
  - `close`：CAS 0→1 → 轮询 `active==0` → store 2；超时 CAS 1→0；
  - 包装实例同理；`escaped` 清单、`cacheKey`、`release` 回调仍留在 `mtx`（冷路径）。
- **指标**：`L1`、`Q1`、`Q4`、`S4`。
- **预期**：短调用收益最明显；长调用（B0）收益有限。
- **保留门槛**：`Q4` 或 `S4` 提升 ≥ MOV，且 `UnloadConcurrency_test` 3 轮全绿。
- **回滚条件**：任何指标未达 MOV；或出现 close 与晚到 enter 的竞态（用变异验证：
  去掉"复读 state"后用例必须变红，否则测试不足以证明正确性）。
- **前提**：与 P1.1/P1.2 无冲突；三项可同属一个 Phase，但**分别提交、分别判定**。

### P2.1 HandleTable 分片空闲表 + 原子 totalSlots（**已实施，keep**）

- **现状**：`newSlot` 的 pop、`release` 的 push 都在同一把 `HandleTable.mtx`；
  分配型单元并发时这是最热的共享结构（design D3d 的 P1.2d）。
- **改动（推荐分片而非纯无锁）**：
  - 64 个 stripe，每个 `ArrayList<Int64>` + 独立 `Mutex`；
  - 槽按 `idx & 63` 固定归属，分配优先本线程/本 stripe，空了再扫描其它 stripe；
  - `totalSlots` 改 `AtomicInt64`，`capacityLimit` 用 CAS 兜底。
- **指标**：`A4`、`S4`、`S8`；辅助 `Q4`。
- **预期**：分配密集场景提升；纯计算单元基本不变。
- **保留门槛**：`A4` 提升 ≥ 10%，或 `S4/S8` 提升 ≥ MOV。
- **回滚条件**：`A4` 提升 < 10% 且 `S4/S8` 未达 MOV；或槽复用语义被破坏
  （`releasedSlotIsReusableWithNewGen`、`AnyHostCast` 的 `slotCount` 断言）。
- **前提**：分配策略必须保留"单线程刚释放的槽下一次复用"的行为；`resetForTest` 清全部 stripe。

### P3.1 JitContext 池化（**评估后不做**：收益上限 5.0% < MOV 8.4%，见 §12）

- **现状**：每次调用 `LibC.malloc(64B)` + `LibC.free`，并各做一次 `NativeMem` 原子计数。
- **改动**：`ThreadLocal<ArrayList<CPointer<Int64>>>` 池，`create` 取、`free` 还（上限 8）；
  归还前必须 `HostFault.clear(ctx)`；超出上限才真正 free。
- **规格前提（硬阻塞）**：`NativeMem.mallocCount/freeCount` 现在统计**真实 native 分配**，
  T27 用例据此断言。池化后必须先把口径改为「`nativeMallocCount` + `acquireCount`」并走
  OpenSpec 变更；否则 **不实施**。
- **指标**：`C1`、`L1`、`Q1`、`Q4`。
- **保留门槛**：`C1` 下降 ≥ 20%（池化主要消除 malloc/free 固定成本），或 `Q4` 提升 ≥ 10%。
- **回滚条件**：未达门槛；或出现 ctx 复用导致的旧 fault/旧 errCode 串味。
- **前提**：P1.1 已完成；NativeMem 口径变更已归档。

### P3.2 SignatureTable / AdapterRegistry 改 COW（**评估后不做**：不在调用路径上，见 §12）

- **现状**：`SignatureTable.getOrBuild` 与 `AdapterRegistry.lookup` 都在全局锁内；
  前者在封送宿主闭包时用，后者在编译/注册/查适配器时用。
- **改动**：与 P1.2 相同的不可变快照 + `AtomicReference` 发布；删除单位置锁读。
- **指标**：`Q4`（宿主闭包密集场景）；无此场景时以 `S4` 为准。
- **保留门槛**：对应指标提升 ≥ MOV。
- **回滚条件**：未达 MOV，或 `AdapterRegistry` 与卸载的可见性出现 UAF
  （前提：`close` 已排空 `active`，即 P5 语义）。
- **注意**：只在 profile 指向此处时才做；不要为了"全无锁"而改。

### P3.3 Signature/Adapter 与卸载的可见性（验证项，不是新改动）

- `AdapterRegistry` 存的是**代码地址**；COW 读者若持有旧快照，必须在代码释放前离开。
  该前提由 `close` 的 active 排空保证。用 `UnloadConcurrency_test` + 适配器回归验证；
  不满足则不做 P3.2。

## 5. 冲突与顺序（实施前必读）

| 交互 | 处理 |
| --- | --- |
| P1.1 × P3.1 | ctx 池复用指针 ⇒ `free` 必须先清 TLS fault；顺序固定 P1.1 → P3.1 |
| P3.1 × NativeMem/T27 | 计数口径是规格问题 ⇒ 先 OpenSpec 变更，再池化 |
| P2.1 × 槽复用测试 | 分片策略必须让单线程复用同一槽；否则改测试之前先改策略 |
| P1.3 × PromotionGroup | enter 双检失败路径不得触碰提升组；close 排空与晚到 enter 必须有复读 |
| P3.2 × 卸载 | 适配器是代码地址；依赖 close 排空，否则 UAF |
| P1.2 × `resetForTest` | 发布空快照；测试线程先 join，避免旧快照跨测试 |

## 8. 停止与升级条件

- 连续 **2 项**改动未达 MOV ⇒ 停止堆优化，改用 `perf`/火焰图定位真实热点；
- `S4` 在 Phase 1 后仍 < 2.6× ⇒ 先查 `isJitBacked` 与解释器回退，再谈锁；
- 任一改动导致全量回归 ⇒ 立即回滚，不进入下一 Phase；
- `8 线程 ≥5×` 只在专用 ≥8 物理核、load < 0.5 的机器上下结论；共享 VM 数据只作趋势。

## 9. 非目标

- 不把 HandleTable 改成"每槽一个原子字"的纯无锁结构（内存与 ABA 成本不匹配）；
- 不改编译管线、`CompileCache`、注册表的锁（不在执行路径）；
- 不为追求"零锁"而改变公开 API 或错误码。

## 10. 句柄 gen 编码阻断：已修复（2026-11-27）

- **现象**：B3 分配型基准在**单线程**第 32768 次复用同一槽后，`call` 抛 `code=99`、`site=-1`
  （探针：`i=32767` 首次失败；与并发无关）。
- **根因**：`HandleTable.makeId` 把 16 位 `gen` 放在 Int64 最高 16 位；`gen = 0x8000` 时拼装值越过
  `Int64.Max`，`Int64(u)` 的**受检转换**抛 `OverflowException`（若换成非受检位转换则得到负 ID，
  被 `id <= 0` 当空句柄）。两条路径都破坏「标识恒正」这一全库依赖的不变量。
- **修复**（变更 `fix-handle-gen-exhaustion`，归档 `2026-11-27-fix-handle-gen-exhaustion`）：
  `GEN_MAX = 0x7FFF`；到达上限的槽**退休**（不进空闲表、永不复用）；新增 `retiredCount()` 诊断。
  回归用例 `HandleTableGenExhaustion_test` 覆盖「复用 32767 次恒正」「退休后分配新槽」「旧 ID 永久失效」，
  并做过去掉退休分支的变异验证（两条用例同时变红）。
- **成本**：每槽每 32767 次复用占 1 个索引位（约 3e-5 槽/次分配），相对 4M 目录可忽略。
- **对基准的影响**：B3 迭代次数已从 5000 恢复到 15000，可跨过 32768 次复用边界；
  A4 仍受共享 VM 噪声影响（0.76–1.38×），Phase 2 判定时建议用专用机器或改短调用口径。

## 12. Phase 3 评估：不做（2026-11-27，数据结论）

### 12.1 单次调用成本分解（临时探针，已删除；release 构建，100k 次 × best-of-3）

| 场景 | ns/call | 与 0 参之差 |
| --- | --- | --- |
| 0 参数单元 `{ => 1 }` | 8583 | — |
| 1 参数单元 `{ n => n + 1 }` | 8977 | +394（实参路径） |
| 4 参数单元 | 9990 | +1407（约 350/实参） |
| `JitContext.create` + `free` | 429 | — |

### 12.2 结论

- **P3.1（ctx 池化）收益上限 = 429 / 8583 ≈ 5.0%**，低于 L1 的 MOV（8.4%）；
  而它需要改 `NativeMem` 计数口径（T27 断言「create 一次 = 一次 malloc」），属规格变更。
  **按硬规则不做**：收益不足以支付规格与泄漏账目的复杂度。
- **P3.2（Signature/Adapter COW）不在调用路径上**（只在封送宿主闭包/建计划时用），无收益证据，不做。
- **实参路径**每个约 350–400 ns（malloc 一次 + 反向拷贝）：改线程私有暂存区可省下这部分，
  但同样只占 ~4–5%，且引入重入分级缓冲的复杂度 ⇒ **不做**。

### 12.3 剩余 8.6 µs 在哪：已知与未知

已知每次调用包含：2 次 `Mutex` 配对（P1.3 已证明去掉无收益）、窗口开合（`Win` + 2 个 `ArrayList`）、
`CallMarshal` + 2 个 `ArrayList`、`cells` 数组、1 次 `malloc/free`、`CFunc` 构造、一次机器码调用。
合计约 8–9 次 GC 分配 + 1 次原生分配。

**未验证的假设**：在这台共享 7 核 A53（load 常驻 3+）上，8.6 µs 很可能由 GC 与缓存未命中主导，
而非某个具体锁。要证实需要 `perf`/GC 计数——构建机**没有 perf**（`perf_event_paranoid=2`），
共享 VM 的噪声也让 <10% 的改动无法判定。

### 12.4 停止条件

> **2026-11-27 更新：本节结论已被 §16 推翻。** 进程内探针证明剩余成本的主项是
> **每次调用 14 次 `ThreadLocal` 访问（~4.4 µs，占一半）**，不需要 perf 即可定位；
> 合并为单个 `RuntimeState` 后 `L1` 下降 32–36%。本节保留为历史记录。

`optimize-call-path.md` §8 的停止条件已满足：连续两项（P3.1/P3.2）无数据支持。
**调用路径优化到此为止**；后续若要把单次调用从 µs 级降到亚 µs，需要：
1. 专用 ≥8 核机器 + `perf`（或仓颉运行时 GC 统计）；
2. 按 profile 决定是减少每调用分配（Win/Marshal 复用）还是消除 `malloc`；
3. 在此之前不再做「猜热点」式的微优化。

## 13. Phase 4：两处残余锁清理（2026-11-27）

### 13.1 JitBindSupport 登记表快照化

- **问题**：`isInstanceOfHost` 对**接口实参**走 `acceptsInterface`，每次取全局 `mtx` + `HashMap` 查找；
  类实参走反射祖先链、不取锁。
- **改法**：两张表合成不可变 `BindSnapshot`，写时复制 + `AtomicReference` 发布；读零锁零拷贝。
- **数据**（临时探针）：1 线程 293 → 241 ns；4 线程每 op 731 → 113 ns；扩展比 **0.40× → 2.13×**。
- **测试**：3 条护栏；其中「发布时序」用 package-internal `publishHook` 确定性复现
  「先发布空表后填充」的变异（初版护栏因旧快照已有同名项而漏检，改用全新探针类后才变红）。

### 13.2 totalSlots 原子化

- **问题**：`openWindow` 每次调用取一次全局 `mtx`，只为读 `totalSlots` 当窗口基址。
- **改法**：`totalSlots` → `AtomicInt64`；`openWindow` 直接 `load()`；`growSlot` 仍在 `mtx` 内
  保证段发布；`pinConst`/`liveCount` 扫描上界缓存一次。
- **数据**：窗口开合 1 线程 1374 → **632 ns/op**（−54%）；4 线程 602 → 315 ns/op（−48%）；
  扩展比 2.28× → 2.00×（单线程基线变快，剩余成本是 `Win` 的 GC 分配）。
- **结果**：调用链上**不再有任何每调用一次的全局锁**。

## 14. 回边安全点（`interrupt_poll`）成本测量（2026-11-27）

### 14.1 方法

临时探针（**已删除**，不入库）：

- 同一空循环单元 `{ n: Int64 => var i = 0; while (i < n) { i = i + 1 }; i }`，分别用
  `JitMode.Auto`（机器码）与 `JitMode.Off`（解释器）编译，各跑 2M 轮、best-of-3；
- 每次调用都断言返回 `n`，确认循环**真跑完**（不是被优化成闭式结果）；
- 另测 `invokeHelper(ctx, H22, [])` 200k 次的单次成本；
- **变异验证**：临时注释 `A64Lower.cj:368` 的 `helperCall0(22)`（回边 poll）后重测，
  用「有/无」差值定出 poll 的真实占比，测完已恢复。

### 14.2 数据（aarch64，共享 7 核 A53）

| 配置 | 每轮成本 | 备注 |
| --- | --- | --- |
| 机器码，**含**回边 poll（当前实现） | **658 / 665 / 662 ns** | 三次独立运行，±1% |
| 机器码，**去掉**回边 poll（变异） | **15 / 15 ns** | 两次完全一致 |
| 解释器，含回边 poll | 5201 / 9823 / 7219 ns | 负载敏感，波动大 |
| 仓颉侧直接调 `invokeHelper(H22, [])` | 182 / 341 / 189 ns | 含 `[ ]` 空数组分配 |

**结论**：aarch64 机器码下，回边 poll 让空循环从 **15 ns/轮 变成 662 ns/轮**，占 **97.7%**。
解释器下 poll 只占约 3%（解释器每轮本身 5–10 µs，dispatch 才是大头）。

### 14.3 为什么机器码里这么贵

`helperCall0(22)` 每次回边都要发射：`movImm64` 物化 hid、物化 argc、**物化 `helperDispatch`
绝对地址（4 条）**、`blr`；进入 `invokeHelper` 还要 `try/catch` + `match(hid)`（100+ 分支）
+ `interruptPoll` 的 TLS 读。空循环的纯执行只有 7 条指令（15 ns），poll 相当于每轮多付 654 ns。

### 14.4 方案选择与实施（`optimize-loop-safepoint`）

| 方案 | 无期限时每轮 | 有期限时中断延迟 | 判定 |
| --- | --- | --- | --- |
| 现状（每回边无条件调 H22） | 662 ns | ≤1 回边 | — |
| **D. `ctx.flags` 带 `DEADLINE` 位，回边按需调 H22** | **15 ns** | ≤1 回边（不变） | **采纳（已实施）** |
| A. 回边节流（每 N 轮一次，N=16） | 约 56 ns | 放宽到 ~10 µs | 不采纳（有语义代价，收益还更小） |
| B. ctx 携带 deadline 时间戳 | 约 18 ns | ≤1 回边 | 不采纳（要扩 64 B 布局） |
| C. 热 case 前置 + 分派地址常驻 | 不确定 | ≤1 回边 | 不采纳（收益不确定） |

D 的做法：

- `CtxFlags.DEADLINE`（bit3）由 `JitContext.create` 按本次调用的 `deadline` 写入
  （桥先 `setDeadline` 再创建 ctx，顺序保证读到本次调用的值）；
- A64 回边：`ldr flags → and 8 → cbz 跳过 → helperCall0(22)`；
- x86 回边：`mov rax,[r15+48] → test rax,8 → jz 跳过 → call H22`。

它同时满足「无期限零成本」与「有期限仍逐回边检查」，**不动 64 B 布局、不放宽中断延迟**。

## 15. 宿主签名两表去锁（2026-11-27，`optimize-signature-tables`）

### 15.1 问题

`CallMarshal.marshalHostClosure` → `pinHostClosure` 的窗口去重只在**同一窗口**内有效；
跨调用时新建 `HostCallback(fn, sig)`，其构造函数进两张全局表：

```cj
this.adapter = SignatureRegistry.adapterOf(...)   // 全局锁 + 线性扫 sameShape
this.plan = SignatureTable.getOrBuild(sig)        // 全局锁 + 线性扫 sameShape
```

实测（临时探针，已删）：单线程 **615 ns/次**，4 线程 **1174 ns**，扩展比 **0.52×**（越并越慢）。
成本分解：`adapterOf` 349 ns、`getOrBuild` 216 ns、`TypeInfo.of`（`probeType`）116 ns。

### 15.2 改法与数据（A/B 同轮，旧/新各两轮）

两表改为「不可变快照 + `AtomicReference`」，`register` 写时复制、读路径零锁。

| 指标 | 旧 | 新 | 变化 |
| --- | --- | --- | --- |
| `HostCallback` 单线程 | 524 / 280 ns | 456 / 252 ns | −11% |
| **`HostCallback` 4 线程每 op** | 1008 / 752 ns | **484 / 360 ns** | **−52%** |
| 4 线程扩展比 | 0.52× / 0.37× | 0.94× / 0.70× | 明显改善 |
| `adapterOf` | 357 / 212 | 316 / 209 | −11% / −1% |
| `getOrBuild` | 216 / 124 | 200 / 108 | −7% / −13% |

### 15.3 被否决的方案：字符串结构键索引

原计划用「结构键 `HashMap`」替代线性扫，实现后**负收益**：

| 版本 | `adapterOf` | `getOrBuild` | 全构造 |
| --- | --- | --- | --- |
| 锁 + 线性扫（旧） | 349 | 216 | 521 |
| **字符串键版** | **790** | **554** | **1306** |
| 快照 + 线性扫（采纳） | **233** | **134** | **244** |

**教训**：表只有个位数条目时，线性扫（逐位比 `UInt16` + 短字符串）只要几十 ns，
而拼键每次要 5–10 次 `StringBuilder` 插值 + 分配。**小表做索引是负优化。**
表规模超过约 50 条时才值得重新评估，且键应缓存在调用方而不是每次现拼。

### 15.4 剩余争用：已解决（`probeType` 惰性化，2026-11-27）

`TypeInfo.of(host)`（即 `HostCallback.probeType`）4 线程扩展比 **0.31–0.35×**，
单线程占全构造 22–38%，是 std 反射元数据缓存内部的争用。

**但这条路径本来就不必走**：`cb.ti` 只在**反射路径**用（`HostCall.cj:69/70`）；
adapter 命中时 H63 直接调类型化适配器，`FunctionTypeInfo` 完全用不到。
带签名的构造却无条件 `probeType` —— 纯浪费。

改法：`HostCallback.init(fn, sig)` 的 `ti` 置 `None`（惰性）；`reflectiveInvoke*`
本就接受 `cached = None` 并现场探测，行为等价。无签名构造 `init(fn)` 必然反射，仍预探测。

| 指标 | 两表去锁后 | `probeType` 惰性化后 |
| --- | --- | --- |
| `HostCallback` 单线程 | 456 / 252 ns | 448 / 255 ns（无变化） |
| **4 线程每 op** | 484 / 360 ns | **159 / 85 ns** |
| **4 线程扩展比** | 0.94× / 0.70× | **2.81× / 2.97×** |

单线程几乎不变（反射只在首次探测时有成本，被其他开销掩盖），但**4 线程争用彻底消失** ——
扩展比从退化（<1×）变成超过本机长调用的 2.2–2.4× 上限。全部宿主闭包用例（18+4+7+33）与全量均绿。

### 15.5 结论

签名两表 + `probeType` 两处合计：`HostCallback` 4 线程构造 **1008 → 159 ns（−84%）**，
扩展比 **0.52× → 2.81×**。宿主闭包实参路径不再是并发瓶颈。

## 16. 线程私有状态合并：TLS 访问 14 → 2 次（2026-11-27，`optimize-runtime-tls`）

### 16.1 问题：剩余 8.6 µs 的主项是 TLS 访问，不是 GC

§12.4 曾判断「剩余成本需要 perf 才能定位」。进程内探针（同轮配对、best-of-3，用后删除）给出了相反结论：

| 测量 | 数据 |
| --- | --- |
| `ThreadLocal` 单次 `get` / `set` | **319 / 304 ns**（std 实现；私有实例 4T 503 vs 共享 508 ⇒ 不是实例争用） |
| `realTlsBundle`（deadline 保存/设置/恢复 + fnTable 保存/设置/恢复，6 次） | **1906 ns** |
| `windowBundle`（`openWindow` + `base` + `cap` + `resetWindow`，4 次 TLS + 2×`Win`） | **1888 ns** |
| `JitFunction.call` 全路径 TLS | **14 次**（deadline 3、fnTable 3、win 5、iter 1、fault 1） |
| 推算 | **~4.4 µs / 8.6–9.7 µs（45–51%）** |

对照项：GC 分配约 1.0–1.4 µs、`enter/exit` 两对 mutex 86 ns、`NativeMem` 两个原子无争用。

### 16.2 改动

- 新增 `runtime/RuntimeState.cj`：`deadlineNanos` / `fnTableBase` / `wins` / `iters` / `faults` /
  `freeHint` 合并为一个线程私有载荷；`RuntimeEnv.current()` 取一次；
- `HandleTable.openWindowWith(rs, cap) -> (base, cap)`、`resetWindow(rs, -1)`、`syncTo(ctx, rs)`：
  窗口侧 5 次 TLS → 0；
- `JitContext.create(..., deadlineNanos: Some(rs.deadlineNanos))`：不再回读 TLS；
- `IterTable` / `HostFault` 改读 `rs.iters` / `rs.faults`，空表/None 时直接跳过清理（0 TLS）；
- `JitFunction.call` 的 deadline 改「值不变不写」（常规无期限调用 0 次写）；
- `JitExecutor.invokeOff` 仅在 `fnTableBase` 变化时 set/restore（稳态 3 次 → 1 次 get）。

### 16.4 结论与残留

**keep。** 单次调用省约 2.0–3.5 µs，是 `optimize-call-path` 系列里单项收益最大的一次；
且证明「TLS 访问次数」是桥接层可继续下探的方向。

残留：

- 稳态仍有 2 次 TLS：`RuntimeEnv.current()` + `MachineEnv.fnTableBase`（后者可再并入 rs，
  但需要把 rs 传入 `JitExecutor.invokeOff` 的调用链）；
- 分配型 helper（`append` / `pin`）每次仍经一次 `current()`（~300 ns/次），
  彻底消除要把 rs 下传到 `CallMarshal` 与 helper 入口；
- 共享 VM 的双峰仍在，`8 线程 ≥5×` 需专用 ≥8 核机器复测。

## 17. helper 表从 O(F)/call 降到 O(1)/call（2026-11-27，`optimize-helper-table`）

### 17.1 问题

`JitFunction.callLocked` 每次调用都 `UserHelperTable.push(0u16, helpers)`，
而 `push` 会新建 `HashMap` 并把该单元全部 F 个 user helper 逐项插入。
F = 注册函数数（含构造器 helper），于是**每次调用付 O(F)**。

同机实测（同一份源码 `{ => fn0(1) }`，只改注册函数数量）：

| 注册函数数 | 每次调用 |
| --- | --- |
| 4 | 11.7 / 11.9 µs |
| 204 | **103 / 197 µs** |
| 每项每次调用 | 456 / 925 ns |

这是当时 f_jit 里最大的一处浪费，量级超过编译路径所有已优化项之和。

### 17.2 改动

1. `UserHelperTable.buildTable(base, entries)` 抽出建表；`pushTable(table)` 只压引用；
   `push(...)` 保留为兼容入口（测试与一次性场景）。
2. `JitFunction` 在 `bindUserHelpers` 时建一次并缓存 `helperTableCache`；
   `callLocked` 用 `helperTableRef()`（包装闭包实例取 `owner` 的表）。

### 17.3 数据

| 注册函数数 | 改前 | 改后 |
| --- | --- | --- |
| 4 | 11.7 / 11.9 µs | 4.03 / 7.70 µs |
| 204 | 103 / 197 µs | **3.97 / 7.60 µs** |
| 差值（204−4） | +91 / +185 µs | **−0.06 / −0.09 µs** |

**O(F) → O(1)**：204 个 helper 的调用成本降到与 4 个 helper 相同（−96%）。

护栏 `HelperTableScope_test` 3 条（嵌套遮蔽/pop 恢复、调用后无栈残余、hid 顺序），
改前 3/3、改后 3/3；全量 1246/1246。

### 17.4 未做

`UserHelperTable.find(hid)` 仍每次调用一次 TLS `get`（~300 ns），因为它的两个调用点
（`runtime/UserHelper.cj`、`runtime/AnyHelpers.cj`）在 C 调用路径上、签名里没有 `rs`。
要消除需要改这两处 helper 的契约，收益与风险不成比例。

## 18. 调用期去分配（2026-11-27，`optimize-call-alloc2`）

### 18.1 改动

1. `CallMarshal.unboxRet(t, cell)`：返回值解包从「现建闭包再立刻调用」改为直接方法调用；
   `makeRetUnboxer` 保留并委托（测试在用）。
2. 零实参单元共享 `JIT` 侧静态空 `cells`（封送循环不执行，不会被写）。

### 18.2 数据：未测得显著收益

`CallPathBench` B1（`{ n => n + 1 }`，5 轮取最小）：

| 臂 | L1 |
| --- | --- |
| 改前 | 3036 ns |
| 改后 | **2975** / 5516 ns |

快模式 −2.0%、慢模式 +2.3%，低于 MOV(3%) 且在噪声内。**不宣称加速**。

### 18.3 结论：本轮进入「测量分辨率以下」

`optimize-helper-table` 之后，剩下的都是每次调用几十到几百 ns 的固定开销，
而本机跨进程波动 ±40%、同进程也有 ±6%，已经无法为这类改动提供判定证据。
继续做「少一个闭包/少一次查表」级别的改动，性价比低且无法验证。
