# 调用路径去串行优化（数据驱动）

> 状态：**全部阶段已判定并归档**。
> P1.1、P1.2、P2.1 数据达标并保留；P1.3 无收益已回滚；P3.1/P3.2 经成本分解判定收益上限低于 MOV，**不做**。
> 本文只定义实验与判定规则；每项的最终数据与决策见 §6/§7/§11/§12。
> 关联归档：`2026-11-26-feat-f-jit-parallel-call`、`2026-11-27-optimize-call-path-phase1`、
> `2026-11-27-optimize-call-path-phase2`。

## 0. 一句话结论

并行执行本身已无全局锁；剩余的是**每次调用路径上的若干短临界区**。本方案按「先测量、再改一步、
用数据决定去留」的方式逐项验证，**没有数据支撑的改动一律回滚**。

## 1. 硬规则（不可协商）

1. **先基线后改码**：每一项改动动手前，必须先在当前 commit 上采集同一指标至少 5 次。
2. **一次只改一项**（或其不可分割的组合），单独提交，保证可 `git revert`。
3. **保留条件**（三项同时满足）：
   - 目标指标中位数提升 ≥ 本文给出的最小可观测收益（MOV）；
   - 其它指标中位数回退 ≤ 2%；
   - 全量测试零失败（`PerfOverride_test` 已知高负载假失败除外，单跑 3 次至少 2 次通过）。
4. **达不到就回滚**，并在 §7 决策日志记录「无效 + 数据」，不保留"看起来更优雅"的代码。
5. **共享构建机**（7 核 Cortex-A53、常驻负载 3+）只做初筛；`8 线程 ≥5×` 的达标结论必须在
   专用 ≥8 物理核机器上复测。
6. 任何改变**可观察语义**的改动（计数口径、错误码、API）必须先走 OpenSpec 变更，不能以
   "性能优化"名义直接改。
7. **前置项单独无收益时先回滚**；若后续项依赖它，则把两者合成一个实验重新判定——
   组合收益必须覆盖两项成本，否则两项都不保留。

- 场景 B1–B4 放在**同一个非门槛测试类**里，只打印 `CP-BENCH ...`，不做时序断言；
- `ParallelThroughput_test` 补 `@Assert(f.isJitBacked(), true)`——当前 734 ms / 2M 次循环
  很可能走解释器，若属实，`S4/S8` 反映的是解释器并行度，不能代表机器码路径；
- 噪声门槛：基线 5 次的中位数 `M` 与相对离散度 `d = max|xi-M|/M`；
  **MOV = max(3%, 2d)**。低于 MOV 的变化视为噪声，不保留。

## 4. 实验卡

每张卡的结构：假设 → 改动 → 指标与预期 → 保留门槛 → 回滚条件 → 前提/冲突。

### T0 建立测量工具与基线（不改产品代码）

- **改动**：新增 `CallPathBench_test`（B1 短调用、B2 字段循环、B3 分配型、B4 ctx 创建/释放）；
  `ParallelThroughput_test` 增加 `isJitBacked` 断言与打印。
- **产出**：上述 6 个指标的基线中位数与离散度；写入 §7。
- **保留条件**：工具能稳定打印、5 次离散度 < 10%；否则先修工具，不进入任何优化。
- **注意**：这是测量基础设施，不参与 keep/revert 判定；没有它，后续任何收益都不成立。

### P1.1 HostFault 改线程本地

- **现状**：`HostFault` 全局 `mtx` + 两张 `HashMap`；`JitContext.free` 每次调用都 `clear`，
  即使无异常也抢一次全局锁（`runtime/HostCall.cj`、`JitContext.cj`）。
- **改动**：改为 `ThreadLocal<HashMap<UInt64, FaultEntry>>`；ctx 仅在调用线程读写，
  `record/causeOf/takeCause/clear` 全走本地表。
- **指标**：`L1`、`Q1`、`Q4`；辅助 `C1`。
- **预期**：短调用每次少 1 次全局锁；长调用（B0）可能落在噪声内。
- **保留门槛**：`Q4` 提升 ≥ MOV，或 `L1` 下降 ≥ MOV；且 `Q4` 回退 ≤ 2%。
- **回滚条件**：无指标达到 MOV，或异常 cause 用例出现跨线程串味。
- **前提**：无。与 P3.1 的顺序约束：**必须先于 ctx 池**（池复用 ctx 指针，旧 fault 必须先清）。

### P1.2 HostFieldTable 改不可变快照 + 无锁读

- **现状**：每次 H64/H65 字段访问都在全局锁内拷贝 bucket 到新 `ArrayList`，
  再锁外匹配（`runtime/HostField.cj`）——一次访问 = 一次锁 + 一次分配。
- **改动**：注册时在写锁内构建不可变快照，`AtomicReference<Snapshot>` 发布；
  `find` 只 `load()` + 数组遍历，不拷贝。
- **指标**：`F1`、`F4`；辅助 `Q1/Q4`。
- **预期**：字段循环应有明显收益（去锁 + 去分配）；普通调用（不访问字段）不受影响。
- **保留门槛**：`F1` 或 `F4` 提升 ≥ 10%（此项预期收益大，门槛高于 MOV）。
- **回滚条件**：`F1/F4` 提升 < 10%，或字段访问用例/注册期用例失败。
- **前提**：`accepts` 仍在锁外求值（可重入注册）；快照只增不删（`resetForTest` 除外）。

### P1.3 JitFunction / EscapedClosure 的 state/active 原子化

- **现状**：`enter/exit` 每次调用各进一次单元 `mtx`（`JitFunction.cj`），包装实例还要进
  `EscapedClosure` 的状态机；这是执行路径上最后一把"整调用级"的锁。
- **改动**：
  - `state: AtomicInt64`、`active: AtomicInt64`；
  - `enterUnit`：读 state → `active+1` → 复读 state；变 1/2 则 `active-1` 并抛 19；
  - `close`：CAS 0→1 → 轮询 `active==0` → store 2；超时 CAS 1→0；
  - 包装实例同理；`escaped` 清单、`cacheKey`、`release` 回调仍留在 `mtx`（冷路径）。
- **指标**：`L1`、`Q1`、`Q4`、`S4`。
- **预期**：短调用收益最明显；长调用（B0）收益有限。
- **保留门槛**：`Q4` 或 `S4` 提升 ≥ MOV，且 `UnloadConcurrency_test` 3 轮全绿。
- **回滚条件**：任何指标未达 MOV；或出现 close 与晚到 enter 的竞态（用变异验证：
  去掉"复读 state"后用例必须变红，否则测试不足以证明正确性）。
- **前提**：与 P1.1/P1.2 无冲突；三项可同属一个 Phase，但**分别提交、分别判定**。

### P2.1 HandleTable 分片空闲表 + 原子 totalSlots（**已实施，keep**）

- **现状**：`newSlot` 的 pop、`release` 的 push 都在同一把 `HandleTable.mtx`；
  分配型单元并发时这是最热的共享结构（design D3d 的 P1.2d）。
- **改动（推荐分片而非纯无锁）**：
  - 64 个 stripe，每个 `ArrayList<Int64>` + 独立 `Mutex`；
  - 槽按 `idx & 63` 固定归属，分配优先本线程/本 stripe，空了再扫描其它 stripe；
  - `totalSlots` 改 `AtomicInt64`，`capacityLimit` 用 CAS 兜底。
- **指标**：`A4`、`S4`、`S8`；辅助 `Q4`。
- **预期**：分配密集场景提升；纯计算单元基本不变。
- **保留门槛**：`A4` 提升 ≥ 10%，或 `S4/S8` 提升 ≥ MOV。
- **回滚条件**：`A4` 提升 < 10% 且 `S4/S8` 未达 MOV；或槽复用语义被破坏
  （`releasedSlotIsReusableWithNewGen`、`AnyHostCast` 的 `slotCount` 断言）。
- **前提**：分配策略必须保留"单线程刚释放的槽下一次复用"的行为；`resetForTest` 清全部 stripe。

### P3.1 JitContext 池化（**评估后不做**：收益上限 5.0% < MOV 8.4%，见 §12）

- **现状**：每次调用 `LibC.malloc(64B)` + `LibC.free`，并各做一次 `NativeMem` 原子计数。
- **改动**：`ThreadLocal<ArrayList<CPointer<Int64>>>` 池，`create` 取、`free` 还（上限 8）；
  归还前必须 `HostFault.clear(ctx)`；超出上限才真正 free。
- **规格前提（硬阻塞）**：`NativeMem.mallocCount/freeCount` 现在统计**真实 native 分配**，
  T27 用例据此断言。池化后必须先把口径改为「`nativeMallocCount` + `acquireCount`」并走
  OpenSpec 变更；否则 **不实施**。
- **指标**：`C1`、`L1`、`Q1`、`Q4`。
- **保留门槛**：`C1` 下降 ≥ 20%（池化主要消除 malloc/free 固定成本），或 `Q4` 提升 ≥ 10%。
- **回滚条件**：未达门槛；或出现 ctx 复用导致的旧 fault/旧 errCode 串味。
- **前提**：P1.1 已完成；NativeMem 口径变更已归档。

### P3.2 SignatureTable / AdapterRegistry 改 COW（**评估后不做**：不在调用路径上，见 §12）

- **现状**：`SignatureTable.getOrBuild` 与 `AdapterRegistry.lookup` 都在全局锁内；
  前者在封送宿主闭包时用，后者在编译/注册/查适配器时用。
- **改动**：与 P1.2 相同的不可变快照 + `AtomicReference` 发布；删除单位置锁读。
- **指标**：`Q4`（宿主闭包密集场景）；无此场景时以 `S4` 为准。
- **保留门槛**：对应指标提升 ≥ MOV。
- **回滚条件**：未达 MOV，或 `AdapterRegistry` 与卸载的可见性出现 UAF
  （前提：`close` 已排空 `active`，即 P5 语义）。
- **注意**：只在 profile 指向此处时才做；不要为了"全无锁"而改。

### P3.3 Signature/Adapter 与卸载的可见性（验证项，不是新改动）

- `AdapterRegistry` 存的是**代码地址**；COW 读者若持有旧快照，必须在代码释放前离开。
  该前提由 `close` 的 active 排空保证。用 `UnloadConcurrency_test` + 适配器回归验证；
  不满足则不做 P3.2。

## 8. 停止与升级条件

- 连续 **2 项**改动未达 MOV ⇒ 停止堆优化，改用 `perf`/火焰图定位真实热点；
- `S4` 在 Phase 1 后仍 < 2.6× ⇒ 先查 `isJitBacked` 与解释器回退，再谈锁；
- 任一改动导致全量回归 ⇒ 立即回滚，不进入下一 Phase；
- `8 线程 ≥5×` 只在专用 ≥8 物理核、load < 0.5 的机器上下结论；共享 VM 数据只作趋势。

## 9. 非目标

- 不把 HandleTable 改成"每槽一个原子字"的纯无锁结构（内存与 ABA 成本不匹配）；
- 不改编译管线、`CompileCache`、注册表的锁（不在执行路径）；
- 不为追求"零锁"而改变公开 API 或错误码。

## 10. 句柄 gen 编码阻断：已修复（2026-11-27）

- **现象**：B3 分配型基准在**单线程**第 32768 次复用同一槽后，`call` 抛 `code=99`、`site=-1`
  （探针：`i=32767` 首次失败；与并发无关）。
- **根因**：`HandleTable.makeId` 把 16 位 `gen` 放在 Int64 最高 16 位；`gen = 0x8000` 时拼装值越过
  `Int64.Max`，`Int64(u)` 的**受检转换**抛 `OverflowException`（若换成非受检位转换则得到负 ID，
  被 `id <= 0` 当空句柄）。两条路径都破坏「标识恒正」这一全库依赖的不变量。
- **修复**（变更 `fix-handle-gen-exhaustion`，归档 `2026-11-27-fix-handle-gen-exhaustion`）：
  `GEN_MAX = 0x7FFF`；到达上限的槽**退休**（不进空闲表、永不复用）；新增 `retiredCount()` 诊断。
  回归用例 `HandleTableGenExhaustion_test` 覆盖「复用 32767 次恒正」「退休后分配新槽」「旧 ID 永久失效」，
  并做过去掉退休分支的变异验证（两条用例同时变红）。
- **成本**：每槽每 32767 次复用占 1 个索引位（约 3e-5 槽/次分配），相对 4M 目录可忽略。
- **对基准的影响**：B3 迭代次数已从 5000 恢复到 15000，可跨过 32768 次复用边界；
  A4 仍受共享 VM 噪声影响（0.76–1.38×），Phase 2 判定时建议用专用机器或改短调用口径。

## 11. Phase 2 实施记录（2026-11-27）

### 11.1 前置争用探针（临时用例，已删除）

| 场景 | 1 线程 | 4 线程每 op | 4 线程扩展比 |
| --- | --- | --- | --- |
| 句柄 churn（openWindow + pin + release + resetWindow） | 3192 ns | 6113 ns | **0.52×** |
| `JitContext` create/free | 415 ns | 276 ns | 1.50× |

句柄 churn 在 4 线程下比单线程还慢一倍：全局 `mtx` 把「取索引 + 写 8 个槽数组 + 归还」整段串行化，
线程越多 convoy 越重。这与分配型基准 B3 的 A4 长期 0.76–1.38× 完全一致。

### 11.2 改动

- 空闲索引分 64 片（`idx & 63` 固定归属），每片一把锁；
- 分配：分片锁内摘索引，**槽写入移出锁**（索引已摘除 ⇒ 不可达 ⇒ 写入者独占）；
- 释放：状态复位 + 世代号 +1 + 归还同一分片，全在该分片锁内（同槽双释放被串行化）；
- 增长（`totalSlots`/段发布）保留全局 `mtx`（每 1024 槽一次）；
- `retiredSlots` 改 `AtomicInt64`（释放路径不再持 `mtx`）；
- 新增 `HandleTableStripeConcurrency_test`（4 线程 × 20000 次 pin/release，断言无重复活槽、计数回基线）。

### 11.3 复测（5 次，taskset 0-4）

| 指标 | 基线（Phase 1 后） | Phase 2 后 | 判定 |
| --- | --- | --- | --- |
| **A4（分配型）** | 76 / 138 / 79（中位 79） | 237 / 264 / 241 / 275 / 266（中位 264） | **+234%，keep** |
| S4（4 线程） | 2.40（P6）/ 2.22（P1.3） | 2.17（1.86–2.39） | 噪声区间内 |
| S8（8 线程） | 1.91 | 1.90 | 持平 |
| S2 | 1.27 | 1.29 | 持平 |
| Q1 | 180681 | 194060 | +7.4% |
| Q4 | 471970（中位，双峰） | 369373（中位，双峰；最好 483687） | 受负载影响，最好值持平 |
| F1 / F4 | 507 / 219（P1.2 后） | 最好 503 / 217；中位 567 / 234（含两次高负载） | 持平 |

**结论：keep。** A4 是唯一直接受分配锁影响的指标，从 ~0.8× 提升到 2.4–2.8×（5 次全部 ≥2.37×），
远超 MOV；其余指标在共享 VM 的噪声范围内。完整记录见
`f_jit/doc/spec/optimize-call-path-phase2/verify.md`。

### 11.4 仍未解决

- **Q4 中位数不可靠**：共享 7 核 VM 的负载让 5 次里总有 1–2 次整体慢 1.7 倍（Q1/F1/F4 同时变差），
  中位数会被抬高/压低；判定时应同时看「最好值」与「全部 5 次的分布」。
- **B1 单次调用仍 ~5 µs**：说明桥接层（封送、ctx malloc/free、错误检查）仍是主开销，
  下一步应做 Phase 3（`JitContext` 池化 + 封送分配），而不是继续动句柄表。

## 12. Phase 3 评估：不做（2026-11-27，数据结论）

### 12.1 单次调用成本分解（临时探针，已删除；release 构建，100k 次 × best-of-3）

| 场景 | ns/call | 与 0 参之差 |
| --- | --- | --- |
| 0 参数单元 `{ => 1 }` | 8583 | — |
| 1 参数单元 `{ n => n + 1 }` | 8977 | +394（实参路径） |
| 4 参数单元 | 9990 | +1407（约 350/实参） |
| `JitContext.create` + `free` | 429 | — |

### 12.2 结论

- **P3.1（ctx 池化）收益上限 = 429 / 8583 ≈ 5.0%**，低于 L1 的 MOV（8.4%）；
  而它需要改 `NativeMem` 计数口径（T27 断言「create 一次 = 一次 malloc」），属规格变更。
  **按硬规则不做**：收益不足以支付规格与泄漏账目的复杂度。
- **P3.2（Signature/Adapter COW）不在调用路径上**（只在封送宿主闭包/建计划时用），无收益证据，不做。
- **实参路径**每个约 350–400 ns（malloc 一次 + 反向拷贝）：改线程私有暂存区可省下这部分，
  但同样只占 ~4–5%，且引入重入分级缓冲的复杂度 ⇒ **不做**。

### 12.3 剩余 8.6 µs 在哪：已知与未知

已知每次调用包含：2 次 `Mutex` 配对（P1.3 已证明去掉无收益）、窗口开合（`Win` + 2 个 `ArrayList`）、
`CallMarshal` + 2 个 `ArrayList`、`cells` 数组、1 次 `malloc/free`、`CFunc` 构造、一次机器码调用。
合计约 8–9 次 GC 分配 + 1 次原生分配。

**未验证的假设**：在这台共享 7 核 A53（load 常驻 3+）上，8.6 µs 很可能由 GC 与缓存未命中主导，
而非某个具体锁。要证实需要 `perf`/GC 计数——构建机**没有 perf**（`perf_event_paranoid=2`），
共享 VM 的噪声也让 <10% 的改动无法判定。

### 12.4 停止条件

`optimize-call-path.md` §8 的停止条件已满足：连续两项（P3.1/P3.2）无数据支持。
**调用路径优化到此为止**；后续若要把单次调用从 µs 级降到亚 µs，需要：
1. 专用 ≥8 核机器 + `perf`（或仓颉运行时 GC 统计）；
2. 按 profile 决定是减少每调用分配（Win/Marshal 复用）还是消除 `malloc`；
3. 在此之前不再做「猜热点」式的微优化。
