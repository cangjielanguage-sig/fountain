# Design

> 依据：报障现象（`{ n: Int64 => !(n < 50) }`，`n = 49`：JIT `true` / 解释器 `false`）、`f_jit` 现行规格（`jit-bytecode-m1.md` §5 / §9，`design-m1.md` §5）与源码直读。行号以本次工作树为准，实施时以符号名为准。

## 1 结论

**根因已定位到单条机器码的位域编码错误**，不在 Parser / Lexer / Lowerer / Interp，也不在 x86。

`f_jit/src/backend/A64Lower.cj:322-325`：

```cangjie
case 0x5E =>
    this.e.ldrOff(9, 20, 0)
    this.e.word(0xD2400009u32) // eor x9,x9,#1（逻辑非；0↔1）
    this.e.strOff(9, 20, 0)
```

`0xD2400009` 按 `EOR (immediate)` 位域解码：

| 字段 | 位 | 现值 | 语义 | 应为 |
| --- | --- | --- | --- | --- |
| `sf` | 31 | 1 | 64 位 | 1 |
| `opc` | 30–29 | `10` | EOR | `10` |
| 固定 | 28–23 | `100100` | — | `100100` |
| `N` | 22 | 1 | 位掩码长度 | 1 |
| `immr` | 21–16 | `000000` | — | `000000` |
| `imms` | 15–10 | `000000` | 掩码 = `#1` | `000000` |
| **`Rn`** | **9–5** | **`00000` → X0** | **左操作数** | **`01001` → X9** |
| `Rd` | 4–0 | `01001` → X9 | 目标 | `01001` |

即实际生成的是 **`EOR X9, X0, #1`**，而注释写的是 `EOR X9, X9, #1`。正确编码是 `0xD2400129`（小端字节 `29 01 40 D2`）。

**为什么表现为「恒 true」**：`A64Compiler.compileOnce` 序言 `e.movReg(19, 0)` 把 ctx 存进 x19 之后，x0 在无 helper 的函数体里不再被写；`!(n < 50)` 恰好无 helper，于是 `x0 = ctx`（栈/堆上的非零指针），`ctx | 1` 恒非零。`str` 把它写回操作数栈顶，`RET` 原样返回；桥在 `CallMarshal.cj:165-166` 以 `cell != 0` 解包 Bool ⇒ **恒 `true`**。差分 harness 对 Bool 返回按 i64 文本化（`RealRunners.cj:392-409`），因此红态会打印一个巨大的十进制数，而不是 `0/1`——这是最省事的失败指纹。

**影响面**：所有走 AArch64 后端的一元 `!`——`!cmp`、`!flag`、`!!x`、`!(a && b)`，以及 `Lowerer.cj:3042-3044` 为 `!~` 追加的那条 `NOT_B`。x86 侧 `X86Lower.cj:972` 是 `48 83 34 24 01`（`48 83 /6 ib` = `XOR qword [rsp], 1`），逐字节核对正确，与解释器 `Interp.cj:533`（`a == 0`）在 0/1 域上等价。

最快的复现不是桥而是 `A64Exec_test.run(src, args)`：它直接返回原始 cell（不做 `!= 0` 解包），红态会打印 `ctx | 1` 这个巨大整数，一眼即可区分「取反失效」与「取反正确但被解包成 true」。

## 2 根因定位方法（可复现的证据链）

本变更把定位过程固化成六步，其中前四步都要落成**可重跑的用例**，不只做一次性手工排查。

### 2.1 分层排除（每层一个判据）

| 步 | 探针 | 判据 | 本次结论 |
| --- | --- | --- | --- |
| S1 AST | `AstShape.exprOf('!(n < 50)')` | 顶层 `Bang` 且唯一子节点是比较（不是 `(!n) < 50`） | 正常：`unary(! cmp(< var(n) lit(50)))` |
| S2 字节码 | `CodeDump.dump(cu.raw)` | 函数体为 `LOADL; PUSH_I64 50; LT_I; NOT_B; RET`，`NOT_B` 恰一条 | 正常，且**否证**了「比较被降成三态 `CMP_I`」这一候选 |
| S3 引擎 | `InterpRunner` / `NativeRunner` 同一 `.fbc` | 解释器 `0`，原生后端非 `0` | 分歧确在原生后端 |
| S4 机器码 | 取 `JitArtifacts.code` 中该函数的字节 | `0x5E` 对应三条 4 字节字，且第二字为 `0xD2400129` | **红态为 `0xD2400009`** |
| S5 位域 | 按 ARM64 `EOR (immediate)` 位域解码 | `Rn == Rd == 9` | **`Rn = 0`** |
| S6 语义 | `x0` 在该点的活跃性 | 若为 ctx 则结果恒非零 | 序言后 x0 = ctx，体内不写 |

只有 S4/S5 同时通过，才可以在不改语义的前提下宣称修复；S6 负责解释「为什么症状是恒 `true` 而不是随机值」。

### 2.2 已证伪的候选（不再重复排查）

| 候选 | 证伪依据 |
| --- | --- |
| `Parser.parseUnary` 把 `!(n<50)` 解析成 `(!n) < 50` | S1：AST 顶层是 `Bang`，子节点是比较 |
| `Lowerer.lowerUnary` 漏发 / 多发 `NOT_B` | S2：`NOT_B` 恰一条且紧跟 `LT_I`；`Lowerer.cj:1727-1729` 只发一条 |
| 比较被降成三态 `CMP_I`（`-1/1/0`）导致取反后非零 | S2：产物是 `LT_I`（`0x54`），不是 `0x50` |
| x86 `emitNotB` 写错 | `48 83 34 24 01` 解码为 `xor qword [rsp], 1`，正确 |
| **A64 `0x5E` 正确**（此前结论） | **该结论依据行尾注释与字形，未做位域解码；S5 显示 `Rn = 0`。注释与实现不一致正是缺陷本体** |
| 解码器 / 栈深度 / 帧布局错位 | 三条指令宽度与栈指针账目正确（`ldr`/`str` 均以 x20 为基址、无深度变化），且失败值恒定而非随机 |

### 2.3 为什么既有 826 条用例没抓到

- `A64Lower` 没有针对性单测；`A64Exec_test` 覆盖算术 / 分支 / 浮点 / 闭包，但**没有一元 `!` 用例**；`A64Emitter_test` 只覆盖编码器原语，不覆盖降低层手写 word。
- 差分矩阵里没有任何一元 `!` 用例；`A1.2` 只断言解释器 `NOT_B` 的栈纪律，`X86Lower_test` 只断言 x86 字节。
- 手写裸字面量本身没有「字段构造 + 编码断言」的双重约束，注释与编码可以长期不一致。

## 3 修复方案

### 3.1 D1（采纳）：修编码，并把机器字交给字段构造

1. `A64Emitter` 新增 `eorImm1(rd: Int64, rn: Int64)`：`word(0xD2400000u32 | (UInt32(rn) << 5) | UInt32(rd))`，注释写明这是 `EOR Xd, Xn, #1`（`N=1, immr=0, imms=0`）。
2. `A64Lower` 的 `0x5E` 改调 `this.e.eorImm1(9, 9)`。
3. 不在 `A64Lower` 里保留裸字面量；未来同族逻辑指令一律走 emitter，避免「注释对、编码错」。

选它的理由：改动面最小（4 个机器字节 + 一个纯函数），语义与原设计（`xor qword [rsp],1`、`(a==0)?1:0`）在 `{0,1}` 域上完全等价，且不触碰 x86 与解释器，天然满足「不改变既有正确语义」。

**规格口径**：既有 `f-jit-backend` 的「两架构降低覆盖全部指令」要求「机器码序列与规格对照表一致」，本缺陷正是对该条的违反，修复即恢复合规，故不 `MODIFIED` 该条；本次新增的「编码可审计」是**防复发机制**（字段构造 + 编码用例），属于新增契约。

### 3.2 D2（否决）：把 `NOT_B` 改成 `cmp + cset eq` 的真值归一

`cmp x9, xzr; cset x9, eq` 与解释器 `a == 0` 逐位同构，还能顺带覆盖非 Bool 操作数。但：

- 它改变了「按位翻转」的实现口径，x86 侧不同构（`xor 1` 只在 `{0,1}` 域等价），要三引擎一致就得同时改 x86 与 Interp 的契约；
- 指令数 3 → 4，触到一条与本缺陷无关的性能与产物面。

因此本次不做。若后续要收口非 Bool 操作数（§7 B1），应作为独立变更，三引擎一起改。

### 3.3 不做的事

- 不改 `Lowerer`、`Parser`、`Lexer`、`Interp`（已证伪）。
- 不改 `X86Lower`（正确）。
- 不新增 opcode、不改 `.fbc`、不改 `CompileCacheKey`。
- 不重排 `0x50–0x6E` 的整段编码（仅做 B6 的抽样审计，发现同类问题另立变更）。

## 4 测试设计（严格 TDD）

### 4.1 顺序

1. **先写红**：语义用例（三引擎 + 绝对值锚定）+ 编码用例（`0xD2400129`）+ 形状用例（AST / 字节码）。
2. **确认红**：语义用例在 AArch64 上以「巨大十进制数 vs `0`」失败；编码用例以 `0xD2400009 != 0xD2400129` 失败；形状用例应**直接通过**（前端本来就对，它是定位分层的一部分，不是本次的修复对象）。
3. **再修**：`eorImm1` + 换调用点。
4. **转绿**：三组用例全绿，`!` 以外的断言逐位不变。

### 4.2 语义矩阵（`UnaryNotDiff_test`）

| 用例 | 源 | 入参 | 期望（解释器绝对值） |
| --- | --- | --- | --- |
| 报障 | `{ n: Int64 => !(n < 50) }` | 49 | `0` |
| 边界 | 同上 | 48 / 49 / 50 / 51 | `0 / 0 / 1 / 1` |
| 极值 | 同上 | `Int64.Min` / `Int64.Max` | `0 / 1` |
| 比较族 | `!(n <= 50)` / `!(n == 5)` / `!(n != 5)` | 50 / 5 / 5 | `0 / 0 / 0` |
| 布尔实参 | `{ b: Bool => !b }` | `true` / `false` | `0 / 1` |
| 双重取反 | `{ n: Int64 => !!(n < 50) }` | 49 | `1` |
| 逻辑组合 | `!(a && b)` / `!(a \|\| b)` | 各类 | 与 `&&`/`\|\|` 真值取反一致 |
| 正则 | `{ s: String => /abc/ !~ s }` | `"abc"` / `"x"` | `0 / 1` |
| 无 `!` 对照 | `{ n: Int64 => n < 50 }` | 49 / 50 | `1 / 0`（修复前后逐位相同） |

每条都断言两件事，缺一不可：

- `InterpRunner().run(...)` 的结果等于上表绝对值（**防止「三引擎一致地错」**）；
- `DiffSession([InterpRunner(), NativeRunner()]).assertTripleEqual(...)` 通过，且 `ran() >= 1`。

x86 证据不另写文件：`NativeRunner` 按 `@When` 条件编译，同一用例在 x86_64 主机上自动走 x86 后端；AArch64 主机上它被计入跳过。

### 4.3 编码用例（`A64NotBEncoding_test`）

- `A64Emitter.eorImm1(9, 9)` 的 hex 为 `290140D2`（与 `A64Emitter_test` 的 objdump 口径一致）。
- 用 `A64Compiler.compileFunction` 编一个 `PUSH_BOOL 1; NOT_B; RET` 的最小单元，在产物里定位 `0x5E` 的三字，断言 `ldr x9,[x20]` / `0xD2400129` / `str x9,[x20]`，并断言解码 `Rn == Rd == 9`。
- 断言产物中**不出现** `0xD2400009`。

### 4.4 形状用例（`UnaryNotShape_test`）

- `AstShape.exprOf('!(n < 50)')` 的稳定形态（`unary(! cmp(...))`）。
- `CodeDump.dump(cu.raw)` 中该函数的 `NOT_B` 恰一条且紧跟 `LT_I`；`!~` 的 `NOT_B` 也恰一条。

这三层把「一次失败能定位到哪一层」变成常设能力：形状红 ⇒ 前端；编码红 ⇒ 后端原语；只有语义红 ⇒ 后端语义 / 桥。

### 4.5 断言分层与假绿禁令

- 编码与形状属**结构断言**，只用于定位，不单独作为验收：验收判据是语义用例。
- 不得用「产物里出现了 `0xD2400129`」替代「49 返回 `0`」。
- 不得放宽任何既有断言换取转绿。

## 5 影响与风险

| 维度 | 结论 |
| --- | --- |
| `.fbc` / 规则集 / 缓存键 | 不变（只改机器码生成） |
| 公开 API / 错误码 | 不变 |
| 性能 | 指令数、访存数不变；无新增 helper |
| 其它指令 | `0x5E` 是独立分支，改动不外溢；B6 抽样确认同段无同类错编码 |
| 回退 | 若语义用例仍红，回退到「保留 `eorImm1` + 恢复旧 raw word」即可定位是否还有第二处缺陷 |

## 6 与既有规格的冲突点（本次一并订正）

`design-m1.md:1528` 与 `jit-bytecode-m1.md:2132` 把 A64 的 `NOT_B` 写作 `ldr x11,[sp]; eor x11,x11,#1; str x11,[sp]`，而 `A64Lower` 实际用 x9 + x20（操作数栈指针）。文档与实现不一致会继续误导按注释排障的人，随本次回写订正为「`ldr x9,[x20]; eor x9,x9,#1; str x9,[x20]`」。

## 7 已知边界与关联发现（登记，不在本次修）

| 编号 | 发现 | 处置 |
| --- | --- | --- |
| B1 | `!` 的操作数没有 Bool 类型收口（`Lowerer.lowerUnary` 只拒 15 型），`!2` 在解释器得 `0`、x86 得 `3`、修复后的 A64 得 `3` —— 三引擎仍分歧 | 本次不修：它不是「正确程序的语义」，收口方式（前端拒绝 vs 三引擎归一）需单独裁定；已在规格中把 `NOT_B` 的契约前提限定为 Bool 操作数 |
| B2 | 机器码以裸字面量手写、无编码测试（本缺陷的温床） | 本次只对 `0x5E` 改为字段构造 + 加编码用例；其余字面量按 B6 抽样审计，发现同类问题另立变更 |
| B3 | 文档把 `NOT_B` 的寄存器写成 x11 / sp | §6 订正 |
| B4 | 差分矩阵长期缺「一元运算符」维度（`!`、`~`、一元 `-` 无系统性对拍） | 本次补 `!` 全矩阵；`~` 与一元 `-` 由既有 A1.1/算术用例覆盖，不扩面 |
