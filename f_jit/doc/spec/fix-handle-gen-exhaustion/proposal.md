# 修复句柄世代号耗尽（gen 溢出）

## 为什么

`HandleTable` 的 ID 布局是 `gen:16 | tag:16 | idx:32`，`gen` 放在 Int64 的最高 16 位。
世代号从 1 起单调 +1，当它到达 `0x8000`（32768）时，拼装值越过 `Int64.Max`：

- `makeId` 的 `Int64(u)` 是**受检转换**，直接抛 `OverflowException`（已用回归用例实测）；
- 若换成非受检位转换，同一位置会得到**负 ID**，而全库判空一律是 `id <= 0`
  （`idxOf` / `tagOf` / `genOf` / `isLiveHandle` / `PromotionGroup.add`），负 ID 会被当空句柄，
  且释放路径提前返回 ⇒ 每 32768 次复用净泄漏一个槽。

两条路径都不可接受。**已实测**（2026-11-26，`optimize-call-path-phase1` 的 B3 基准）：单线程第 32768 次
复用即失败（对外表现为 `code=99`），与并发无关。任何分配型长跑（高 QPS 服务、批量转换）都会踩到。

## 影响

- 正确性：长跑必然失败，且失败点取决于历史调用次数，极难定位；
- 度量：分配型基准（A4）无法超过 25k 次复用，阻断 Phase 2 的收益判定；
- 范围：`f_jit` 全部句柄路径（`pin` / `append` / `moveOutGroup` / 常量槽）。

## 变更内容

1. 世代号上限收到 `0x7FFF`（符号位永远为 0，标识恒正）；
2. 到达上限的槽**退休**：保持失效、不再进入空闲表、不再复用；
3. 新增 `retiredCount()` 诊断（审计退休槽数）。

## 非目标

- 不改 ID 位域布局（`gen` 仍是 16 位，只是不越过符号位）；
- 不回收退休槽（目录上限 4M 槽，退休开销 1 槽 / 32767 次复用）；
- 不改变句柄窗口、提升组、并发的既有语义。
