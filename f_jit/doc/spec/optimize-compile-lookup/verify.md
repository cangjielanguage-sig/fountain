# 验证记录：`optimize-compile-lookup`（判定：不做）

## 1. 基线

探针：注册 200 个 `PredefinedFunction`，源码含 50 个调用点（`f0(n) + … + f49(n)`），
编译 20 次取均值、best-of-3（探针已删）。

| 运行 | 单次编译 |
| --- | --- |
| 1 | 47 710 730 ns（**47.7 ms**） |
| 2 | 24 868 169 ns（**24.9 ms**） |
| 3 | 24 942 466 ns（**24.9 ms**） |

（load 3.4–5.7，双峰。）

## 2. 名字查找的成本上限

| 项 | 估算 |
| --- | --- |
| `slotOf` 线性扫 | 50 调用点 × 200 条 × ~5 ns ≈ **50 µs** |
| 占单次编译（快峰 24.9 ms） | **≈0.2%** |
| `ClassRegistryView.classOf`（类型注解几十次 × 几十类） | 同量级或更小 |
| `ClassRegistry.snapshot` 双拷贝（无注册类时 C=0） | 可忽略 |

## 3. 判定

名字查找的收益上限约 **0.2%**，远低于 MOV（3%）。按硬规则 **不做**。

编译 25 ms 的主成本不在名字解析，而在 **源码前端 + 机器码发射**（Lexer/Parser/Lowerer/
A64Emitter）；要优化它必须逐段 profile，属于独立课题，不以「名字索引」名义夹带。

## 4. 影响

- 无代码改动、无新增测试；全量基线保持 **1230/1230**。
- 若未来要降编译延迟，建议先做「编译分段计时」（Lexer/Parser/Lowerer/Emit/装载），
  再按段决定，而不是从名字查找入手。
