# 为什么：并发编译的扩展比只有 1.3–1.7×

4 线程各编译 6 段**不同**源码（共享 7 核 A53、load 3+，3 次运行）：

| 配置 | 4 线程扩展比 |
| --- | --- |
| 各线程独立 `Compiler` | 1.23× / 1.30× / 1.35× |
| 共用一个 `Compiler` | 1.46× / 1.46× / 1.70× |
| `JitMode.Off`（纯字节码） | 2.68× / 2.76× / 3.71× |

- 共享 `Compiler` 不比独立慢 ⇒ `Compiler.mtx` 与 `ClassRegistry.mtx` **不是**瓶颈；
- 关掉 JIT 发射后扩展比翻倍 ⇒ 限制在**代码发射 / 可执行内存**；
- `CompileCache` 的 `awaitReady` 是自旋 500 万次 + 每轮取全局锁，同 key 等待者会拖慢其它 key
  （这是**锁层面**唯一确定的问题，与 1.3× 的主因不一定相同）。

## 变更内容

1. **M0 测量（先只测不改）**：统计单次编译里 `mmap` / `mprotect` 的次数与耗时占比，
   判定 C3 是否值得立项；
2. **C1**：`CompileCache.awaitReady` 改指数退避（不依赖已废弃的 `Monitor`），
   把单位时间取锁次数降 3 个数量级；
3. **C2**：`Compiler.snapshot()` 缓存 + 注册时失效，消除共享 `Compiler` 的 O(F) 拷贝；
4. **C3（条件项）**：代码缓冲池化 / 预分配，仅当 M0 显示 mmap 占比 ≥15% 才做。

完整方案与判定门槛见 `f_jit/doc/optimize-compile-path.md`。

## 非目标

- 不改前端语义、产物格式、公开 API；
- 不改调用路径（已收口，见 `doc/optimize-call-path.md`）；
- C3 不改变 `close` 的生命周期语义（缓冲归还前必须已排空在飞调用）。
