# Design

## Context

`JitFunction` 原有 `call<T>(args)`；M3.1 引入 deadline 时需要「带选项」的入口。当时的方案是新增 `invoke<T>(args, options)` 并让 `call` 委托（D3：不引入 `tryInvoke`）。2026-10-22 的合入把 `invoke` 并入 `call` 的重载。本次只对齐规格。

## 决策

### D1 用同名重载，不保留 `invoke`

- **为什么能重载**：仓颉按参数个数/类型分派；`call(args)` 与 `call(args, CallContext())` 是不同签名。
- **为什么不要两个名字**：`invoke` 与 `call` 语义完全相同，只差一个可选参数；两个名字会让调用方每次都要判断「我该用哪个」，也让错误消息/文档出现两套口径。
- **为什么不用默认参数**：`CallContext` 是 struct，默认参数无法表达「不传就用 `CallContext()`」的零构造语义（且会让所有调用点都构造一次）。
- **兼容性**：`invoke` 移除属破坏性；仓内调用方只有测试，已随合入改完。

### D2 `tryInvoke` 继续不引入

保持 M3.1 的裁定：不抛变体没有消费场景，且会引入「同一错误两条 API 口径」。需要非抛行为时由宿主自行 `try/catch`。

### D3 规格文本以「同名重载」表述

规格写「`call<T>(args)` SHALL 等价于 `call<T>(args, CallContext())`」，而不是写「内部委托」——后者是实现细节；等价性才是契约。

## 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 下游仍调用 `invoke` | 编译错误（显式） | 破坏性已在合入提交标注；错误消息直接指出方法不存在 |
| 重载让「带选项」不易被发现 | 可发现性下降 | README 与规格同时给出两种形态；`JitBacked_test` 固化双载重 |
