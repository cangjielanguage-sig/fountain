# Proposal

## Why

`JitFunction` 上现在有两个都叫「卸载」的概念，名字却指向不同粒度：

1. `unload()` 卸的是**编译单元**（代码内存 / 常量句柄，终态不可复用）；
2. `close()` 卸的是**一个闭包包装**（提升组计数 −1、归零释放），单元继续可用。

`close()` 这个名字借用了通用资源关闭的习惯（文件、连接、流），但它在 `JitFunction` 上既不是「关闭单元」也不是「销毁对象」，只释放该闭包捕获的槽。调用方极易把它误当成 `unload` 的别名——反过来也一样。改名 `unloadFn()` 让两个粒度在名字上就区分开：`unload` 是单元，`unloadFn` 是这一个函数值。

另外，`unload()` 完成后**没有把单元从 `CompileCache` 逐出**。缓存仍持有已卸载的 `JitFunction`，于是同一份源码再编译时命中的是死句柄，任何调用都以 19 失败。规格「卸载状态机与资产清点」早已写明「同键编译 SHALL 按未命中重新编译并产出新句柄」，实现没跟上——这是**规格-实现缺口**，不是新需求。

## What Changes

- `JitFunction.close()` 重命名为 `unloadFn()`；语义、错误码（非包装实例 19 / site=−1）、幂等性一概不变。`isClosed` 属性名保持不变（它描述的是包装状态，不是操作名）。
- `JitFunction` 记录自己被发布到编译缓存时的键（`cacheKey`，由 `CompileCache.finish` 写入）。
- `unload()` 成功进入终态（`state=2`）时，按该键把自己从 `CompileCache` 逐出；超时回退到可用态（返回 `false`）**不逐出**。
- 文档与规格同步改名；补一条「卸载后同源重编得到新单元」的用例。

## Capabilities

### Modified Capabilities

- `f-jit-facade-bridge`：`统一调用包装`（释放入口改名）、`卸载状态机与资产清点`（补缓存逐出）。

## Impact

- **API（破坏性）**：`close()` 移除，改调 `unloadFn()`。仓内调用方只有测试（18 处），已同步；仓外调用方会得到编译错误而不是静默失效。
- **缓存语义**：卸载后同源编译会重新执行管线（`CompileCache.runs()` +1），而不是拿到已卸载的旧单元。这是**修正**，不是回归。
- **性能**：`unload` 多一次哈希删除；无热路径影响（`unload` 本来就非常规路径）。
- **不在本次范围**：`isClosed` 改名（保持原名）；「卸载中窗口内到达的同键编译」的排队语义（见 design D3 已知边界）。
