# Design

## Context

`JitFunction` 有两种生命周期：单元级（`unload`）与闭包包装级（原 `close`）。缓存 `CompileCache` 是进程级 `HashMap<String, JitFunction>`，键为「模式 / 版本 / 严格浮点 / 指纹」，已有 `remove(key)` 但没有任何调用方。`JitFunction` 不知道自己被存在哪个键下，因此先要建立「单元 → 缓存键」的反向引用。

## 决策

### D1 改名 `close` → `unloadFn`

- **为什么不是 `closeFn`**：两个名字都以 `Fn` 结尾会更对称，但 `unload` 才是这两个操作共同的语义核心（释放占用的资源），`close` 只是通用习惯。改成 `unloadFn` 后，`unload`（单元）/ `unloadFn`（闭包值）在调用点并排出现时能直接读出粒度差。
- **为什么不动 `isClosed`**：属性描述的是「这个包装是否已释放」这一**状态**，与操作名解耦；改名会连带影响用户面再导出清单，收益不足以抵掉额外破坏面。保留原名，在文档里注明它与 `unloadFn` 的对应关系。
- **破坏性处置**：不做兼容别名。留一个 `close` 转发会让「两个名字」的问题原地保留，且用户无从得知该用哪个。

### D2 缓存键反向引用与逐出时机

- `JitFunction` 增加 `cacheKey: ?String`，由 `CompileCache.finish` 在发布时写入（`internal bindCacheKey`）。
- 逐出发生在**成功进入终态**的那次状态切换内：`state = 2` 的同时取走 `cacheKey`、置 `None`、调用 `CompileCache.remove(key)`。
- **超时回退不逐出**：`unload(timeoutMs)` 排空失败会把状态退回 `0`（可用），此时单元仍有效，逐出会让下一次编译产出重复单元，破坏「同键只编译一次」。
- 幂等：第二次 `unload` 在 `state == 2` 处直接返回 `true`，`cacheKey` 已为 `None`，不会重复删除。
- 包装实例的 `unload()` 委托给 owner，逐出的自然是单元自己的键——这是期望行为（卸单元就是卸全部）。

### D3 已知边界：卸载中窗口

`state == 1`（卸载中）期间到达的同键编译，仍可能从缓存拿到正在卸载的单元并立即被 19 拒绝。本次只保证**终态之后**的编译一定未命中重编。

不在本次修的理由：要在 `state == 1` 就逐出，就必须在超时回退时重新发布；而「逐出 → 别的线程编译出新单元 → 我方超时回退又把旧单元写回」会让缓存持有较旧的一份，产生两个同键单元。要彻底解决需要给缓存项加「代次/状态」维度，属独立的缓存并发改造。已在 `verify.md` 登记。

## 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 仓外调用方仍写 `close()` | 编译错误（显式） | proposal 已标破坏性；改名本身就是要消除歧义 |
| 逐出后同源重编拿到不同实例 | 若调用方缓存了旧**键**会失效 | 键是内部概念、不暴露；对外只有句柄，句柄本就随卸载失效 |
| 持锁调用 `CompileCache.remove` | 锁序风险 | 现有路径均为「缓存锁 → 单元字段写（不取单元锁）」，与「单元锁 → 缓存锁」不构成环 |
