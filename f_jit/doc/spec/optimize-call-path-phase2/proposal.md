# 为什么：句柄分配锁形成 convoy

`optimize-call-path.md` 的 Phase 2 目标是「`freeSlots` 分片 + 原子 `totalSlots`」。
实施前先做了争用探针（临时用例，已删除）：

| 场景 | 1 线程 | 4 线程每 op | 4 线程扩展比 |
| --- | --- | --- | --- |
| 句柄 churn（openWindow + pin + release + resetWindow） | 3192 ns | 6113 ns | **0.52×** |
| `JitContext` create/free | 415 ns | 276 ns | 1.50× |

句柄 churn 在 4 线程下**吞吐只有单线程的一半**：锁持有时间大于临界区本身，线程越多越慢。
这与分配型基准 B3 的 A4 长期落在 0.76–1.38× 一致（4 线程几乎没有扩展）。

**根因**：`newSlot` 把「取空闲索引 + 写 8 个槽数组」整段放在全局 `mtx` 里；`release` 同样。
每次分配/释放都串行，且临界区里还有 `ArrayList` 的 pop/push。

## 变更内容

1. 空闲索引改为 **64 个分片**（按 `idx & 63` 固定归属），每个分片一把独立锁；
2. 分配：先在分片锁内摘索引，**槽写入移出锁**（槽被摘除后不可达，写入者独占）；
3. 释放：状态复位 + 世代号 +1 + 归还分片**在同一把分片锁内**完成（同槽双释放被串行化，
   第二次因世代号不匹配而幂等返回）；
4. 增长（`totalSlots` / 段发布）保留全局 `mtx`（每 1024 槽一次，冷路径）；
5. 常量路径（`markConst` / `releaseConst`）保留 `mtx`（冷路径、跨调用共享）。

## 非目标

- 不做纯无锁（每槽原子字 / Treiber 栈）；分片已足够，且保持可回滚；
- 不改 `PromotionGroup`、`IterTable`、`JitContext`；
- 不改任何公开 API 与错误码。

## 判定

按 `optimize-call-path.md` §1：目标指标 `A4`（分配型）或 `S4/S8` 达 MOV（≥3% 且 ≥2×离散度），
其它指标回退 ≤2%，全量零失败才保留；否则整体回滚并记录数据。
