# 等待 OpenSpec 任务：周期进度报告与停滞诊断

**适用**：六步流程（工作流 F / G / H / I / J）中，任一步经 `opsx-*` 技能发起 opsx 任务后，任务在后台运行、需要等待结果时。任务由融合侧 CodeBuddy 执行，通常几分钟到几十分钟。

## 1. 节奏

- 任务发起后（Bash 工具后台模式）立即进入等待循环：**每 5 分钟一轮**。
- 每轮先采集快照，再输出报告：

```bash
python3 <skill-root>/scripts/opsx_progress.py \
  --repo <仓库根> --change <变更名> --stage <当前步骤> --log <后台任务输出文件>
```

- 用 `sleep 300` 控制节拍（Bash 工具 `timeout` 设 320000 以上，或后台跑 sleep）。
- 收到任务完成通知（或输出被截断、退出码出现）→ 出最终报告并退出循环。
- 任务在首个 5 分钟内完成 → 直接给最终报告，不做周期报告。

## 2. 每轮报告模板

```
【OpenSpec 进度 · 第 N 轮 · 已等待 X 分钟】
项目/模块：<项目名> / <模块名>
变更：<变更名>
阶段：
- ① 环境与刷新 … ✅ / 🔄 / ⬜
- ② propose ……
- ③ 用户评审 ……
- ④ apply ……
- ⑤ verify ……
- ⑥ archive + 落盘 ……
进行中（<当前阶段>）：<客观详情>
停滞：否 / 是（连续 N 轮无变化）
```

硬要求：

- **六项阶段一个不能少**；未开始的写 `⬜ 未开始`，不要省略。
- 已完成 `✅`；当前进行中 `🔄`（只允许一个）；等用户拍板 `⏳`；未开始 `⬜`。
- **「进行中」必须给客观详情**，至少包含：tasks 勾选进度（x/y）、当前任务（第一个未勾项）、近 10 分钟改动文件、后台输出尾部（传了 `--log` 时）。禁止「正在开发中」「继续推进」这类空话。
- 报告以快照数据为准，不凭印象编。

## 3. 停滞判定

- 连续 **3 轮**（约 15 分钟）快照无变化（tasks 勾选数、git 改动数、近 10 分钟文件、后台输出大小都没变）→ 停滞。
- 出现明确错误迹象（ssh 断开、输出出现 error/异常、任务退出码非 0）→ 立即停滞。
- 快照里出现 `停滞：**是**` 即触发，不要等到第 4 轮。

## 4. 停滞诊断（暂停周期报告）

先输出诊断块，再按顺序尝试：

```
【停滞诊断 · 已 X 分钟无进展】
卡点：<阶段 + 具体任务>
事实：<快照证据：tasks 停在哪、文件无改动、日志尾部>
可能原因：<2–4 条，按可能性排序>
解决方案：
  A. <首选>（代价 / 风险）
  B. <备选>
  C. <兜底：交还用户>
尝试：<先做成本最低的一步，给出命令与结果>
```

尝试顺序（每步都给命令与结果，不空谈）：

1. **ssh 连通**：`ssh running@172.16.105.2 'echo ok'`；不通 → 按 `opsx-*` 技能的连接协议重新询问/更新配置。
2. **任务是否还活着**：`ssh running@172.16.105.2 'ps aux | grep codebuddy | grep -v grep'`。
3. **融合侧 CodeBuddy 日志**：`ssh running@172.16.105.2 'ls -t ~/.codebuddy/logs | head -3'`，再 `tail` 看最新日志。
4. **后台输出尾部**：读 `--log` 文件最后几十行，查 error / 权限 / 网络等关键字。
5. **任务确实已死**：终止后台任务 → 重跑 `plan` 并执行（apply 从 `tasks.md` 当前勾选继续，已勾任务不会重做）。
6. **仍无解**：附完整证据与建议交还用户，不空转。

**解决后的恢复动作（按顺序，缺一不可）**：

1. **更新并报告进度**：`opsx_progress.py --reset` 重新计轮 → 立即采集一次新快照 → 按第 2 节模板输出「恢复后的进度报告」（六阶段状态要反映解决动作带来的变化：任务重跑后的 tasks 勾选、改动文件、后台输出）。
2. **回到 OpenSpec 流程当前步骤继续**：从六步中的当前步骤接着走（不跳步、不重头）；用户评审门禁、产物落盘要求照旧。
3. **继续 TDD 验证**：若当前在 apply，继续按 `test-driven-development` 技能逐任务 Red-Green-Refactor——先失败测试、再最小实现、绿了才勾任务；进入 verify 前 `fboot build` / 全量回归 / 冒烟全绿的门禁不变。
4. **恢复周期报告**：之后回到每 5 分钟一轮的等待循环，继续按第 2 节报告。

未解决且没有新动作 → 交还用户，不空转。

## 5. 红旗

| 你正想做 | 现实 |
| --- | --- |
| 后台跑了，安静等结果 | 用户看不到进度；每 5 分钟一轮报告 |
| 报告写「还在跑」 | 六阶段状态 + 进行中客观详情，缺一项等于没报 |
| 卡住了先问用户 | 先诊断并尝试（ssh → 进程 → 日志 → 重扫输出），带证据和方案再找用户 |
| 停滞了继续报流水账 | 停滞即暂停周期报告，转诊断块 |
| 问题解决了直接继续下一轮报告 | 先更新并报告进度（`--reset` + 新快照），再回到六步当前步骤；apply 里继续 TDD 验证（测试绿才勾任务），不能跳 |
| 诊断块只说「可能有问题」 | 每轮诊断必须有新动作或新信息；没有就交还用户 |

## 6. 示例

正常报告（第 3 轮）：

```
【OpenSpec 进度 · 第 3 轮 · 已等待 10 分钟】
项目/模块：fountain / f_store
变更：add-wal-support
阶段：
- ① 环境与刷新 ✅ 完成（openspec update 已跑）
- ② propose ✅ 完成（四件套齐）
- ③ 用户评审 ✅ 通过
- ④ apply 🔄 进行中（tasks 8/23）
- ⑤ verify ⬜ 未开始
- ⑥ archive + 落盘 ⬜ 未开始
进行中（apply）：tasks 8/23；当前任务「实现段切换的失败用例」；近 10 分钟改动 3 个文件
（f_store/src/wal.cj、f_store/src/log/shard.cj、f_store/src/test/wal_test.cj）；后台输出 12.4 KB（尾部：test compile ok）
停滞：否（连续 0 轮无变化）
```

停滞诊断：

```
【停滞诊断 · 已 15 分钟无进展】
卡点：④ apply（tasks 停在 8/23，当前任务「实现段切换的失败用例」）
事实：近 10 分钟 0 个文件改动；后台输出 12.4 KB 无新增；快照连续 3 轮无变化。
可能原因：
  1. CodeBuddy 卡在测试命令（编译死循环 / 等待输入）
  2. 远程任务已死但 ssh 连接未断（后台假活）
  3. 融合侧磁盘或资源问题
解决方案：
  A. 查远程进程与日志，确认是死是活（成本最低，先做）
  B. 确认已死 → 终止后台任务并重跑 apply（tasks 从 8/23 继续）
  C. 仍不通 → 交还用户，附证据
尝试：ssh 连通 ✓；ps 显示 codebuddy 仍在但 CPU 0% → 疑似等待输入，按 A→B 处理。
```

恢复后的进度报告（接在上例之后）：

```
【OpenSpec 进度 · 第 1 轮（恢复后）· 已等待 2 分钟】
项目/模块：fountain / f_store
变更：add-wal-support
阶段：
- ① 环境与刷新 ✅ 完成
- ② propose ✅ 完成
- ③ 用户评审 ✅ 通过
- ④ apply 🔄 进行中（tasks 8/23，重跑后已继续；当前任务「实现段切换的失败用例」按 TDD 先写失败测试）
- ⑤ verify ⬜ 未开始
- ⑥ archive + 落盘 ⬜ 未开始
进行中（apply）：重跑后后台输出恢复增长，近 5 分钟改动 2 个文件；tests 先红（符合 TDD），等待实现转绿。
停滞：否（连续 0 轮无变化；本轮变化项：tasksDone、recent）
```

## 7. 与其它规则的关系

- 六步产物与门禁（用户评审、verify CRITICAL、交付门禁）不受本协议影响——进度报告不等于放行。
- 停滞恢复后同样适用 TDD 门禁：apply 里逐任务 Red-Green-Refactor（`test-driven-development`），测试绿了才勾任务；verify 前 build / 全量回归 / 冒烟全绿。
- `fboot run` 的「后台跑 + 轮询日志」是另一条规则（见 SKILL.md「必须遵守」），别混用。
