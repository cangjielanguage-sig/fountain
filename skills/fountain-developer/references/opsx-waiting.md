# 等待 OpenSpec 任务：周期进度报告与停滞诊断

**适用**：六步流程（工作流 F / G / H / I / J）中，任一步经 `opsx-*` 技能发起 opsx 任务后，任务在后台运行、需要等待结果时。任务由融合侧 CodeBuddy 执行，通常几分钟到几十分钟；若任务里在跑 `cjpm build` / `cjpm test`，报告还必须带上 cjpm 状况（见第 3 节）。

## 1. 节奏

- 任务发起后（Bash 工具后台模式）立即进入等待循环：**每 5 分钟一轮**。
- 每轮先采集快照，再输出报告：

```bash
python3 <skill-root>/scripts/opsx_progress.py \
  --repo <仓库根> --change <变更名> --stage <当前步骤> --log <后台任务输出文件>
```

- 任务涉及 `cjpm build` / `cjpm test` 时，快照**再加 `--cjpm`**（经 ssh 采集融合侧进程与 cjpm 输出）。
- 用 `sleep 300` 控制节拍（Bash 工具 `timeout` 设 320000 以上，或后台跑 sleep）。
- 收到任务完成通知（或输出被截断、退出码出现）→ 出最终报告并退出循环。
- 任务在首个 5 分钟内完成 → 直接给最终报告，不做周期报告。

## 2. 每轮报告模板

```
【OpenSpec 进度 · 第 N 轮 · 已等待 X 分钟】
项目/模块：<项目名> / <模块名>
变更：<变更名>
阶段：
- ① 环境与刷新 … ✅ / 🔄 / ⬜
- ② propose ……
- ③ 用户评审 ……
- ④ apply ……
- ⑤ verify ……
- ⑥ archive + 落盘 ……
进行中（<当前阶段>）：<客观详情>
cjpm 状况：<在跑什么 / 进程 / 输出进展 / 测试进度>（任务不含 cjpm 时省略本行）
停滞：否 / 是（连续 N 轮无变化）
```

硬要求：

- **六项阶段一个不能少**；未开始的写 `⬜ 未开始`，不要省略。
- 已完成 `✅`；当前进行中 `🔄`（只允许一个）；等用户拍板 `⏳`；未开始 `⬜`。
- **「进行中」必须给客观详情**，至少包含：tasks 勾选进度（x/y）、当前任务（第一个未勾项）、近 10 分钟改动文件、后台输出尾部（传了 `--log` 时）。禁止「正在开发中」「继续推进」这类空话。
- 报告以快照数据为准，不凭印象编。

## 3. cjpm build / test 期间的状况报告

apply（逐任务 TDD 的测试）与 verify（build / 全量回归 / 冒烟）都会跑 cjpm。任务在跑 cjpm 时，每轮报告的 cjpm 板块必须给：

- **在跑什么**：`cjpm build` / `cjpm test`（最近命令），跑在哪个模块（命令里的 cwd）
- **进程**：cjpm / cjc 的 PID、已运行时长、CPU%、STAT（`R` 运行、`S` 睡眠、`D` 不可中断 IO）；进程列表是融合侧全局视图，多项目并行时可能含其他项目的进程——以「最近命令 + 输出文件」为准
- **输出进展**：输出文件（如 `/tmp/xxx.log`）大小与最近 5 分钟增量、尾部 3–5 行（编译到哪个文件 / 模块、测试跑到哪个用例、是否有 error）
- **测试进度**：尾部能看出用例名 / 进度百分比就直接引用；看不出就说明「编译阶段 / 输出无新增」

**判定「测试用例耗时过久」**：同一个 `cjpm test` 的输出尾部**连续 2 轮（约 10 分钟）**停在同一个用例 / 同一行，且输出文件大小不增、进程 CPU ≈ 0% → 按第 5 节的「测试卡死专项」检查死锁 / 活锁 / 长时间阻塞。编译慢但输出持续增长（新文件、新警告出现）**≠** 卡死，继续正常报告。

## 4. 停滞判定

- 连续 **3 轮**（约 15 分钟）快照无变化（tasks 勾选数、git 改动数、近 10 分钟文件、后台输出大小、cjpm 输出大小都没变）→ 停滞。
- 出现明确错误迹象（ssh 断开、输出出现 error/异常、任务退出码非 0）→ 立即停滞。
- 快照里出现 `停滞：**是**` 即触发，不要等到第 4 轮。
- 测试卡死（第 3 节的 2 轮信号）先做第 5 节的专项检查，不立即暂停周期报告；若检查后仍无进展并达到 3 轮，转入停滞诊断。

## 5. 停滞诊断（暂停周期报告）

先输出诊断块，再按顺序尝试：

```
【停滞诊断 · 已 X 分钟无进展】
卡点：<阶段 + 具体任务>
事实：<快照证据：tasks 停在哪、文件无改动、日志尾部>
可能原因：<2–4 条，按可能性排序>
解决方案：
  A. <首选>（代价 / 风险）
  B. <备选>
  C. <兜底：交还用户>
尝试：<先做成本最低的一步，给出命令与结果>
```

尝试顺序（每步都给命令与结果，不空谈）：

1. **ssh 连通**：`ssh running@172.16.105.2 'echo ok'`；不通 → 按 `opsx-*` 技能的连接协议重新询问/更新配置。
2. **任务是否还活着**：`ssh running@172.16.105.2 'ps aux | grep codebuddy | grep -v grep'`。
3. **融合侧 CodeBuddy 日志**：`ssh running@172.16.105.2 'ls -t ~/.codebuddy/logs | head -3'`，再 `tail` 看最新日志。
4. **后台输出尾部**：读 `--log` 文件最后几十行，查 error / 权限 / 网络等关键字。
5. **任务确实已死**：终止后台任务 → 重跑 `plan` 并执行（apply 从 `tasks.md` 当前勾选继续，已勾任务不会重做）。
6. **仍无解**：附完整证据与建议交还用户，不空转。

### 5.1 测试卡死专项：死锁 / 活锁 / 长时间阻塞

**触发**：`cjpm test` 输出尾部连续 2 轮（约 10 分钟）停在同一用例 / 同一行，输出文件大小不增，进程 CPU ≈ 0%（或长时间 `STAT D`）。

按序检查（每步给命令与结果）：

1. **区分三类**：
   - **死锁**：多个线程互相等锁——CPU ≈ 0%，线程 `S` 状态，输出不再增长
   - **活锁**：忙等 / 重试——CPU 100% 但无进展（输出不增），线程持续 `R`
   - **长时间阻塞**：`STAT D`（不可中断 IO），或等 socket / 文件 / 子进程 / 超时
2. **看进程与线程**：
   - `ps -eo pid,ppid,stat,pcpu,etime,args | grep -E "cjpm|cjc|test"`（找测试进程）
   - 线程级：`ps -T -p <测试进程 PID>`（或 `top -H -p <PID>`），看哪个线程卡住、状态如何
3. **加探针定位**（可添加，用于确定卡点）：
   - 在可疑路径加临时打印——锁获取前/后（`println("PROBE lock-acquire <name>")`）、循环/等待点的迭代次数与等待条件、线程入口/出口
   - 统一标记 `// PROBE(<任务名>)`，**只改可疑路径、不改逻辑**；定位后**必须移除**，不得留在交付代码
   - 用最小用例验证（只跑该用例；拿不准过滤方式就临时调整测试入口，用后还原）
4. **对照**：单独跑该用例确认是否稳定卡死；换一个用例确认是否与用例相关（排除测试框架本身）。
5. **按结论处理**：死锁 → 修锁顺序 / 缩小锁范围（先写能复现的并发用例，走 TDD）；活锁 → 退避 / 让出；阻塞 → 加超时 / 异步化 / 换非阻塞 API。
6. 若是 SDK / STDX 并发原语缺陷 → 按 `references/sdk-bug-handling.md`（最小复现用例 → 询问保存路径 → 绕过 → 绕不过报告进度并暂停）。

**解决后的恢复动作（按顺序，缺一不可）**：

1. **更新并报告进度**：`opsx_progress.py --reset` 重新计轮 → 立即采集一次新快照（含 `--cjpm`）→ 按第 2 节模板输出「恢复后的进度报告」（六阶段状态要反映解决动作带来的变化：任务重跑后的 tasks 勾选、改动文件、cjpm 输出恢复增长）。
2. **回到 OpenSpec 流程当前步骤继续**：从六步中的当前步骤接着走（不跳步、不重头）；用户评审门禁、产物落盘要求照旧。
3. **继续 TDD 验证**：若当前在 apply，继续按 `test-driven-development` 技能逐任务 Red-Green-Refactor——先失败测试、再最小实现、绿了才勾任务；探针已移除、测试转绿后再勾；进入 verify 前 `fboot build` / 全量回归 / 冒烟全绿的门禁不变。
4. **恢复周期报告**：之后回到每 5 分钟一轮的等待循环，继续按第 2 节报告（含 cjpm 状况）。

未解决且没有新动作 → 交还用户，不空转。

## 6. 红旗

| 你正想做 | 现实 |
| --- | --- |
| 后台跑了，安静等结果 | 用户看不到进度；每 5 分钟一轮报告 |
| 报告写「还在跑」 | 六阶段状态 + 进行中客观详情，缺一项等于没报 |
| 任务在跑 cjpm，但不报 cjpm 状况 | 必须给：在跑什么、进程、输出增量、尾部（第 3 节） |
| 测试跑了 10 分钟没动静，再等等 | 2 轮无输出增量 + CPU ≈ 0% → 按 5.1 查死锁 / 活锁 / 阻塞（可加探针），别干等 |
| 加了探针定位完不删 | `PROBE(...)` 必须移除，不得留在交付代码 |
| 卡住了先问用户 | 先诊断并尝试（ssh → 进程 → 日志 → 重扫输出 / 测试卡死专项），带证据和方案再找用户 |
| 停滞了继续报流水账 | 停滞即暂停周期报告，转诊断块 |
| 问题解决了直接继续下一轮报告 | 先更新并报告进度（`--reset` + 新快照），再回到六步当前步骤；apply 里继续 TDD 验证（测试绿才勾任务），不能跳 |
| 诊断块只说「可能有问题」 | 每轮诊断必须有新动作或新信息；没有就交还用户 |

```
卡死检查：线程栈显示 2 个线程分别持锁等待对方（疑似死锁）→ 已在 `<用例>` 加 PROBE 定位到
```

```
【停滞诊断 · 已 15 分钟无进展】

事实：近 10 分钟 0 个文件改动；后台输出 12.4 KB 无新增；快照连续 3 轮无变化。
可能原因：
  1. CodeBuddy 卡在测试命令（编译死循环 / 等待输入）
  2. 远程任务已死但 ssh 连接未断（后台假活）
  3. 融合侧磁盘或资源问题
解决方案：
  A. 查远程进程与日志，确认是死是活（成本最低，先做）
  B. 确认已死 → 终止后台任务并重跑 apply（tasks 从 8/23 继续）
```

## 8. 与其它规则的关系

- 六步产物与门禁（用户评审、verify CRITICAL、交付门禁）不受本协议影响——进度报告不等于放行。
- 停滞恢复后同样适用 TDD 门禁：apply 里逐任务 Red-Green-Refactor（`test-driven-development`），测试绿了才勾任务；verify 前 build / 全量回归 / 冒烟全绿。
- 测试卡死若根因是 SDK / STDX 并发原语缺陷 → 走 `references/sdk-bug-handling.md`（复现用例 → 保存路径 → 绕过 → 阻塞报告并暂停）。
- `fboot run` 的「后台跑 + 轮询日志」是另一条规则（见 SKILL.md「必须遵守」），别混用。
