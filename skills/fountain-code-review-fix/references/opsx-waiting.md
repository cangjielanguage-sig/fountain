# OpenSpec 流程与 cjpm/cjc 执行：周期进度报告与停滞诊断

**适用**：工作流 F / G / H / I / J / L 中，**从进入 OpenSpec 六步（步骤 1 起）或执行任何 `cjpm` / `cjc` 命令开始**，全程按本协议报告。**不再判断「是否在等任务结束」，也不再单独判断「测试用例是否耗时太久」**——任务在前台还是后台、是不是在等结果，都不影响报告；测试慢只是「状态停滞」的一种表现，统一按第 4 节判定。

## 1. 节奏

- **启动条件**（满足任一即开始，不需要用户要求）：
  - 进入 OpenSpec 六步流程（步骤 1 环境与刷新开始）；
  - 执行任何 `cjpm` / `cjc` 命令（`cjpm build` / `cjpm test` / `fboot build` / 直接 `cjc` 等）。
- 启动后**每 5 分钟一轮**，采集快照并输出报告：

```bash
python3 <skill-root>/scripts/opsx_progress.py \
  --repo <仓库根> [--change <变更名>] [--stage <当前步骤>] [--log <后台输出文件>]
```

- 脚本**默认采集 cjpm/cjc 状况**（经 ssh 查融合侧进程与输出尾部）；ssh 不通时报告「不可用」并继续，不中断流程。
- 用 `sleep 300` 控制节拍（Bash 工具 `timeout` 设 320000 以上，或后台跑 sleep）。
- **结束条件**：当前步骤结束且相关 `cjpm` / `cjc` 进程全部退出 → 出最终报告并退出循环；进入下一步骤时重新开始计时。
- 整个流程持续报告，直到流程结束或用户明确叫停；**不存在「这一步不需要报」的阶段**。
- 单个动作在首个 5 分钟内完成 → 直接给最终报告，不补周期报告。

## 2. 每轮报告模板

```
【OpenSpec 流程进度 · 第 N 轮 · 已进行 X 分钟】
项目/模块：<项目名> / <模块名>
变更：<变更名>
阶段：
- ① 环境与刷新 … ✅ / 🔄 / ⬜
- ② propose ……
- ③ 用户评审 ……
- ④ apply ……
- ⑤ verify ……
- ⑥ archive + 落盘 ……
进行中（<当前阶段>）：<客观详情>
cjpm/cjc 状况：<在跑什么 / 进程 / 输出进展 / 测试进度>
停滞：否 / 是（同一状态连续 N 轮、约 X 分钟无变化）
```

硬要求：

- **六项阶段一个不能少**；未开始的写 `⬜ 未开始`，不要省略。
- 已完成 `✅`；当前进行中 `🔄`（只允许一个）；等用户拍板 `⏳`；未开始 `⬜`。
- **「进行中」必须给客观详情**，至少包含：tasks 勾选进度（x/y）、当前任务（第一个未勾项）、近 10 分钟改动文件、后台输出尾部（传了 `--log` 时）。禁止「正在开发中」「继续推进」这类空话。
- **cjpm/cjc 板块每轮都要有**：没在跑就写「未在运行（最近一次：…）」，不许省略。
- 报告以快照数据为准，不凭印象编。

## 3. cjpm / cjc 状况

无论任务是否由 opsx 发起，只要在跑 `cjpm` / `cjc`，每轮必须给：

- **在跑什么**：`cjpm build` / `cjpm test` / `cjc ...`（最近命令），跑在哪个模块（命令里的 cwd）
- **进程**：cjpm / cjc 的 PID、已运行时长、CPU%、STAT（`R` 运行、`S` 睡眠、`D` 不可中断 IO）；进程列表是融合侧全局视图，多项目并行时可能含其他项目的进程——以「最近命令 + 输出文件」为准
- **输出进展**：输出文件（如 `/tmp/xxx.log`）大小与最近 5 分钟增量、尾部 3–5 行（编译到哪个文件 / 模块、测试跑到哪个用例、是否有 error）
- **测试进度**：尾部能看出用例名 / 进度百分比就直接引用；看不出就说明「编译阶段 / 输出无新增」

这些事实同时是第 4 节停滞判定的输入：**输出持续增长 = 有进展**；编译慢但新文件、新警告不断出现，不算停滞。

## 4. 停滞判定

- **同一状态连续 3 轮（约 15 分钟）无变化** → 停滞。状态与变化都按快照判定：阶段、当前任务、tasks 勾选数、git 改动数、近 10 分钟文件、后台输出大小、cjpm/cjc 输出大小、cjpm/cjc 进程数。
- 「同一状态」= 同一阶段 + 同一当前任务；任务推进或阶段切换即视为变化。
- 出现明确错误迹象（ssh 断开、输出出现 error/异常、任务退出码非 0）→ **立即停滞**，不等 3 轮。
- 快照里出现 `停滞：**是**` 即触发，不要等到第 4 轮。
- **不再有单独的「测试用例耗时过久」判定**：测试/编译卡住与其它状态卡住走同一套判定与诊断。

## 5. 停滞诊断（暂停周期报告）

先输出诊断块，再按顺序尝试：

```
【停滞诊断 · 同一状态已 X 分钟无变化】
卡点：<阶段 + 具体任务>
事实：<快照证据：tasks 停在哪、文件无改动、日志尾部、cjpm/cjc 进程状态>
可能原因：<2–4 条，按可能性排序；包含死锁 / 活锁 / 长时间阻塞 / 死循环>
解决方案：
  A. <首选>（代价 / 风险）
  B. <备选>
  C. <兜底：交还用户>
尝试：<先做成本最低的一步，给出命令与结果>
```

诊断顺序（每步都给命令与结果，不空谈）：

1. **ssh 连通**：`ssh running@172.16.105.2 'echo ok'`；不通 → 按 `opsx-*` 技能的连接协议重新询问/更新配置。
2. **任务是否还活着**：`ssh running@172.16.105.2 'ps -eo pid,ppid,stat,pcpu,etime,args | grep -E "codebuddy|cjpm|cjc" | grep -v grep'`。
3. **检查死锁 / 活锁 / 长时间阻塞 / 死循环**（任何卡住的状态都查，不限于测试）：
   - **死锁**：多个线程互相等锁——CPU ≈ 0%，线程 `S` 状态，输出不再增长
   - **活锁**：忙等 / 重试——CPU 100% 但无进展（输出不增），线程状态在 `R`/`S` 间反复
   - **死循环**：CPU 100%、线程持续 `R`，且**间隔 2–3 秒多次采样调用栈停在同一栈**（退出条件缺失 / 边界错误）；与活锁的区别——栈完全不变，看不到外部条件推进
   - **长时间阻塞**：`STAT D`（不可中断 IO），或等 socket / 文件 / 子进程 / 超时
   - 命令：`ps -T -p <PID>`（或 `top -H -p <PID>`）看线程状态；gdb 可用时 `gdb -p <PID> -batch -ex "thread apply all bt"` 对比多次采样
4. **加探针定位**（代码级可疑时）：
   - 在可疑路径加临时打印——锁获取前/后（`println("PROBE lock-acquire <name>")`）、循环/等待点的迭代次数与等待条件、线程入口/出口
   - 统一标记 `// PROBE(<任务名>)`，**只改可疑路径、不改逻辑**；定位后**必须移除**，不得留在交付代码
   - 用最小用例验证（只跑该用例；拿不准过滤方式就临时调整测试入口，用后还原）
5. **融合侧 CodeBuddy 日志**：`ssh running@172.16.105.2 'ls -t ~/.codebuddy/logs | head -3'`，再 `tail` 看最新日志。
6. **后台输出尾部**：读 `--log` 文件最后几十行，查 error / 权限 / 网络等关键字。
7. **对照**：单独跑卡住的用例 / 命令确认是否稳定复现；换一个用例确认是否与用例相关（排除框架本身）。
8. **任务确实已死**：终止后台任务 → 重跑 `plan` 并执行（apply 从 `tasks.md` 当前勾选继续，已勾任务不会重做）。
9. **SDK / STDX 并发原语缺陷** → 按 `references/sdk-bug-handling.md`（最小复现用例 → 询问保存路径 → 绕过 → 绕不过报告进度并暂停）。
10. **仍无解**：附完整证据与建议交还用户，不空转。

**解决后的恢复动作（按顺序，缺一不可）**：

1. **更新并报告进度**：`opsx_progress.py --reset` 重新计轮 → 立即采集一次新快照 → 按第 2 节模板输出「恢复后的进度报告」（六阶段状态要反映解决动作带来的变化：任务重跑后的 tasks 勾选、改动文件、cjpm/cjc 输出恢复增长）。
2. **回到 OpenSpec 流程当前步骤继续**：从六步中的当前步骤接着走（不跳步、不重头）；用户评审门禁、产物落盘要求照旧。
3. **继续 TDD 验证**：若当前在 apply，继续按 `test-driven-development` 技能逐任务 Red-Green-Refactor——先失败测试、再最小实现、绿了才勾任务；探针已移除、测试转绿后再勾；进入 verify 前 `fboot build` / 全量回归 / 冒烟全绿的门禁不变。
4. **恢复周期报告**：之后回到每 5 分钟一轮的循环，继续按第 2 节报告（含 cjpm/cjc 状况）。

未解决且没有新动作 → 交还用户，不空转。

## 6. 红旗

| 你正想做 | 现实 |
| --- | --- |
| 「这一步没在等任务 / 没在跑测试，不用报」 | 进入 OpenSpec 六步或执行任何 cjpm/cjc 就开始报，没有「不需要报」的阶段 |
| 后台跑了，安静等结果 | 用户看不到进度；每 5 分钟一轮报告 |
| 报告写「还在跑」 | 六阶段状态 + 进行中客观详情 + cjpm/cjc 状况，缺一项等于没报 |
| 「任务在跑 cjpm，但不报 cjpm 状况」 | 每轮必报；快照脚本默认采集，没在跑也要写「未在运行」 |
| 「测试 10 分钟没动静，再等等」 | 不单独判断测试耗时；同一状态连续 3 轮（约 15 分钟）无变化即转停滞诊断 |
| 「才 2 轮没变化，再等一轮」 | 3 轮是阈值；到 3 轮必须暂停周期报告、转诊断块 |
| 加了探针定位完不删 | `PROBE(...)` 必须移除，不得留在交付代码 |
| 卡住了先问用户 | 先诊断并尝试（ssh → 进程/线程 → 死锁/活锁/阻塞/死循环 → 日志 → 重扫输出），带证据和方案再找用户 |
| 停滞了继续报流水账 | 停滞即暂停周期报告，转诊断块 |
| 问题解决了直接继续下一轮报告 | 先更新并报告进度（`--reset` + 新快照），再回到六步当前步骤；apply 里继续 TDD 验证（测试绿才勾任务），不能跳 |
| 诊断块只说「可能有问题」 | 每轮诊断必须有新动作或新信息；没有就交还用户 |

```
  2. 测试框架等待超时（长时间阻塞）

  A. 按统一锁顺序修复并补并发用例（TDD 先红）——首选
  B. 先加 PROBE 确认锁获取顺序，再修复
```


## 8. 与其它规则的关系

- 六步产物与门禁（用户评审、verify CRITICAL、交付门禁）不受本协议影响——进度报告不等于放行。
- 停滞恢复后同样适用 TDD 门禁：apply 里逐任务 Red-Green-Refactor（`test-driven-development`），测试绿了才勾任务；verify 前 build / 全量回归 / 冒烟全绿。
- 卡死若根因是 SDK / STDX 并发原语缺陷 → 走 `references/sdk-bug-handling.md`（复现用例 → 保存路径 → 绕过 → 阻塞报告并暂停）。
- `fboot run` 的「后台跑 + 轮询日志」是另一条规则（见 SKILL.md「必须遵守」），别混用。
