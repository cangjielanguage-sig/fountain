# 审查清单

本文件是 reviewer 子 agent 的**筛查主线**：先用第 0 节的信号表扫一遍，命中后进对应小节拿判据、证据要求和修法。深度技术细节不在本文件重复，按章节号跳：

- 性能：`performance-optimization.md`（记作 `perf §N`）
- 内存：`memory-optimization.md`（记作 `mem §N`）

## 0. 使用约定

每条发现必须能回答三件事，缺一件就不写进报告：

1. **位置**：`path/to/file.cj:{行号}`，行号尽量窄到函数。
2. **判据**：为什么这是问题（触发了下面哪一条），而不是"我觉得可以更好"。
3. **证据等级**：
   - `静态确定`——只读代码即可判定（不可达语句、递归无出口、锁内 I/O）。
   - `需实测`——结论依赖输入规模或运行时（是否热点、锁竞争比例、命中率）。这类**不作为「发现」**：要么补齐数据后再判，要么写进「待验证假设」并说明怎么测。
   - `待确认`——缺少调用链或下游信息。写明缺什么，不要猜。
4. **来源**：`本次改动` 还是 `存量`（见 §11）。存量缺陷同样要报，但不能和本次改动引入的问题混在一起统计。

**每次审查都是全量推进**：一次运行覆盖全部模块与模块内全部 `.cj` / `.md`，不做增量（不按 diff 挑模块、不沿用上次结论）。

**不确定 API / 语言特性时先查文档**：用 `cangjie-doc-lookup` 核对签名与语义，凭记忆断言视为证据不足。

**严重度只由后果决定，不由修复难度决定。** 崩溃 / 数据错误 / 无界增长 / 静默失效 = 严重；可维护性与可读性 = 轻微。

| 快扫信号 | 去看 |
| --- | --- |
| `return` 后面还有语句、`if (false)`、只被测试引用的非 public 函数 | §1 死代码（**public 无引用不算**） |
| 两处代码形状不同但做的事一样 | §2 重复逻辑 |
| `{}`、`return None`、`TODO`、`catch {}` | §3 空实现 |
| 函数调用自己，或递归遍历用户可控结构 | §4 栈溢出 |
| 全量读入 / 按报文字段预分配 / 全局集合只增不减 | §5 OOM |
| 有 profile / 基准数据，想知道瓶颈在哪 | §6.1 热点瓶颈定位 |
| `synchronized` 里还有 I/O、日志、解析 | §6.2 大粒度锁 |
| `spawn` 后立刻 `get()`、并发度配置为 1 | §6.3 并发串行 |
| 嵌套循环、热点 `contains`、`remove(at: 0)` 当队列 | §6.4 低效算法 |
| 全局 `var` / 单例字段被多线程读写、检查-然后-写入 | §12.1 并发安全 |
| 一把大锁、锁里还有 I/O / 解析 / 回调 | §12.2 锁粒度（性能面见 §6.2） |
| 想知道"内存还能怎么降" | §7 |
| 想知道"CPU 还能怎么降" | §8 |
| 函数内大量临时对象，想降峰值内存 / GC | §9 local mode 可行性 |
| 模块里的 README / `doc/**` 与实现不符 | §13 文档一致性 |
| README 说的能力代码里没有，或新 public API 没进 README | §14 功能完备性与 README 覆盖 |
| 读到的现有函数可能有边界 / 空值 / 并发问题 | §11 现有代码的 BUG |

## 1. 死代码

**硬原则一：对外可达的 `public` 声明即使在本项目内没有任何引用，也不算死代码。** fountain 的 `f_*` 是给下游项目用的库，`public` 就是对外契约（README、其他仓库、外部使用者都可能引用）。

**硬原则二：非公共顶级声明（`internal` / `protected` / `private` 修饰的顶层类型）里的 `public` 成员，全项目没有使用就是死代码。** 类型本身对外不可见，它的 `public` 成员随之不可达——`public` 只是"在包 / 模块内放宽"，不是对外契约。

因此判死代码看的是**对外是否可达**，不是修饰符字面：

| 可见性 / 位置 | 判据 |
| --- | --- |
| `private`（文件 / 类型内） | 按"本项目内无调用者"判 |
| `internal`（默认，当前包及子包） | 按"本包及子包内无调用者"判 |
| `protected` | 只有「`public open class` / `public abstract class`（非 `sealed`）的成员」不算死代码，**其余未使用的 `protected` 一律算死代码** |
| `public` 且**对外可达**（顶层声明是 `public`，且所属嵌套链每层都是 `public`） | **一律不判死代码**；最多记一句"对外 API，仓内无引用"，作为信息不作问题 |
| `public` 成员但**对外不可达**（所属顶层声明是 `internal` / `protected` / `private`，或嵌套链上有非 public 类型） | **全项目无使用即死代码**——类型不可见，成员同样不可达 |

`protected` 只有一条豁免，其余全判：

| 所属声明 | 本项目内未使用时的判定 |
| --- | --- |
| `public open class` / `public abstract class` 的 `protected` 成员（类**非 `sealed`**） | **不算死代码**——外部模块可继承该类并访问该成员，它是扩展点 |
| `sealed` 类（`sealed abstract class` / `sealed class` / `sealed interface`）的 `protected` 成员 | **死代码**——`sealed` 只能在本包继承，外部无法继承，`protected` 实际只在本模块可见 |
| 非 `public` 类（`internal` / `protected` / `private` 修饰的类）的 `protected` 成员 | **死代码**——外部不可见 |
| 顶层 `protected` 函数 / 变量 | **死代码**——仅本模块可见 |
| 其他任何 `protected` 声明（嵌套类成员、接口里的、以及上面没列到的） | **死代码** |

一句话：**除「`public open class` / `public abstract class` 的 `protected` 成员」之外，本项目内没有使用的 `protected` 声明都是死代码。**

| 形态 | 识别方式 |
| --- | --- |
| 不可达语句 | `return` / `throw` / `break` / `continue` 之后的同层语句 |
| 恒真恒假分支 | `if (false)`；`Option` 上已被上游保证 `Some` 的 `None` 分支；`match` 里被前面 case 完全覆盖的 case |
| 无调用者 | **非 public** 的函数 / 类 / 常量 / 顶层 `let` 在可预见范围内无引用；未使用的 `import` |
| 仅测试使用 | **非 public** 符号只在 `*_test.cj` 命中——可提"是否该收窄可见性"，但这是可见性建议，不是死代码 |
| 注册了但永不触发 | 回调没人 publish、路由未暴露、定时器注册后立刻返回 `None` 失效 |
| 读了不用 | 配置项 / DAO 查询结果赋给局部变量后再无使用；死配置字段 |
| 兼容残留 | 旧签名、旧字段、旧枚举值，调用方已全部迁走 |
| 条件编译死分支 | `@When[...]` 在当前模块构建配置下恒不成立 |

机械动作（每个文件都做一遍，不做等于这一维没审）：

1. 每个 `private` 符号：全仓搜符号名，只有定义处命中 → 死代码。
2. 每个 `internal` 符号：在**本包及子包**内搜引用，无引用 → 死代码。
3. 每个 `protected` 符号：只要它不是「`public open` / `public abstract`（非 `sealed`）类的成员」，就在本 module 内搜引用——无引用 → 死代码；上面那一类则**不判**。
4. 每个 `public` 符号，先判**对外可达性**：
   - 顶层声明是 `public`，且整条嵌套链每层都是 `public` → **不判死代码**，只记录"仓内有无引用"作信息。
   - 所属顶层声明是 `internal` / `protected` / `private`，或嵌套链上有非 public 类型 → 它的 `public` 成员等于"包内放宽"，在**全项目**搜使用，无使用 → 死代码。
5. 每个 `return` / `throw` / `break` / `continue`：看同层后续语句。
6. 每个局部 `let` / `var`：赋值后是否被读取。
7. 每个 `import`：是否真的用到。

判据：

- 非 public 符号的"未使用"要给出搜索范围（`private` 全仓、`internal` 本包及子包、`protected` 与顶层 `protected` 在本 module 内），不能只在一个文件里搜不到就下结论。
- `protected` 只有一种豁免：`public open` / `public abstract` 且非 `sealed` 的类，其成员是给外部子类的扩展点，不判；**其余 `protected` 声明不必再分情况，无引用即死代码**。
- 对外不可达的 `public` 成员按"全项目无使用"判；判之前先确认所属顶层声明与嵌套链的可见性，别只看成员自己写了 `public`。
- 对外可达的 `public` 若想收窄可见性（例如只给测试用的公开 API），单独作为「可见性建议」提出，需用户确认无下游依赖；**不要写成死代码，也不要默认建议删除**。
- 本项目允许破坏性变更，但"删对外可达的 public API"仍是需要用户拍板的契约变更，报告里写清影响面。

误报边界：反射/宏生成调用（`@Bean`、`@Controller`、`@DAO`、`@Test` 的成员不是死代码）、框架按约定调用的回调、序列化字段、**对外可达的 `public` API（库对外契约）**、**接口实现 / 父类覆盖的成员**（即使全项目没有按名调用，也会经接口或父类被调用，不算死代码）。

## 2. 表现形式不同的重复逻辑

重复的判据是**语义相同**，不是语法相同。以下都算：

| 形态 | 例子 |
| --- | --- |
| 换控制流 | 同一套过滤，一处 `for + if`，一处 `while`，一处 `match` |
| 跨层复制 | Controller 校验一遍、Service 再校验一遍，规则文字不同但判定一样 |
| 字面量复制 | 同一张状态码表、同一个 SQL 片段、同一个正则、同一组字段名散落多处 |
| 只改类型名 | 两个函数体逐行对齐，只有 `Int64`/`Int32`、`User`/`Account` 不同 |
| 换算复制 | 时间、字节、金额、百分比的换算在多个文件各写一遍 |
| 近似重复 | `git diff` 两块代码相似度高，但其中一块少了边界判断——这往往同时是缺陷 |

机械动作：

1. 同文件内：把每个函数体压成一行摘要「输入 → 输出 → 副作用」，两两比对；摘要相同而语法不同就是重复。
2. 跨文件：搜相同的错误消息文案、正则、状态码表、字面量常量、SQL 片段。
3. 判断能否合并前，先列出差异点（边界、错误文案、日志级别、可空性、精度）；差异是业务要求就不是重复。

判据与建议：

- 合并建议必须**点名语义差异**：错误消息文案、边界是否包含、日志级别、可空性、并发假设、精度。有实质差异就不是重复，要么保留两份，要么把差异显式参数化。
- 抽取落点要守分层：下层模块不能反向依赖上层；通用能力放 `f_util` / 模块内 `util`，而不是新建共享包。
- 泛型不能乱上：如果两处唯一共同点是"都是循环"，抽取只会增加间接层。此时应报"命名不一致/实现漂移"而不是"重复逻辑"。

误报边界：为可读性刻意展开的简单逻辑、测试里的准备代码、两个模块本来就要求独立演进（避免耦合）。

## 3. 空实现

| 形态 | 严重度 |
| --- | --- |
| 公开契约承诺有行为，函数体为空或只 `return None` / `false` / `0` | 严重 |
| `TODO` / `FIXME` / `throw UnsupportedException` 占位仍在默认配置的主路径上 | 严重 |
| 接口给了默认空实现，实现类忘记覆盖 | 严重 |
| `catch (_: Exception) {}` 静默吞掉异常 | 严重（至少一般） |
| `case None => ()` 当兜底把错误吃掉 | 看语义：可选字段正常缺失可接受；`Result` 失败被丢弃是一般以上 |
| 开关打开后走进空分支（功能未接完） | 严重 |
| 有意的 Null Object / no-op 策略 | 不是问题，但必须有注释说明为什么可以空 |

判据：调用方是否依赖这个函数的副作用或返回值？有没有用例覆盖？空实现要么补上，要么把契约（返回类型、是否可选、调用方如何降级）写清楚，不能停在"看起来能编译"。

## 4. 栈溢出风险

| 形态 | 说明 |
| --- | --- |
| 无界递归 | 深度由输入决定：链表 / 树 / JSON / AST / 目录遍历 / 表达式求值 / 嵌套配置 |
| 间接递归 | A→B→A，或 `equals` / `hashCode` / `toString` 重载里又调用自身 |
| 自引用结构 | 父子互指、图有环，递归打印或深度比较直接无限递归（崩溃，不是慢） |
| 每帧大对象 | 递归函数内声明大 `Array` / 大 `struct`，栈帧变大后允许深度骤降 |
| 深度拷贝 | `clone` / `deepCopy` 递归整棵对象图 |
| 尾递归当保险 | 仓颉不保证尾调用优化，"是尾递归"不能作为安全依据 |

判据：

- 给出**可达深度上界**的推导：输入长度上限？配置上限？有没有访问集合做环检测？上限是"用户可控"还是"代码常量"？
- 平台栈大小以官方文档为准（用 `cangjie-doc-lookup` 现场查，不凭记忆写默认值）；报告里写清"按 N 层估算"而不是断言具体字节数。

修法：显式栈迭代 / 累加器 + 循环 / 递归深度计数 + 超限抛明确异常 / 访问 `HashSet` 做环检测 / 打印与比较只走一层字段。

误报边界：深度由不可变常量限定的递归（如固定 4 层协议解析）、深度很小且无环的树。

## 5. OOM 风险

| 形态 | 触发条件 |
| --- | --- |
| 一次性物化 | 整文件读入、`readToEnd`、全量 `split`、大对象 `toString`、`toArray` |
| 按不可信长度预分配 | `Array(n, repeat: x)` 的 `n` 来自报文头 / 配置 / DB 字段 |
| 无界容器 | 全局 `ArrayList` / `HashMap` / 队列随请求增长，GC 后条目仍在（`mem §3.1`、`§4.1`、`§5.2`） |
| 一次提交全量任务 | 为整个输入 `spawn` 并保存全部 `Future`（`perf §12.1`） |
| 平方级增长 | 循环里 `result = result + part`、循环里追加同一个副本 |
| 缓存键无界 | 用户 ID / 请求 ID 做 key，没有容量、TTL、淘汰 |
| 长期持有 | 闭包捕获大对象（`mem §7.1`）、`ThreadLocal` 不清（`mem §8.2`）、注册表不注销（`mem §6.2`） |
| 递归 + 每层分配 | 与 §4 同源，先爆栈再爆堆 |

判据（**必须量化**，否则只能是轻微）：

- 最坏输入规模 × 单元素内存 ≈ 峰值，与进程可用内存 / 容器 limit 对比。
- 有没有**拒绝路径**：大小上限、分页、流式、背压，而不是"到 OOM 才知道"。
- 上限写在哪里（常量 / 配置），改上限是否需要动代码。

修法优先级：流式 → 有界 → 分批 → 缩短生命周期；纯"调大堆"不算修复。

## 6. 低性能实现

### 6.1 热点瓶颈定位（先定位，再谈优化）

性能审查的第一步是**证明瓶颈在哪**，不是罗列"这里可能慢"。

**硬性前提：热点瓶颈结论必须有性能测试数据支持。**「数据」指至少一种可复核的测量结果——`cjprof record/report` 输出、`cjpm bench` 前后对照、带输入规模与轮数的分段计时日志。没有数据时：

- **不作为「发现」**（不当缺陷报、不参与严重度统计）；
- 只能写进报告末尾的「待验证假设」，注明缺哪种数据、怎么采（如「对该模块跑 `cjprof record`，输入 10k 条」）；
- **不进 `todo.md` / `tasks.md`**，也不得在交付说明里写成结论。

「调用次数多」「循环嵌套深」「用了锁」都只是**线索**，不是热点证据。

| 瓶颈类型 | 证据从哪来 | 典型信号 |
| --- | --- | --- |
| CPU 计算 | `cjprof record/report` 的 self time 占比 | 某函数自耗时占 30%+；调用次数不多但单次很贵 |
| 锁竞争 | 线程状态（BLOCKED / WAITING）+ 锁等待时长 | **CPU profile 里看不出来**；并发上不去、核利用率低 |
| I/O 等待 | 分段计时、系统调用统计 | CPU 空闲但延迟高；批量小、调用次数多 |
| GC 停顿 | `cjprof heap` / 分配量 / GC 次数 | 吞吐抖动；CPU 时间里含 GC 线程 |
| 序列化 / 日志 | 分段计时 | 业务逻辑很快、端到端慢；日志量大 |
| CFFI / 系统调用边界 | 调用次数 × 单次开销 | 单次很短但次数巨大（`perf §10.1`） |
| 内存带宽 / 缓存未命中 | 平台 profiler | 计算简单但耗时随数据量非线性 |

判定要求（缺任一条，本次热点结论不成立，降为待验证假设）：

1. **函数级定位**：热点函数名 + 自耗时占比 + 调用路径（谁调的）。
2. **输入规模**：在什么 n / 并发度 / 数据分布下成立；换输入会不会消失。
3. **对照**：与上一版或替代实现同环境对比；绝对值与占比都要给。
4. **排除法**：先排除 I/O、GC、锁等待，再谈纯 CPU 代码优化。
5. **收益上限**：按 Amdahl 估「占比 × 预期降幅」＝端到端可降比例；低于噪声（约 5%）不做。

常见误判（必须避免）：

- **调用次数最多 ≠ 最热**：看 self time，不看调用次数；被调百万次的轻函数可能不如被调千次的解析函数。
- **平均值掩盖长尾**：延迟问题看 P95 / P99，不看均值。
- **单线程 profile 代表并发场景**：锁竞争、线程池饥饿在 CPU profile 里几乎不出现。
- **微基准代表生产**：合成数据分布不同，热点会迁移；`cjpm bench` 的结论要回到真实负载复核。
- **"代码看起来低效" 当热点**：没有占比数据时，只能写进「待验证假设」。

报告写法：`热点瓶颈：<函数> 自耗时 <X>%（<工具>，输入 <n>，并发 <c>）→ 可优化点 <…> → 预期端到端 <Y>%`。

### 6.2 大粒度锁的热点

| 形态 | 判据 |
| --- | --- |
| 锁内做 I/O / DB / 序列化 / 正则 / 日志 | 临界区出现任何可能阻塞或 O(输入) 的动作（`perf §8.3`） |
| 一把全局锁保护多个无关资源 | 能按 key / 分片切开却用单锁 |
| 纯读也拿写锁 | 读多写少 → 读写锁 / 不可变快照 / 原子替换引用 |
| 锁内调用外部回调 | 回调可能再取同一把锁 → 死锁，且放大持有时间 |
| 多把锁顺序不一致 | 死锁（**按正确性问题报严重**） |
| `synchronized` 内 `spawn(...).get()` | 自锁等待（**严重**） |
| 每次操作新建锁对象 | 等于没有互斥（**严重**） |
| 用并发容器就当复合操作原子 | 检查-然后-写入仍需锁或 CAS（**严重**） |

证据：临界区包含哪些语句、单次持有时间量级、竞争线程数、是否在请求主路径。

修法：缩小临界区 → 分片 → 不可变发布 → `Atomic`（仅单值；跨字段不变量继续用锁）→ 读写锁。

### 6.3 并发串行热点

| 形态 | 判据 |
| --- | --- |
| `spawn` 后立刻 `get()` | 形式并发、实际串行（`perf §8.2`） |
| 批内只放 1 个任务 | 窗口 / 批大小配成 1，或循环里逐个 `get()` |
| 所有任务抢同一把锁 / 同一个连接 / 同一个 writer | 并行度上限 = 1 |
| 单消费者队列 + CPU 密集处理 | 消费端成为串行段 |
| 高竞争 CAS 自旋 | 重试次数可能超过实际工作量 |
| 任务内再等子任务 | 池被自己的子任务占满 → 饥饿 |
| 定时任务逐条串行处理 | 单轮耗时随表增长，挤占下一轮 |

证据：并发度上限、实际并行度、串行段占比；"并发度 = 核数"之类的假设要写出来。

修法：独立任务先提交再统一汇合 → 有界窗口 → 按 key 分片 → 把串行段（锁、单连接、单 writer）移出热点或改为批量。

### 6.4 低效算法实现

| 形态 | 复杂度代价 |
| --- | --- |
| 双层循环做匹配 / 去重 / 交集 | O(n·m) |
| 热点里对 `Array` / `ArrayList` 反复 `contains` / `indexOf` | 每次 O(n)（`perf §3.1`） |
| `remove(at: 0)` 当队列头 | 每次 O(n)（改用索引队列 / 双端队列） |
| 每请求排序只为取 top-k | O(n log n)，可用堆或单趟选择 |
| 同一输入重复解析 / 重复编译正则 | 每次 O(size) |
| 循环内字符串 `+` | O(n²)（`perf §4.1`） |
| 每次重新计算昂贵 hash / key | 常数巨大 |
| 正则回溯型写法 | 最坏指数级 |
| 只判存在却全量扫描 | 可提前返回（`perf §2.3`） |
| 已知规模却不预分配 | 多次扩容复制（`perf §3.2`，需实测） |

证据：输入规模 n、调用次数、复杂度量级、实际耗时占比。要能回答"n 到多大时它会成为瓶颈"。

修法：换数据结构 → 降复杂度 → 提前退出 → 预计算 → 批量，且必须附等价性用例（顺序、重复值、异常顺序都不能变）。

## 7. 可降低堆内存占用的可行性方案

§5 报的是"会不会 OOM"，本节报的是"现状能省多少"。写成可行方案，不写"建议优化内存"。

**先决条件：没有性能测试数据的方案只能写成「待验证假设」。** 本节每条都必须在「前置证据」里标明 `已有基线` 或 `无基线（待验证）`；后者不得进 `todo.md` / `tasks.md`，也不得在交付说明里写成结论。

每条按这个格式：

```markdown
- **现状**：持有什么、多大、活多久（对象数 / 字节量 / 生命周期）
- **方案**：具体改动（改哪个类型、哪个生命周期、哪个上限）
- **预期**：可量化收益（减少的对象数 / 峰值占比 / 每轮分配量）
- **代价**：语义变化、额外 CPU、复杂度、需要重启或改配置
- **验证**：多轮负载下 `getAllocatedHeapSize()` + RSS + 业务计数是否达到有界稳态（`mem §1.2`）
- **前置证据**：已有 / 待补（待补的只能定为轻微）
```

候选按收益/风险排序：

1. 缩短生命周期（缩作用域、`ThreadLocal.set(None)`、注册表对称注销）
2. 删除中间副本（`toArray` / `clone` / 多份表示同时存活，`mem §2.2`、`§5.3`）
3. 流式化（分块读、边解析边消费，`mem §5.1`）
4. 有界化（缓存容量 + 淘汰、队列容量 + 背压、历史保留条数）
5. 表示优化（`class`→`struct`、字段瘦身、共享不可变串、避免 `Any` 装箱）
6. 池化（**最后一项**，且必须有上限；无界池会把峰值变常驻，`mem §2.3`）
7. `WeakRef`（仅限可重建对象，且必须清理失效键；它不是淘汰策略，`mem §4.3`）

必须同时说明的假象：`clear()` 只清元素不还物理内存（`mem §3.2`）；手动 `gc()` 不保证归还；RSS 单次下降不构成修复证明。

## 8. 可降低 CPU 占用的可行性方案

格式同 §7，同样**先决于性能测试数据**：无基线的方案只能标「待验证假设」，不得进修复清单。候选按收益/风险排序：

1. 降复杂度（§6.4）
2. 减少分配与 GC 压力（临时集合、循环拼接、装箱）
3. 缓存 / 预计算（先证命中率；低命中缓存反而更慢，`perf §7.3`）
4. 批量化 I/O 与跨边界调用（`perf §9.2`、`§10.1`）
5. 有界并行（窗口 + 独立任务先提交后汇合，`perf §12.1`）
6. 降低锁竞争（§6.2）
7. 去掉异常控制流（缺失键走 `Option` 而非抛异常，`perf §6.3`）
8. 降低日志 / 序列化放大（`perf §9.1`）
9. 热路径去抽象（无捕获 Lambda 提升、`Any` 换具体类型，`perf §6.1`、`§11.3`）
10. 预热 / 懒初始化取舍（启动期 vs 首请求）

验证：`cjpm bench` 同环境对照，或 `cjprof record/report` 定位热点；报告绝对值、单位、中位数与离散程度，**不接受一次最快值**，也不接受"关掉日志后变快了"当作端到端结论（`perf §9.3`）。

## 9. local mode 改造可行性（实验特性）

local mode 用类型描述"对象不离开当前函数"，运行时把这类对象放进函数专属 local region，**函数返回时整块释放**，不等 GC。它降的是**峰值内存**，不是吞吐——官方文档明确写了这一点，所以只能靠峰值内存对照来证明收益。

| 形态 | 判据 |
| --- | --- |
| 函数内创建、函数内用完的大对象（解析中间结构、临时数组、批量拼接串） | 有逃逸就不成立；先确认对象没有作为返回值 / 成员 / 全局变量逃逸 |
| 高频短生命周期临时对象的分配热点 | 需要分配量 / 峰值内存证据，不能只凭"临时对象多" |
| 峰值内存高、GC 后 RSS 不回落 | 先按 `mem §1` 排除长期强引用与无界容器，再看 local region 是否受益 |
| 已启用 local mode 的模块与未启用的模块混链 | 编译产物不保证跨 SDK 兼容；同包及其依赖须同版本 SDK 编译 |

改造可行性必须写清的约束（缺一条就只能是「待验证假设」）：

1. **实验特性**：需要 `--experimental --enable-local-mode`；`cjpm` 无单独开关，只能在 `cjpm.toml` 的 `compile-option` 逐模块开启（`override-compile-option` 会波及全部依赖，且让 `exclave` / `demode` 成为关键字）。
2. **逃逸检查**：`@ local!` 值不能作为 `@ ~local` 返回、不能存进全局 / 静态成员；需要返回时用 `exclave`。工具链（`cjfmt` / `cjlint` / LSP / `cjdb`）不保证完整支持。
3. **非 `Copyable` 类型要重建**：给普通对象加标注不会把它变成 local 对象，得用 local 构造函数（如 `String(text) @ local!`、`localText.split`）；std API 是否有对应 mode 重载要逐个核对签名。
4. **容量上限**：所有线程活跃 local region 共用 `cjLocalRegionMaxSize`，超限抛 `LocalRegionOutOfMemoryError`；这是新的 OOM 面，必须评估最坏输入。
5. **数据口径**：`getAllocatedLocalObjectSize()` 统计 local region（不计入 `getAllocatedHeapSize()`），调用会暂停所有仓颉线程，不能在热点里频繁用；收益必须同时给峰值内存（RSS / `getUsedHeapSize()`）与分配量对照。

结论写法：

- 可行 → 给「改造范围（哪几个函数 / 类型）+ 预期峰值降幅 + 代价（实验特性、工具链、SDK 锁版）+ 验证方式（改前改后峰值内存、`-O2`、同输入）」。
- 不可行 → 写清被哪条约束卡住（逃逸 / 无 mode 重载 / 工具链 / 容量上限）。
- **没有前后峰值数据 → 只能是「待验证假设」**，不得写成优化建议，更不得进 `tasks.md`。

## 11. 现有代码的 BUG（存量缺陷）

不是只有 diff 里的行才叫缺陷。**读到的现有代码有 BUG 同样要报**——只是要标清来源，别把它算成本次改动引入的回归。

### 判定来源

| 来源 | 判据 |
| --- | --- |
| **本次改动** | 出问题的行 / 分支落在本次 diff 内（分支模式看 `git diff --cached`，快照模式无 diff 则全算存量） |
| **存量** | 不在本次 diff 内；快照模式统一记「存量（无基线可比）」 |

用 `git blame -L <start>,<end> -- <file>`、`git log -S "<符号>"` 核实，**不要凭"看起来像老代码"下结论**。

### 最值得报的形态

| 形态 | 例子 |
| --- | --- |
| 边界差一 / 越界 | 循环里访问 `i + 1`；切片上界写成 `<=`；`size - 1` 在空集合上成立 |
| 空集合 / 空串 / `None` 未处理 | 直接取 `[0]`、`Option` 无条件取、除零 |
| 错误处理缺失或静默 | 返回值被忽略、异常被吞、失败路径当成功 |
| 资源不对称 | 打开未关、异常跳过释放、CFFI acquire 未 release |
| 并发正确性 | 共享可变状态无保护、检查后写入非原子、锁顺序不一致 |
| 语义与命名 / 注释不符 | 名为 `validate` 只做了 trim；注释承诺 A，实现做 B |
| 契约与实现不符 | 公开 API 声称幂等 / 线程安全，实现不成立 |
| 与规格 / README 冲突 | 参数默认值、返回结构、错误码与 `doc/` 记载不一致 |

### 约束（防止审查变成全仓考古）

- 只审**本轮范围内的文件**，不为找存量缺陷做全仓扫描；读上下文时撞见就报，没读到的不臆测。
- 存量缺陷**默认只报不修**：进 `todo.md` 时标 `[存量]`，是否纳入修复由用户在门禁决定；未确认不得进 `tasks.md`。
- 存量缺陷同样要给位置、判据、证据等级；拿不准是缺陷（"可能是有意为之"）的写 `待确认`，说明缺什么信息（规格、调用方约束、上游契约）。
- 与本次改动同源但涉及未改动行的，记「存量（本次改动放大）」并说明放大路径。

## 12. 并发安全与锁粒度

**默认立场：除非有证据证明这段代码只在单线程使用，否则按"会被多线程并发调用"审查。** 顺序永远是**先证明安全，再谈锁粒度**——不允许为了去锁、缩锁而牺牲正确性。

### 12.1 并发安全（先证明"安全"）

| 形态 | 判据 |
| --- | --- |
| 共享可变状态无保护 | 全局 `var` / 静态成员 / 单例字段被多线程读写，无锁、无原子、无线程封闭 |
| 检查-然后-写入 | `if (!map.contains(k)) { map.add(k, v) }`；容器线程安全**不代表**组合操作原子 |
| 惰性初始化 | 双重检查锁定写错（缺原子/同步）、`if (x == None) { x = ... }` 的首次赋值竞态 |
| 发布逸出 | 构造未完成就把 `this` 交给别的线程或注册回调；注册时立即回调 |
| 迭代与修改并发 | 遍历容器时另一线程增删，快照语义未定义 |
| 锁对象误用 | 每次操作新建 `Mutex()`；锁可变对象；不同代码路径锁不同实例 |
| 死锁 | 多锁顺序不一致；锁内调用外部回调（回调再取锁）；`synchronized` 内 `spawn(...).get()` |
| 可见性 | 用普通字段当跨线程信号，而不走原子 / 锁 / 通道；依赖"写完立刻被看到" |
| 条件等待 | 条件变量虚假唤醒未在循环里重查条件；等待超时后状态未处理 |
| 跨线程资源 | 连接 / 文件句柄 / 迭代器被多线程共享；`ThreadLocal` 残留（`mem §8.2`） |
| 异步语义 | `Future` 异常被吞、取消后仍改状态、超时但任务继续跑（`perf §12.2`） |
| 有界性 | 无界任务队列 / 线程池堆积（`mem §5.2`） |

判据：**要么指出两个并发访问者与它们之间的同步手段，要么明确"该对象线程封闭"**。只写"可能有并发问题"不算证据。

### 12.2 锁粒度（越小越好，最好没有）

按顺序问，前一档能满足就不要用后一档：

1. **能不能不要锁**：不可变数据；线程封闭（每线程一份）；单写者 / 消息传递；整块状态原子替换（快照 + CAS）。
2. **能不能更小**：
   - **缩小临界区**：只保护不变量本身；I/O、解析、序列化、日志、外部回调一律移到锁外。
   - **分片**：按 key 哈希到多把锁 / 多段容器，而不是一把全局锁。
   - **读写分离**：读多写少用读写锁 / 不可变快照 / 写时复制。
   - **单值用 `Atomic`**；跨字段不变量继续用锁，别把复合操作拆散。
3. **最后才接受粗锁**：一把锁保护整个状态时，必须说明为什么不能细分。

判定要求：

- 报「大粒度锁」必须给出：临界区里做了什么、单次持有时长量级、竞争线程数或调用频率、是否在请求主路径。
- **去锁 / 细粒度化是设计变更**：写清替代方案如何维持原有不变量，并附并发压力测试（多线程跑同一用例 + 断言最终状态）。
- 无锁化若引入 CAS 自旋，高竞争下可能比锁更差——同样要有数据（`perf §8.3`）。
- 与 §6.2 的分工：§12.2 判"该不该这么锁"（设计），§6.2 判"这个锁是否已成热点"（性能证据）。

误报边界：明确只被单线程调用的内部辅助函数、文档声明非线程安全的类型、每次调用新建的局部对象（无线程共享）。**"这个类可能在多线程里用"不算证据**，要指出具体共享路径（全局 / 单例 / 成员 / 注册表 / 回调）。

## 13. 文档与代码一致性（.md 文件）

审查范围包含模块内**全部 `.md`**（`README.md`、`README_en.md`、`doc/**/*.md`）。文档承诺就是对外契约，写错会把使用者带沟里，所以 `.md` 与 `.cj` 一样逐文件读。

| 形态 | 判据 |
| --- | --- |
| API / 配置 / 默认值与源码不符 | 文档写的函数名、参数、默认值、错误码在 `src/` 里找不到或不一致 |
| 示例代码不能用 | 示例引用了不存在的 API、旧签名或不存在的模块 |
| `README_en.md` 与 `README.md` 不同步 | 章节、参数、示例缺失，或两版结论相反 |
| 文档过期 | 描述的功能已删除 / 改名；写着"暂不支持"其实已支持 |
| 关键段落缺失 | 安装、快速开始、配置、限制条件缺失，按文档用不起来 |
| 链接 / 路径失效 | 指向已删除文件、错误相对路径、死链 |
| 规格与实现漂移 | `doc/spec/**` 的验收口径与当前实现不一致 |

判据：必须给出**两边位置**——文档行号 + 代码行号（或"代码中不存在"的搜索证据）。只说"文档可能过期"不算。

严重度：文档承诺与实现相反、示例跑不通 → 一般；拼写、格式、措辞 → 轻微。

误报边界：`CHANGELOG` 的历史条目、明确标注"历史 / 已废弃"的文档、`doc/spec/<已归档变更>/`（按"当时结论是否自洽"核对，不要求与当前实现一致）、第三方移植说明。

## 14. 功能完备性与 README 覆盖

§13 管"写了但写错"，本节管**"该有的没有"**：功能没做完、README 没覆盖到。两者共用同一条判据——**找到承诺源，指出缺失面**。

### 14.1 功能完备性

| 形态 | 判据 |
| --- | --- |
| 承诺了但没实现 | README / 接口注释 / 设计文档说支持某能力，代码里没有入口，或直接 `throw UnsupportedException` |
| 半成品 | 主路径上还有 `TODO` / `FIXME`；只处理部分输入（只支持 ASCII、只支持单文件）；错误分支写"暂不处理" |
| 接线缺失 | 配置项被读取却从未使用；`@Bean` 注册了却没人 `lookup`；命令 / 路由注册了但没有分发；枚举新 case 没有分支 |
| 只做了一半的分支 | `match` 少一个 case 落到 `_ => ()`；开关只在一处判断，另一处仍走旧逻辑 |
| 能力未接入 | 新模块没进 workspace `members` / 模块索引 / `.modules`；新配置项没进默认配置样例 |
| 版本与依赖漂移 | `cjpm.toml` 版本与仓库发布策略不一致；依赖版本与 fboot 版本不匹配 |

判据：给出**承诺源**（文件:行号）与**缺失证据**（代码里搜不到 / 是空实现 / 是 TODO）。只有"感觉没做完"不算。

### 14.2 README 覆盖

以 `src/` 的公开声明为基准，逐个对照模块 README：

| 检查 | 判据 |
| --- | --- |
| 公开 API 未文档化 | `public` 类型 / 函数 / 宏 / 配置项在 README 中检索不到（列出符号名） |
| 缺关键段落 | 用途、依赖与安装、快速开始、配置项表、限制与注意事项、示例，缺哪段写哪段 |
| 示例覆盖不足 | 只有 hello world，核心能力（配置、扩展点、错误处理）没有示例 |
| 中英不同步的"缺失" | `README_en.md` 少整节（措辞差异归 §13） |
| 索引未登记 | 新模块没写进根 `README.md` 的模块表 / 模块索引 |
| 版本与命令过期 | README 里的版本号、安装命令、运行命令与当前工程不符 |

判据：README 遗漏必须**点名符号或段落**，并说明影响（按文档用不起来 / 不知道有这个能力）。

严重度：README 承诺的功能不存在 → 严重；公开 API / 关键配置完全无文档 → 一般；次要参数、示例缺失 → 轻微。

误报边界：`internal` 实现细节不必写进 README；`@Bean` 实现类、测试辅助、生成代码不算"公开 API 未文档化"。
