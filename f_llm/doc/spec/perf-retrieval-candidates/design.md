# Design

## Decisions

### D1. 统一用 `max(k*4, 20)` 作为「值得付远程开销」的候选数

`limit`（或 `topK`）通常 5，取 4 倍留出被过滤掉的余量；下限 20 保证小结果集也有足够候选。

**替代**：按分数阈值截断。否决——分数分布随模型/语料变化，阈值难以设得稳。

### D2. Hydra 采取「先紧后松」

前 bound 个拉完仍不足 `limit` 时，把 bound 放宽到全量继续找。**正确性优先于往返次数**：宁可多查，
也不能因为过滤（用户/命名空间）把结果集削空。

### D3. 记忆重排：未入选候选预置 0 分而不是缺键

下游 `rerankScores.get(id).getOrThrow()` 假定每个候选都有键；预置 0 既满足该假定，又让未重排的候选排在后面。

### D4. 知识候选上限降到 400

1000 条候选的正文全量驻留（1000 × 数百字）在默认 5 条结果面前不划算；400 仍覆盖 2 页词面召回。
参数保留可调，需要更高召回的后端可显式传 `maxCandidates`。

### D5. SkillCatalog 不缓存列表

`skills.upsert` 后新技能必须立刻可检索（既有用例就依赖这一点）。缓存方案要么加版本号失效（要改 SkillStore 契约），
要么用 TTL（引入不确定的陈旧窗口），两条都不划算——重复的只是一次本地 `skills.list()`。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 候选上限下调导致长尾召回变少 | `limit` 内结果不变；需要时显式传 `maxCandidates` |
| Hydra 放宽逻辑写错会漏结果 | 放宽条件只看「hits < limit」，不做额外判断；既有 hydra 用例回归 |
| 重排只覆盖前 N 个 | 前 N 已是融合分最高的，重排本就是在高分候选里微调顺序 |
