### 测试缺失场景（建议补充）

#### 高优先级
1. **并发读写测试**：目前没有任何多线程并发测试。MemTable 使用 ConcurrentSkipListMap，理论上支持并发，但缺少验证。场景：
   - 多线程同时 add，验证 sequence 不冲突
   - 一边 add 一边 get，验证一致性
   - 一边 flush 一边 add（MemTableManager swap + 新写入）

2. **WAL 损坏恢复**：仅有截断记录测试。缺少：
   - CRC 校验失败场景（部分字节翻转）
   - 中间记录损坏，后续记录仍可恢复

3. **Compaction 多文件合并（>2 源）**：SSTableMerger 测试最多只有 2 个源。实际 L0 compaction 可能合并 4+ 个 SSTable 文件。缺少：
   - 3+ 源归并测试
   - L0 到 L1 compaction 的端到端测试（L1已有数据，L0有4个文件）

#### 中优先级
4. **MemTable 容量边界**：当 MemTable 达到阈值时，MemTableManager.add() 返回 false（触发 flush）。缺少此场景的测试。

5. **WAL 轮转**：WAL 达到一定大小后是否会轮转？当前测试未覆盖。

6. **Store 自动 flush 线程**：Store 启动后台 WAL flush 线程，缺少对此线程行为的测试。

#### 低优先级
7. **极端大小**：key/value 为 0 字节、接近上限大小的测试仅有 WALRecord 覆盖，SSTable、MemTable 缺少覆盖。

8. **BloomFilter 行为**：代码中未见 BloomFilter 实现，如需添加应考虑误判率测试。

## 二、性能优化分析

### 优化点 1：L0 查询 O(N_sstables) — **关键热点**

**现状**：`LevelManager.get()` 对 L0 层所有 SSTable 逐个调用 `.get()`。L0 层 key range 可能重叠，无法通过 min/max key 过滤。当 L0 有大量文件（如 4~8 个）时，每次查询都线性扫描全部文件。

```cangjie
// LevelManager.get() 中类似逻辑：
for (sst in level0files) {
    let result = sst.get(key)
    if (result.isSome()) { return result }
}
```

**优化方案**：
- **(A)** 对每个 L0 SSTable 建立内存 BloomFilter，先用 BloomFilter 排除不可能存在的 key，再执行 mmap 查询。可减少 90%+ 的无效磁盘访问。
- **(B)** 对 L0 文件按时间排序，优先查询最新的 SSTable（新数据覆盖旧数据），在找到第一个匹配后提前返回。当前实现已按 sequence 范围排序，但未做提前退出优化检查。
- **(C)** 激进方案：L0 文件数量达到阈值（如 4）后立即触发 Compaction（当前 needCompact 已实现），但 compaction 本身有 IO 开销，需平衡。

### 优化点 2：SSTableIterator 逐 Block 读取 — **读放大**

**现状**：`SSTableIterator.next()` 每次跨 block 时触发 mmap 切片读取。每个 Data Block 单独解码，无预取。

```cangjie
// 每次跨 block:
let blockData = mapping[blockOffset..blockEnd]
let entries = decodeDataBlock(blockData)
```

**优化方案**：
- **(A) 预取下个 Block**：当前 Block 读取完毕后，异步预取下一个 Block 的数据（利用 OS page cache 的 readahead，或手动 madvise）。
- **(B) Block 缓存**：对热点 SSTable 的 Index Block 和数据 Block 做 LRU 缓存，避免重复 mmap 解码。

### 优化点 3：ByteArray 比较开销 — **CPU 热点**

**现状**：`ByteArray` 是 struct，包装了 `Array<Byte>`。每次 `compareTo` 调用时，生成迭代器逐个字节比较。MemTable 底层 `ConcurrentSkipListMap` 大量调用比较操作。

```cangjie
public func compareTo(other: ByteArray): Int64 {
    let a = bytes
    let b = other.bytes
    let minLen = min(a.size, b.size)
    for (i in 0..minLen) {
        let cmp = Int64(a[i].toInt64() - b[i].toInt64())
        if (cmp != 0) { return cmp }
    }
    return Int64(a.size - b.size)
}
```

**优化方案**：
- **(A) 前缀缓存**：对 ByteArray 增加 `hashCode` 缓存字段，先用 hash 快速排除不相等的情况。
- **(B) 内联比较**：确保 compareTo 被 JIT/AOT 内联展开。当前逐字节循环可能无法被向量化。考虑对 >= 8 字节的后缀使用 `Int64` 比较。
- **(C) 避免复制**：`toInt64()` 和减法每次可能产生装箱。改用原生 `UInt8` 差值比较。

### 优化点 4：WAL 每次写入 syscall 开销 — **写吞吐瓶颈**

**现状**：`WAL.append()` 每次调用 `file.write()` 直接落盘。虽然有后台定期 `sync()`，但每次 append 仍产生一次 write syscall。

```cangjie
public func append(key: Array<Byte>, value: Option<Array<Byte>>, ...): Int64 {
    let record = WALRecord(seq, key, value, expireAt)
    let encoded = record.encode()
    file.write(encoded)  // 每次一次 syscall
    ...
}
```

**优化方案**：
- **(A) 用户态缓冲**：WAL 内部维护一个 `Array<Byte>` 缓冲区（如 64KB），多条记录先写入缓冲区，缓冲区满或 sync 时一次性 `file.write()`。
- **(B) 批量 append 接口**：提供 `appendBatch(entries: Array<(Key, Value)>)` 接口，一次编码一批记录后单次写入。

### 优化点 5：SSTable finishWrite() 全量排序 — **写入尾延迟**

**现状**：`finishWrite()` 阶段对全部 EntryValue 执行排序、索引构建、BloomFilter 构建、多 Block 分割编码。这导致 finish 时延迟与数据量成正比。

```cangjie
public func finishWrite(): SSTableMetadata {
    entries.sortBy(...)  // 全量排序
    // 构建 index + Bloom + 多 Block 编码 + 写 footer
}
```

**优化方案**：
- **(A) 写到即排序**：由于调用方（MemTable iterator）已按序提供数据，可保证 `write()` 调用本身有序，省去 `finishWrite()` 中的排序步骤。只需加断言/校验。
- **(B) 流式构建 Index**：每写满一个 Data Block（~4KB）就立即构建 Index Entry，而非等 finish 时批量构建。

### 优化点 6：Compaction 期间锁竞争

**现状**：`LevelManager` 在 compaction 期间持有锁，阻塞同层级的 get 操作。

**优化方案**：
- **(A)** 使用读写锁（`ReentrantReadWriteLock`），get 操作仅需读锁，compaction 替换文件列表时需写锁。
- **(B)** 文件替换使用原子引用切换（`AtomicReference<ArrayList<SSTable>>`），避免 get 路径上的锁竞争。

### 优化点 7：SSTable.open() mmap 开销 — **启动/恢复延迟**

**现状**：`SSTable.open()` 使用 mmap 映射整个文件。大量 SSTable 文件（如 100+）会导致启动时大量 mmap 调用和虚拟地址空间占用。

```cangjie
public static func open(path: String): SSTable {
    let file = File(path, OpenMode.Read)
    let mapping = file.map(FileMapMode.Read)  // mmap 整个文件
    ...
}
```

**优化方案**：
- **(A) 延迟 mmap**：open 时只读取 Footer/Index，get 时才 mmap 对应 data block 区域。
- **(B) mmap 窗口化**：对于大文件，仅 mmap index 区域；data blocks 使用 pread 按需读取。

## 三、总结

### 测试评分：7.5/10
- 单元测试覆盖全面，核心路径均有覆盖
- 并发测试完全缺失
- 损坏恢复测试不足

### 性能评分：6/10
- **最优先修复**：L0 O(N) 查询 + BloomFilter（优化1）
- **次优先**：ByteArray 比较开销（优化3）、WAL 缓冲写入（优化4）
- **可按需优化**：SSTable 预取（优化2）、mmap 延迟加载（优化7）、finishWrite 排序消除（优化5）

### 建议的优化优先级排序

| 优先级 | 优化项 | 预期收益 | 实现难度 |
|--------|--------|----------|----------|
| P0 | L0 查询加 BloomFilter | 读延迟降低 50%+ | 中 |
| P1 | ByteArray 比较内联优化 | CPU 使用降低 10-20% | 低 |
| P1 | WAL 用户态缓冲 | 写吞吐提升 2-5x | 低 |
| P2 | SSTable 延迟 mmap/预取 | 启动延迟降低 + 大文件读优化 | 中 |
| P2 | Compaction 读写锁 | 并发读性能提升 | 低 |
| P3 | finishWrite 消除排序 | 写入尾延迟降低 | 低（需确保有序保证） |

#### 1.1 【P0 正确性】修复 Store.close 数据丢失竞争窗口 ✅

**文件**: `Store.cj`  
**类型**: 缺陷修复 | **预计**: 0.5 人天

**问题（B8）**：`close()` 直接 flush active MemTable 而非先 swapActive。存在极窄竞争窗口——close 启动后仍有并发 add() 通过 `guardOpen()` 进入但在 flush 完成后才修改 MemTable，导致该数据未持久化。

**修复方案**：
1. `close()` 中先 flush 已有的 immutable，腾出 immutable 槽位
2. 再调用 `memTableManager.swapActive()` 将 current active 原子切换为 immutable（flushLock 保护）
3. 刷 immutable MemTable → SSTable
4. 再执行 WAL sync + close + levelManager.closeAll

**验收标准**：并发 add + close 重复 100 次不丢数据  
**Commits**: `d276a9a7` (fix) + `dd9c48d0` (test) + `bc4f64d8` (fix)  
**测试验证**: StoreTest(11) + StoreIntegrationTest(22) + ConcurrencyTest(5, 含testCloseDuringConcurrentWrites) + CompactionTest(6) 全部通过  
**压测结果**: 3 writer × 50ms = 1754 笔跨 close 边界的并发写入，reopen 后 100% 恢复

### 第3阶段：性能优化 + 文档同步（预计 4~6 人天）

#### 3.1 【P2 性能】WAL 用户态缓冲写入

**结论：WAL 不适合用户态缓冲** — 缓冲写入与 WAL 崩溃恢复语义冲突。
缓冲的数据在进程崩溃时丢失，违背 WAL 设计目标。
`append()` 始终同步 `file.write()`（数据到 OS page cache），
`fsync` 每 100 次执行一次，syscall 降低 100 倍。

## 五、并发安全审查修复

### 5.1 WAL 轮转竞争条件修复

**问题**：`currentFileSize` 是 `var Int64`（非原子），多线程 `append()` 并发写入时，
多个线程同时读到 `currentFileSize >= maxFileSize` 并同时调用 `rotate()`，
导致多余 WAL 文件被创建、文件引用被覆盖。

**修复**：
- `currentFileSize` 改为 `AtomicInt64`，使用 `fetchAdd` 原子累加
- `prevSize >= maxFileSize` 比较在 `fetchAdd` 返回值上进行
- 新增 `rotating: AtomicBool`，用 `compareAndSwap(false, true)` 确保
  只有一个线程执行 `rotate()`
- `rotate()` 完成后 `rotating.store(false)` 释放

### 5.2 并发安全总表

| 模块 | 状态 | 说明 |
|------|------|------|
| MemTable | ✅ 无锁 | ConcurrentSkipListMap + AtomicInt64 byteCount |
| MemTableManager | ✅ 无锁 | AtomicReference<MemTablePair> 单 CAS |
| LevelManager | ✅ 无锁 | AtomicReference<ArrayList<SSTable>> 快照 + CAS |
| SSTable | ✅ 修复 | pread引入消除seek竞争(`869e29e5`)，补充guardNotClosed修复关闭fd后读竞争(`4fdd9051`) |
| Store | ✅ 安全 | AtomicBool closed + AtomicInt64 sequence |
| WAL | ✅ 修复 | currentFileSize AtomicInt64 + rotating CAS 防护 |
| Compactor | ✅ 安全 | AtomicBool running/stopSignal |

### 5.3 SSTable pread 关闭 fd 后读竞争

**问题**：`869e29e5` 引入 pread 替代 seek+read，Linux 上 `get()` 使用构造时保存的 fd 做 `pread`。`close()` 被另一个线程调用时关闭 `this.file`（fd 被内核回收），但 `get()` 可能已通过 `guardReadable()` 状态检查，随后用已关闭的 fd 调用 `pread` 返回 -1（EBADF）。

**影响**：返回值为全零缓冲区的 `scanBuffer` 扫描，最终静默返回 `None`。

**修复**：`4fdd9051`
- `guardNotClosed()` 新增辅助方法，pread 失败后检查 `closed.load()`，已关闭则抛 `StoreClosedException`
- Linux get() 路径检查 `positionedRead` 返回值，失败时先调 `guardNotClosed()` 区分关闭竞争 vs I/O 错误，再返回 `None`
- 非 Linux 路径不变：close() 已有 `synchronized(getLock) {}` drain，所有 get 持有锁，自然安全

## 六、第二轮代码审查修复

### 6.1 【P0 BUG】WAL.oldFiles 无同步保护 ✅

**文件**: `WAL.cj`  
**类型**: 并发缺陷修复 | **提交**: `2f9febc4`

**问题**：`oldFiles: ArrayList<String>` 被多线程并发读写：
- `rotate()`（单线程，由 `rotating` CAS 保护）执行 `add(walPath)`
- `takeOldFiles()`（可被多线程从 `cleanupRotatedWALFiles()` 调用）执行 `for+clear`

**修复**：加 `oldFilesLock: Mutex` 保护，`rotate()` 和 `takeOldFiles()` 均 `synchronized(oldFilesLock)` 操作。

**设计决策**：未采用 `AtomicReference<ArrayList<String>>` copy+CAS 无锁方案。因为 `rotate()` 频繁调用（每 64MB），ArrayList copy 产生大量分配和 GC 压力。Mutex 在无竞争时 ~5-10ns，远轻于 copy。

### 6.2 【P1 严重】Compaction 文件名冲突 ✅

**文件**: `Compaction.cj`  
**类型**: 数据损坏修复 | **提交**: `2f9febc4`

**问题**：`Compaction.compact()` 用本地变量 `var sstIndex: Int64 = 0`，每次 compaction 从 0 开始。多次 compaction 到同一 level 时产生同名 `.sst` 文件，`OpenMode.ReadWrite` 打开已有文件覆盖同一 inode，正在读旧 SSTable 的 `pread` 读到被覆盖后损坏的数据。

**修复**：改用全局 `sstableFileSeq.incrFetch()`，与 `flushMemTable` 一致。

### 6.3 【P2 资源泄漏】SSTableIterator 不释放 File 句柄 ✅

**文件**: `SSTableIterator.cj`  
**类型**: 资源泄漏修复 | **提交**: `b48b8941`

**问题**：`SSTable.iterator()`/`tailer()` 每次创建独立 `File(path, OpenMode.Read)` 传递给 `SSTableIterator`，但迭代器永不关闭该 File 句柄。长时间运行累积大量 FD。

**修复**：
- `SSTableIterator <: Iterator & Resource`，实现 `close()` 关闭独立 File
- 新增 `setDone()` 方法，在迭代耗尽（7 处 `done = true`）时自动 `close()`
- `next()` 入口处检查 `done` 时也确保关闭

**设计决策**：未采用 `dup()+fd` 方案。独立 File 句柄与 `SSTable.close()` 互不影响，足够安全。实现 `Resource` 后也支持 `try-with-resource` 显式关闭。

### 6.4 【P3 优化】PrefixIterator 实时过期判断 ❌ 不修复

**文件**: `PrefixIterator.cj`  
**类型**: 优化放弃

**问题**：每次 `next()` 都调 `DateTime.now()`。

**结论**：不可缓存。PrefixIterator 是外部驱动的增量遍历，遍历期间 key 可能从未过期变为过期。缓存 `now` 会返回过期 key，违反正确性。SSTableMerger 可缓存 `now` 是因为它是批处理操作（一次性合并完）。

## P0 必修

### WAL.append 写已关闭文件 ✅

- **文件**: `f_store/src/WAL.cj:84-87`

## P1 建议

### SSTableIterator FD 泄漏 ✅

- **文件**: `f_store/src/SSTableIterator.cj:28-29`, 调用点在 `SSTable.cj:266-274`
- **问题**: iterator()/tailer() 每次打开独立 File 句柄。调用者 break 提前退出循环时 FD 泄漏。高频前缀扫描场景（多 SSTable + 高 QPS）可能在数分钟内耗尽系统 FD 限制。
- **改进方案**: (a) iterator/tailer 调用点全部改用 `try(iter = sst.iterator())` 确保退出时自动 close；(b) 或在 SSTableIterator 中加引用计数 / 注册到 SSTable 的生命周期管理。
- **已修复**: PrefixIterator 实现 Resource，close() 排空源触发 SSTableIterator 自动关闭。next() 返回 None 时自动 close()。外部调用者可用 try-with-resource 提前终止。

### SSTable.close() 非 Linux 与 get() 竞争 ✅

- **文件**: `f_store/src/SSTable.cj`
- **问题**: close() 用 `synchronized(getLock){}` 空等 pending reads，但释放锁后 file.close() 之前新 get() 可能获取锁开始 I/O，随后被突然关闭的文件打断。
- **改进方案**: 将 `file.close()` 移入 `synchronized(getLock){}` 块内执行。get() 锁内加 guardReadable() 二次检查。
- **已修复**: close() 中 file.close() 在锁内执行；get() 非 Linux 路径锁内加 guardReadable() 双重检查。

### Store.get() 重复 DateTime.now() ✅

- **文件**: `f_store/src/Store.cj:114-128`, `f_store/src/LevelManager.cj:62`
- **问题**: get() 走 MemTable → Immutable → LevelManager 三路径时每段都新调 DateTime.now()。同一请求中调用 2-3 次系统调用。
- **改进方案**: 在 Store.get() 入口调用一次 DateTime.now()，将 now 作为参数沿调用链传递到 checkExpiryAndGet 和 LevelManager.get。
- **已修复**: Store.get() 顶部计算一次 now，checkExpiryAndGet 接受 now 参数，3 次调用复用同一个 now。

### Compaction 异常孤儿文件 ✅

- **文件**: `f_store/src/Compaction.cj:117-131`, `f_store/src/store_func.cj`
- **问题**: compact() 中 writer.write 或 finishWrite 抛出异常时，当前 writer 的 File 句柄泄漏、已写入部分数据的 .sst 文件成为孤儿。
- **改进方案**: 在 merge 循环外围加 try-finally，catch 时 close writer 并删除临时文件。

## P3.4 PrefixIterator.next() 每次调用 DateTime.now() — 非问题

**涉及文件：** `f_store/src/PrefixIterator.cj:86-88`

### 问题描述

`PrefixIterator.next()` 在每条目的过期判断处调用 `DateTime.now()`：

```cj
if (let Some(expireAt) <- bestEntry.expireAt) {
    if (expireAt <= DateTime.now().toUnixTimeStamp().toNanoseconds()) {
        continue
    }
}
```

被调用 N 次（N = 前缀匹配的条目数），每次产生一次系统调用。

### 为什么不修复（设计决策）

`PrefixIterator` 是**外部驱动的增量遍历**，遍历操作可能跨越数百毫秒甚至更长时间。在这期间：

1. 遍历开始时未过期的 key，可能在遍历到它时已过期
2. 如果构造函数中缓存 `now` 值，整个遍历期间使用同一时间戳，会导致**返回已过期的 key**，违反正确性语义
3. 这与 `SSTableMerger` 不同：`SSTableMerger` 是批处理操作（一次性归并完所有数据），缓存 `now` 是安全的

### 量化分析

| 场景 | N 次 DateTime.now() 总耗时 | 备注 |
|------|---------------------------|------|
| 遍历 1000 条 | ~0.3ms | 每次 ~300ns（Linux vDSO） |
| 遍历 10000 条 | ~3ms | 可忽略的开销 |
| 遍历 100000 条 | ~30ms | 仍然 < 遍历本身 I/O 耗时的 1% |

每次 `DateTime.now()` 在 Linux x86_64 上通过 vDSO 完成，约 200-400ns，不涉及上下文切换。总开销远低于遍历的 I/O 等待时间。**不优化**。

### P0.1 Linux: SSTable.get() + close() 未同步导致 fd 重用 → 静默数据损坏 ✅

**优先级**：P0（数据正确性/损坏风险）

**问题**：SSTable Linux 路径 `get()` 使用保存的 `this.fd` 做 `positionedRead`（pread），而 `close()` 对 Linux 路径不使用 `getLock` 保护。时间窗口：
1. 线程 A: `get()` → `guardReadable()` 通过

**修复**（方案 A）：
- L79-80: `getLock` 声明去掉 `@When[os != "Linux"]`，全平台可用
- L300-321: Linux `get()` pread 路径改为 `synchronized(getLock) { guardReadable(); ... }`
- L484-490: Linux `close()` 文件关闭路径改为 `synchronized(getLock) { ... file.close() }`

**非 Linux 路径为何安全**：原有 `synchronized(getLock)` 保护 get/close 互斥，不受影响。

**测试**：`SSTableTest.sstableConcurrentGetAndCloseNoRace` — 2 线程并发 get + 主线程 close，验证无数据错误。

### P1: LevelManager 过期快照导致虚假 StoreClosedException

**位置**: `LevelManager.cj:87-130`（`getInLevel` 方法）

**问题**: `LevelManager.getInLevel()` 先从 `AtomicReference` 原子加载 SSTable 列表快照，然后遍历快照并调用 `sst.get(key)`。若 **Compaction 线程在快照加载后** 关闭了其中某个 SSTable，Reader 访问已关闭 SSTable 的 `guardReadable()` 抛出 `StoreClosedException`：

```
Reader 线程                         Compactor 线程
─────────────────────────────────────────────────────
levels[level].load() → 快照 [A, B, C]
                                    removeSSTables(level, [B])
                                    B.close() → CAS closed=true
                                    → state.store(CLOSED)
                                    → synchronized(getLock)
                                    → file.close()
                                    → 释放 getLock
for (sst in [A, B, C]):
  sst.get(key)  // sst = B
  → synchronized(getLock)
  → guardReadable()
  → state == CLOSED → throw StoreClosedException!
```

**根因**: 锁无关数据结构（AtomicReference copy+CAS）天然允许读取者持有过期快照。当快照中的元素被 Compaction 删除并关闭后，访问该元素触发 `guardReadable()` 抛 `StoreClosedException`，但 Store 本身未关闭，属于**误报**。

**修复**: `getInLevel()` 中 `sst.get(key)` 加 try-catch 捕获 `StoreClosedException`，跳过该 SSTable 继续向后查找。

**改动量**: `LevelManager.cj` 两处加 try-catch（+4 行），无跨文件修改。

**测试**: `ConcurrencyTest.testCompactionStaleSnapshotNoException` — 预写 ~32MB 触发 compaction + 4 读线程 + 1 写线程并发 2s，验证无异常抛给上层。

**提交**: `fd11636a`

### P2: writeStreamToSSTables 异常路径中 remove 失败绕过 result 清理

**位置**: `store_func.cj:134-161`

**问题**: `writeStreamToSSTables()` catch 块三步清理逻辑中，步骤 2（删除当前 writer 孤儿文件）失败时创建新 `SSTableWritingException` 并立即 throw，跳过了步骤 3（关闭 + 删除 result 中已 `finishWrite` 的 SSTable），导致 FD 泄漏 + `.sst` 文件残留。

```cj
// 改前
} catch (e: Exception) {
    let ex = SSTableWritingException(e)
    writer.close()                                    // 步骤 1 ✓
    try {
        if (exists(writerPath)) {
            remove(writerPath)                        // 步骤 2
        }
    } catch (e2: Exception) {
        let thrown = SSTableWritingException(e2)
        thrown.addSuppressed(e)
        throw thrown  // ← 提前 return，步骤 3 被跳过！
    }
    for (sst in result) { ... }                       // 步骤 3（不会执行）
    throw ex  // ← 不会执行
}
```

**修复**: 步骤 2 异常通过 `addSuppressed` 附加到主异常，不提前 throw，确保步骤 3 始终执行：

```cj
} catch (e: Exception) {
    let ex = SSTableWritingException(e)
    writer.close()
    try {
        if (exists(writerPath)) { remove(writerPath) }
    } catch (e2: Exception) {
        ex.addSuppressed(e2)  // 附加而非提前 throw
    }
    for (sst in result) {
        try {
            sst.close()
            if (exists(sst.getMetadata().filePath)) { remove(sst.getMetadata().filePath) }
        } catch (ee: Exception) { ex.addSuppressed(ee) }
    }
    throw ex
}
```

### P3-1: WAL.sync() 与 WAL.close() 竞态导致 file.flush() 在已关闭文件上调用

**位置**: `WAL.cj:83-87`

**问题**: `WAL.sync()` 没有使用 `appendLock` 保护，与 `WAL.close()` 存在竞态：

```
Store.syncWAL()                Store.close()
─────────────────              ─────────────────
guardOpen() → closed=false
                               closed.CAS(true) → true
                               WAL.close()
                               → WAL.closed.CAS(true)
                               → synchronized(appendLock)
                               → file.flush()
                               → file.close()
                               → 释放 appendLock
WAL.sync()
!WAL.closed.load() → true
file.flush() → 文件已关闭 → 异常！
```

**修复**: `sync()` 加 `synchronized (appendLock)` 保护，确保与 `close()` 互斥：

```cj
func sync(): Unit {
    synchronized (appendLock) {
        if (!closed.load()) {
            file.flush()
        }
    }
}
```

**测试**: `WALTest.walSyncCloseRace` — 3 写线程持续 append+sync，100ms 后 close，验证无异常。

**提交**: `fd11636a`

### WAL mmap 写（Linux）

**目标**: 用 mmap 写替代 `file.write()` syscall，减少每次 append 的内核态切换。

**实现**:
- `store_func.cj`: 新增 `mmap`/`munmap`/`ftruncate`/`fallocate`/`memcpy` 的 FFI 绑定（`@When[os == "Linux"]`）
- `WAL.cj`:
  - `init()`: `ftruncate(fd, maxFileSize)` → `fallocate(fd, 0, 0, maxFileSize)` → `mmap(NULL, maxFileSize, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0)`
  - `append()`: `memcpy(mmapPtr + writePos, encoded)` 替代 `file.write(encoded)`（0 syscall 写 page cache）
  - `syncRecords()`: 统一使用 `file.flush()`（`fsync`）刷 mmap 脏页，与 write 路径兼容
  - `rotate()`: `munmap` 旧文件 → 创建新文件 → `mmap` 新文件
  - `close()`: `file.flush()` → `munmap` → `file.close()`
- 非 Linux 路径保持原有 `File.write()` + `file.flush()` 不变

**mmap sync 设计决策**: 最初使用 `msync(MS_SYNC)` 同步，但在 WSL2 上 `msync` 比 `fsync` 慢导致 TTL 回归（+41.5%）。改用 `file.flush()` (fsync) 统一处理，解决回归问题。

**实测收益**（~50B 小记录 benchmark）:
- add/get/remove/prefix 与 file.write 路径持平（±2% 噪声）
- `file.write()` syscall 对小记录（~50B）非主要瓶颈（~1-2µs）
- mmap 为大记录（KB+）生产场景做好基础架构支持

**涉及文件**: `f_store/src/WAL.cj`、`f_store/src/store_func.cj`

## P3 — 优化建议

### P3.1 LevelManager.getInLevel() L0 搜索未利用 Bloom Filter 跳过

**位置**: `LevelManager.cj:88-104`

L0 遍历时对每个 SSTable 调用 `sst.get(key)`（内部含 Bloom Filter 检查）。但 Bloom Filter 的否定能力在跳表/内存中已经能快速判断。可以考虑在 LevelManager 层缓存 Bloom Filter 的否定结果，减少 SSTable.get() 调用。

**位置**: `WAL.cj:70-73`

### P1-1: LevelManager.getOverlappingSSTables() Ln 路径 getMetadata() 缺 try-catch

**位置**: `LevelManager.cj:242-249`

**问题**: `getOverlappingSSTables()` 对 Ln 层调用 `sst.getMetadata()` 获取 minKey/maxKey。`getMetadata()` 内部调用 `guardReadable()`，若 Compaction 在 `AtomicReference.load()` 获取快照后关闭了该 SSTable，则取时抛 `StoreClosedException`：

```
Store.prefix()                          Compactor
───────────────────────                  ─────────
getSSTablesInRange()
  → getOverlappingSSTables(L1)
    → levels[1].load() → [A, B]         removeSSTables(1, [A])
    → for sst in [A, B]:                A.close() → STATE_CLOSED
      → sst.getMetadata()               → file.close()
      → guardReadable() → throw!
```

影响链：
1. `Store.prefix()` 调用 `levelManager.getSSTablesInRange()` → 无 try-catch
2. `Compactor.compact()` → `getOverlappingSSTables()` 同样受影响
3. 异常传播到用户 → `StoreClosedException` 但 Store 实际未关闭

**修复**: `getOverlappingSSTables()` 中 Ln 路径的 `sst.getMetadata()` 外加 try-catch（与 `getInLevel()` 一致）：

```cj
for (sst in sstList) {
    if (sst.isClosed()) {
        continue
    }
    try {
        let meta = sst.getMetadata()
        let withinMax = max.isNone() || meta.minKey <= max.getOrThrow()
        if (withinMax && meta.maxKey >= min) {
            result.add(sst)
        }
    } catch (_: StoreClosedException) {}
}
```

同时为 L0 也添加 `isClosed()` 前置检查（当前 L0 无条件添加所有 SSTable 到 result，若其中有已关闭的 SSTable，后续 `sst.tailer()` 将抛异常）。

**改动量**: `LevelManager.cj` 约 10 行修改。

### P1-3: SSTableIterator.skipBefore() 逐条目分配 kBuf（与 scanBuffer 零拷贝不一致）

**位置**: `SSTableIterator.cj:128-129`

**问题**: `skipBefore()` 中跳过的每条记录都新建 `Array<Byte>(keyLen)` + `copyTo()`，而 `SSTable.scanBuffer()` 已用零拷贝切片比较。skipBefore 在定位大数据集的起始点时，可能跳过大量条目，每次跳过都产生一次堆分配：

```cj
// skipBefore L128-129（每跳过一条分分配一次）
let kBuf = Array<Byte>(keyLen, repeat: 0u8)

// scanBuffer L533-534
let keySlice = buf[offset .. offset + keyLen]  // 零拷贝切片
if (keySlice == targetKey) { ... }
```

**修复**: skipBefore 改用零拷贝切片 `blockData[off .. off + keyLen]` 与 `startKey.bytes` 比较（写一个局部字节数组比较函数，或直接用 ==）。

### P2: MemTable.add() byteCount 在 key 更新时重复计数 ✅ 已完成

**位置**: `MemTable.cj:28-33`

**问题**: `byteCount.fetchAdd()` 无条件累加新 entry 大小，忽略 `table.add()` 替换旧 entry 时释放的空间：

```cj
func add(key: ByteArray, entry: EntryValue): ?EntryValue {
    let old = table.add(key, entry)

let newSize = key.bytes.size + valueSize(entry) + ENTRY_OVERHEAD
let oldSize = if (let Some(oldEntry) <- old) {

} else { 0 }
byteCount.fetchAdd(newSize - oldSize)
```
