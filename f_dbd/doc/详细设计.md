# f_dbd 详细设计

> 需求来源：`.autocode/dbware.md`；参照实现：`f_rpc`（f_codec / f_protocol / f_net 用法）、`f_mockdb`（`std.database.sql` 驱动实现范例）、`f_dbpool`（连接池）。  
> 版本基线：1.3.16。本文给出**包级定义、各包顶级声明、每个顶级声明的公共成员及调用关系**；实现粒度到"可直接照此写声明与用例"，不含具体函数体。

---

## 1. 模块定位与总览

`f_dbd` 是一个动态库模块，承担两件事：

1. **fdbm 的驱动**：完整实现 `std.database.sql` 的 `Driver` / `Datasource` / `Connection` / `Statement` / `QueryResult` / `UpdateResult` / `Transaction` / `ColumnInfo` 体系，把 SQL 与参数经 `f_net` 发往 `fdbm`，按 `f_protocol` 的 **CONSUME**（请求）/ **RESP**（响应）命令收发，编解码用 `f_codec`（`@DataAssist` 类的 `DefaultCodec` 路径）。
2. **f_dbd 与 fdbm 的共用代码**：承载 SQL 与 SQL 参数的 `SqlPayload`、驱动数据类型实现与映射（`SqlTypes`）、结果集/列信息 payload、错误码与错误 payload —— 这些类由 f_dbd 编码、fdbm 解码（或反之），因此必须放在 f_dbd 的包里供 fdbm 直接 import。

另有**多 fdbm 负载均衡**驱动 `MultiD`：客户端侧对多个 fdbm 节点做加权随机/轮询选择，每个节点用 `f_dbpool.DatabasePool` 池化一条条 f_dbd 连接。

### 1.1 运行时位置

```
应用（f_orm / 直接使用 std.database.sql）
   │  DriverManager.getDriver(<dbd_driverName> | 'multidbd').open(url, opts)
   ▼
f_dbd：Datasource ──►（MultiD 时：每节点一个 f_dbpool.DatabasePool）──► Connection
   │                                                                    │
   │  Statement.set / query / update                                    │ 每 Connection 独占一个 f_net Client（= 1 条 TCP）
   ▼                                                                    ▼
f_net.Client<DataAny> ── Message.consume(SqlPayload/列读) ── TCP ──► fdbm
                       ◄─ Message.resp(UpdateResultPayload/QueryResultServerPayload/单元格) ─┘
```

## 2. 包结构

| 包                           | 目录               | 职责                                                                                               | 依赖方向                                                    |
| --------------------------- | ---------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `fountain::f_dbd`           | `src/dbd.cj`     | 根包：驱动注册入口、版本信息、对 `common` 的公开重导出                                                                 | → common / driver / multid                              |
| `fountain::f_dbd.common`    | `src/common/`    | **共用代码**：payload 类、列信息、**结果集与流列实现（`QueryResultImpl`/`DbdInputStream`）**、错误码与错误 payload、类型映射与严格解码 | → f_data / f_dbpool / f_exception(无) / std.database.sql |
| `fountain::f_dbd.exception` | `src/exception/` | **重导出** `DbdException`（实现体在 `common`，见 §4；避免 common↔exception 包级循环） | → common（`public import`） |
| `fountain::f_dbd.driver`    | `src/driver/`    | 单节点驱动：URL 解析、`Datasource`/`Connection`/`Statement`/`Transaction`、请求传输与超时（结果集与流列见 common）         | → common / exception / f_net / f_protocol / f_data      |
| `fountain::f_dbd.multid`    | `src/multid/`    | `MultiD` 多节点负载均衡驱动 + 连接池配置                                                                       | → driver / common / f_dbpool / f_concurrent / f_config  |

依赖方向**单向**：`common` ← `exception` ← `driver` ← `multid`；`common` 不反向依赖任何本模块包（保证 fdbm 只依赖 `common` 时不会拖入网络客户端代码）。

`fdbm` 侧只 import `fountain::f_dbd.common`（payload 与类型映射）与 `fountain::f_dbd.exception`（错误码）。

## 3. `fountain::f_dbd.common`：共用代码

### 3.1 顶层常量

```cangjie
/** 列读请求的控制哨兵：推进到下一行（响应为 DataBool：true=有新行） */
public const NEXT_ROW: Int64 = -1
/** URL 未指定端口时的默认端口 */
public const DEFAULT_PORT: UInt16 = 8112
/**
 * 单元格（标量）读取的转换标志（B 口径：越界即报错）：
 *   = THROWING_ON_INT_OVERFLOW | IGNORE_FIELD_TYPE_NOT_MATCH
 * 刻意**不含** WRAPPING_ON_INT_OVERFLOW（否则窄类型读宽列会静默回绕）与
 * IGNORE_FIELD_NOT_CONVERTABLE（该位在 NumberData 中排在最前，会把越界静默变成 None，
 * 使 THROWING 根本轮不到）；IGNORE_FIELD_NOT_FOUND / IGNORE_NONE 只服务对象字段填充，
 * 与标量转换无关，故不保留。
 */
public const CELL_READ_FLAG: DataConversionFlag = THROWING_ON_INT_OVERFLOW | IGNORE_FIELD_TYPE_NOT_MATCH
/** 流列分块的默认块大小（64 KiB）：`bufSize <= 0` 时使用；f_dbd 的 `fetch_rows` 选项默认值也取它 */
public const DEFAULT_STREAM_CHUNK: Int64 = 65536
```

### 3.2 顶层函数

```cangjie
/**
 * 严格解码：保留溢出策略位、去掉全部 IGNORE_* 位（即 flag = DEFAULT_DATA_FLAG & !SILENCE）时，
 * 字段缺失 / 类型不匹配 / 无法转换都会抛 DataException。
 * 用于区分"同一条 CONSUME 上承载的多种载荷"（SqlPayload / QueryResultColumnPayload / 各响应类型）。
 * 宽松解码（DEFAULT_DATA_FLAG，含 SILENCE）会把异构载荷转成"字段为空的同形对象"，见 f_net Client 的注释教训。
 */
public func decodeStrict<T>(data: Data): ?T where T <: DataFields<T>
```

- 语义：`try { convert<T>(data, flag: DEFAULT_DATA_FLAG & !SILENCE) } catch (_: DataException) { None<T> }`，其中 `DEFAULT_DATA_FLAG & !SILENCE == WRAPPING_ON_INT_OVERFLOW`（`DataConversionFlag` 是 `UInt64` 的别名，`SILENCE`/`DEFAULT_DATA_FLAG` 都是整数常量，位反用仓颉的一元 `!`，**没有 `~` 运算符**）。
- **为什么不能取 `flag: 0`**：`f_data` 的整数解码（`NumberData.cj`）要求四个溢出策略位之一被置位才肯把 `DataReal` 转成 `Int64` 等类型，`flag: 0` 时**所有含整数字段的载荷都解不出来**（`QueryResultColumnPayload.index/bufSize`、`ColumnInfoImpl.length/scale/displaySize`、`UpdateResultPayload`、`DbdErrorPayload.code` 全会失败）。保留 `WRAPPING_ON_INT_OVERFLOW` 后整数可解，而 `IGNORE_*` 全关仍保证"异构载荷判别"成立。
- **为什么留 `WRAPPING_ON_INT_OVERFLOW`，而不是 `THROWING_ON_INT_OVERFLOW` / `SATURATING_ON_INT_OVERFLOW`**（四个策略位必须留其一，否则连区间内的整数也解不出来）：
  1. **判别器只回答"这是不是期望的载荷类型"**。字段越界是**数据问题**不是类型问题：用 `THROWING` 时，一个结构合法但某个值越界的载荷会被判成 `None` → 上层回 `ERROR(PROTOCOL)`，把数据问题误诊为协议问题。用 `WRAPPING`，判别**只**由结构决定（字段缺失 / 类型不匹配 / 不可转换，即全部 `IGNORE_*` 位为 0）。
  2. **改动面最小，且"判别宽松 / 取值严格"是刻意分工**：`decodeStrict` 就是 `DEFAULT_DATA_FLAG` 去掉 `SILENCE`（只差一处），数值语义与框架默认一致；**越界是否算错由取值侧决定**——取值走 B 口径 `CELL_READ_FLAG`（含 `THROWING`），报错发生在那里才带得上正确的错误码（`CONVERSION`）与具体列。判别侧若也用 `THROWING`，只会把"取值失败"提前伪装成"载荷类型不对"。
  3. **`THROWING` 的失败形态是"错的异常种类"**：该位走 `DataReal.toInt64(strategy: Throwing)` → `Decimal.toInt64(overflowHandling: Throwing)`，std 文档明确抛 `OverflowException`（`<: ArithmeticException`，**不是 `DataException`**），本函数的 `catch (_: DataException)` 接不住 → 会穿透成 fdbm 侧的 `ERROR(INTERNAL)` 或 f_dbd 侧的非 `SqlException`，破坏"对外统一抛 `SqlException`"的契约。
  4. **`WRAPPING` 的代价与兜底**：越界时会静默回绕。但协议字段（`index`/`bufSize`/`length`/`scale`/`displaySize`/`code`/`rowCount`/`lastInsertId`）全部由两端自己的编码器从整型字段产生，正常路径不可能越界；真正的防线放在**语义校验**上（`index ∈ [0, columnInfos.size)`、`bufSize >= 0`、哨兵值只由本模块内部构造），而不是指望数值转换抛异常。
- 调用方：fdbm 的请求分发（判别请求种类）、f_dbd 的响应解码（判别响应种类）。

### 3.3 `SqlPayload` —— SQL 与 SQL 参数

```cangjie
@DataAssist[fields props]
public class SqlPayload {
    private var sql: String = ''              // 宏把私有字段改名为 sql_，生成的属性仍叫 sql（= 线上键名）
    // 类型必须显式写出：`@DataAssist` 的 `props` 生成要读 `VarDecl.declType`，
    // 推断写法（`= ArrayList<DataAny>()`）会让宏抛 `ASTException: 'VarDecl' has no explicit type`（已实测）
    private var params: ArrayList<DataAny> = ArrayList<DataAny>()

    public init()
    public init(sql: String)
    public func add<T>(param: T): Unit where T <: ToData
    public func addNull(): Unit
}
```

| 成员                       | 意义                                                                                                                                                                                                                                                 | 调用关系                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `sql`（`props` 生成公共属性）    | 待执行 SQL 文本，原样透传（fdbm 不转换方言）                                                                                                                                                                                                                        | f_dbd `DbdStatement.query/update` 写入；fdbm SQL 解析器读取                     |
| `params`（`props` 生成公共属性） | 参数列表，顺序 = `set(index)` 的 index 升序；未设置的 index 编码为 `DataNone`。**字段声明为 `var` 是硬要求**：`let` 会让宏生成的属性成为非 mut 属性（`ReadonlyField`），fdbm 解码 CONSUME 载荷时 `DataObject.set("params", ...)` 取不到可变字段 —— 默认 flag 静默丢参数、严格 flag 抛 `DataException`（见 §3.4 字段可解码性规则） | fdbm 执行器按位替换 `?` 占位符                                                    |
| `add<T>(param)`          | 参数编码入口：`params.add(DataAny(param.toData()))`                                                                                                                                                                                                       | `DbdStatement` 内部把已转换好的 `Data` 以 `add<Data>(data)` 追加（`Data <: ToData`） |
| `addNull()`              | 追加 `DataAny(DataNone.INSTANCE)`，对应 `setNull(index)` 或空洞参数                                                                                                                                                                                          | 同上                                                                      |


> 说明：`DataAny` 既可用于参数，也是线上统一载荷（`Message.data` 的 `Data`），因此 params 用 `ArrayList<DataAny>` 而不是 `ArrayList<Data>`：`DataAny` 是 `DataFields` 具现类，满足 `@DataAssist[fields]` 对字段类型的约束。

### 3.4 `UpdateResultPayload` —— 更新类结果

```cangjie
import std.database.sql.*                        // UpdateResult

@DataAssist[fields props]
public class UpdateResultPayload <: UpdateResult {
    private var rc: Int64 = 0                    // 数据字段：props 生成 public mut prop rc，线上键名就是 rc，可解码
    private var liid: Int64 = 0                  // 数据字段：键名 liid

    public init()
    public init(rowCount: Int64, lastInsertId: Int64) {
        this.rc = rowCount                       // 命中的是宏生成的 mut prop rc（私有字段已被宏改名为 rc_）
        this.liid = lastInsertId
    }
    @DataExclude[field]                          // 只读接口属性不参与序列化，否则解码时会被判为"找不到可变字段"
    public prop rowCount: Int64 {
        get() {
            rc
        }
    }
    @DataExclude[field]
    public prop lastInsertId: Int64 {
        get() {
            liid
        }
    }
}
```

| 成员                                        | 意义                                                        | 调用关系                          |
| ----------------------------------------- | --------------------------------------------------------- | ----------------------------- |
| `rc` / `liid`（`props` 生成的 `mut` 属性）       | **数据字段**：受影响行数 / 自增主键。`mut` ⇒ 可解码；**线上键名是 `rc` / `liid`** | fdbm 编码、f_dbd 解码              |
| `rowCount` / `lastInsertId`（手写只读属性）       | **接口属性**：满足 `UpdateResult`；`@DataExclude[field]` 使其不参与序列化 | 应用只读；`get()` 转发 `rc` / `liid` |
| `init()` / `init(rowCount, lastInsertId)` | 无参构造供解码（字段靠声明处初值兜底）、全参构造供 fdbm 构造响应                       | —                             |

- 编码方：fdbm（update/DDL 与透传语句的响应）；解码方：f_dbd。`DbdStatement.update()` 直接把解码结果作为 `UpdateResult` 返回（§5.5），**不再需要适配器类**。
- **偏离记录（两条死路与最终形态）**：需求草图写 `UpdateResultPayload <: UpdateResult`。
  1. `private var rowCount` + `props`：宏生成的是 **`mut prop rowCount`**，而仓颉要求"实现类型与接口的成员属性 `mut` 修饰必须一致"（开发指南 `class_and_interface/interface.md`），`UpdateResult` 的 `rowCount`/`lastInsertId` 是**非 mut** 属性 ⇒ 编译不过；
  2. `private let rowCount` + 手写非 mut 属性：属性进字段表但只是 `ReadonlyField`（无 setter）⇒ 能编码、**不能解码**（默认 flag 静默丢值、严格 flag 抛 `DataException`）；
  3. **最终采用（2026-10-14 用户拍板）**：数据字段与接口属性**分名** —— `rc`/`liid` 承载数据且可解码，`rowCount`/`lastInsertId` 作为只读属性满足接口，并用 `@DataExclude[field]` 排除出序列化。代价：**线上键名变成 `rc`/`liid`**（协议字段名，两端同版本，无兼容问题）。
- **字段可解码性规则（对全部共用 payload 类都适用，实现与用例按此校验）**：
  1. 字段表 `dataFields()` 只收 **public** 成员（宏见 `DataAssist.cj:382`）⇒ `private` 成员既不编码也不解码；
  2. `props` 为私有字段生成的属性**保留原名字**、把私有字段改名为 `<名字>_`（`DataAssist.cj:165-184`）⇒ **线上键名 = 声明时的字段名**（如字段 `rowCount` → 键名 `rowCount`）。键名完全由声明决定：`UpdateResultPayload` 用 `rc`/`liid`，`ColumnInfoImpl` 用 `nm`/`tn`/`len`/`scl`/`nl`/`ds`（见 §3.7 对照表）；
  3. 属性/字段是 **`mut`（`var`）** 才登记为 `MutableField`（可解码）；`let` 字段、手写的非 mut `prop` 一律登记为 **`ReadonlyField`**（只有 getter，`ReadonlyField.cj`）⇒ **只能编码、不能解码**；
  4. 解码路径 `DataObject.set(name, ...)` 在 `mutableField(name)` 取不到时：`IGNORE_FIELD_NOT_FOUND` 在位（`DEFAULT_DATA_FLAG`）**静默跳过**（值停留在构造初值），该位被清掉（如 `decodeStrict`）则**抛 `DataException`**（`DataObject.cj:119-128`）。
  5. **私有 `var` 字段必须保留声明处初值**：因为字段被宏改名为 `<名字>_`，构造函数里写 `属性名 = 初值` 命中的是宏生成的同名 **mut 属性**（setter 写的是 `<名字>_`），并不是对字段本身的确定初始化 —— 编译期初始化检查过不去。仓库既有 54 个带 `props` 的 `@DataAssist` 类，私有 `var` 字段无一例外都带内联初值。  
     ⇒ **任何需要解码的载荷，数据字段必须是 `var`**；"用 `private let` + 手写非 mut `prop` 来让 payload 直接实现 std 接口"这条路**不可用**（编码看着正常，解码会丢值或报错）；"初值全部搬到构造函数"在 `props` 类上也**不可行**（规则 5）。
  6. **既要"可解码"又要"实现只读属性接口"时，唯一形态是"分名 + 排除"**（已用于 `UpdateResultPayload`（`rc`/`liid`）与 `ColumnInfoImpl`（`nm`/`tn`/`len`/`scl`/`nl`/`ds`））：数据字段走 `props`（`mut` ⇒ 可解码，**其名即线上键名**），接口要求的只读属性手写并加 `@DataExclude[field]` 排除出字段表（`DataExclude` 支持 public prop）。
  7. **字段/元素类型必须是 `DataFields`**：`Array<T>` 仅当 `T <: DataFields<T>` 时才是 `DataFields`（`CollectionData.cj:75`），所以 std 接口类型（`ColumnInfo`、`UpdateResult` 等）既不能做字段类型、也不能做数组元素类型；又因仓颉泛型**不变**，`Array<具体类>` 与 `Array<接口>` 之间必须显式逐项转换（如 `Array<ColumnInfo>(n) { i => cis[i] }` —— 元素本身已是 `ColumnInfo`，只是容器类型不能直接赋值）。
- **`ColumnInfoImpl` 同样采用这一招**（2026-10-14 用户拍板）：6 个数据字段用短名 `nm`/`tn`/`len`/`scl`/`nl`/`ds`（即线上键名），6 个只读接口属性手写并加 `@DataExclude[field]` 排除 —— 适配器类 `DbdColumnInfo` **取消**（见 §3.7 的键名对照表）。

### 3.5 `QueryResultServerPayload` —— 查询的首包响应

```cangjie
@DataAssist[fields props]
public class QueryResultServerPayload {
    private var columnInfos: Array<ColumnInfoImpl> = []

    public init()
    public init(columnInfos: Array<ColumnInfoImpl>)
}
```

- `columnInfos`：物理驱动的列信息（fdbm 填充），f_dbd 侧由 `QueryResultImpl.columnInfos`（§3.10）逐项转换为 `Array<ColumnInfo>` 暴露。
- **不携带 `hasData`/首行状态**（2026-10-17 用户拍板）：fdbm 执行 `query()` 后**不预取任何行**，首包只描述列信息；f_dbd 的每次 `next()`（含第一次）都发 `NEXT_ROW` 请求（§3.10、§7.2）。客户端因此没有"预取行"这一隐式状态，不会出现首行跳过或重复。
- **偏离记录（为什么字段是 `Array<ColumnInfoImpl>`，以及为什么不实现 `QueryResult`）**：
  1. 需求草图写 `Array<ColumnInfo>`，但 `@DataAssist[fields]` 要求字段类型 `F <: DataFields<F>`（`MutableField.new` 的约束），而 `Array<T> <: DataFields` 仅在 **`T <: DataFields<T>`** 时成立（`f_data/src/base/CollectionData.cj:75`）；`ColumnInfo` 是 std 接口、不实现 `DataFields` ⇒ **字段类型不合法，编译不过**；
  2. 仓颉泛型**不变**（互操作文档明确"Java 数组是协变的，而仓颉泛型是不变的"）⇒ `Array<ColumnInfoImpl>` 不能赋给 `Array<ColumnInfo>`，两者之间必须显式逐项转换；
  3. **本类不实现 `QueryResult`**（2026-10-14 用户提议后经核对否决）：`QueryResult <: Resource` 是**完整结果集接口**（`columnInfos` + `next()` + 已废弃的 `next(values)` + `get<T>()` + `getOrNull<T>()` + `close()` + `isClosed()`，见 std 文档 `database_sql_package_interfaces.md:273-279`）。本类只是**查询首包**（仅列信息），行数据由后续 `NEXT_ROW` / CELL 请求按需拉取，`next/get` 在此无从实现；`QueryResult` 的实现者是 **`QueryResultImpl`**（§3.10，用本类作首包 + `QueryResultColumnPayload` 作列读请求）。且本类是 fdbm/f_dbd **共用载荷**，fdbm 侧也要构造它，不应耦合驱动行为。
  4. 列信息以接口类型暴露：`ColumnInfoImpl` **自身实现 `ColumnInfo`**（"分名 + 排除"，见 §3.7），数组元素本身就是 `ColumnInfo`；但泛型不变，`QueryResultImpl.columnInfos` 仍需把 `Array<ColumnInfoImpl>` **显式逐项转换**为 `Array<ColumnInfo>`（一句 `Array<ColumnInfo>(n) { i => cis[i] }`，无适配器类）。

### 3.6 `QueryResultColumnPayload` —— 游标操作（列读 / 推进）

```cangjie
@DataAssist[fields props]

    private var index: Int64 = 0
    private var bufSize: Int64 = 0

    public init()
    public init(index: Int64, bufSize: Int64 = 0)

    public static func cell(index: Int64, bufSize!: Int64 = 0): QueryResultColumnPayload
    public static func nextRow(): QueryResultColumnPayload     // index = NEXT_ROW

```

| `index`             | 语义                                                               | 响应负载                               |
| ------------------- | ---------------------------------------------------------------- | ---------------------------------- |
| `>= 0`              | 读取**当前行**第 index 列（0 起）                                          | 该单元格的值（`Data`），NULL 用 `DataNone`   |
| `NEXT_ROW (-1)`     | 推进到下一行（**服务端总是执行一次物理 `next()`**；无首行预取，第一次 `next()` 也发本请求） | `DataBool`：`true`=有新行，`false`=无更多行 |

- `bufSize`：仅当该列是 InputStream 类型（见 §8 类型映射）时有效，表示本次最多返回的字节数；`0` 表示使用 f_dbd 默认块大小。
- **偏离记录**：需求草图只给出"列读"，没有"推进"的载荷。本设计在同一 payload 上用 `NEXT_ROW` 负索引哨兵补齐推进；**关闭不复用本 payload**，改由 `Message.unsubscribe` 携带 `QueryResultClosePayload`（§3.6.1）承担，避免"数据面哨兵"与"控制面关闭"两种语义混在同一个字段里。
- 约束：**一条 TCP 连接上同一时刻至多一个打开的游标**（payload 中没有会话/语句标识，会话由连接隐式确定；见 §7.3）。

### 3.8 `DbdErrorCode` 与 `DbdErrorPayload`

> **实现形态（与上文表格的偏差，2026-10-17 实测登记）**：仓颉 `enum` 的构造器**不支持** `| INTERNAL = 0` 这样的整数字面量赋值（`开发指南/enum.md`：构造器只能带参数、不能带默认值；`| X = 0` 会报 `expected declaration, found '='`）。因此线上数值改由成员属性 `value` 给出、反向解析由 `static func parse(Int64)` 给出，**编号表与上表逐项一致**；`toString()` 与 `operator func ==` 同样在 enum 体内手写（`==` 按 `value` 比较）。对调用方（`.value` / `.toString()` / `==`）无任何可见差异。

```cangjie
public enum DbdErrorCode <: Equatable<DbdErrorCode> & ToString {

    | NO_DRIVER | CURSOR_STATE | TX_STATE | DB_ERROR | TIMEOUT | CONFIG | CACHE | IO
    | ID_GENERATOR | CONVERSION

    public prop value: Int64 { get() { match (this) { case INTERNAL => 0 /* … */ } } }
    public func toString(): String
    public operator func ==(other: DbdErrorCode): Bool     // 按 value 比较
    public static func parse(value: Int64): DbdErrorCode   // 未知值 → INTERNAL
}

@DataAssist[fields props]
public class DbdErrorPayload {
    private var code: Int64 = 0        // DbdErrorCode.value
    private var sqlState: String = ''
    private var message: String = ''

    public init()
    public init(code: DbdErrorCode, message: String, sqlState!: String = '')

    public func errorCode(): DbdErrorCode
}
```

- fdbm 的所有失败路径都必须回 `Message.error(id, data: DbdErrorPayload(...))`，禁止不回包（否则客户端只能等超时）。
- `sqlState` 直接透传物理库的 `SqlException.sqlState`（`DB_ERROR` 时）。


### 3.9 `SqlTypes` —— 类型映射与数值转换

```cangjie
public struct SqlTypes {
    /** 物理驱动的 typeName（任意拼写，忽略大小写）→ 读取类型；未知 → Unknown（fdbm 侧用） */
    public static func readType(typeName: String): SqlReadType

    /** 归一成仓颉类型名：fdbm 用它填 `ColumnInfoImpl.tn` 并作为列读的 typeName；未知 → `String` + WARN（fdbm 侧用） */
    public static func canonicalName(typeName: String): String

    /** 按列类型从物理结果集读一格并编码为 Data（fdbm 侧唯一取值入口） */
    public static func readData(result: QueryResult, index: Int64, typeName: String): Data

    /** 打开该列的流并返回（**同一行同一列只打开一次**，由调用方持有；NULL 列返回 0 字节的空流） */
    public static func readStream(result: QueryResult, index: Int64): InputStream

    /** 从已打开的流里读一块：循环 `read` 直到凑满 size 或某次 `read` 返回 0；返回实际字节（可能为空） */
    public static func readChunk(stream: InputStream, size: Int64): Array<Byte>

    /** 便捷版（一次性场景）：等价于 `readChunk(readStream(result, index), size)`；**游标路径不要用它**（会重复打开流） */
    public static func readStream(result: QueryResult, index: Int64, size: Int64): Array<Byte>

    /** 参数编码：任意受支持 T → Data；不支持的类型抛 DataException */
    public static func encodeParameter<T>(value: T): Data

    /** 列值解码：Data → T；NULL（DataNone）返回 None */
    public static func decode<T>(data: Data): ?T where T <: DataFields<T>
}

public enum SqlReadType <: Equatable<SqlReadType> & ToString {
    | Boolean | Int8 | Int16 | Int32 | Int64 | UInt8 | UInt16 | UInt32 | UInt64
    | Float32 | Float64 | Decimal | BigInt | String | Bytes | DateTime | Duration
    | Stream  // InputStream 列
    | Unknown
}
```

| 成员                                  | 意义与关键行为                                                                                                                                                                                                                                                                                                                    | 调用关系                                                                                       |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `readType(typeName)`                | 识别物理驱动的任意 `typeName` 写法（`Sql*` 抽象名 / 仓颉类型名 / 方言拼写）→ `SqlReadType`；**识别表与驱动能力表在 fdbm 文档"列类型归一"**（代码放本结构体，避免两端各写一份）                                                                                                                                                                                                          | `canonicalName` / `readData` / `readStream`，**均为 fdbm 调用**（f_dbd 不用）                       |
| `canonicalName(typeName)`           | `readType` → **仓颉类型名**（`Int64`/`String`/`Array<Byte>`/`std.io.InputStream`/…）；`Unknown` → `String` 并记 WARN（原始 `typeName` 入日志）。fdbm 用它写 `ColumnInfoImpl.tn`，列读时把该名字当 `typeName` 传给 `readData`                                                                                                                               | fdbm 构造列信息 / 列读；**f_dbd 不用**（它看到的 `tn` 已是仓颉类型名）                                            |
| `readData(result, index, typeName)` | 用 `readType` 选 `get<T>(index)`，再 `T.toData()`；NULL 由 `getOrNull<T>(index)` 判出后返回 `DataNone.INSTANCE`                                                                                                                                                                                                                       | fdbm 执行器读单元格                                                                               |
| `readStream(result, index)`         | **打开流**：`getOrNull<InputStream>(index)`；NULL 列 → 0 字节空流（`ByteArrayInputStream(Array<Byte>())`）。语义：**同一行同一列只调用一次**，返回的流由 fdbm 的 `QueryCursor` 按行缓存持有；这里不读数据、也不做 "是否流类型" 的判断（非流列由驱动抛 `SqlException`，原样透传）                                                                                                                    | fdbm `QueryCursor.cell` 首次请求该流列时                                                           |
| `readChunk(stream, size)`           | **读一块**：循环 `read` 直到凑满 `size` 或某次 `read` 返回 0；返回实际字节（可能为空）。`size <= 0` → 按 `DEFAULT_STREAM_CHUNK` 处理。EOF 的线上表征是**后续请求返回空数组**，客户端**不得**以"短块"判定流结束（`InputStream.read` 不保证一次读满）                                                                                                                                               | fdbm `QueryCursor.cell` 的后续块请求；与 §5.7 客户端契约一致                                              |
| `readStream(result, index, size)`   | 便捷版 = `readChunk(readStream(result, index), size)`；**每次调用都会重新打开流**（对真流式驱动等于重复取列值）⇒ 仅用于"一次性整块读"场景，游标路径必须用上面两个                                                                                                                                                                                                               | 慎用（见左栏）                                                                                    |
| `encodeParameter<T>(value)`         | `Statement.set<T>` 的参数编码：先按受支持类型（§8 左列）逐一运行时判定，命中即构造对应 `Data`；否则若 `value` 是 `ToData`（`Any` 装箱后 `is ToData` 判定）取 `value.toData()`；都不满足抛 `DataException`                                                                                                                                                                     | `DbdStatement.set`                                                                         |
| `decode<T>(data)`                   | 单元格（标量）转换，**B 口径**：`DataNone` → `None<T>`；否则 `convert<T>(data, flag: CELL_READ_FLAG)` —— ① 数值越界/分数值 → 抛 `DataException` 或 `OverflowException`（`OverflowException <: ArithmeticException`，**两种都要捕获**）；② 不可转换（如非数字字符串读成整数）→ `DataException`；③ 宽松型转换仍保留（`IGNORE_FIELD_TYPE_NOT_MATCH` 在位，如任意列 `get<String>` → `x.toString()`） | `QueryResultImpl.get/getOrNull`（§3.10；`get` 把 `None` 与两种异常统一转成 `DbdException(CONVERSION)`） |

- **职责边界**：`readType` / `canonicalName` / `readData` / `readStream` 由 **fdbm** 调用（只有它接触物理驱动）；`encodeParameter` / `decode` 由 **f_dbd** 调用。f_dbd 侧看到的 `typeName` 永远是 `canonicalName` 的输出（仓颉类型名）。
- **单元格数值溢出策略：已定 B（越界即报错）**（2026-10-13 用户拍板）。`SqlTypes.decode<T>` 一律使用 `CELL_READ_FLAG`（§3.1），落地口径：
  - `get<Int64>` 读 `bigint` 列 → 精确；`get<Int32>` 读超出 `Int32` 范围的值、或 `get<Int64>` 读带小数部分的值 → `DbdException(CONVERSION)`，**不再静默回绕/截断**；
  - `get<String>` 对任意列仍可用（`IGNORE_FIELD_TYPE_NOT_MATCH` 在位，走 `x.toString()`）；非数字字符串与数值列互读且不可转换 → `DbdException(CONVERSION)`；
  - `getOrNull<T>` 只对 SQL NULL（`DataNone`）返回 `None<T>`，越界/类型不符同样抛 `DbdException(CONVERSION)`（"可空但精确"）；
  - **与既有驱动的差异**：`f_mockdb` 等驱动走 `DEFAULT_DATA_FLAG`（含 `WRAPPING`）会静默回绕；本驱动的严格口径**必须写进模块 README**（实现阶段落地时同步 `README.md`/`README_en.md`）；`f_orm` 只是把 `get<T>` 的异常上抛，不受额外影响。

> 实现注意：`std.database.sql.Statement.set<T>` 的 `T` **无约束**，不能在签名上加 `where T <: ToData`；参数编码必须走运行时判定（`let any: Any = value` 后按上表 `match`），与 `f_orm/src/base/SqlDSL.cj:133` 的 `case Some(x: ToData)` 写法同源。

### 3.10 `QueryResultImpl <: QueryResult` —— 结果集（协议侧实现）

**用查询首包 `QueryResultServerPayload`（仅列信息）与列读载荷 `QueryResultColumnPayload`（列读 / `NEXT_ROW`）实现 std 的 `QueryResult`；关闭走 `Message.unsubscribe`（载荷 `QueryResultClosePayload`）/ `Message.ack`（§5.9、§7.3）**，是驱动对外返回的结果对象本体。

```cangjie
/** 列读请求的发送器：把 QueryResultColumnPayload 发出去并拿到响应 Data（driver 层注入传输实现；用例注入桩） */
public type ColumnRequestSender = (QueryResultColumnPayload) -> Data
/** 关闭游标：把 QueryResultClosePayload（qid）发出去并等到 ACK（driver 层注入；用例注入桩） */
public type ResultCloser = (QueryResultClosePayload) -> Unit

public class QueryResultImpl <: QueryResult {
    public init(payload: QueryResultServerPayload, queryId: String, send: ColumnRequestSender,
                closer!: ResultCloser, chunkSize!: Int64 = DEFAULT_STREAM_CHUNK)

    public prop columnInfos: Array<ColumnInfo>

    public func next(): Bool
    public func get<T>(index: Int64): T
    public func getOrNull<T>(index: Int64): ?T
    public func close(): Unit
    public func isClosed(): Bool

    // std 中标记为 deprecated 的成员同样实现（“完整实现 std.database.sql 全部 API”）
    public func next(values: Array<SqlDbType>): Bool
}
```

| 成员 | 语义 | 调用关系 |
| --- | --- | --- |
| `init(payload, queryId, send, closer!, chunkSize!)` | 用**首包**（仅列信息）、**查询标识 qid** 与**两个发送器**构造；`send` 把 `QueryResultColumnPayload` 发给 fdbm 并返回响应 `Data`，`closer(payload)` 发 `UNSUBSCRIBE` 并等 `ACK`（异常原样抛出） | `DbdStatement.query()` 注入 `p => transport.request(p, queryTimeout).data` 与 `p => transport.unsubscribe(p, queryTimeout)`；`queryId` 取自查询 RESP 的 `Message.id.toString()` |
| `columnInfos` | `payload.columnInfos`（`Array<ColumnInfoImpl>`）**显式逐项转换**为 `Array<ColumnInfo>`（元素自身即 `ColumnInfo`；泛型不变，不能直接赋值） | 见 §3.7、§3.4 规则 7 |
| `next()` | **无预读**：每次调用（含第一次）都 `send(QueryResultColumnPayload(NEXT_ROW, 0))` 取 `DataBool`；`true` → 当前行可读，`false` → 结果集耗尽（此后再次调用直接返回 `false`、不再发请求） | 与 fdbm 的物理游标严格一一对应（§7.2） |
| `get<T>(index)` | 当前行第 index 列的**强类型、精确**取值：NULL、数值越界/带小数、类型不可转换 → 均抛 `DbdException(CONVERSION)`（B 口径，§3.9）；`index` 越界同样 `CONVERSION`。**无客户端缓存**：每次调用都发 `send(QueryResultColumnPayload(index, 0))` 并当场转换响应 `Data`；同一单元格重复 `get` 会重复请求（fdbm 用当前行缓冲应答）。**类型分派口径固定为 §10.1 实验的胜者：候选 B（`None<T>` + `match case _: ?X`）＋接口子类型兜底**；热路径不构造任何 `TypeInfo`（只在兜底的冷路径上用一次 `TypeInfo.of<T>()` + 预缓存常量，见下） | 惰性拉取，符合"以 ColumnInfo 的索引发起列读请求" |
| `getOrNull<T>(index)` | **可空但精确**：仅 SQL NULL（`DataNone`）返回 `None<T>`；越界/类型不符与 `get<T>` 同样抛 `CONVERSION`；同样每次调用都发请求、不缓存 | — |
| `get<InputStream>(index)` | 该列为流列（`columnInfos[i].typeName ∈ {InputStream, std.io.InputStream}`）时返回 `DbdInputStream`（§3.11），按 `chunkSize` 分块拉取；返回流对象时不预读，首次 `read` 才发块请求 | 与 §7.2 时序一致 |
| `close()` | 幂等：首次调用执行 `closer(QueryResultClosePayload(queryId))`（`UNSUBSCRIBE` → 等 `ACK`）；**无论成功或失败都释放本地状态、失效已打开的流**；之后 `next/get` 抛 `DbdException(CURSOR_STATE)`；第二次调用不再发包 | `try (r = stmt.query()) {...}` 自动回收；`DbdStatement.close()` 也会调用 |
| `next(values)` | deprecated 兼容：忽略 `values`，等价 `next()` | 完整实现 std API |

- **为什么放在 common 包**：它只依赖两个 payload + 两个发送器函数，不需要网络与传输类型 ⇒ 属"不依赖网络"的共用层，且能用**桩发送器/桩 closer** 直接单测（无预读、无缓存、流列状态机、关闭握手都不必起回环连接）；driver 层只剩"注入 `transport.request` / `transport.unsubscribe` 并把实例交给应用"。命名与 `ColumnInfoImpl`（同为 std 接口的实现类）对齐。
- **结果集状态**：查询标识 `queryId`、当前行是否有效、是否已耗尽、已打开的流（按列索引）、是否已关闭；**没有 `hasData`、行缓存或单元格缓存**（`next()` 只推进游标，`get` 只把本次响应转成 `T`）。

**类型分派的实现口径（2026-10-17 实验结论，§10.1）**：`T` 的判定分三段 —— ① 先判"是不是流目标"（候选 B 的 `?InputStream` 精确匹配 + 接口子类型兜底）；② 其余类型走候选 B 的 `match`，命中即调**具体实例化**的 `SqlTypes.decode<X>`；③ 都不命中才抛 `CONVERSION`：

```cangjie
// 0) 流列：只打开句柄，**不发列读请求**（首次 read 才发块请求，§3.11）
if (isStreamTarget<T>()) {
    return Some(asTarget<T>(openStreamAsAny(index), index))
}
// 1) 热路径：`None<T>` + `match case _: ?X`（§8 表序），命中即调具体实例化的 decode
var value: Any = match (None<T>) {
    case _: ?String => decoded<String>(data)
    case _: ?Int64 => decoded<Int64>(data)
    // …其余 §8 全表类型…
    case _ => fallbackAsAny<T>()          // 不在表内 → CONVERSION
}
// 2) 收口：装箱值 → `case x: T`（`get<T>` 的 T 无约束，decode 又要 DataFields，只能这样接）
match (value) {
    case x: T => Some(x)
    case _ => throw DbdException(CONVERSION, ...)
}

// 冷路径兜底：`T` 是 `InputStream` 的**实现类**时，B 的精确匹配认不出，
// 必须补一次子类型判定（§10.1 语义差异，与候选 A 行为一致）
private static func isStreamTarget<T>(): Bool {
    let probe: ?T = None<T>
    match (probe) {
        case _: ?InputStream => true
        case _ => TypeInfo.of<T>().isSubtypeOf(TI_INPUT_STREAM)
    }
}
```

- **为什么是这样**：B 在全部 38 个测量点上均快于 A（最保守的一处也有 1.61 倍），且耗时几乎不随命中深度增长；但 B 的 `Option<T>` 运行时**精确**匹配认不出接口实现类，故保留一次 `TypeInfo` 兜底 —— 兜底在冷路径上，不影响热路径。
- 兜底只对**接口类型**做（`§8` 里只有 `InputStream` 是接口）；值类型与 `Array<Byte>` 都是具体类型，B 已精确覆盖。
- `T` 无编译期约束、`SqlTypes.decode<T>` 又要求 `T <: DataFields<T>` ⇒ 只能先用 B 把 `T` 落到**具体**类型分支，再用装箱值 `match (value) { case x: T }` 收口（`f_mvc/src/global_func.cj` 的同形写法）。`InputStream` 不是 `DataFields`，所以它必须在 `decode` 之前被分走。

> **实现偏差登记（2026-10-17）**：流列句柄**按列索引复用** —— 同一行同一列重复 `get<InputStream>` 返回
> **同一个** `DbdInputStream`。原因：服务端当前行缓冲缓存的是物理流的**句柄**（D3），若客户端每次都新建
> 一个流，两个流会交错消耗同一个物理流（第二次 `get` 拿到的会是后续块而不是流的开头）。
> 这与"客户端不缓存"（规则 8）并不冲突：句柄不是数据，且随行失效（规则 1）；真正的数据块仍然每次 `read` 才取。

**游标一致性规则（必须实现并测试）**：

1. 进入新行（`next()` 返回 `true`）前，任何已打开但未读完的 `DbdInputStream` 立即失效（服务端在 `NEXT_ROW` 时由物理驱动自动丢弃余量，无需额外请求）；对失效流再 `read` 抛 `DbdException(CURSOR_STATE)`。
2. `next()` 在服务端无游标（被新语句关闭、连接断开）时抛 `DbdException(CURSOR_STATE)`，**不静默返回 `false`**。
3. 同一连接上同一时刻只有一个游标；**打开的 `QueryResult` 独占该连接**（结果集耗尽但未 `close()` 仍视为打开）：在它 `close()` 之前，该连接上任何 `Statement` 的 `query/update` 以及事务 SQL 方法（`begin/commit/rollback/save/...`）都直接抛 `DbdException(CURSOR_STATE)`、不发包（§5.5、§5.8）。这不是可选优化——`QueryResultColumnPayload` 不带结果标识，若允许另一 `Statement` 发起查询，旧结果集的 `next/get` 会作用到新游标上（静默串数据），而不是得到 `CURSOR_STATE`。
4. `next()` 一旦返回 `false`（结果集耗尽），再次调用仍返回 `false`（终态，不抛异常、不再发请求）。
5. 未调用 `next()`（或当前行已失效）就调用 `get/getOrNull` → 抛 `DbdException(CURSOR_STATE)`。
6. `get/getOrNull` 的 `index` 必须在 `[0, columnInfos.size)`；越界抛 `DbdException(CONVERSION)`。
7. `close()` 之后 `isClosed() == true`；`close()` 可重复调用（第二次不再发 `UNSUBSCRIBE`）。
8. **客户端不缓存**：除终态（已耗尽/已关闭）外，每次 `next/get/getOrNull` 都向 fdbm 发一次请求；`get<InputStream>` 的每次 `read` 在本地块耗尽后发一次块请求。

### 3.11 `DbdInputStream <: InputStream` —— 流列的分块读

```cangjie
public class DbdInputStream <: InputStream {
    public func read(buffer: Array<Byte>): Int64   // 返回读入字节数；0 表示流结束
}
```

- 构造（包内可见）：绑定 `QueryResultImpl` + 列 index + 块大小 `chunkSize`。
- `read(buffer)`：优先消费本地块；块空则经所属结果集的发送器发 `QueryResultColumnPayload(index, chunkSize)` 取下一块；返回 `0` 表示 EOF（服务端返回空数组）；所属结果集已 `close()` 或本行已失效后抛 `DbdException(CURSOR_STATE)`。
- **不预读**：本地块只保存"上一次块响应中尚未消费完的字节"；块耗尽后，下一次 `read` 才发新的块请求，不会提前拉取下一块。
- 不提供 `close/isClosed`（`std.io.InputStream` 只要求 `read`）；提前放弃由 `QueryResultImpl.next()/close()` 统一失效（见 §3.10 规则 1）。

> **实现偏差登记（2026-10-17）**：收到**空块**后本流进入 EOF 终态，之后 `read` 直接返回 0、**不再发包**。
> 理由：EOF 与"结果集耗尽 / 已关闭"同为终态（规则 8 允许的例外），若不记这个标记，"读完后继续 read"
> 会变成每调用一次就发一次无谓的块请求。线上表征仍是"后续请求返回空数组"（§3.9 `readChunk` 口径不变），
> 客户端侧只是不再重复确认。

## 4. `DbdException`（实现体在 `common`，`exception` 包重导出）

> **声明位置（2026-10-17 用户拍板，解包级循环）**：`DbdException` 的实现体放在 `fountain::f_dbd.common`（`src/common/DbdException.cj`），`fountain::f_dbd.exception` 只做 `public import fountain::f_dbd.common.DbdException` 重导出。原因：`QueryResultImpl`/`DbdInputStream` 在 common 需要抛 `DbdException`，而 `DbdException` 需要 common 的 `DbdErrorCode`/`DbdErrorPayload`；若类留在 exception，就会形成 `common → exception → common` 的包级循环（cjpm 实测拒绝构建）。对调用方而言 `import fountain::f_dbd.exception.*` 的写法与类型身份都不变。

```cangjie
public class DbdException <: SqlException {
    public prop code: DbdErrorCode      // 细粒度错误码（DbdErrorCode）
    public prop cause: ?Exception       // 原始异常（网络/编解码/物理库），便于排查

    public init(code: DbdErrorCode, message: String,
                sqlState!: String = '', cause!: ?Exception = None)
    public init(payload: DbdErrorPayload, cause!: ?Exception = None)
}
```

- 继承 `SqlException`（`public open class SqlException <: Exception`，构造 `init(message, sqlState, errorCode)`）：应用既能按 `SqlException` 统一 catch，也能按 `DbdException.code` 细分。
- 所有对外 API（`Driver.open` / `Datasource.connect` / `Statement.*` / `QueryResult.*`）的失败都抛 `DbdException`（即 `SqlException`）。
- `payload` 构造器用于把对端 `DbdErrorPayload` 还原成异常。

| 成员                                 | 语义                                                                                                                            | 调用关系                    |

| `setNull(index)`                   | `params[index] = DataNone.INSTANCE`                                                                                           | 同上                      |
| `query()`                          | 构造 `SqlPayload(sql, params)` → CONSUME → 期望 RESP `QueryResultServerPayload` → 记录 RESP 的 `Message.id.toString()` 为 `qid`，用首包、qid、列读发送器与 closer 构造 `QueryResultImpl`（§3.10）并返回，成功后向 Connection 登记 `activeResult` | 见 §7.2 时序；执行前受连接级结果集独占约束 |
| `update()`                         | 同上，期望 RESP `UpdateResultPayload` → 直接返回（它自身实现 `UpdateResult`，见 §3.4） | 见 §7.1；执行前同样要求连接上的 `activeResult` 已关闭 |
| `setOption`                        | 写入语句级选项（`query_timeout` / `update_timeout` / `fetch_rows`），覆盖连接级                                                              | —                       |
| `close()`                          | 幂等：若 `openResult` 未关闭先按 §3.10 关闭（`UNSUBSCRIBE` + `ACK`，失败忽略）；清空参数表与结果引用 | `Statement <: Resource` |

### 5.6 结果集：使用 common 的 `QueryResultImpl`（§3.10）

本包**不再单独声明结果集实现类**：`public class QueryResultImpl <: QueryResult` 位于 common 包——它只依赖首包 `QueryResultServerPayload` 与两个发送器（列读 / 关闭），与网络无关，因此能用桩发送器/桩 closer 单测（状态机与全部游标规则见 §3.10）。driver 层的职责只有"注入发送器"这一步：

```cangjie
// DbdStatement.query() 内部（示意）
let resp = transport.request(SqlPayload(sql, params), queryTimeout)
let payload = /* 由 resp.data 解出的 QueryResultServerPayload */
let qid = resp.id.toString()
let sender: ColumnRequestSender = { p => transport.request(p, queryTimeout).data }
let closer: ResultCloser = { p => transport.unsubscribe(p, queryTimeout) }
return QueryResultImpl(payload, qid, sender, closer: closer, chunkSize: fetchRows)   // 交给应用，静态类型 QueryResult
```

- 发送器内部即 `DbdTransport.request`（§5.9）⇒ `send` 抛出的 `DbdException`（超时/断链/服务端错误）会原样冒泡到 `next/get`。
- `close()` 走 `UNSUBSCRIBE`/`ACK`（§5.9）而非列读哨兵；连接已断时 closer 的异常被 `QueryResultImpl.close()` 吞掉（本地仍关闭，§3.10 规则 7）。

### 5.7 流列：使用 common 的 `DbdInputStream`（§3.11）

`QueryResultImpl.get<InputStream>(index)` 返回的分块流对象声明在 common 包（§3.11），driver 层无需额外代码。

### 5.8 `DbdTransaction <: Transaction`

```cangjie
public class DbdTransaction <: Transaction {
    public mut prop accessMode: TransactionAccessMode
    public mut prop deferrableMode: TransactionDeferrableMode
    public mut prop isoLevel: TransactionIsoLevel

    public func begin(): Unit
    public func commit(): Unit
    public func rollback(): Unit
    public func save(savePointName: String): Unit
    public func rollback(savePointName: String): Unit
    public func release(savePointName: String): Unit
}
```

| 成员                                 | 语义                                                                    | 调用关系              |
| ---------------------------------- | --------------------------------------------------------------------- | ----------------- |
| 三个 `mut prop`                      | 按 `std` 语义可读写，仅作记录（**不**自动转换成方言语句；见 §9 偏离记录，需要时用 `begin`/`save` 透传扩展） | —                 |
| `begin()`                          | 向 fdbm 发 `SqlPayload('begin')`；成功前重复调用抛 `SqlException`                | fdbm 会话控制语句（§7.4） |
| `commit()` / `rollback()`          | 发 `'commit'` / `'rollback'`；未 `begin()` 调用抛 `SqlException`            | 同上                |
| `save(name)`                       | 发 `'savepoint <name>'`；name 需通过标识符校验（防注入）                             | —                 |
| `rollback(name)` / `release(name)` | 发 `'rollback to savepoint <name>'` / `'release savepoint <name>'`     | —                 |

- 事务期间该连接上的所有语句由 fdbm 固定路由到**同一个物理连接**（见 §7.4），保证 read-your-writes。
- **与打开的结果集互斥**：`begin/commit/rollback/save/rollback(name)/release` 都会发 `SqlPayload`，执行前必须确认连接上没有未关闭的 `QueryResult`；否则抛 `DbdException(CURSOR_STATE)`、不发包（§5.4、§7.3）。

### 5.9 `DbdTransport`（包内可见，非公开 API）

```cangjie
class DbdTransport {
    init(host: String, port: UInt16, options: DbdOptions)
    func request(payload: ToData, timeout: Duration): Message   // CONSUME → 等 RESP/ERROR
    func unsubscribe(payload: QueryResultClosePayload, timeout: Duration): Unit   // UNSUBSCRIBE → 等 ACK
    func isClosed(): Bool
    func close(): Unit
}
```

- 用 `Client<DataAny>.builder(queueSize!: 1024, socketCount!: 1, host!:, port!:, checkDuration!:, checker!:).build()` 建链（与 `f_rpc/src/client/ClientConfig.cj` 同构）。
- `request`：`Message.consume<...>(once: true, qos: QoS.AtMostOnce, data: payload)` → `client.transfer(msg, timeout)`；`None`（超时/断链）→ `DbdException(TIMEOUT | IO)` 并按 §7.4 关闭传输；`Command.ERROR` → 解 `DbdErrorPayload` → `DbdException`；其余非 `RESP` → `DbdException(PROTOCOL)`。
- `unsubscribe`：`Message.unsubscribe(data: payload)`（f_protocol **新增的带载荷重载**，自动生成新 `MessageID`）→ `client.transfer(msg, timeout)`；`None` → `DbdException(TIMEOUT | IO)`；`Command.ERROR` → `DbdException`；非 `ACK` → `DbdException(PROTOCOL)`。载荷 `QueryResultClosePayload.qid` 显式标识目标结果集（§3.6.1），不再依赖连接隐式单游标；ACK 的 id 与请求 id 相同。
- 所有单元格/控制响应都在这里统一解 `DataAny`（f_net 的 Client 用中性解码，`Data` 原样交给上层转换）。

```cangjie
public class MultiDatasource <: Datasource {
```

| 成员                       | 语义                                                                                                                                                                                                                                                                                                                   | 调用关系                                                                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `init(url, opts!)`       | 解析 `MultiDUrl` → 每节点 `DbdDatasource` + `DatabasePool`（池参数取 `MultiDConfig`）→ 组装 `LoadBalance<Int64, Unit, Connection>(0, algo)`；算法与取值区间必须按 `f_concurrent` 的既有实测口径：`random` → `Int64Weight(1, Σw)`（闭区间，Σw 为总权重），`roundrobin` → `RoundRobin<Int64>(step: 1, min: 1, max: Σw)`；每个节点 `add(weight, {_ => pool.connect()})` | `DatabasePool(ds, initSize!, …, checkSql!)` 与 f_orm 的构造方式一致；**取值区间必须落在权重桶内部**（`min=0`/`origin=min` 会永远命中第一个节点，`f_concurrent`/`f_net` 均已记录该坑），用例固定一条"只有 node1 有权重时 100 次全落 node1" |
| `connect()`              | `loadbalance.call(())`；池已关闭 → `DbdException(CONFIG)`（`ConnectionException('database pool is closed')` 映射）；池耗尽等待超时 → `DbdException(TIMEOUT)`                                                                                                                                                                          | 返回池化连接（`PooledConnection`），其 `close()` 即归还，且**非幂等**（重复 `close()` 抛 `ConnectionException('The database connection was returned multiple times.')`）——本类对外只承诺"归还一次"，不承诺幂等           |
| `setOption`              | 转发给每个节点 `DbdDatasource.setOption`（如统一 username/password/timeout）                                                                                                                                                                                                                                                     | 必须在首次 `connect()` 前调用                                                                                                                                                            |
| `close()` / `isClosed()` | 关闭全部 `DatabasePool`（幂等，用 `pool.close()`，**不**等待池内部任务）。刻意不用 `DatabasePool.closeAndAwait`：借用者（连接）由应用持有，库侧无法保证"先归还再等待"，等待只会白等到超时；需要确定性收尾的场景由应用自行在归还全部连接后调 `closeAndAwait`                                                                                                                                               | `Resource`                                                                                                                                                                       |

> **泛型实参修正（偏离记录）**：需求草图写 `LoadBalance<Int64, DatabasePool, Connection>`。`f_concurrent.LoadBalance<W, D, R>` 中 `D` 是"被选中函数 `(D) -> R` 的**入参类型**"（`call(data: D): R`），不是节点对象类型；节点选择只由权重决定。若保留 `D = DatabasePool`，每个节点的闭包都会忽略入参，调用点必须凭空传一个池，语义含混。本设计改用 `LoadBalance<Int64, Unit, Connection>`，节点池由闭包捕获，选择语义与需求完全一致。

## 7. 通讯协议（CONSUME / RESP / UNSUBSCRIBE / ACK / ERROR）

### 7.1 报文矩阵

| 方向 | 命令 | 载荷 | 说明 |
| --- | --- | --- | --- |
| f_dbd → fdbm | `CONSUME` (`once: true`, `qos: QoS.AtMostOnce`) | `SqlPayload` | 执行 SQL（更新/查询/会话控制/透传） |
| f_dbd → fdbm | `CONSUME` | `QueryResultColumnPayload` | 游标操作（列读 / `NEXT_ROW`） |
| f_dbd → fdbm | `UNSUBSCRIBE` | `QueryResultClosePayload`（`qid`，新 `MessageID`） | 关闭指定结果集（§3.10 `close()`） |
| fdbm → f_dbd | `RESP` (`qos: AtMostOnce`, `ack: false`) | `UpdateResultPayload` | 更新/DDL/会话控制语句的响应 |
| fdbm → f_dbd | `RESP` | `QueryResultServerPayload` | 查询首包（仅列信息） |
| fdbm → f_dbd | `RESP` | 单元格 `Data`（基础类型 / `DataNone` / `Array<Byte>` 集合） | 列读响应 |
| fdbm → f_dbd | `RESP` | `DataBool` | `NEXT_ROW` 响应 |
| fdbm → f_dbd | `ACK` | 无 | `UNSUBSCRIBE` 完成：已清缓冲、读尽并关闭物理结果集 |
| fdbm → f_dbd | `ERROR` | `DbdErrorPayload` | 任何失败路径 |

- 关联：`MessageID` 原样回带，`f_net.Client` 按 id 唤醒等待者（与 f_rpc 同一机制）。
- 请求种类判别：fdbm 用 `decodeStrict<SqlPayload>` / `decodeStrict<QueryResultColumnPayload>` 依次尝试（严格 flag，失败得到 `None` 而非"空对象"）；`UNSUBSCRIBE` 由 `Command` 直接识别，载荷按 `decodeStrict<QueryResultClosePayload>` 解；其余无法判别 → `ERROR(PROTOCOL)`。

### 7.2 查询时序（含游标）

```
f_dbd                                    fdbm
 │ SqlPayload('select ...', params)  ─────►│ 解析/路由 → 借物理连接 → prepareStatement().query()
 │                                        │ 记录列信息、把 QueryResult 挂到会话游标（不预取行）
 │ ◄──── RESP QueryResultServerPayload    │ （仅列信息；客户端记录 qid = RESP.id.toString()）
 │ next() ──► QueryResultColumnPayload(NEXT_ROW) ──►│ 物理结果集 next()
 │ ◄──── RESP DataBool(true)              │
 │ get<String>(0) ─► QueryResultColumnPayload(0) ──►│ 从当前行缓冲读第 0 列
 │ ◄──── RESP DataString('...')           │
 │ get<String>(0) ─► QueryResultColumnPayload(0) ──►│ 再次请求（客户端无缓存）
 │ get<InputStream>(1) ─► QueryResultColumnPayload(1, bufSize=65536)
 │ ◄──── RESP DataCollection(字节)        │ readStream(...)
 │ （读完 → 下一块请求返回空数组 = EOF）    │
 │ close() ──► UNSUBSCRIBE(qid) ──────────►│ ① 清空当前行缓冲 ② 读尽驱动结果集 ③ close
 │ ◄──── ACK                              │ ④ 回 ACK
```

- 同一连接上存在未关闭的 `QueryResult` 时，任何 `Statement` 的 `query/update` 或事务 SQL 方法 → 客户端直接抛 `CURSOR_STATE`，不发包（§5.5、§5.8）；服务端的“先关闭旧游标”仅在绕过客户端约束时才发生（§7.3）。

### 7.3 会话与游标生命周期（fdbm 侧契约）

- 会话由 TCP 连接隐式确定（f_net 的 `SocketBuffer` 即会话键）；**同一连接同一时刻至多一个游标**。`qid` 用于校验与日志（当前仍单游标，多游标扩展时作为定位键）。
- 新 `SqlPayload`（无论更新还是查询）到达时：先关闭旧游标 → 再执行新语句。**正常客户端流程不应出现这种情况**：客户端在发出任何 `SqlPayload` 前已按 §5.5 挡住未关闭的结果集；服务端的“先关闭旧游标”只是防御。若绕过客户端约束，旧结果集的 `next/get` 会落到新游标上（`QueryResultColumnPayload` 无结果标识），**不是**得到 `CURSOR_STATE`。
- **客户端前置约束（必须实现）**：任何新 `SqlPayload`（Statement 的 `query/update`、`DbdTransaction` 的 SQL 方法）发出前，客户端必须确认同连接上没有未关闭的 `QueryResult`；有则直接 `CURSOR_STATE`、不发包。`prepareStatement`/`createTransaction`/`set`/`Statement.close` 不涉及 `SqlPayload`，不受限。
- `UNSUBSCRIBE` 的语义（fdbm 按 `payload.qid` 定位；2026-10-17 用户拍板）：
  1. 用 `qid` 匹配当前游标：**无游标 / 已关闭 / qid 不匹配 → 直接回 `ACK`（幂等；不得关闭当前其他游标）**；
  2. 命中后**立即清空**该 `QueryResult` 的当前行/单元格缓冲（丢弃未读数据；此后到达的列读请求一律回 `CURSOR_STATE`）；
  3. 对数据库驱动的 `QueryResult` **循环 `next()` 读尽**（部分驱动要求消费完才能安全关闭；读尽过程中的异常只记日志）；
  4. `close()` 数据库端 `QueryResult`，归还物理连接；
  5. 回 `Message.ack(id)`。**无论 2–4 是否抛异常都要回 ACK**（关闭失败只记 ERROR，避免客户端卡在 `close()`）；重复 `UNSUBSCRIBE` 走第 1 步。
- 连接断开由服务端清理（f_net 无断连回调，采用周期巡检 `buffer.isClosed()` 回收，见 fdbm 详细设计）。
- 会话控制语句（`begin`/`commit`/`rollback`/`savepoint`…）使会话 pin 住一个写物理连接；`commit`/`rollback` 后解 pin。

### 7.4 超时与断链

| 场景                                     | 行为                                                                                                                                                                                                                                                                             |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 请求超时（`query_timeout`/`update_timeout`） | `transfer(msg, timeout)` 返回 `None` → `DbdException(TIMEOUT)`；**立即关闭传输并把 `state` 置 `Broken`**，同时失效当前游标与进行中的事务——服务端可能已推进状态，继续复用会错位                                                                                                                                               |
| `UNSUBSCRIBE` 超时/断链 | `DbdException(TIMEOUT/IO)`；`QueryResultImpl.close()` 吞掉该异常并本地关闭（§3.10 规则 7），连接按本节置 `Broken` |
| 连接被对端关闭                                | 下一次请求失败 → `DbdException(IO)`；同样关闭传输、置 `Broken`、失效游标与事务                                                                                                                                                                                                                         |
| 心跳与静默重建                                | f_net 的 Client 有内部 checkTimer（`checkDuration` 必填；`pingTimeout` 默认 1s；连续失败 `CHECK_FAILURE_TOLERANCE = 3` 次即拆链重建），**重建对上层不通知**。因此本设计的会话状态（游标、事务 pin）**一律由服务端按键（连接）维护**：重建后服务端视为全新会话，客户端后续的游标操作得到 `CURSOR_STATE`、`commit` 得到 `TX_STATE` —— 这就是 fail-fast 检测点（客户端不得假设跨重建的会话状态仍然有效） |
| 服务端错误                                  | `ERROR` + `DbdErrorPayload` → `DbdException`，连接保持可用（与 SQL 语义错误一致）                                                                                                                                                                                                              |

### 7.5 版本与兼容

- 协议无独立版本号；两模块同仓库同版本发布（`FountainVersion`），不承诺跨版本混用。`Message` 层已有 version 字节与 CRC 校验（f_protocol 负责）。

## 8. 类型映射表（线上口径 = `SqlTypes` 的对外事实来源）

> 本节是**线上协议的口径**：`ColumnInfoImpl.tn` 与列读请求里出现的 `typeName` 一律是**仓颉类型名**（`Int64`/`String`/`Array<Byte>`/`std.io.InputStream`…），由 fdbm 归一保证。`Sql*` 抽象名与方言拼写的识别表、驱动能力实测表在 **fdbm 文档"列类型归一"一节**——识别与归一发生在 fdbm（它才接触物理驱动），但实现代码仍放在共用包 `fountain::f_dbd.common`（`SqlTypes.readType` / `canonicalName`），以免两端各写一份表。

**`ColumnInfo.typeName` 的口径**：std 的定义是"如果在仓颉中有对应数据类型的定义，返回对应类型的 `toString` 返回值；否则由数据库驱动定义"（`database_sql_package_interfaces.md:83`），所以驱动可能报出 `Sql*` 抽象名、仓颉类型名、方言拼写三类写法（方言实测见 `f_orm/src/wrap/QueryResultWrap.cj:59-79`：`int4`/`bytea`/`money`/`varchar`…）。**fdbm 把它们统一归一成仓颉类型名再返回**，因此线上只有一种形态：

- 口径：**`typeName` 就是 `get<T>` 里那个 `T`** —— 报 `Int64` 就表示该列可用 `getOrNull<Int64>` 取，报 `Array<Byte>` 就按整块字节取，报 `std.io.InputStream` 就按流取。`ColumnInfoImpl.tn` 只写仓颉类型名（见 fdbm 文档"列类型归一"）；f_dbd 因此**只认仓颉类型名**，不认识 `Sql*` 与方言拼写，也不需要认识。
- 落地核对：在 fdbm 侧跑一条 `select` 打印物理驱动的 `typeName` 与归一结果（方法与驱动能力差异见 fdbm 文档）。万一 fdbm 的归一漏了某个拼写，该列会落到下面的未知兜底（WARN + 原始 `typeName`），按日志补表即可。

> **实现形态的三条偏差（2026-10-17 实测登记）**：
> 1. **`SqlReadType` 的构造器名不能取 `Int8`/`UInt64`/`Float32`…**：仓颉 `enum` 构造器不允许用基础类型关键字
>    （`| Int8` 报 `expected a enum value name after '|'`），且构造器名 `String` 会遮蔽 `String` 类型本身
>    （enum 体内再写 `String` 报 `'String' is not a type`）。故整数/浮点改为 `I8/I16/I32/I64`、`U8/U16/U32/U64`、
>    `F32/F64`，`String` 改为 `Text`；`toString()` 仍返回上表的原名字，语义一一对应。
> 2. **`BigInt` 与方言 `BIGINT` 同名冲突**：前者要 `BigInt`、后者要 `Int64`（fdbm §9.6 两行），归一化又要求
>    "大小写不敏感"，只能靠拼写区分 ⇒ 对 `trimmed == 'BigInt'`（仓颉类型名的唯一拼写）走 `BigInt`，
>    其余大小写（`BIGINT` / `bigint`）按方言归 `Int64`。
> 3. **`decode<T>` 额外拦截"分数值读整数"**：`convert` 走 `Decimal.toIntX` 会把 `3.7` 截成 `3`（不视为溢出），
>    与 B 口径"带小数即报错"不符 ⇒ 在 `decode` 里对 `DataReal.integer == false` 且 `T` 为整型时显式抛
>    `DataException`。判定只在"带小数部分"这条**冷路径**上做（`TypeInfo.of<T>()` + 预缓存常量），不影响热路径分派。
>
> 另：`std.io` 没有 `ByteArrayInputStream`，NULL 列的 0 字节空流改用空 `ByteBuffer`（读即返回 0，等价 EOF）；
> 仓颉 `String` 无 `trim`/`substring`（`indexOf` 返回 `?Int64`），去长度后缀改用"已知基名 + `startsWith`"匹配。

**唯一支持的表（仓颉类型名）**

| `typeName`（同时就是 `get<T>` 的 `T`）                     | `SqlReadType` | fdbm 读取                             | 编码                                    | 备注                       |
| --------------------------------------------------- | ------------- | ----------------------------------- | ------------------------------------- | ------------------------ |
| `String`                                            | String        | `get<String>`                       | `DataString`                          | —                        |
| `Rune`                                              | String        | `get<Rune>`                         | `Rune.toData()`（f_data 扩展）            | 文本类                      |
| `Bool`                                              | Boolean       | `get<Bool>`                         | `DataBool`                            | —                        |
| `Int8` / `Int16` / `Int32` / `Int64`                | 对应整数          | `get<同左>`                           | `DataReal`                            | —                        |
| `UInt8`（`Byte` 等价） / `UInt16` / `UInt32` / `UInt64` | 对应无符号整数       | `get<同左>`                           | `DataReal`                            | 驱动写 `Byte` 时按 `UInt8` 处理 |
| `Float32` / `Float64`                               | 对应浮点          | `get<同左>`                           | `DataReal`                            | —                        |
| `Decimal` / `std.math.numeric.Decimal`              | Decimal       | `get<Decimal>`                      | `DataReal`                            | 带包名前缀形式等价                |
| `BigInt`                                            | BigInt        | `get<BigInt>`                       | `DataReal`                            | —                        |
| `Array<Byte>` / `Array<UInt8>`                      | Bytes         | `get<Array<Byte>>`                  | `DataCollection<Array<UInt8>, UInt8>` | 整块字节                     |
| `InputStream` / `std.io.InputStream`                | Stream        | `readStream` 打开一次 + `readChunk` 按块读 | 分块 `Array<Byte>`                      | **依赖驱动能力**，见下            |
| `DateTime` / `std.time.DateTime`                    | DateTime      | `get<DateTime>`                     | `DataDateTime`                        | 带包名前缀形式等价                |
| `Duration`                                          | Duration      | `get<Duration>`                     | `DataDuration`                        | —                        |

- **未知/无法识别的 `typeName`**（例：`SqlVarchar`、`int4`、`BIGINT`、`bytea`、`timestamp with time zone`、`uuid`——**正常不该出现在线上**，fdbm 已归一）→ `SqlReadType.Unknown` → 按 `String` 读取与编码（`DataString`），记一次 WARN（**原始 `typeName` 打进日志**，便于按实际拼写补表）；与 `f_orm` 取值器的兜底 `case _ => getOrNull<String>` 同口径。
- **判定顺序**：① 精确匹配（大小写不敏感）；② 去掉包名前缀后再匹配一次（`std.io.`、`std.time.`、`std.math.numeric.`）；③ 仍未命中 → Unknown。**不做**"去长度后缀 / 前缀匹配 / 方言长名"等归一（那属于 `Sql*` 抽象名与方言拼写，已在 fdbm 侧完成）。
- **流列（`InputStream`）的可用性取决于 fdbm 侧的物理驱动**（f_dbd 侧只是把 `InputStream` 列按块请求、把字节回给应用）：哪些驱动能给出 `get<InputStream>`、哪些只能给 `Array<Byte>`、以及由此产生的大对象建议，全部记在 **fdbm 文档**（驱动能力实测表）；本模块只负责"若报 `InputStream` 就按流处理（`bufSize` 分块），否则按报出的仓颉类型整块处理"。
- 数值溢出：`get<T>`/`getOrNull<T>` 统一使用 `CELL_READ_FLAG`（B 口径：越界/带小数 → `DbdException(CONVERSION)`，见 §3.9）；本驱动**不提供**"回绕/截断"读取选项——需要那种语义时应在 SQL 里显式转换（如 `cast(x as signed)`），让结果在服务端就落在目标类型区间内。

## 9. 关键设计决策与取舍

| 决策                                                            | 理由                                                                        | 代价/限制                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 载荷判别用**严格解码**而不是"按 T 直接解"                                     | `Message.decode<T>`/`tryFromData<T>` 默认宽松，异构载荷会解成"字段为空的同形对象"（f_net 已记录该坑） | 每次判别多一次 try/catch；代码需集中封装（`decodeStrict`）                                                                           |
| 列读/推进共用 `QueryResultColumnPayload`（`NEXT_ROW` 负索引哨兵）；关闭走 `UNSUBSCRIBE/ACK`              | 需求草图的 payload 没有会话/语句标识，连接即会话；关闭是控制面操作，用 `Message.unsubscribe` 语义更准确，也避免把"关闭"混进列索引                                     | 关闭多一次 RTT；`NEXT_ROW` 哨兵仍需两端共享                                                                                                  |
| **一条连接一个游标**                                                  | 服务端状态最简单、可预测；`qid` 只做校验/日志，不引入多游标调度                                                | 同一连接上多语句交错读取不支持（打开新游标即关闭旧游标，需在文档与用例中固化）                                                                             |
| **查询不预读、客户端不缓存**（2026-10-17 用户拍板） | 每次 `next/get/getOrNull` 都向 fdbm 取数，客户端没有隐藏状态，首行不会跳过/重复；重复 `get` 由 fdbm 的当前行缓冲应答 | 每次取值一次往返；应用重复读同一单元格需自行承担开销（可先取到局部变量） |
| **打开的 `QueryResult` 独占 Connection**（2026-10-17 用户拍板） | `QueryResultColumnPayload` 无结果标识，服务端又是一连接一游标；若允许其他 Statement 在结果集打开时执行 SQL，旧结果集的 `next/get` 会静默作用到新游标上。Statement 对象可以多开，SQL 执行按结果集串行 | 应用必须在执行下一条 SQL/事务控制前 `close()` 结果集；否则得到 `CURSOR_STATE` |
| **Statement 不独占 Connection** | `prepareStatement` 是本地操作，多个 Statement 可并存；真正稀缺的是连接上的唯一游标 | Statement 生命周期与连接使用解耦；但执行 SQL 仍受"打开的 `QueryResult` 独占 Connection"约束 |
| **关闭消息携带 qid**（2026-10-17 用户拍板）：f_protocol 新增 `Message.unsubscribe(data!)` 重载，载荷为 `QueryResultClosePayload` | 不再只靠连接隐式单游标；close 可校验目标结果集，为同连接多游标留出扩展位 | `qid` 需从查询 RESP 捕获；fdbm 需维护 qid→游标映射（当前单游标下退化为校验） |
| 每个 `DbdConnection` 独占一个 `f_net.Client`（1 条 TCP）               | 连接隔离、故障隔离；与 `preferredPooling=true` 配合由上层池化                               | 连接数 = TCP 数；池参数即 TCP 上限                                                                                             |
| 参数编码走运行时判定（`Any` 装箱 + `is ToData`）                            | `std.Statement.set<T>` 无类型约束，编译期无法要求 `T <: ToData`                        | 每次 set 有一次类型判定开销（可忽略）                                                                                               |
| 二进制/流列用 `Array<Byte>` → `DataCollection<Array<UInt8>, UInt8>` | 用现有 `f_data` 类型，零新增编解码注册                                                  | 每字节按 `DataReal` 编码，线上开销大；大对象须走 `SqlReadType.Stream` 分块（依赖驱动支持 `get<InputStream>`，见 §8 的实测表）                         |
| **线上 `typeName` 只出现仓颉类型名**（fdbm 归一；2026-10-14 用户拍板）           | `typeName` 直接就是 `get<T>` 的 `T`，f_dbd 不必认识方言与 `Sql*` 抽象拼写，协议只有一种名字形态       | 归一表由 fdbm 维护（识别表与驱动能力表在 **fdbm 文档 §9.6**）；fdbm 漏归一时该列退化为 Unknown→String（WARN + 原始 `typeName`），**二进制列会退化成字符串**，按日志补表 |
| `MultiD` 内部每节点一个 `DatabasePool`，`preferredPooling=false`      | 需求指定；池化的是"到 fdbm 的连接"                                                     | 池参数是 `multidbm_*` 一套统一值，不区分节点                                                                                       |
| 驱动注册用 `static init` + `DriverManager.register`                | 与 `f_mockdb.MockDriver` 一致；f_dbd 由应用的动态库扫描加载（`PackageInfo.load` → 包初始化）触发 | 若应用不加载 f_dbd 动态库则驱动不可见（与 f_orm/f_mvc 的既有约束一致）                                                                       |
| 事务隔离级别属性只记录不下发                                                | fdbm 不做方言转换；`Transaction` 的三个属性在方言间语义差异大                                  | 需要隔离级别时用 `begin`/`save` 透传语句扩展（后续版本）                                                                                |

**对需求草图的偏离汇总**（均已在上文展开）：

1. `Array<ColumnInfo>` → `Array<ColumnInfoImpl>`（`DataFields` 约束）。两个载荷类都用"**数据字段分名 + 只读接口属性 `@DataExclude[field]` 排除**"的形态**自身实现** std 接口：`UpdateResultPayload <: UpdateResult`（线上键名 `rc`/`liid`）、`ColumnInfoImpl <: ColumnInfo`（线上键名 `nm`/`tn`/`len`/`scl`/`nl`/`ds`）；**不再有适配器类**，`Array<ColumnInfoImpl>` → `Array<ColumnInfo>` 只做显式逐项转换（泛型不变）。
2. 列读协议只补充 `NEXT_ROW` 一个哨兵操作；**取消首行预取与 `hasData`**，首次 `next()` 也发请求；关闭改用 `Message.unsubscribe`（载荷 `QueryResultClosePayload.qid`）/`Message.ack`（§7.1、§7.3）。
3. 严格判别用 `DEFAULT_DATA_FLAG & !SILENCE`（保留溢出策略位），**不能**用 `flag: 0`（整数载荷会全部解不出来）。
4. `LoadBalance` 泛型实参修正为 `<Int64, Unit, Connection>`（第二实参是选中函数的入参类型，不是节点对象类型）。
5. `MultiD.open` 的 URL scheme 同时接受 `multidbm://` 与 `multidbd://`；`MultiDatasource.init` 增加 `opts` 形参。
6. 连接池默认值以需求**示例值**为准（需求中"# 默认是…"注释与示例冲突，按笔误处理），fdbm/f_dbd 两侧同口径。
7. 单元格读取采用 **B 口径（越界即报错）**：`CELL_READ_FLAG = THROWING_ON_INT_OVERFLOW | IGNORE_FIELD_TYPE_NOT_MATCH`，与既有驱动（`DEFAULT_DATA_FLAG`，会静默回绕）不同 —— 属于**用户拍板的偏离**（2026-10-13），需在模块 README 写明。
8. **新增 `QueryResultImpl <: QueryResult`（common 包，§3.10）**：需求草图只给了两个 payload，没有明确"谁实现 `QueryResult`"。本设计把结果集实现显式化，放在 common 包并注入列读发送器 `ColumnRequestSender` 与关闭器 `ResultCloser`（driver 层只注入 `transport.request` / `transport.unsubscribe`）——好处是状态机（无预读/无缓存、游标两操作、关闭握手、流列）能用桩发送器/桩 closer 单测，且命名与 `ColumnInfoImpl` 对齐；`DbdInputStream`（§3.11）随之下沉到 common 包（它必须由 `QueryResultImpl.get<InputStream>` 构造，跨包反向依赖不允许）。
9. `category`：需求草图的 `'Database Middleware'` 不在 cjpm 允许的分类清单内（且用了单引号）⇒ 取允许清单内的五项：`Database Driver` / `Database Framework` / `Data Encapsulation and Transfer` / `Network` / `Distributed`（对应驱动本体、多节点数据源组合、payload 共用层、f_net 客户端传输、MultiD 分布式客户端）。
10. **`DbdException` 实现体放 `common`，`exception` 包重导出**（2026-10-17 用户拍板）：`QueryResultImpl`/`DbdInputStream` 在 common 需要抛 `DbdException`，而 `DbdException` 依赖 common 的 `DbdErrorCode`/`DbdErrorPayload`；类留在 exception 会形成 `common → exception → common` 包级循环（cjpm 拒绝构建）。对外 `import fountain::f_dbd.exception.*` 不变。

**跨模块 API 增补**：f_protocol 增加 `Message.unsubscribe<T>(data!: T)` 重载（自动生成 `MessageID`），供 `DbdTransport.unsubscribe` 使用；原有 `unsubscribe(id)` / `unsubscribe(id, data!)` 语义不变。

**可选加固（后续版本，不替代连接级独占）**：给 `QueryResultColumnPayload` 增加结果标识（复用 `qid` 或改用数值 cursor id），服务端每次列读 / `NEXT_ROW` 都校验；这样即使客户端漏了连接级守卫，旧结果集最多得到 `CURSOR_STATE`，不会串到新游标。当前版本不实现，因为每次列读都带字符串 qid 的线上开销不划算，且连接级独占已能堵住正常路径。

## 10. 测试策略（TDD 分层）

### 10.1 正式开发前的性能前置实验：`get<T>` 的类型判定（开发阻塞项）

`QueryResultImpl.get<T>(index)` / `getOrNull<T>(index)` 每次取值都要把**运行时泛型 `T`** 分派到 §8 的具体类型分支，是结果集最热的路径。**正式开发开始前先用微基准实测两种候选实现，胜者作为 §3.10 的实现口径**；实验完成前不写分派代码。

**候选 A：`TypeInfo` 子类型比较（每个具体类型的 `TypeInfo` 预缓存）**

```cangjie
// QueryResultImpl 的 private static let：§8 表内每个类型一条（Array<Byte>/InputStream 等同理）
private static let TI_INT64 = TypeInfo.of<Int64>()
private static let TI_STRING = TypeInfo.of<String>()
// ...

// 热路径：T 的 TypeInfo 仍须每次取；X 的 TypeInfo 只构造一次
let ti = TypeInfo.of<T>()
if (ti.isSubtypeOf(TI_INT64)) {
    // Int64 分支
} else if (ti.isSubtypeOf(TI_STRING)) {
    // String 分支
} // ...
```

**候选 B：`None<T>` + `match case _: ?X`**

```cangjie
let probe: ?T = None<T>
match (probe) {
    case _: ?Int64 => // Int64 分支
    case _: ?String => // String 分支
    // ...
    case _ => // 兜底
}
```

**语义差异（选型前必须先对齐）**

| 维度 | A `isSubtypeOf` | B `case _: ?X` |
| --- | --- | --- |
| 匹配关系 | 子类型（含接口实现类） | `Option<T>` 的运行时类型**精确**匹配（泛型不变） |
| `T` 为 `InputStream` 的实现类 | 命中 `TI_INPUT_STREAM` | **不命中** `?InputStream`，落兜底 |
| 未知类型 | 全部不命中 → 兜底 | `case _` → 兜底 |

- 线上 `typeName` 只会是 §8 表内的**精确类型名**，正常输入下两者应等价；但实验必须额外喂入"`T` 为接口实现类/别名"的输入，若 B 的行为与 A 不同，B 必须补子类型兜底，**不能仅凭速度选 B**。
- 别名按同一类型处理：`Byte` ≡ `UInt8`、`std.io.InputStream` ≡ `InputStream`、`std.time.DateTime` ≡ `DateTime`（§8）。

**实验口径**

| 项 | 规定 |
| --- | --- |
| 位置 | f_dbd 的 cjpm 单元测试（`src/*_perf_test.cj`），纯内存，不建网络、不落盘 |
| 被测对象 | 只测"类型判定 + 分支选择"；输入为同一份已解码 `Data`，不含 `send` 与 `decode` 的实际转换 |
| 用例矩阵 | §8 全表每个类型 × {首分支命中, 末分支命中, 未命中}；另测 `getOrNull` 的 NULL 短路（`DataNone` 直接返回，不分派） |
| 预热/计时 | 每用例预热 ≥ 10⁴ 次，计时 ≥ 10⁶ 次，重复 ≥ 5 轮取**中位数**；用单调时钟 |
| 防优化 | 累加每次分派结果并在结束时校验，防止死代码消除；两候选使用相同编译选项 |
| 观测 | ns/次、两候选比值、`private static let` 常量对产物体积的影响 |
| 判定 | 中位数低者胜；差距 < 5% 视为持平，按可维护性（B 的 `match` 更直观）选择并记录理由 |
| 产出 | 结果表 + 结论 + 日期回写本节；胜者固化为 §3.10 的实现口径（选 A 写明"预缓存 `TypeInfo` + `isSubtypeOf`"，选 B 写明"`None + match`"及子类型兜底） |

### 10.1.1 实验结果（2026-10-17 实测，**候选 B 胜出**）

**环境**：`cjc 1.3.0-alpha.20261016001051 (cjnative)`，`aarch64-unknown-linux-gnu`，Linux 6.6.0；
用例为 `f_dbd/src/common/dispatch_perf_test.cj`（`GetDispatchPerfTest`），随 `cjpm test` 跑（release 构建）。

每次分派结果累加后在测试体内用 `@Assert` 校验（防死代码消除）。

> **矩阵说明**：要求里的"{首分支命中, 末分支命中, 未命中}"用**两种分支顺序**实现 —— canonical（§8 表序）
> 与 reversed（完全倒序）。同一类型在两种布局下的命中深度互补（深度 d 与 n+1-d），故每个类型都得到
> "靠前的深度"与"靠后的深度"两组数据；链首/链尾两个极端位置由 `String`/`Duration` 直接锚定。
> 未命中的成本与具体 `T` 无关（都是"扫完整条链 + 兜底"），故以一组代表性未受支持类型作探针。
> 另：候选通过**同一个高阶函数**计时（`(Data) -> Int64` 函数值），两候选承担完全相同的调用开销，
> 因此绝对值含一次间接调用，但**比值**不受影响。

**结论与观察**

1. **候选 B 全面胜出**：38 个测量点（19 类型 × 2 布局 + 5 未命中探针 × 2 布局）**无一例外**优于 A，
   最保守的一处也有 1.61 倍（`Duration`/reversed 61.98%），远超 5% 的持平阈值 ⇒ 按 §10.1 判定规则选 B。
   合计口径下 B 只有 A 的 **6.01%**（均值 1958 → 117 ns/次）。
2. **A 的成本随命中深度快速上升，B 几乎不上升**：A canonical 从深度 1 的 123 ns 涨到深度 19 的 528 ns
   （约 21 ns/分支），而 B 从 68 ns 到 160 ns（约 5 ns/分支）；A 在 reversed 且深度靠后时出现
   6.9–8.1 μs 的**极坏值**（`TypeInfo.of<T>()` 与 `isSubtypeOf` 的组合在深链上明显劣化），B 同场景仍 < 160 ns。
   ⇒ 不仅更快，**尾延迟也更可控**，而 `get<T>` 是宽表逐列读取的热路径。
3. **语义差异确实存在且已钉死**（`semanticDifferenceOnInterfaceImplementor`）：`T` 为 `InputStream` 的
   实现类时，A 返回 17（子类型命中），B 返回 0（精确匹配不命中）；别名 `Byte ≡ UInt8` 在两候选下等价。
   ⇒ 选 B 必须补接口子类型兜底，**不得仅凭速度裸用 B**（§10.1 语义差异表与候选 D5）。
4. **`private static let` 预缓存 `TypeInfo` 的产物体积影响**：胜者是 B ⇒ 实现里只剩**接口**分支需要两个
   `TypeInfo` 常量（`InputStream`；`SqlTypes` 的整数集合另有一份），不再为 19 个类型各留一个常量；
   常量从 ~19 个降到实际实现所需的**极少数**个，产物与静态初始化负担一同下降。
5. **复用到 `SqlTypes.encodeParameter<T>`**：该处是**同一种**运行时判定（§10.1 约束 3），
   本节结论同样适用 —— 但它当前用 `Any` 装箱 + `match`，与 B 不同形，是否改写为 B 形态**另行决策**（不在本实验范围）。

**横向影响**：`src/common/dispatch_perf_test.cj` 会长期留在测试集里（它是本节结论的可复证据）。
跑满 10⁶ 次/轮的全模块 `cjpm test` 约需 **7.6 分钟**（其余 60+ 用例合计不到 1 秒），日常可
`cjpm test --filter GetDispatchPerfTest` 单独跑；要看到上面的结果表需加 `--show-all-output`
（`cjpm test` 默认捕获测试内的 stdout）。

**约束**

1. 两候选的**外部行为必须完全一致**：既定的「越界即报错」口径（§3.9，越界/带小数 → `DbdException(CONVERSION)`）、NULL、越界索引、流列、`CURSOR_STATE` 全部按 §3.10 规则。
2. 热路径**禁止**出现 `TypeInfo.of<X>()`（X 为具体类型），只允许一次 `TypeInfo.of<T>()` + 预缓存的 `private static let`；候选 B 无此开销。
3. 结论可复用到 `SqlTypes.encodeParameter<T>` 的同构分派（§3.9），但实验只以 `get<T>` 为准。

### 10.3 必须固化的不变量

1. 任何失败路径都有回包（`ERROR` / `RESP` / `ACK`），客户端不得依赖超时兜底。
2. `get<T>` 与列类型不符必须抛 `SqlException`，不得静默给出错误值。
3. `close()` 幂等；`next()` 在游标失效后抛异常而非返回 `false`。
4. 严格解码判别：交叉喂入 `SqlPayload`/`QueryResultColumnPayload` 必须恰好命中其一。
5. 事务内所有语句落到同一物理连接（由 fdbm 保证，f_dbd 只发语句）。
6. 连接上有未关闭 `QueryResult` 时（含已耗尽但未 `close()`），任何 `Statement` 的 `query/update` 与事务 SQL 方法都必须抛 `CURSOR_STATE` 且不发包（§5.4/§5.5/§5.8）；Statement 对象本身可并存。
7. 客户端不缓存：除终态（已耗尽/已关闭）外，每次 `next/get/getOrNull` 都发一次 fdbm 请求（§3.10 规则 8）。
8. `close()` 正常路径必须完成 `UNSUBSCRIBE(qid)` → `ACK`；fdbm 在回 ACK 前已清空缓冲、读尽并关闭物理结果集（§7.3）；qid 不匹配按幂等 ACK 处理。

## 11. 2026-10-21 评审修复：协议与驱动口径

### 11.1 驱动注册（G03）

- 注册名 = `dbd_driverName`（后端方言名）；`fdbm` 只作兼容别名（名字未被占用时注册）。
- `static init` 未配置时**不注册、不结束进程**；`DbdDriver()` / `dbdDriver()` 抛 `DbdException(CONFIG)`。
- 测试不再依赖外部环境变量：用例显式 `Config.set([('dbd_driverName', 'postgres')])`。

### 11.2 流列（G04 / G05）

- `bufSize = -1` 是 NULL 探测的保留值：服务端对流列回 `DataNone`（NULL）或首块；客户端把它作为流的初始缓冲。
- 旧服务端按 `<= 0` 返回首块，NULL 时为空数组 → 客户端退化为空流（向后兼容）。
- 流列只能按 `InputStream` 读；`get<Array<Byte>>` / `get<String>` 等标量读取在发请求之前抛 `CONVERSION`。
- 首次打开才探测；同一行内重复 `getOrNull<InputStream>` 复用同一句柄；行推进/关闭使流失效。

### 11.3 选项、URL 与错误映射（G01 / D12 / G06 / G07）

- 非法、`0`、负数的超时值保留原值并 WARN；`copy()` 返回独立副本。
- URL 一律使用 `String` 的字节下标；`%XX` 按字节解码后整体还原 UTF-8，非法/残缺 → `CONFIG`；`database` 同样解码。
- MultiD 只按状态判定池关闭（`CONFIG`），其余 `ConnectionException` → `TIMEOUT`；不依赖异常消息文本。
- `DatabaseResources` 借连接失败映射 `TIMEOUT`（池耗尽/等待超时）。

### 11.4 根包入口（G02）

- `fountain::f_dbd` 重导出错误码/异常、`DbdDriver`/`DbdUrl`/`dbdDriver`、`MultiD`/`MultiDUrl`/`MultiDatasource`，并提供 `fdBDVersion()`。
