# f_io 代码审查与优化记录

---

## 第一轮审查：uring 模块性能瓶颈（2026-05-02）

> 来源：全面静态审查 f_io/src/uring/\**/*.cj（lockfree 子系统 + 核心层）
> 2 个 P2 + 2 个 P3 问题已修复并提交，1 个 P3 记录待后续

### 已修复

#### P2 — SQEPreallocator.allocSlot() 调用 ioUringGetSQEFFI 非线程安全 ✅

- **位置**: `lockfree/sqe_pool.cj:69-87`
- **问题**: `allocSlot()` 在多线程并发时调用 `ioUringGetSQEFFI(ringPtr)`，该函数直接修改 SQ ring 的 `sqe_tail` 指针（liburing 内部无锁保护）。多线程使用分离 API（`allocSlot → getSQE → commitSlot → flush`）时，SQ tail 竞争导致 SQE 覆盖或重复提交。`submitAsync()` 路径通过 `submitMutex` 保护，但分离 API 路径无保护。
- **修复**: 新增 `sqeMutex: Mutex`，`allocSlot()` 中 `ioUringGetSQEFFI` 调用用 `synchronized(sqeMutex)` 保护。互斥范围仅覆盖 unsafe 块（get_sqe + 写 sqeSlots），`allocated.fetchAdd` 的索引分配仍为无锁。
- **测试**: `LockFreeComponentTest.testSQEPreallocatorConcurrent` — 8 线程并发 allocSlot → flush → waitCQE，验证全部 8 个 NOP 完成。

#### P2 — IoUringPromise.isCompleted/isCancelled 每次 mutex 锁 ✅

- **位置**: `uring_future.cj:248-261`
- **问题**: `isCompleted()` 和 `isCancelled()` 每次调用都 `synchronized(mutex)` 加锁。高频轮询场景下，每次 ~10-50ns 锁开销。
- **修复**: `completed` 和 `cancelled` 从 `Bool` 改为 `AtomicBool`。`isCompleted()` / `isCancelled()` 变为无锁 `load()`。`tryGetResult()` 先无锁检查 `completed`，不满足立即返回 `None`。锁保留在 `waitUntil` / `notifyAll` 路径（Condition 要求持锁）。
- **测试**: `IoUringPromiseTest` 共 6 个用例，覆盖 complete/cancel/error/timeout/idempotent。

#### P3 — LockFreePromise.onComplete notifyAll 应改为 notify ✅

- **位置**: `lockfree_promise.cj:65-67`
- **问题**: `onComplete()` 中调用 `cond.notifyAll()`，但 LockFreePromise 是单次操作，通常只有一个等待线程。
- **修复**: 改为 `cond.notify()`，减少不必要的线程竞争。

#### P3 — IoUringLockFree.allocatedSlotCount O(n) 遍历 ✅

- **位置**: `lockfree_uring.cj:311-320`
- **问题**: `allocatedSlotCount()` 遍历整个位图统计已分配位，O(capacity/32) 每调用一次。capacity=32768 时，单次调用遍历 32768 次 `isAllocated`。
- **修复**: `AtomicSlotAllocator` 新增 `AtomicUInt32 allocatedCount` 缓存，`alloc()` 成功时 `fetchAdd(1)`，`release()` 时 `fetchSub(1)`，`reset()` 归零。`getAllocatedCount()` 以 O(1) 替代 O(n) 遍历。
- **测试**: `LockFreeComponentTest.testSlotAllocatorAllocatedCount` — 分配/释放/重置全过程验证计数正确。

### 待修复

#### P3 — countTrailingZeros 软件实现而非硬件指令

- **位置**: `slot_allocator.cj:161-187`
- **问题**: `countTrailingZeros` 使用二分法软件实现（15 次位运算 + 分支），非一条 `TZCNT`/`BSF` 指令。槽位密集（高负载）时 CAS 竞争加剧，多次执行软件 CTZ 的开销放大。
- **方案**: 若仓颉支持 FFI 内联 `__builtin_ctz` 或 `TZCNT` FFI，应优先使用硬件指令。
- **现状**: 当前软件实现是标准二分法 CTZ，已是最优纯软件方案。硬件指令需额外 FFI C 文件 + 链接依赖，暂缓实施。

### 已确认无性能问题

- **SQEPool.flush 失败后重置计数器**: submit 失败意味着 ring 不可用，后续操作必然抛异常，不会产生静默数据损坏。
- **LockFreePromise 100 次自旋**: I/O 操作最低延迟 ~1μs，100 次自旋 (~30ns @ 3GHz) 实际不够，但逻辑上正确（回退到 Condition wait 无语义错误）。
- **allocSlot + reap + sleep 循环**: 槽位满时先 reap（非阻塞）再 sleep，与预期行为一致。SQ 还有空间时 submit 仍可进行。
- **CompletionSlotArray 无锁回调**: setCallback → store callback → fetchAdd generation 的 ordering 由 AtomicReference + AtomicUInt64 保证。
- **IoUringPool.getRing 无锁轮询**: AtomicInt64.fetchAdd 足够轻量，无性能问题。
