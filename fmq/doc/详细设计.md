# fmq 详细设计

> 需求来源：`.autocode/mq.md`（第 8–11、19–144 行：模块定义、编解码/通讯/核心功能、`fmq` 服务进程与管理进程）。
> 共用 API（数据模型、记录编解码、协议载荷与命令）见 `../../f_mq/doc/详细设计.md`（下文简称「f_mq 设计」）。
> 开发顺序见同目录 `开发计划.md`。

## 1. 模块定位

- 编译目标：**可执行文件**（`cjpm.toml: output-type = "executable"`），模块名 `fmq`，包名前缀 `fountain::fmq`。
- 两个子命令（规格第 101、124 行）：
  - `fmq server`：服务进程（`MQServer`，阻塞运行）；
  - `fmq manager`：管理进程（`MQManager`，一次性命令）。
- 依赖模块（`cjpm.toml`）：`f_mq`（共用 API）、`f_base`、`f_codec`、`f_concurrent`、`f_config`、`f_data`、
  `f_io`（SegmentedLog/ByteBuffer）、`f_log`、`f_net`、`f_process`（`getAbsoluteCommandDir`）、`f_protocol`、
  `f_time`、`f_util`。
- 运行时形态：**独立进程，不被 fboot 加载**（与 `f_rpc` 的「动态库 + Initializer」形态不同，规格第 10 行明确要求可执行文件），
  因此不注册 `f_app.SubCommand`，`main` 自己解析 `server` / `manager`。

## 2. 包级设计

| 包 | 意义 | 依赖（本模块内） | 依赖（模块外） |
| --- | --- | --- | --- |
| `fountain::fmq` | 入口：`main`、子命令解析分发、`--help` 文本 | config, server, manager | f_process |
| `fountain::fmq.config` | `MQConfig`：全部 `mqServer_*` 配置项、节点列表、路径解析与校验 | — | f_config, f_util, f_process, f_data |
| `fountain::fmq.meta` | 元数据：`MetaStore`（metas 目录持久化）、`MQAssignment`（队列分布）、`MetaSyncer`（节点间复制）、`MQFileNames`（文件名转义） | — | f_mq(base), f_codec, f_data, f_net, f_log |
| `fountain::fmq.queue` | 队列与消费状态：`QueueManager`、`QueueLog`、`GroupCursor`、`CursorStore`、`DeadLetterQueue`、`LogCleaner` | — | f_io, f_mq(base), f_codec, f_time, f_log, f_concurrent |
| `fountain::fmq.cluster` | 集群：`NodeRegistry`（节点表/连接/存活）、`BackupReplicator`（备份副本推送） | meta | f_net, f_mq(base), f_log |
| `fountain::fmq.server` | 服务：`MQServer`（装配/启动/关闭）、`MQCommandExecutor`（命令分发）、`SubscriberRegistry`（订阅表）、`MQMatcher`（匹配）、`ConsumeService`（取消息） | config, meta, queue, cluster | f_net, f_protocol, f_mq(base), f_log |
| `fountain::fmq.manager` | 管理端：`MQManager`（子命令实现）、`MQManagerArgs`（参数解析）、`MQManagerOutput`（输出渲染） | — | f_mq(base), f_net, f_config, f_log, f_util |

依赖方向：

```
fountain::fmq ──> server ──> {config, meta, queue, cluster} ──> f_mq(base)
                   manager ──> f_mq(base) + f_net（独立，不依赖 server/meta/queue）
```

> `config` 里的 `MQConfig` 用 `protected`（模块级可见）：它要被 `server`/`meta`/`queue`/`cluster` 这些**兄弟包**使用，
> Cangjie 的 `internal` 只到「本包及子包」，兄弟包读不到（规格第 103 行要求 `protected struct MQConfig`，与此一致）。

## 3. 配置（`MQConfig`）

```cj
protected struct MQConfig {
    // ---- 服务端配置项（`mqServer_*`）----
    static prop port: UInt16                 // mqServer_port，默认 2350
    static prop ackTimeout: Duration         // mqServer_ackTimeout，默认 10s
    static prop deadMsgThreshold: Int64      // mqServer_deadMsgThreshold，默认 3
    static prop deadMsgTTL: Duration         // mqServer_deadMsgTTL，默认 72h
    static prop segmentedLogDir: String      // mqServer_segmentedLogDir，默认 /var/log/fmq/segmentedLogs
    static prop deadMsgDir: String           // mqServer_deadMsgDir，默认 /var/log/fmq/deadMsgs
    static prop segmentedLogMaxSize: Int64   // mqServer_segmentedLogMaxSize，默认 1G（1073741824）
    static prop segmentedLogTTL: Duration    // mqServer_segmentedLogTTL，默认 72h
    static prop backup: Int64                // mqServer_backup，默认 0；负数 → 启动即报错退出
    static prop tombstoneTTL: Duration       // mqServer_tombstoneTTL，默认 7d（墓碑回收下限）
    static prop antiEntropyInterval: Duration // mqServer_antiEntropyInterval，默认 30s
    // ---- 复用客户端配置项（决策 D1）----
    static prop nodes: Array<String>         // mqClient_hosts，节点表（顺序 = 节点下标）
    static prop selfIndex: Int64             // 本机在 nodes 中的下标（按 port 匹配，见 §6.1）
    static prop metaDir: Path                // <fmq 可执行文件目录>/metas
    // ---- 校验与帮助 ----
    static func validate(): Unit             // 启动期全量校验，失败抛 MQConfigException
    static func helpText(): String           // 配置项名 + 意义 + 默认值（供 `fmq server --help`）
}
```

- 上面的代码块是**签名清单**（非可编译代码：`static prop` 要写成 `{ get() { … } }`，struct 还要 `private init(){}`）；
  范式对齐 `fleet/src/server/FleetServerConfig.cj:21-86`（`internal struct` + `public static prop` + `private init(){}`）。
- 读取方式：`Config.getString(...)` + `strictPort()` / `strictInt64()` / `strictDuration()`
  （`Config.getDuration` 支持 `10s`/`72h`）；**每个配置项都走严格解析**——显式设置但解析失败直接抛 `MQConfigException`，
  不静默回落默认值（A63）。字节量（`1G`/`2M`/`2048K`/`10b`）由 `MQConfig.parseByteSize` 解析
  （`MQConfig.cj:186-234`，显式字节扫描，不用 `f_util.computeBytes`：后者对本 SDK 的大写单位不稳定）；
  `port` 用 `MQHost.parseHost` 解析，非法 `host:port` 报错（A64）。
- 静态属性在**首次使用时**读配置（与 `f_protocol` 的 `ProtocolConfig` 同一考量：包初始化期 `Config` 可能未就绪）。
- 启动期校验（`MQConfig.validate`，任一不满足即打印错误并退出，退出码 2）：
  1. `port == 0`；`ackTimeout` / `deadMsgTTL` / `segmentedLogTTL` / `tombstoneTTL` / `antiEntropyInterval` 必须为正；
  2. `segmentedLogMaxSize <= 0` → 报错；`backup < 0` → `mqServer_backup must not be negative`；
  3. `nodes` 为空 → `mqClient_hosts is required`；任一项不是合法 `host:port` → 报错；
  4. `backup > nodes.size - 1`（副本数超过其它节点数）→ 报错；
  5. 节点表中任意两项端口重复 → 报错；
  6. `deadMsgThreshold < 1` → 报错；
  7. `selfIndex` 无法定位（没有配置项的端口等于 `port`）→ `mqServer_port ${port} is not in mqClient_hosts`。

## 5. 公共成员详解

> 约定：`protected` 成员面向模块内其它包，`internal`/`private` 仅在包内使用；服务端类型的公开面按「可测」设计——
> 业务逻辑（分配、游标、清理、匹配）都不依赖套接字，因此可以在单元测试里直接构造与断言。
> 另：下文凡声明 `<: Resource` 的类型（`MetaStore`/`QueueLog`/`QueueManager`/`DeadLetterQueue`/`NodeRegistry`）
> 都必须同时实现 `isClosed(): Bool`（`Resource` 的接口要求），签名清单为省篇幅只写 `close()`。

### 5.4 `MQAssignment`

```cj
protected class MQAssignment {
    /** 轮转分配：队列 i → 节点 (start + i) % nodeCount；返回 owners 与「下一次起始下标」 */
    static func allocate(topic: String, queueNum: Int64, nodeCount: Int64, start: Int64): MQTopicAssignment
    /** 下一主题的起始下标 = (start + queueNum) % nodeCount（规格第 27–28 行的例子：4 队列 3 节点后，从 A 的下一个节点 B 开始） */
    static func nextStart(start: Int64, queueNum: Int64, nodeCount: Int64): Int64
    /** 结构自检：owners 长度 = queueNum、每项在 [0, nodeCount) */
    static func validateStructure(assignment: MQTopicAssignment): Bool
    /** 结构自检 + 与当前节点数一致 */
    static func validate(assignment: MQTopicAssignment, nodeCount: Int64): Bool
}
```
- 例（规格第 28 行）：3 节点 A(0) B(1) C(2)、`/topic1` 4 队列、start=0 → owners = [0,1,2,0]（A 拿 0、3；B 拿 1；C 拿 2），
  `nextStart = (0+4)%3 = 1`；`/topic2` 2 队列、start=1 → owners = [1,2]（B 拿 0、C 拿 1，A 没有）。
- 纯函数、无 I/O ⇒ 单元测试直接覆盖规格例子。

### 5.5 `MetaStore`

```cj
protected class MetaStore <: Resource {
    init(metaDir: String, origin!: Int64 = 0, nodeCount!: Int64 = 0)
    // origin = 本机节点下标（同 revision 时打破平局）；nodeCount = 集群节点数（加载时校验 owners 用，0 = 不校验）
    /** 载入已落盘的元数据（topics/、groups/、tombstones/、revision、轮转指针） */
    func load(): Unit
    func topicOf(topic: String): ?MQTopicAssignment
    func topics(): Array<MQTopicAssignment>
    func groupsOf(topic: String): Array<MQSubscribeGroupMeta>
    func allGroups(): Array<MQSubscribeGroupMeta>
    func groupExists(topic: String, group: String): Bool
    prop nextStartNode: Int64
    /** 本地注册：存在性检查 + 分配 + 落盘 + 推进指针在同一临界区（A28） */
    func registerTopic(meta: MQTopicMeta, nodeCount: Int64): (MetaApplyResult, ?MQTopicAssignment)
    func registerGroup(meta: MQSubscribeGroupMeta): MetaApplyResult
    /** 应用远端分配：写盘 + 更新索引；`nextStart` 不为空时同步推进轮转指针 */
    func applyTopic(assignment: MQTopicAssignment, nextStart!: ?Int64 = None): MetaApplyResult
    func applyGroup(meta: MQSubscribeGroupMeta): MetaApplyResult
    /** 注销：先写墓碑、再删元数据；返回墓碑（调用方负责广播），不存在返回 None */
    func removeTopic(topic: String): Array<MQMetaTombstone>
    func removeGroup(topic: String, group: String): ?MQMetaTombstone
    /** 应用墓碑：墓碑按 (revision, origin) 只进不退；仅当墓碑比本地条目「更新」（`isNewer`：revision 更大，
        或 revision 相同且 origin 更大）时才删除本地条目；输掉的墓碑零副作用 */
    func applyTombstone(tombstone: MQMetaTombstone): MetaApplyResult
    func allTombstones(): Array<MQMetaTombstone>
    func topicTombstone(topic: String): ?MQMetaTombstone      // 区分「主题已删」与「主题尚未到达」
    func nextRevision(): Int64                                // Lamport 计数，落盘 revision.meta
    func gcTombstones(nowMs: Int64, ttlMs: Int64): Int64       // 回收过期墓碑，返回数量
    func advanceNextStart(value: Int64): Unit
    func snapshot(): MQMetaSnapshot
    func dropTopicLocally(topic: String): Unit                 // 快照「缺失兜底」用，不写墓碑
    func dropGroupLocally(topic: String, group: String): Unit
    func close(): Unit
}
```
- 目录布局（`metaDir` = `<fmq 可执行文件所在目录>/metas`，`MQConfig.metaDir`）：

```
metas/
├── assign.meta                          # codec(nextStartNode: Int64)
├── revision.meta                        # codec(本机已发出的最大 revision: Int64)
├── topics/%2Forder.meta                 # codec(MQTopicAssignment)
├── groups/%2Forder/%00.meta             # codec(MQSubscribeGroupMeta)（%00 = 默认组）
├── tombstones/t_%2Forder.meta           # 主题墓碑
├── tombstones/g_%2Forder_%00.meta       # 组墓碑
└── offsets/%2Forder/0/%00.cursor        # 游标位点（由 CursorStore 维护）
```
- 原子性：`AtomicFile.write(path, bytes)` —— 写 `<file>.tmp` → `flush` → `fsync(file)` → `rename` 覆盖 →
  `fsync(parent)`；任一 fsync/rename 失败向上抛错，内存状态不更新（A37）。
  单条记录很小（< 1KB），不需要 WAL。
- 载入失败（文件损坏/解码失败）→ 记 ERROR 并**跳过该条**继续（不因一条坏元数据拒绝启动），同时不再对外提供该条；
  孤儿组（`groups/` 下有文件但 `topics/` 下无对应主题）直接丢弃并记 ERROR，不进入索引与快照（A35）。
- 删除顺序固定为「组 → 主题」（`dropTopicLocked`）：反过来中途崩溃会留下没有主题的孤儿组文件。

```cj
    /** 主题落地回调（装配到 QueueManager.openTopic）/ 删除生效回调（装配到清理） */
    mut prop onTopicApplied: ?(String) -> Unit
    mut prop onDeleted: ?(MQDeregisterPayload) -> Unit
    func close(): Unit
}
```
- 复制流程（「所有主题/订阅组元数据都会保存在所有 `fmq` 服务节点上」）：
  1. 节点 X 收到 `REGISTER`（来自 manager 或 peer）→ 在本地 `MetaStore` 应用（主题：`MQAssignment.allocate` 用当前
     轮转指针算出 `startNodeIndex`/`owners`，随后写入 `assign.meta` 的下一个起始下标）；
  2. X 把**已解析的分配结果**用 `MQInternalMessage{kind: "metaSync", payload: codec(MQTopicAssignment)}` 广播给
     其它所有节点（用 `Message.register(data)` 构造；`REGISTER` 工厂不接受 `MessageID`，帧 id 由它内部新建，
     响应侧用 `Message.resp(id: 请求 id, …)` 配对，见 `f_protocol/src/default/Message.cj`）；
  3. peer 收到后 `applyRemote`：已存在且完全一致 → 幂等跳过（不重复广播）；已存在但不同 → 记 WARN、保留先到者；
  4. X 向请求方回 `RESP`（主题 → `MQTopicAssignment`；订阅组/注销 → `MQResult`）。
- 删除走墓碑：`deregister` 先本地写墓碑 + 删元数据，再广播墓碑；peer 的 `applyRemoteTombstone` 在墓碑
  `Applied` 且本地条目确实消失后触发 `onDeleted`，由装配层清理队列目录、游标、订阅与指标计数器（A25）。
  快照合并里「本地更旧且快照缺失」的兜底删除同样触发清理。
- **不新增命令**：上述内部消息都承载在 `REGISTER` / `DEREGISTER` 上，由载荷类型区分（f_mq 设计 §3.4）。
- 冲突与顺序：同一 revision 不同内容按「先到者优先 + WARN」；`nextStartNode` 只增不减，乱序快照不会让分配回退。
- 反熵：每个 `mqServer_antiEntropyInterval`（默认 30s）按「未知存活优先、已判死最后」的顺序向 peer 拉一次
  全量快照；失败的 peer 只记 WARN（不再维护 `pendingPeers` 补发队列），下一轮重试由定时器承担。

### 5.7 位置与读取约定（`LogPosition` / `logMetas` / `openEntryStream`）

`f_io` 在 2026-10-12 的 `d72c87b0` 之后提供了 MQ 需要的全部能力，因此 MQ **不自建索引、不自己扫目录、不自己删段**：

| 需求 | 用 f_io 的哪个 API（`f_io/src/SegmentedLog.cj`） |
| --- | --- |
| 写入位置 `(segmentedIndex, segmentedOffset)` | `append(data): LogPosition`（写前偏移，`:177-201`） |
| 段清单与每段有效长度 | `logMetas(): ArrayList<SegmentedMeta>`（`index/size/creationTime/updateTime/last`，`:241-253`） |
| 从任意位置顺序读 | `openEntryStream(index: Int64, offset: Int64): InputStream`（`:302-331`，跳过预分配空洞） |
| 按编号 / 时间删段 | `removeById(index)`、`removeUpdatedBefore(time)`、`removeBetween(range)` 等（`:257-300`；**当前段永不被删**） |
| 重启续号 | `SegmentedLog(config)` 自动取「目录里最大编号 + 1」开新段（README「创建实例」；编号只增不减） |

约定（写进 `QueueLog`/`GroupCursor` 的实现与用例）：

1. **位置只用 `LogPosition`**：`append` 的返回值即消息位置，持久化/回传都用它；
   读侧用 `openEntryStream(pos.seq, pos.offset)` 从该位置继续读。
2. **`LogPosition.seq/offset` 已是 `public let`**（2026-10-12 用户拍板，为 MQ 放宽；`f_io/src/SegmentedLog.cj:37-51`）：
   MQ 直接读 `append` 返回值的两个字段，再回传给 `openEntryStream(pos.seq, pos.offset)` 续读。
   历史：放宽前字段是默认 `internal`，跨模块读会报 `error: can not access field 'seq'`（两次实测）；
   因此不再需要「用 `logMetas()` 推导位置」的退路。
3. **流是有界的快照**：`openEntryStream` 在创建时快照「段列表 + 每段长度」（`:312-330`）⇒ 之后新 append 的数据**不会**
   出现在已打开的流里；`GroupCursor` 读完当前流后必须**用最新位置重开**（§5.11）。
3.1 **关流要转 `Resource`**：`openEntryStream` 的返回类型是 `InputStream`，该接口没有 `close()`
   （`ChainedSegmentStream` 实现的是 `Resource`）⇒ 代码里写 `if (let r: Resource <- stream) { r.close() }`
   （2026-10-12 实测：直接 `stream.close()` 报 `error: 'close' is not a member of interface 'InputStream'`）。
4. 段的有效长度一律以 `logMetas().size` 为准（封口段在 rotate/close 时会截断到实际长度；当前段是已写入字节数），
   **不用文件长度推断**（Linux 下预分配到 `maxFileSize`，见 `f_io/src/SegmentedLog.cj:552-565`）。

### 5.8 `QueueLog`

```cj
protected class QueueLog <: Resource {
    static let PREFIX_SIZE: Int64 = 4                    // 记录长度头
    static let MAX_RECORD_SIZE: Int64 = 64 * 1024 * 1024 // 单条记录上限（再受段上限约束）
    /** `warnNowMs` 仅供用例注入时钟做 WARN 限流，生产用默认值 */
    init(dir: String, maxFileSize: Int64, syncInterval: Int64,
        warnNowMs!: () -> Int64 = {=> DateTime.now().toUnixTimeStamp().toMilliseconds()})
    /** 追加一条记录；空记录或超过 `effectiveMaxRecord` 抛 `IllegalArgumentException`（写入前拒绝） */
    func append(record: Array<Byte>): LogPosition
    /** 读单条：Ok(`LogReadResult.Record`) / `Corrupt` / `SegmentGone` 三态 */
    func readAt(position: LogPosition): LogReadResult
    /** 从位置起打开顺序读流（游标用；读完须用最新位置重开，见 §5.7 约定 3） */
    func openRecordsFrom(position: LogPosition): QueueRecordReader
    /** 把位置归一化到「现存段 + 段内偏移」；`strict` 时空洞/缺段返回 `None` */
    func resolveStart(position: LogPosition, strict!: Bool = false): ?LogPosition
    /** 段清单（转发 logMetas，供游标/清理器判断） */
    func segments(): ArrayList<SegmentedMeta>
    /** 段清单（目录不可读时返回空数组，不抛异常） */
    func segmentsOrEmpty(): ArrayList<SegmentedMeta>
    /** 删除单个段（清理器用；不存在的段视为成功） */
    func removeById(index: Int64): Unit
    /** 测试观测 API：从位置起扫描，返回（记录数，第一条记录的发布时间）。
        生产 `stats` 不用它——`ConsumeService.stats` 走 `resolveStart(strict) + openRecordsFrom` 的单趟扫描 */
    func scanAfter(position: LogPosition): (Int64, ?DateTime)
    /** 有效字节数（各段 size 之和，用于「是否有新消息」的快速判断） */
    prop size: Int64
    func sync(): Unit
    func close(): Unit
}
```
- `effectiveMaxRecord = min(MAX_RECORD_SIZE, maxFileSize - PREFIX_SIZE)`：段上限小于记录上限时取段上限，
  保证记录不跨段、写入前即拒绝（`IllegalArgumentException`；`f_io.SegmentedLog` 另以
  `LogRecordTooLargeException` 兜底段容量），不会出现越界写。
- **写入**：`SegmentedLog(LogConfig(dir, filePrefix: "log", maxFileSize, syncInterval))` 的 `append` 直接给出位置（§5.7）。
  MQ 不再维护第二份索引文件；每条记录的位置取 `append` 的返回值（`seq`/`offset` 已是 `public let`，§5.7 约定 2）。
- **重启语义（决策 D2，已被 f_io 收口）**：`SegmentedLog(config)` 的构造会取「目录里最大编号 + 1」开**新段**
  （`f_io/README.md`「创建实例」；`f_io/src/SegmentedLog.cj:129-150`），因此 MQ **不需要**自己扫目录取 `maxSeq`，
  也天然「永不续写旧段」（「重开旧段会从偏移 0 覆盖写」的坑不再可能发生）。旧段只读、按 TTL 清理。
- **读取**：`openRecordsFrom(position)` → `SegmentedLog.openEntryStream(pos.seq, pos.offset)`
  （`f_io/src/SegmentedLog.cj:302-331`）：按目录里现有段读、每段最多读有效长度，**不会读到预分配空洞**；
  `readAt` 即「开流 → 解出一条记录 → 关流」，用于少量随机读。
- **段长度**：一律取 `segments()`（即 `logMetas()`）里的 `size`；不用文件长度推断（Linux 预分配，见 §5.7 约定 4）。
- **记录格式（跨版本约束）**：段内每条记录为

  ```
  +----------------+---------------------------+
  | 4B 大端 length | length 字节的记录体        |
  +----------------+---------------------------+

  length = 记录体字节数（不含 4 字节头），取值 1..effectiveMaxRecord（**不可跨段**，见 §6.4）
  记录体 = MQMessageRecord.encode(...) 的原始字节
  ```

  读取端按 `length` 取整条；`length <= 0` 或剩余字节不足视为损坏并停止读取。记录不跨段：
  当前段剩余空间不足时先轮转再写。前缀只用于顺序读取定界，不是索引；`LogPosition.offset`
  指向前缀起点。**升级时不得改变前缀宽度、字节序或「不含头部」的含义**，否则旧段无法按边界读取。

### 5.14 `LogCleaner`

```cj
protected class LogCleaner {
    init(queues: QueueManager, deadLetter: DeadLetterQueue, floorOf: (String, Int64) -> Int64,
         ttl: Duration, deadMsgTTL: Duration, interval!: Duration = Duration.minute * 5,
         backupLogs!: () -> Array<(Int64, String, Int64, QueueLog)> = {=> []},
```

- 删除条件（两条都要满足）：`logMetas()[i].updateTime + ttl < now` **且** `meta.index < floor`

  备份队列用 `backupFloor` 给位点段号；当前段由 f_io 保证不会被删：`removeById` 指名当前段会抛 IllegalArgumentException）。
  没有任何组/位点时 `floor = 1`，全部保留。

  - 段清单与时间戳：`logMetas()` 给出 `index/size/creationTime/updateTime/last`（`f_io/src/SegmentedLog.cj:241-253`）；
  - 精确删除：`removeById(index)`；批量语义另有 `removeUpdatedBefore(time)` 等（`:257-300`），
    但**批量接口无法排除「仍被慢速游标引用」的段**，所以清理器走「自己挑编号 + `removeById`」。
- 备注：`takeOldFiles()`（`:222-237`）只交出**本进程内**轮转过的段（重启后拿不到历史段），因此**不再使用**它做清理；
  若将来 f_io 的删除接口语义变化，本节的「两条都要满足」是回归用例的锚点。

## 6. 服务端机制设计

### 6.1 启动装配与生命周期

```
main(fmq server)
 └─ MQConfig 读取与校验（§3；backup<0 / 缺 nodes / 定位不到自身 → 退出码 2，打印原因）
 └─ 目录准备：metas / segmentedLogDir / deadMsgDir（Directory.create(recursive: true)）
 └─ MetaStore(metas).load()
 └─ NodeRegistry(nodes, selfIndex)（懒连接 peer；自带心跳 PING）
 └─ MetaSyncer.syncFromPeers()（向第一个可达 peer 拉全量快照并合并；全部不可达 → WARN，仅用本地元数据）
 └─ QueueManager.openTopic(每个本地 topic 的分配)：只开 owner = 本机的队列
 └─ DeadLetterQueue / ConsumeService / SubscriberRegistry / MQMatcher
 └─ BackupReplicator.start()（backup > 0 时）/ LogCleaner.start()
 └─ MQServer.start()：先起巡检/反熵/备份/清理定时器，最后才构造 Server<DataAny>(bindAt = port,
        checkDuration = 30s, executors = 200, checker = {=> Message.ping()}) 并
        spawn { server.start(executor.execute) }——端口在 start() 末尾才绑定
 └─ 安装退出钩子：ExitCallbacks.toExitGracefully() + atExit(0, {=> server.close()})（仅 server 分支）
 └─ 关闭（13 步，见 §6.12）：server → cleanupTimer → antiEntropy → backup → cleaner → consume
          → subscribers → backupStore → queues.sync → queues → deadLetter → meta → registry
          每步单独 try/catch；失败步骤下一次 close() 只重试失败项（A59）
```

- 「本机身份」判定（决策 D1）：`port` 与 `mqClient_hosts` 中某项的端口相等者为自身；若多项同端口 → 退出并提示
  端口重复；若无匹配 → 退出（`this node is not in mqClient_hosts`）。
- `checkDuration` 取常量 30s（连接有效性巡检，规格未给配置项）。

### 6.2 元数据（metas）

- 布局与原子写见 §5.5；**所有节点都保存全量主题与订阅组元数据**（规格第 24、29、34 行）。
- 轮转指针 `assign.meta` = 「下一个新主题的起始节点下标」（规格第 27–28 行），由**收到注册的节点**推进并随
  `MQTopicAssignment.startNodeIndex` 落盘到 `topics/<esc>.meta`（`owners` 同时落盘 ⇒ 分配结果自包含）；
  `owners[queueNum-1]` 即规格第 27 行要求的「该主题最大队列编号分配到了哪个节点」，因此在触发注册的节点和
  每个收到复制的节点上都能直接读出。
- 元数据变更的可见性顺序：先落盘（本地），再广播，最后回响应。

### 6.3 注册/注销的处理与复制

见 §5.6；补充规则：

| 操作 | 校验 | 结果 |
| --- | --- | --- |
| registerTopic | `MQTopic.isValid(topic)`；`queueNum >= 1`；主题不存在 | 分配 + 落盘 + 广播 + 建本地队列；重复 → `TOPIC_ALREADY_EXIST` |
| registerSubscriber | 主题已注册；组名合法（非空串或空串均合法）；组不存在 | 落盘 + 广播；重复 → `GROUP_ALREADY_EXIST` |
| deleteTopic | 主题存在（规格第 44 行：删除该主题所有元数据、队列、消息） | 写主题墓碑 → 删组/主题元数据 → 广播墓碑 → 清本机队列目录、游标、订阅、计数器 |
| deleteSubscribeGroup | 主题与组存在（规格第 46 行） | 写组墓碑 → 删组元数据 → 广播墓碑 → 清该组游标、订阅、计数器 |
| 客户端使用未注册组 | `groupExists` 为假（**含默认组 `""`**） | `SUBSCRIBE` 回 `GROUP_NOT_EXIST`（规格第 59 行） |

- 删除主题时，本地只删除**本机持有的队列**；其它节点收到墓碑后由 `MetaSyncer.onDeleted` 回调清理各自的
  队列目录、游标、订阅与指标计数器（`MQCommandExecutor.cleanupAfterDelete`，与直连删除同一套逻辑）。
- 墓碑先落盘、再删元数据、最后广播：任何一步之后崩溃，重启都能凭墓碑/快照把删除收敛（A25/A35）。
- 删除是危险操作，**只有 manager 能发起**（规格第 45、47 行）：服务端不接受来自普通客户端连接的 register/deregister？
  —— 规格说「客户端不可使用此命令」，因此 `QUEUE` 侧按「连接是否 manager」无法区分（同一 TCP 协议），
  本设计按**能力收敛**：`REGISTER`/`DEREGISTER` 只由 `fmq manager` 实现，`f_mq` 客户端 API 不提供入口（§5.6 的调用方）。
  「恶意客户端直连发 REGISTER」不在本期威胁模型内（见 §8 Q1）。

### 6.4 队列与日志

- 布局：`<segmentedLogDir>/<topicEsc>/<queueIndex>/log_<seq>.log`；死信：`<deadMsgDir>/log_<seq>.log`
  （**都由 `SegmentedLog` 管理，MQ 不再写第二份索引**）。
- 写入路径（publish）：`QueueManager.pickQueue(topic)`（本机队列轮转）→ `QueueLog.append(record)`（返回 `LogPosition`）
  → `BackupReplicator.record(...)`（backup > 0）。
- 记录格式：`[4B 大端长度][记录字节]`，长度取值 `1..effectiveMaxRecord`，其中
  `effectiveMaxRecord = min(QueueLog.MAX_RECORD_SIZE, maxFileSize - 4)`
  （`QueueLog` 构造期按段上限推导；`maxFileSize <= 4` 直接构造失败）。写入前先拒绝空记录与超限记录
  （`IllegalArgumentException`），`f_io.SegmentedLog.append` 再按段容量兜底（`LogRecordTooLargeException`）；
  **一条记录不可跨段**。读取端在分配缓冲前校验 `0 < length <= MAX_RECORD_SIZE` 且 `length <= 段剩余字节`，
  否则判段损坏（A45）；`length == 0` 同样判损坏——写入侧从不产生零长度头，出现即说明数据被写坏，
  MUST NOT 当成「本段已读完」的干净结束。游标路径把损坏作为
  `LogReadResult.Corrupt` 结局：记 ERROR 且不推进位点；`QueueLog.resolveStart(strict: true)`（`stats` 的起点
  解析）与 `QueueRecordReader` 的损坏结局会抛 `QueueCorruptionException`（`scanAfter` 为测试观测 API，同样抛出）。
- 读取路径：`QueueLog.openRecordsFrom(position)` 顺序解码；随机读单条用 `readAt(position)`；
  段长度与时间戳一律取 `logMetas()`。
- 重启：`SegmentedLog(config)` 自动开新段（编号 = 目录里最大编号 + 1）⇒ 不会续写旧段（§5.8 决策 D2）；
  有效数据量以 `logMetas().size` 为准，不用文件长度推断（Linux 下预分配到 `maxFileSize`）。
- TTL：`LogCleaner` 每 5 分钟一轮：挑 `updateTime + ttl < now` 且「无游标引用」的段 → `removeById(index)`（§5.14）。
  默认 `segmentedLogTTL = 72h`、`segmentedLogMaxSize = 1G`（达到上限由 `SegmentedLog.append` 内的轮转处理，
  `f_io/src/SegmentedLog.cj:177-201`）。
- `syncInterval = 1`（每条 fsync）；`sync()` 在关闭时调用。

### 6.5 组游标、投递、重投与死信（核心算法）

状态（每个 `(topic, queueIndex, group)` 一个 `GroupCursor`）：

```
committed    : LogPosition          已「连续确认」的位置（落盘）
scanPosition : LogPosition          已扫描到的位置（初始 = committed）
entries      : ArrayList<DeliveryRecord>   committed 之后的所有未决/已决位置（按位置顺序追加）
DeliveryRecord { position, next, owner: ?String, deliverCount, lastDeliverTime, delivered, decided }
  owner    = 已分配给哪个订阅（None 表示组内可取）
  next     = 该条的结束位置（= position 之后的起点）
  decided  = 已决（已确认 / 不适用 / 已进死信），不再投递
```

`next(subscription, groupMembers, matcher)`（`consume` 的服务端实现，规格第 69–95 行）：

1. **优先重投/交付已分配**：在 `entries` 里按位置顺序找第一条满足以下条件的记录：
   - 未被确认（`decided = false`），且 `owner` 为空或等于本订阅；
   - 与该订阅匹配（tags/filter；`delivered=false` 的分配项跳过 filter 复检，匹配在分配时已判定）；
   - 且（`delivered=false`）或（`now - lastDeliverTime >= ackTimeout`）。
   → 命中：`deliverCount++`、`lastDeliverTime = now`、`owner = Some(subscription.subscribedId)`、`delivered = true`，返回该条；
     若 `deliverCount > deadMsgThreshold`（默认 3 ⇒ 第 4 次投递）→ 转入死信并标记为已决，继续找下一条。
2. **扫描新消息**：用 `QueueLog.openRecordsFrom(scanPosition)` 的顺序流逐条解码记录（读尽后再用最新位置重开，见 §5.7 约定 3）：
   - 与**本订阅**匹配 → 建 `DeliveryRecord{owner: None, delivered: true, deliverCount: 1}`，返回该条；
   - 与**组内其它活跃订阅**匹配 → 建 `DeliveryRecord{owner: 其它订阅, delivered: false, deliverCount: 0}`（分配，
     不推进 `committed`），继续扫描；
   - 与组内任何订阅都不匹配 → 记为「已决（不适用）」并 `advance()`，DEBUG 日志 + 跳过计数，继续扫描；
   - BODY 无法评估（`Unsupported`）→ 写已决项、`advance()`、WARN，并记 `unsupportedAt` 供 `takeUnsupported()` 一次性上报；
   - 日志读尽 → 返回 `None`。
3. **推进 `committed`**：从 `committed` 之后开始，把连续的「已决」（已确认 / 不适用 / 已进死信）位置吞并，
   每前进一步都 `CursorStore.save`（消息不丢优先）。
4. `sweep(activeSubscriptions)` 在每次 `ConsumeService.consume` 进入队列循环时调用（**没有独立的
   GroupCursor 定时器**，也不依赖 `MQServer` 的巡检周期）：
   若某条 `owner` 已不在活跃订阅里，把 `owner` 置回 `None`；组内已无活跃订阅时 `next` 直接返回 `None`，
   **保留为未决**（阻塞该组推进，即「组内无人在线则暂停」，不丢消息）。

`ack(subscriptionId, position)`：

1. `entries` 中该位置不存在（`committed` 之前 / 已进死信）→ 返回 `false`（回 `ACK_UNKNOWN`）；
2. 存在但 `owner` 是别的订阅，或该位置尚未投递（`delivered = false`）→ 返回 `false`；
3. 否则标记已确认并删除 `entries` 项 → 触发步骤 3 的推进 → 返回 `true`。

`autoAck = true` 的投递：在步骤 1/2 命中时**立即**按 `ack` 处理（不建 `entries` 项，直接视为已确认），
即「服务端向订阅者发送消息时自动确认，客户端不需要调用 ack」（规格第 64 行）。

**乱序 ACK 处理（规格第 91 行）**：`entries` 允许「后面的先确认」——先确认的位置留在 `entries` 之外，
`committed` 只在**连续**前缀被确认时推进；空洞位置仍可由重投路径再次投递。不采用「取最大 position 推进」的写法
（旧实现的坑：会产生被跳过的空洞而永久丢失可重投信息）。

**重启语义**：`entries`/`scanPosition`/流缓存都是内存态，重启后从 `committed` 重新扫描 ⇒ 未确认的消息会被**重复投递**
（at-least-once），不会丢；`committed` 之前的消息不再投递。
**位置失效**：若 `committed` 指向的段已被 TTL 清理删掉，`openEntryStream` 会抛 `IllegalArgumentException`
（`f_io/src/SegmentedLog.cj:327-329`）⇒ 游标记 WARN 并跳到现存最老的段继续（等价于「日志保留期短于消费滞后」时丢消息，
运维上应保证 `segmentedLogTTL` 大于最慢组的滞后；§5.14 的「无游标引用才删」已经把这个窗口降到最小）。

### 6.6 死信

- 触发：某条记录对某个组投递次数超过 `deadMsgThreshold`（默认 3）。
- 写入：`DeadLetterQueue.append(MQDeadLetterMessage{topic, queueIndex, subscribeGroup, segmentedIndex,
  segmentedOffset, deliverCount, deadTime, record})`，然后该位置对该组记为已决（可推进 `committed`）。
- 死信是**按组**的：同一条消息在 A 组进死信，不影响 B 组继续消费（规格第 60 行「消息可以在不同的订阅组之间重复消费」）。
- 清理：段文件最后修改时间超过 `deadMsgTTL`（默认 72h）自动删除（规格第 108 行），由 `LogCleaner` 统一执行。
- 消费：`DeadLetterQueue.iterate` 提供顺序读取（§8 Q3）。

### 6.7 命令处理

| 命令 | 载荷 | 处理 |
| --- | --- | --- |
| `REGISTER` | `MQTopicMeta` | `MetaSyncer.registerTopic` → 回 `MQTopicAssignment`；非法/重复 → `ERROR` |
| `REGISTER` | `MQSubscribeGroupMeta` | `MetaSyncer.registerGroup` → 回 `MQResult` |
| `REGISTER` | `MQInternalMessage(metaSync)` | 请求 → 回 `MQMetaSnapshot`；`metaApply` → 应用并回 `MQResult` |
| `DEREGISTER` | `MQDeregisterPayload` | 按 `kind` 删主题/组；同时清理订阅与游标；广播；回 `MQResult` |
| `PUBLISH` | `Array<Byte>` | 主题不存在 → `TOPIC_NOT_EXIST`；本机无该主题队列 → `NOT_OWNER`；否则 append + 备份，回 `RESP(MQResult(0))` |
| `PUBLISH` | `MQInternalMessage(backup)` | 写 `<segmentedLogDir>/backup/...`，回 `RESP(MQResult(0))` |
| `SUBSCRIBE` | `MQSubscribePayload` | 校验主题/组 → 登记订阅（绑定当前 `SocketBuffer`）→ 回 `MQResult` |
| `UNSUBSCRIBE` | `MQUnsubscribePayload` | 注销 + `GroupCursor.release` → 回 `MQResult` |
| `CONSUME` | `MQConsumePayload` | `ConsumeService.consume` → 回 `MQConsumeResult`（无消息则 `record = []`） |
| `ACK` | `MQAckPayload` | `ConsumeService.ack` → 回 `MQResult(0/ACK_UNKNOWN)` |
| 其它 | — | `ERROR` + `MQResult(INTERNAL)` |
| 无法解析的载荷 | — | `ERROR` + `MQResult(INTERNAL)`，并记 WARN（不关连接） |

- 连接断开：`f_net` 的 executor 无法直接感知断链（读循环负责），因此 `MQServer` 用独立的 2s
  定时器（不并入 `LogCleaner`）对 `SubscriberRegistry` 里 `isDisconnected()` 的订阅做清理
  （`cleanupSubscribers()`，按 `subscribedId` + 代次摘除，避免旧快照误删重订阅）。

### 6.8 备份复制（`mqServer_backup > 0`）

- 目标节点：环形后续 `backup` 个（规格第 114–116 行：A→{B,C}、B→{C,A}、C→{A,B}）。
- 内容：记录字节 + 每条消息的真实状态（`MQBackupPayload.records/states/cursors`，
  `MQBackupState{segmentedIndex, segmentedOffset, deliverCount, acked}`；`acked = position < committed`）+
  每组位点 `MQBackupCursor{group, segmentedIndex, segmentedOffset}`——恢复时据此避免重放已确认消息（A26）。
- 时机与批处理：publish 只入队；独立工作线程在 64 条或 100ms 时取走整批，锁外按 `(topic, queueIndex)` 分组串行发送，
  保证同队列顺序；发布线程不再被 RPC 阻塞（A27）。
- 失败重试：失败批次 `attempts++` 后放回队首；超过 3 次或队列满则丢弃并记 ERROR（含数量与目标）。
  队列上限 8192 条（§8 Q5）。
- 清理：`LogCleaner` 扫描 `BackupStore.allLogs()`，保留边界取该队列各组位点的最小值（无位点则全部保留）并叠加
  `segmentedLogTTL`，磁盘不再无界增长（A66）。
- 接收方只存不投递；副本目录与本地队列目录分离，恢复流程（按 `backup/<owner>/<topic>/<queue>` 打开日志 +
  `cursors/<group>.cursor` 重建 committed）本期不做 CLI，但数据足以恢复。

### 6.9 线程模型

| 线程 | 来源 | 职责 |
| --- | --- | --- |
| accept 循环 | `MQServer` spawn | `Server<DataAny>.start` |
| 每连接读循环 | `f_net` Server（每连接一个） | 解帧、PING 回 ACK、投递 executor |
| 执行线程池 | `f_net` Server（`executors`，默认 200） | `MQCommandExecutor.execute` |
| 每连接写线程 | `f_net` SocketBuffer（每连接一个） | 顺序写帧 |
| 心跳线程 | `f_net` Client（每连接一个 Timer） | PING/重连（节点间 + manager 连服务端） |
| `LogCleaner` Timer | MQ | 段文件 TTL 清理 |
| `BackupReplicator` Timer | MQ | 备份批量 flush |

- 并发安全：`MetaStore` 用 `Mutex` 保护「内存索引 + 落盘」；`QueueLog.append` 由 `SegmentedLog` 自身的
  `appendLock` 串行化（`f_io/src/SegmentedLog.cj:127, 178-201`）；`openEntryStream` 在 `appendLock` 下快照段列表
  （同文件 `:315-326`）；
  `SubscriberRegistry`/`ConsumeService` 的游标表用 `Mutex` + `HashMap`（读写比低，热点在 `GroupCursor` 内部）；
  每个 `GroupCursor` 有独立 `Mutex`（不同组之间不互相阻塞）。
- `GroupCursor.next` 与 `sweep` 可能并发：同一个 `Mutex` 串行化；`sweep` 由 `ConsumeService.consume`
  在每次取消息时调用（断链订阅的 `subscribedId` 不在 `activeIds` 里），`GroupCursor` 自身不持有定时器。

### 6.10 `fmq server --help`

- 逐项打印配置项：名 / 意义 / 默认值（`MQConfig.helpText()`），外加启动方式与 `metas`、日志目录说明（规格第 121–122 行）。

### 6.11 指标与延迟投递

**指标**：`MQMetrics` 维护进程内累计计数（`delivered` / `acked` / `redelivered` / `deadLettered` 与
`skippedUnreadable` / `skippedNoMatch` / `skippedUnsupported`，按 topic + group）。
`backlog` 与 `lagMs` 在查询时由 `ConsumeService.stats` 对每个队列做单趟扫描计算（不再按组重复扫描）：
`backlog` 是 `committed` 之后的记录数，`lagMs` 是最早一条记录的发布时间到现在的毫秒数。
`stats` 请求走 `REGISTER` + `MQInternalMessage{kind="stats"}`，子载荷是 topic 字符串；响应是可读的
TSV 文本（首行 `#\t节点\t时间`，其后每行 `R\t...`），manager 直接渲染表格。
统计只覆盖被查询节点的本地队列；计数器重启归零，`backlog/lagMs` 始终按持久化状态计算。

**延迟投递**：主题元数据 `delayingMs`（默认 0）随 `MQTopicAssignment` 落盘、广播与快照复制。
`GroupCursor` 扫描新记录时，用 `MQMessageRecord.publishTime(record)` 取 messageId 末尾 23 位 UTC
时间戳；若 `now - publishTime < delaying`，把 `scanPosition` 停在该记录并返回空——不建未决项、
不推进 `committed`，后续记录也不能越过（FIFO）。因此延迟跨重启有效（时间戳在记录内）。
非标准 messageId 无法解析时按已到期处理并记 WARN。延迟依赖生产者与服务端时钟同步（NTP）。

### 6.12 关闭顺序

`MQServer.close()` 按启动的相反顺序执行，单步失败只记录该步骤，再次调用只重试失败步骤：

```
server → cleanupTimer → antiEntropy → backup → cleaner → consume → subscribers →
backupStore → queues.sync → queues → deadLetter → meta → registry
```

`queues.sync()` 是独立步骤（落盘刷盘），失败会被记为失败步骤并可在下次 `close()` 重试。

## 7. `fmq manager` 设计

| 子命令 | 参数 | 等价协议调用 | 输出 |
| --- | --- | --- | --- |
| `registerTopic` | `<topic> <queueNum> [delaying=<DurationString>]` | `REGISTER` + `MQTopicMeta` → `MQTopicAssignment` | `<topic> 已注册，队列 0..3（共 4 个），延迟：0s，分配：0→0,1→1 …` |
| `deleteTopic` | `<topic>` | `DEREGISTER` + `kind="topic"` | `topic 已删除` |
| `registerSubscriber` | `<topic> <group>` | `REGISTER` + `MQSubscribeGroupMeta` | `订阅组 <group> 已注册` |
| `deleteSubscribeGroup` | `<topic> <group>` | `DEREGISTER` + `kind="group"` | `订阅组 <group> 已删除` |
| `listTopics` | — | `REGISTER` + `MQInternalMessage(metaSync, MQMetaSyncRequest)` → `MQMetaSnapshot` | 表格：topic / queueNum / delaying / 分配 |
| `listSubscribeGroups` | `<topic>` | 同上，过滤该 topic | 表格：订阅组 |
| `stats` | `[topic]` | `REGISTER` + `MQInternalMessage(kind=stats)` → TSV | 表格：topic/group/queueNum/delaying/backlog/lagMs/delivered/acked/redelivered/deadLettered/skippedUnreadable/skippedNoMatch/skippedUnsupported |

- 参数位置：`fmq [<配置项>=<值> ...] <子命令> ...` 与 `fmq <子命令> ... [--server=host:port]` 两种顺序都接受
  （`MQManagerArgs` 跳过配置参数定位子命令）；配置项位置错误不再返回 2。
- 默认服务端：`--server` 缺省时读 `mqServer_port` → `127.0.0.1:<port>`；配置读不到或连不上 → 打印
  `无法连接消息队列服务` 并返回 1（规格第 126 行）。
- 错误分类：服务端回 `ERROR` 时打印服务端错误码文案（不是「无法连接」）；`RESP` 但载荷不是快照 → 协议错误；
  只有发送失败/超时才归为连接失败。
- 输出渲染集中在 `MQManagerOutput`（纯函数），用例直接断言表格字符串。
- `--help`：列出全部子命令与参数（规格第 142–143 行）。
- 连接使用 `f_net` 的 `Client<DataAny>`（`checker = {=> Message.ping()}`），每次命令「一次请求一次响应」后关闭。

## 8. 关键设计决策与开放问题

### 决策

| 编号 | 决策 | 理由 / 依据 |
| --- | --- | --- |
| D1 | 服务端节点表复用 `mqClient_hosts`；本机身份按 `mqServer_port` 与该表端口匹配 | 规格只在 `f_mq` 一节给了节点列表，服务端却需要「所有服务节点」（§6.1）；匹配规则可测 |
| D2 | 队列日志**永不续写旧段**：重启由 `SegmentedLog(config)` 自己开新段（编号 = 目录里最大编号 + 1） | 2026-10-12 起由 f_io 保证（`d72c87b0`；`f_io/README.md`「创建实例」、`f_io/src/SegmentedLog.cj:129-150`）。旧版需要 MQ 自己扫 `maxSeq` 拼 `startSeq`，这部分代码已从设计里删掉 |
| D3 | publish 在本机持有的队列间轮转选队列 | 规格未定义队列选择；记录格式里没有队列号（§3.2），只能由接收节点决定；轮转可保证本机各队列均衡 |
| D4 | 记录读取用 `SegmentedLog.openEntryStream(index, offset)`（可指定起始位置），**不自建索引、不自己扫目录删段** | f_io 在 `d72c87b0` 补齐了「按位置顺序读 + `logMetas()` 段元数据 + `removeById`/时间批量删」；早期版本给不出段内偏移、也拿不到历史段，当时才设计了「每段一个索引文件 + seek」，现已删除（自建索引还会引入第二份写盘与掉电一致性问题） |
| D5 | 游标位点落在 `metas/offsets/`，每次确认都落盘 | 规格第 98 行把元数据放 metas；「最后完成消费的位置」属于消费元数据；消息不丢优先 |

| D7 | `entries`（在飞/已分配位置）只在内存，不落盘 | 规格只要求落「最后完成消费的位置」；重启后从 `committed` 重扫 = at-least-once（重复投递优于丢消息） |
| D8 | 死信条目自描述（`MQDeadLetterMessage` 含原文与来源上下文） | 旧实现把死信元数据另存一份易脱节；自描述条目可用同一套 codec 读取 |
| D9 | 内部消息（元数据同步/备份）承载在 `REGISTER`/`PUBLISH` 上，用 `MQInternalMessage` 信封 | 协议命令号已满（f_mq 设计 §3.1），不新增命令 |
| D10 | 队列位置沿用 `f_io.LogPosition`（即规格的 `segmentedIndex`/`segmentedOffset`），其 `seq`/`offset` **已放宽为 `public let`** | 2026-10-11/12 两次实测确认跨模块不可读（`error: can not access field 'seq'`）后，2026-10-12 用户拍板：「SegmentedLog 就是为这个 MQ 做的本次修改」，直接在本 worktree 把两个字段改成 `public let`（纯可见性放宽，f_io 回归 19/19 通过） |
| D11 | 记录字节一律经 `f_mq` 的 `MQBytes.fromData` 还原（兼容 >4096 字节载荷落 `/tmp/tmpFile<UUID>/` 临时文件的形态），失败返回 `None` | 同 f_mq 设计 D9；`File` 形态读回后要清理临时文件 |
