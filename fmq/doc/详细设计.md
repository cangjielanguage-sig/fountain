# fmq 详细设计

> 需求来源：`.autocode/mq.md`（第 8–11、19–144 行：模块定义、编解码/通讯/核心功能、`fmq` 服务进程与管理进程）。
> 共用 API（数据模型、记录编解码、协议载荷与命令）见 `../../f_mq/doc/详细设计.md`（下文简称「f_mq 设计」）。
> 开发顺序见同目录 `开发计划.md`。

## 1. 模块定位

- 编译目标：**可执行文件**（`cjpm.toml: output-type = "executable"`），模块名 `fmq`，包名前缀 `fountain::fmq`。
- 两个子命令（规格第 101、124 行）：
  - `fmq server`：服务进程（`MQServer`，阻塞运行）；
  - `fmq manager`：管理进程（`MQManager`，一次性命令）。
- 依赖模块（`cjpm.toml`）：`f_mq`（共用 API）、`f_base`、`f_codec`、`f_concurrent`、`f_config`、`f_data`、
  `f_io`（SegmentedLog/ByteBuffer）、`f_log`、`f_net`、`f_process`（`getAbsoluteCommandDir`）、`f_protocol`、
  `f_time`、`f_util`。
- 运行时形态：**独立进程，不被 fboot 加载**（与 `f_rpc` 的「动态库 + Initializer」形态不同，规格第 10 行明确要求可执行文件），
  因此不注册 `f_app.SubCommand`，`main` 自己解析 `server` / `manager`。

## 2. 包级设计

| 包 | 意义 | 依赖（本模块内） | 依赖（模块外） |
| --- | --- | --- | --- |
| `fountain::fmq` | 入口：`main`、子命令解析分发、`--help` 文本 | config, server, manager | f_process |
| `fountain::fmq.config` | `MQConfig`：全部 `mqServer_*` 配置项、节点列表、路径解析与校验 | — | f_config, f_util, f_process, f_data |
| `fountain::fmq.meta` | 元数据：`MetaStore`（metas 目录持久化）、`MQAssignment`（队列分布）、`MetaSyncer`（节点间复制）、`MQFileNames`（文件名转义） | — | f_mq(base), f_codec, f_data, f_net, f_log |
| `fountain::fmq.queue` | 队列与消费状态：`QueueManager`、`QueueLog`、`RecordIndex`、`GroupCursor`、`CursorStore`、`DeadLetterQueue`、`LogCleaner` | — | f_io, f_mq(base), f_codec, f_time, f_log, f_concurrent |
| `fountain::fmq.cluster` | 集群：`NodeRegistry`（节点表/连接/存活）、`BackupReplicator`（备份副本推送） | meta | f_net, f_mq(base), f_log |
| `fountain::fmq.server` | 服务：`MQServer`（装配/启动/关闭）、`MQCommandExecutor`（命令分发）、`SubscriberRegistry`（订阅表）、`MQMatcher`（匹配）、`ConsumeService`（取消息） | config, meta, queue, cluster | f_net, f_protocol, f_mq(base), f_log |
| `fountain::fmq.manager` | 管理端：`MQManager`（子命令实现）、`MQManagerArgs`（参数解析）、`MQManagerOutput`（输出渲染） | — | f_mq(base), f_net, f_config, f_log, f_util |

依赖方向：

```
fountain::fmq ──> server ──> {config, meta, queue, cluster} ──> f_mq(base)
                   manager ──> f_mq(base) + f_net（独立，不依赖 server/meta/queue）
```

> `config` 里的 `MQConfig` 用 `protected`（模块级可见）：它要被 `server`/`meta`/`queue`/`cluster` 这些**兄弟包**使用，
> Cangjie 的 `internal` 只到「本包及子包」，兄弟包读不到（规格第 103 行要求 `protected struct MQConfig`，与此一致）。

## 3. 配置（`MQConfig`）

```cj
protected struct MQConfig {
    // ---- 规格给定的配置项（`.autocode/mq.md` 第 105–119 行）----
    static prop port: UInt16                 // mqServer_port，默认 2350
    static prop ackTimeout: Duration         // mqServer_ackTimeout，默认 10s
    static prop deadMsgThreshold: Int64      // mqServer_deadMsgThreshold，默认 3
    static prop deadMsgTTL: Duration         // mqServer_deadMsgTTL，默认 72h
    static prop segmentedLogDir: String      // mqServer_segmentedLogDir，默认 /var/log/fmq/segmentedLogs
    static prop deadMsgDir: String           // mqServer_deadMsgDir，默认 /var/log/fmq/deadMsgs
    static prop segmentedLogMaxSize: Int64   // mqServer_segmentedLogMaxSize，默认 1G
    static prop segmentedLogTTL: Duration    // mqServer_segmentedLogTTL，默认 72h
    static prop backup: Int64                // mqServer_backup，默认 0；负数 → 启动即报错退出
    // ---- 复用客户端配置项（决策 D1）----
    static prop nodes: Array<String>         // mqClient_hosts，节点表（顺序 = 节点下标）
    static prop selfIndex: Int64             // 本机在 nodes 中的下标（按 port 匹配，见 §6.1）
    // ---- 帮助文本 ----
    static func helpText(): String           // 配置项名 + 意义 + 默认值（供 `fmq server --help`）
}
```

- 上面的代码块是**签名清单**（非可编译代码：`static prop` 要写成 `{ get() { … } }`，struct 还要 `private init(){}`）；
  范式对齐 `fleet/src/server/FleetServerConfig.cj:21-86`（`internal struct` + `public static prop` + `private init(){}`）。
- 读取方式：`Config.getValue<UInt16>(...) ?? 2350u16`、`Config.getDuration(...)`（支持 `10s`/`72h`）、
  `Config.getString(...)`；`segmentedLogMaxSize` 用 `f_util.computeBytes(size: String): ?Int64`
  （`f_util/src/Utils.cj:25-34`，`1G` → `Some(1073741824)`；**格式非法会抛 `IllegalArgumentException`，不是返回 None**，
  取值需显式兜底，例如 `Config.getString(key).let{computeBytes(it)}.getOrThrow() ?? 1073741824`）。
- 静态属性在**首次使用时**读配置（与 `f_protocol` 的 `ProtocolConfig` 同一考量：包初始化期 `Config` 可能未就绪）。
- 启动期校验（任一不满足即打印错误并退出，退出码 2）：
  1. `backup < 0` → `mqServer_backup must not be negative`（规格第 118 行）；
  2. `nodes` 为空 → `mqClient_hosts is required`；
  3. `selfIndex` 无法定位（没有配置项的端口等于 `port`）→ `mqServer_port ${port} is not in mqClient_hosts`；
  4. `deadMsgThreshold < 1` → 报错。

## 5. 公共成员详解

> 约定：`protected` 成员面向模块内其它包，`internal`/`private` 仅在包内使用；服务端类型的公开面按「可测」设计——
> 业务逻辑（分配、游标、清理、匹配）都不依赖套接字，因此可以在单元测试里直接构造与断言。
> 另：下文凡声明 `<: Resource` 的类型（`MetaStore`/`QueueLog`/`QueueManager`/`DeadLetterQueue`/`NodeRegistry`）
> 都必须同时实现 `isClosed(): Bool`（`Resource` 的接口要求），签名清单为省篇幅只写 `close()`。

protected class MQFileNames {

### 5.4 `MQAssignment`

```cj
protected class MQAssignment {
    /** 轮转分配：队列 i → 节点 (start + i) % nodeCount；返回 owners 与「下一次起始下标」 */
    static func allocate(topic: String, queueNum: Int64, nodeCount: Int64, start: Int64): MQTopicAssignment
    /** 下一主题的起始下标 = (start + queueNum) % nodeCount（规格第 27–28 行的例子：4 队列 3 节点后，从 A 的下一个节点 B 开始） */
    static func nextStart(start: Int64, queueNum: Int64, nodeCount: Int64): Int64
    static func ownersOf(assignment: MQTopicAssignment): Map<Int64, Int64>    // queueIndex → nodeIndex
}
```
- 例（规格第 28 行）：3 节点 A(0) B(1) C(2)、`/topic1` 4 队列、start=0 → owners = [0,1,2,0]（A 拿 0、3；B 拿 1；C 拿 2），
  `nextStart = (0+4)%3 = 1`；`/topic2` 2 队列、start=1 → owners = [1,2]（B 拿 0、C 拿 1，A 没有）。
- 纯函数、无 I/O ⇒ 单元测试直接覆盖规格例子。

### 5.5 `MetaStore`

```cj
protected class MetaStore <: Resource {
    init(metaDir: String)
    /** 载入已落盘的元数据（topics/ 与 groups/ 全部文件 + 轮转指针） */
    func load(): Unit
    func topicOf(topic: String): ?MQTopicAssignment
    func topics(): Array<MQTopicAssignment>
    func groupsOf(topic: String): Array<MQSubscribeGroupMeta>
    func groupExists(topic: String, group: String): Bool
    func nextStartNode(): Int64
    /** 应用主题注册：写盘 + 更新内存索引；已存在返回 duplicated */
    func applyTopic(assignment: MQTopicAssignment): MetaApplyResult
    func applyGroup(meta: MQSubscribeGroupMeta): MetaApplyResult
    /** 注销：删除元数据文件 + 内存项 */
    func removeTopic(topic: String): Bool
    func removeGroup(topic: String, group: String): Bool
    func snapshot(): MQMetaSnapshot
    func close(): Unit
}
```
- 目录布局（`metaDir` = `<fmq 可执行文件所在目录>/metas`，规格第 98 行）：

```
metas/
├── assign.meta                       # codec(nextStartNode: Int64)
├── topics/%2Forder.meta              # codec(MQTopicAssignment)
├── groups/%2Forder/%00.meta          # codec(MQSubscribeGroupMeta)（%00 = 默认组）
└── offsets/%2Forder/0/%00.cursor     # 游标位点（由 CursorStore 维护）
```
- 原子性：写文件采用「写 `<file>.tmp` → `File.renameFrom`/`rename` 覆盖」的方式（std.fs），避免半写文件；
  单条记录很小（< 1KB），不需要 WAL。
- 载入失败（文件损坏/解码失败）→ 记 ERROR 并**跳过该条**继续（不因一条坏元数据拒绝启动），同时不再对外提供该条。

### 5.6 `MetaSyncer`

```cj
protected class MetaSyncer {
    init(store: MetaStore, registry: NodeRegistry)
    /** 注册/注销的入口：本地应用 + 广播（幂等） */
    func registerTopic(meta: MQTopicMeta): MQTopicAssignment
    func registerGroup(meta: MQSubscribeGroupMeta): MQResult
    func deregister(payload: MQDeregisterPayload): MQResult
    /** 收到 peer 的 metaSync 请求 → 返回全量快照 */
    func snapshotFor(requesterIndex: Int64): MQMetaSnapshot
    /** 启动期：向第一个可达 peer 拉快照并合并（本地缺的补、冲突记录 WARN 保留先到者） */
    func syncFromPeers(): Unit
    /** 收到 peer 的 metaApply（转发来的变更）→ 应用到本地，不再广播 */
    func applyRemote(assignment: MQTopicAssignment): MetaApplyResult
    func applyRemoteGroup(meta: MQSubscribeGroupMeta): MetaApplyResult
    func applyRemoteDelete(payload: MQDeregisterPayload): Bool
}
```
- 复制流程（规格第 24、29、34 行「所有主题/订阅组元数据都会保存在所有 `fmq` 服务节点上」）：
  1. 节点 X 收到 `REGISTER`（来自 manager 或 peer）→ 在本地 `MetaStore` 应用（主题：`MQAssignment.allocate` 用当前
     轮转指针算出 `startNodeIndex`/`owners`，随后写入 `assign.meta` 的下一个起始下标）；
  2. X 把**已解析的分配结果**用 `MQInternalMessage{kind: "metaSync", payload: codec(MQTopicAssignment)}` 广播给
     其它所有节点（用 `Message.register(data)` 构造；`REGISTER` 工厂不接受 `MessageID`，帧 id 由它内部新建，
     响应侧用 `Message.resp(id: 请求 id, …)` 配对，见 `f_protocol/src/default/Message.cj:215-217, 234-236`）；
  3. peer 收到后 `applyRemote`：已存在且完全一致 → 幂等跳过（不重复广播）；已存在但不同 → 记 WARN、保留先到者；
  4. X 向请求方回 `RESP`（主题 → `MQTopicAssignment`；订阅组/注销 → `MQResult`）。
- **不新增命令**：上述内部消息都承载在 `REGISTER` / `DEREGISTER` 上，由载荷类型区分（f_mq 设计 §3.4）。
- 冲突与顺序：同一时刻只对**一个**节点做变更（运维约定）；并发注册产生的冲突按「先到者优先 + WARN」处理，
  写在文档与日志里（规格未定义并发注册语义，见 §8 Q2）。

### 5.7 `RecordIndex`

```cj
protected class RecordIndex {
    init(path: String, createNew!: Bool)
    /** 追加一条索引项（定长 24B：seq/offset/size 各 8B 小端），返回条目序号 */
    func append(seq: Int64, offset: Int64, size: Int64): Int64
    func size: Int64                       // 条目数
    func at(ordinal: Int64): ?(Int64, Int64, Int64)     // (seq, offset, size)
    func sync(): Unit
    func close(): Unit
    static func countOf(indexPath: String): Int64        // 只按文件大小算条目数（用于段枚举）
}
```
- 索引文件与段文件**同名配对**：段 `log_<seq>.log` ↔ 索引 `idx_<seq>.idx`（同目录），删除段时一起删（§6.4 的 TTL 清理）。
- 定长 24B：可直接按 `ordinal * 24` 定位（`File.seek(SeekPosition.Begin(...))`），不需要读整个索引文件。

### 5.8 `QueueLog`

```cj
protected class QueueLog <: Resource {
    init(dir: String, maxFileSize: Int64, syncInterval: Int64)
    /** 追加一条记录；返回 LogPosition(seq, offset) */
    func append(record: Array<Byte>): LogPosition
    /** 按位置读回原始记录（seek 段文件 offset 读 size） */
    func readAt(position: LogPosition): ?Array<Byte>
    /** 当前消息总数（各段索引条目数之和） */
    prop size: Int64
    /** 位置 → 序号（供游标把 (seq,offset) 落盘后仍能索引） */
    func ordinalOf(position: LogPosition): ?Int64
    func positionOf(ordinal: Int64): ?LogPosition
    /** 段序号顺序列表（含当前段） */
    func segmentSeqs(): Array<Int64>
    func sync(): Unit
    func close(): Unit
}
```
- **写入**：`SegmentedLog(LogConfig(dir, filePrefix: "log", maxFileSize, syncInterval, startSeq))` 的 `append` 返回
  `LogPosition(seq, offset)`（`f_io/src/SegmentedLog.cj:36-45, 140-163`），紧接着 `RecordIndex.append` 落索引。
- **重启语义（决策 D2，重要）**：`SegmentedLog` 的构造把 `currentSize` 置 0 并对文件 `ftruncate+fallocate+mmap`
  到 `maxFileSize`（同文件 `:98-137, 280-290`）⇒ **重开已有段会从偏移 0 覆盖写**。因此 `QueueLog` 启动时：
  1. 扫描目录取出 `log_<seq>.log` 的最大 seq = `maxSeq`；
  2. 用 `startSeq = maxSeq + 1` 新建段（**永不续写旧段**）；旧段只读、按 TTL 清理；
  3. 若目录为空 → `startSeq = 1`。
  > 预分配只在 Linux 生效（非 Linux 的 `initFileMapping` 是空实现，`f_io/src/SegmentedLog.cj:291-292`）；
  > 因此「已写数据量」在任何平台都**一律以 `RecordIndex` 为准**，不用文件长度推断。
- **读取**：不依赖 `openEntryStream()`（它无法给出段内偏移，且空日志行为不可靠），而是「索引 + seek」随机读：
  `at(ordinal)` → (seq, offset, size) → 打开/复用 `log_<seq>.log` 的 `File` → `seek(Begin(offset))` → 读 `size` 字节。
- **读缓存**：每段一个 `File` 句柄按最近使用缓存（上限 8 个），避免每条消息重复 open。

  （`f_io/src/SegmentedLog.cj:37-45`；按语言规则省略即 `internal`，仅当前包及子包可见）。本设计按「fmq 能读到」
  书写；若实测读不到，需先给 `f_io` 的 `LogPosition` 加 `public prop seq/offset`（纯新增、向后兼容）。
  同类先例：`DataPath` 也没有修饰符却被 `f_orm` 跨模块使用（`f_orm/src/base/SqlDSL.cj:20, 86`），故需实测。

## 6. 服务端机制设计

### 6.1 启动装配与生命周期

```
main(fmq server)
 └─ MQConfig 读取与校验（§3；backup<0 / 缺 nodes / 定位不到自身 → 退出码 2，打印原因）
 └─ 目录准备：metas / segmentedLogDir / deadMsgDir（Directory.create(recursive: true)）
 └─ MetaStore(metas).load()
 └─ NodeRegistry(nodes, selfIndex)（懒连接 peer；自带心跳 PING）
 └─ MetaSyncer.syncFromPeers()（向第一个可达 peer 拉全量快照并合并；全部不可达 → WARN，仅用本地元数据）
 └─ QueueManager.openTopic(每个本地 topic 的分配)：只开 owner = 本机的队列
 └─ DeadLetterQueue / ConsumeService / SubscriberRegistry / MQMatcher
 └─ BackupReplicator.start()（backup > 0 时）/ LogCleaner.start()
 └─ MQServer 构造 Server<DataAny>(bindAt = port, checkDuration = 30s, executors = 200,
        checker = {=> Message.ping()})，spawn { server.start(executor.execute) } 并阻塞等待关闭信号
 └─ 关闭：Server.close() → BackupReplicator.close() → LogCleaner.close() → 各 QueueLog.sync()/close()
          → CursorStore 落盘 → NodeRegistry.close()
```

- 「本机身份」判定（决策 D1）：`port` 与 `mqClient_hosts` 中某项的端口相等者为自身；若多项同端口 → 退出并提示
  端口重复；若无匹配 → 退出（`this node is not in mqClient_hosts`）。
- `checkDuration` 取常量 30s（连接有效性巡检，规格未给配置项）。

### 6.2 元数据（metas）

- 布局与原子写见 §5.5；**所有节点都保存全量主题与订阅组元数据**（规格第 24、29、34 行）。
- 轮转指针 `assign.meta` = 「下一个新主题的起始节点下标」（规格第 27–28 行），由**收到注册的节点**推进并随

  `owners[queueNum-1]` 即规格第 27 行要求的「该主题最大队列编号分配到了哪个节点」，因此在触发注册的节点和
  每个收到复制的节点上都能直接读出。
- 元数据变更的可见性顺序：先落盘（本地），再广播，最后回响应。

### 6.3 注册/注销的处理与复制

见 §5.6；补充规则：

| 操作 | 校验 | 结果 |
| --- | --- | --- |
| registerTopic | `MQTopic.isValid(topic)`；`queueNum >= 1`；主题不存在 | 分配 + 落盘 + 广播 + 建本地队列；重复 → `TOPIC_ALREADY_EXIST` |
| registerSubscriber | 主题已注册；组名合法（非空串或空串均合法）；组不存在 | 落盘 + 广播；重复 → `GROUP_ALREADY_EXIST` |
| deleteTopic | 主题存在（规格第 44 行：删除该主题所有元数据、队列、消息） | 删除本地队列目录与文件、删订阅组、删游标、广播删除；再删元数据 |
| deleteSubscribeGroup | 主题与组存在（规格第 46 行） | 删组元数据 + 该组的游标位点 + 该组的活跃订阅；广播 |
| 客户端使用未注册组 | `groupExists` 为假（**含默认组 `""`**） | `SUBSCRIBE` 回 `GROUP_NOT_EXIST`（规格第 59 行） |

- 删除主题时，本地只删除**本机持有的队列**；其它节点的队列由对应节点处理（广播的删除消息携带同一步骤）。
- 删除是危险操作，**只有 manager 能发起**（规格第 45、47 行）：服务端不接受来自普通客户端连接的 register/deregister？
  —— 规格说「客户端不可使用此命令」，因此 `QUEUE` 侧按「连接是否 manager」无法区分（同一 TCP 协议），
  本设计按**能力收敛**：`REGISTER`/`DEREGISTER` 只由 `fmq manager` 实现，`f_mq` 客户端 API 不提供入口（§5.6 的调用方）。
  「恶意客户端直连发 REGISTER」不在本期威胁模型内（见 §8 Q1）。

### 6.4 队列与日志

- 布局：`<segmentedLogDir>/<topicEsc>/<queueIndex>/log_<seq>.log` + `idx_<seq>.idx`；死信：`<deadMsgDir>/log_<seq>.log` + 索引。
- 写入路径（publish）：`QueueManager.pickQueue(topic)`（本机队列轮转）→ `QueueLog.append(record)`（返回位置）→
  `RecordIndex.append` → `BackupReplicator.record(...)`（backup > 0）。
- 重启：永不续写旧段（§5.8 决策 D2）；段文件预分配 `maxFileSize`（`ftruncate+fallocate`），
  因此**不能用文件长度判断已写数据量**，一切以索引为准。
- TTL：`LogCleaner` 每 5 分钟一轮；删除条件见 §5.14。默认 `segmentedLogTTL = 72h`、
  `segmentedLogMaxSize = 1G`（达到上限由 `SegmentedLog.append` 自动 `rotate`，同文件 `:149-151`）。
- `syncInterval = 1`（每条 fsync）；`sync()` 在关闭时调用。

### 6.5 组游标、投递、重投与死信（核心算法）

状态（每个 `(topic, queueIndex, group)` 一个 `GroupCursor`）：

```
committed    : LogPosition          已「连续确认」的位置（落盘）
scanOrdinal  : Int64                已扫描到的序号（初始 = committed 之后的第一条）
entries      : TreeMap<(seq,offset), DeliveryRecord>    committed 之后的所有未决/已决位置
```

`next(subscription, matcher)`（`consume` 的服务端实现，规格第 69–95 行）：

1. **优先重投/交付已分配**：在 `entries` 里按位置顺序找第一条满足以下条件的记录：
   - 未被确认（在 `entries` 中），且 `target` 为空或等于本订阅；
   - 与该订阅匹配（tags/filter；`delivered=false` 的分配项跳过 filter 复检，匹配在分配时已判定）；
   - 且（`delivered=false`）或（`now - lastDeliverTime >= ackTimeout`）。
   → 命中：`deliverCount++`、`lastDeliverTime = now`、`target = None`、`delivered = true`，返回该条；
     若 `deliverCount > deadMsgThreshold`（默认 3 ⇒ 第 4 次投递）→ 转入死信并标记为已决，继续找下一条。
2. **扫描新消息**：从 `scanOrdinal` 开始逐条读 `QueueLog.readAt`：
   - 与**本订阅**匹配 → 建 `DeliveryRecord{target: None, delivered: true, deliverCount: 1}`，返回该条；
   - 与**组内其它活跃订阅**匹配 → 建 `DeliveryRecord{target: 其它订阅, delivered: false, deliverCount: 0}`（分配，
     不推进 `committed`），继续扫描；
   - 与组内任何订阅都不匹配 → 记为「已决（不适用）」，继续扫描；
   - 日志读尽 → 返回 `None`。
3. **推进 `committed`**：从 `committed` 之后开始，把连续的「已决」（已确认 / 不适用 / 已进死信）位置吞并，
   每前进一步都 `CursorStore.save`（消息不丢优先）。
4. 每次调用 `sweep`（定时器，粒度 `min(ackTimeout, 1s)`）处理「无任何匹配订阅者的超期分配项」：
   若某条 `target` 指定的订阅已消失，把 `target` 置回 `None`；若组内已无匹配者且超期，**保留为未决**
   （阻塞该组推进，即「组内无人在线则暂停」，不丢消息）。

`ack(subscriptionId, position)`：

1. `entries` 中该位置不存在（`committed` 之前 / 已进死信）→ 返回 `false`（回 `ACK_UNKNOWN`）；
2. 存在但 `target` 是别的订阅且已被投递给它（`delivered=true` 且 `target` 非空）→ 返回 `false`；
3. 否则标记已确认并删除 `entries` 项 → 触发步骤 3 的推进 → 返回 `true`。

`autoAck = true` 的投递：在步骤 1/2 命中时**立即**按 `ack` 处理（不建 `entries` 项，直接视为已确认），
即「服务端向订阅者发送消息时自动确认，客户端不需要调用 ack」（规格第 64 行）。

**乱序 ACK 处理（规格第 91 行）**：`entries` 允许「后面的先确认」——先确认的位置留在 `entries` 之外，
`committed` 只在**连续**前缀被确认时推进；空洞位置仍可由重投路径再次投递。不采用「取最大 position 推进」的写法
（旧实现的坑：会产生被跳过的空洞而永久丢失可重投信息）。

**重启语义**：`entries`/`scanOrdinal` 是内存态，重启后从 `committed` 重新扫描 ⇒ 未确认的消息会被**重复投递**
（at-least-once），不会丢；`committed` 之前的消息不再投递。

### 6.6 死信

- 触发：某条记录对某个组投递次数超过 `deadMsgThreshold`（默认 3）。
- 写入：`DeadLetterQueue.append(MQDeadLetterMessage{topic, queueIndex, subscribeGroup, segmentedIndex,
  segmentedOffset, deliverCount, deadTime, record})`，然后该位置对该组记为已决（可推进 `committed`）。
- 死信是**按组**的：同一条消息在 A 组进死信，不影响 B 组继续消费（规格第 60 行「消息可以在不同的订阅组之间重复消费」）。
- 清理：段文件最后修改时间超过 `deadMsgTTL`（默认 72h）自动删除（规格第 108 行），由 `LogCleaner` 统一执行。
- 消费：`DeadLetterQueue.iterate` 提供顺序读取（§8 Q3）。

### 6.7 命令处理

| 命令 | 载荷 | 处理 |
| --- | --- | --- |
| `REGISTER` | `MQTopicMeta` | `MetaSyncer.registerTopic` → 回 `MQTopicAssignment`；非法/重复 → `ERROR` |
| `REGISTER` | `MQSubscribeGroupMeta` | `MetaSyncer.registerGroup` → 回 `MQResult` |
| `REGISTER` | `MQInternalMessage(metaSync)` | 请求 → 回 `MQMetaSnapshot`；`metaApply` → 应用并回 `MQResult` |
| `DEREGISTER` | `MQDeregisterPayload` | 按 `kind` 删主题/组；同时清理订阅与游标；广播；回 `MQResult` |
| `PUBLISH` | `Array<Byte>` | 主题不存在 → `TOPIC_NOT_EXIST`；本机无该主题队列 → `NOT_OWNER`；否则 append + 备份，回 `RESP(MQResult(0))` |
| `PUBLISH` | `MQInternalMessage(backup)` | 写 `<segmentedLogDir>/backup/...`，回 `RESP(MQResult(0))` |
| `SUBSCRIBE` | `MQSubscribePayload` | 校验主题/组 → 登记订阅（绑定当前 `SocketBuffer`）→ 回 `MQResult` |
| `UNSUBSCRIBE` | `MQUnsubscribePayload` | 注销 + `GroupCursor.release` → 回 `MQResult` |
| `CONSUME` | `MQConsumePayload` | `ConsumeService.consume` → 回 `MQConsumeResult`（无消息则 `record = []`） |
| `ACK` | `MQAckPayload` | `ConsumeService.ack` → 回 `MQResult(0/ACK_UNKNOWN)` |
| 其它 | — | `ERROR` + `MQResult(INTERNAL)` |
| 无法解析的载荷 | — | `ERROR` + `MQResult(INTERNAL)`，并记 WARN（不关连接） |

- 连接断开：`f_net` 的 executor 无法直接感知断链（读循环负责），因此 MQ 在 `MQServer` 的巡检（与 `LogCleaner`
  同一批定时器）里对 `SubscriberRegistry` 里 `buffer.isClosed()` 的订阅做清理（`removeByBuffer`）。

### 6.8 备份复制（`mqServer_backup > 0`）

- 目标节点：环形后续 `backup` 个（规格第 114–116 行：A→{B,C}、B→{C,A}、C→{A,B}）。
- 内容：记录字节 + 每条消息的状态（`MQBackupPayload.records/states`，`MQBackupState{index, offset, deliverCount, acked}`）。
- 时机与批处理：publish 落盘后入队，`BackupReplicator` 每 100ms 或累积 64 条 flush 一次；队列上限 8192 条，
  超出丢弃并记 WARN（§8 Q5）。
- 接收方只存不投递；副本目录与本地队列目录分离，便于「万一主节点挂了，从相邻节点恢复」时人工指定数据目录（本轮不实现恢复）。

### 6.9 线程模型

| 线程 | 来源 | 职责 |
| --- | --- | --- |
| accept 循环 | `MQServer` spawn | `Server<DataAny>.start` |
| 每连接读循环 | `f_net` Server（每连接一个） | 解帧、PING 回 ACK、投递 executor |
| 执行线程池 | `f_net` Server（`executors`，默认 200） | `MQCommandExecutor.execute` |
| 每连接写线程 | `f_net` SocketBuffer（每连接一个） | 顺序写帧 |
| 心跳线程 | `f_net` Client（每连接一个 Timer） | PING/重连（节点间 + manager 连服务端） |
| `LogCleaner` Timer | MQ | 段文件 TTL 清理 |
| `GroupCursor.sweep` Timer | MQ | 超期分配项复位 + 死信判定 |
| `BackupReplicator` Timer | MQ | 备份批量 flush |

- 并发安全：`MetaStore` 用 `Mutex` 保护「内存索引 + 落盘」；`QueueLog.append` 由 `SegmentedLog` 自身的
  `appendLock` 串行化（`f_io/src/SegmentedLog.cj:96, 144`）；`RecordIndex.append` 用独立 `Mutex`；
  `SubscriberRegistry`/`ConsumeService` 的游标表用 `Mutex` + `HashMap`（读写比低，热点在 `GroupCursor` 内部）；
  每个 `GroupCursor` 有独立 `Mutex`（不同组之间不互相阻塞）。
- `GroupCursor.next` 与 `sweep` 可能并发：同一个 `Mutex` 串行化。

### 6.10 `fmq server --help`

- 逐项打印配置项：名 / 意义 / 默认值（`MQConfig.helpText()`），外加启动方式与 `metas`、日志目录说明（规格第 121–122 行）。

## 8. 关键设计决策与开放问题

### 决策

| 编号 | 决策 | 理由 / 依据 |
| --- | --- | --- |
| D1 | 服务端节点表复用 `mqClient_hosts`；本机身份按 `mqServer_port` 与该表端口匹配 | 规格只在 `f_mq` 一节给了节点列表，服务端却需要「所有服务节点」（§6.1）；匹配规则可测 |
| D2 | 队列日志**永不续写旧段**，重启后开新段（`startSeq = maxSeq + 1`） | `SegmentedLog` 重开段会把 `currentSize` 置 0 并对文件预分配/映射（`f_io/src/SegmentedLog.cj:98-137, 280-290`）⇒ 续写会从偏移 0 覆盖 |
| D3 | publish 在本机持有的队列间轮转选队列 | 规格未定义队列选择；记录格式里没有队列号（§3.2），只能由接收节点决定；轮转可保证本机各队列均衡 |
| D4 | 记录读取走「每段一个索引文件 + seek」，不用 `openEntryStream()` | `openEntryStream` 只覆盖「旧段 + 当前段内存快照」，给不出段内偏移，空日志行为不可靠；索引同时解决重启续读与 (seq,offset) 反查 |
| D5 | 游标位点落在 `metas/offsets/`，每次确认都落盘 | 规格第 98 行把元数据放 metas；「最后完成消费的位置」属于消费元数据；消息不丢优先 |
| D6 | `syncInterval = 1`（每条 append fsync） | 规格没有该配置项；消息队列默认不应丢已确认的消息 |
| D7 | `entries`（在飞/已分配位置）只在内存，不落盘 | 规格只要求落「最后完成消费的位置」；重启后从 `committed` 重扫 = at-least-once（重复投递优于丢消息） |
| D8 | 死信条目自描述（`MQDeadLetterMessage` 含原文与来源上下文） | 旧实现把死信元数据另存一份易脱节；自描述条目可用同一套 codec 读取 |
| D9 | 内部消息（元数据同步/备份）承载在 `REGISTER`/`PUBLISH` 上，用 `MQInternalMessage` 信封 | 协议命令号已满（f_mq 设计 §3.1），不新增命令 |
| D10 | 队列位置沿用 `f_io.LogPosition`（`(seq, offset)` 即规格的 `segmentedIndex`/`segmentedOffset`），**依赖 f_io 把这两个字段可见性放宽为 `public`** | 规格要求的位点是 SegmentedLog 的位置；`LogPosition` 的字段现在没有修饰符（默认 `internal`，仅 `fountain::f_io` 包及子包可见），**2026-10-11 实测 fmq 侧读不到**（`error: can not access field 'seq'`）。放宽可见性是纯新增、向后兼容；备选（不改 f_io）不可行——offset 由 `SegmentedLog` 内部决定，外部无法自行推算 |
| D11 | 记录字节一律经 `f_mq` 的 `MQBytes.fromData` 还原（兼容 >4096 字节载荷落 `/tmp/tmpFile<UUID>/` 临时文件的形态），失败返回 `None` | 同 f_mq 设计 D9；`File` 形态读回后要清理临时文件 |

### 开放问题（需用户裁决；未裁决时按「建议」实现）

| 编号 | 问题 | 建议 |
| --- | --- | --- |
| Q1 | 「客户端不可使用 register/deregister」如何在协议层强制？（同一 TCP 协议下 server 无法区分 manager 与普通客户端） | 本期按「客户端 API 不提供入口 + 文档约定」实现；若要强隔离，可给 manager 加一次性口令或独立端口 |
| Q2 | 多节点并发注册同一主题的冲突语义 | 本期：先到者优先 + WARN；若需强一致，需引入带版本号的注册协议（改动面较大） |
| Q3 | 死信队列的「专门的消费者」具体形态？（规格第 95 行） | 本期提供 `DeadLetterQueue.iterate`；候选：复用 `f_protocol` 现成的 `DLQ_LIST`/`DLQ_REDELIVER`/`DLQ_REDELIVER_ALL` 三个命令（`f_protocol/src/default/constants.cj:118-120`，当年为 MQ 预留）、`fmq manager listDeadMsgs`、或对外暴露回调接口 |
| Q4 | `syncInterval`、连接巡检周期、`consume` 单次超时等参数是否需要成为配置项？ | 本期为常量；需要时按 `mqServer_*` 命名补齐 |
| Q5 | 备份副本的恢复流程（谁接管、客户端如何切节点）与队列满时的丢弃策略 | 本期只做「副本落盘」；恢复流程需专门设计（涉及客户端路由与元数据变更） |
| Q6 | BODY 为对象类型时服务端 filter 不可评估（f_codec 的解码约束） | 与 f_mq 设计 §7 Q3 同一问题：本期回 `FILTER_UNSUPPORTED_BODY`；根治需扩展 `f_codec` |
| Q7 | 是否同意给 `f_io.LogPosition` 的两个字段加 `public`（D10 的前置）？这是本次唯一要改到既有模块公开 API 的地方 | 建议同意（2 个词的可见性放宽、纯新增、向后兼容）；若不同意，需要另定 MQ 的位置表示（如 f_io 增加一个返回 `(Int64, Int64)` 的公开函数，本质相同） |
