**目标成员**：`QueueLog.openFrom`、`QueueLog.readAt`、`QueueLog.segments`、`QueueLog.size`。

**Red（`src/queue/QueueLog_test.cj`，第 1 批）**

| 用例 | 断言要点 |
| --- | --- |
| `openFromReadsFromGivenPosition` | 写入 5 条后 `openFrom(第 3 条的位置)` → 依次解出第 3、4、5 条（含跨段场景） |
| `openFromSkipsPreallocatedHole` | 1MB 小段 + 多于一个段的写入：读到段的最后一条即停，不会解出预分配区的 0 填充 |

### F2 `DeliveryRecord` + `GroupCursor`（本计划最关键的一步）

**目标成员**：`next`、`ack`、`release`、`sweep`、`committed`、`references`、`close`。

**Red（`src/queue/GroupCursor_test.cj`）**——用一个真实 `QueueLog`（`/tmp` 小段）+ 假订阅视图：

| 用例 | 断言要点 |
| --- | --- |
| `nextDeliversInOrder` | 3 条消息按序投递，位置与记录一一对应 |
| `ackAdvancesCommitted` | ack 第 1 条后 `committed` 前进；再 ack 第 2、3 条持续前进 |
| `outOfOrderAckKeepsHole` | ack 2、3 而不 ack 1 → `committed` 不前进（**规格第 91 行的核心场景**）；再 ack 1 → `committed` 一次推进到 3 |
| `redeliveryAfterAckTimeout` | 不 ack 且注入时钟前进 10s → 同一条被再次投递（`deliverCount` 增加，规格第 93 行） |
| `deadLetterAfterThreshold` | 连续 4 次投递机会都不 ack（`deadMsgThreshold=3`）→ 该条进死信、`committed` 可越过（规格第 94 行） |
| `autoAckDoesNotBlockCursor` | `autoAck=true` 的投递直接推进 `committed`，无 `entries` 残留（规格第 64 行） |
| `unmatchedMessageIsSkipped` | 组内无任何订阅匹配的记录 → 直接视为已决，`committed` 越过 |
| `messageAssignedToOtherSubscription` | 记录只匹配 S2：S1 取时不停留在该条（不阻塞后续匹配 S1 的记录），S2 取时能拿到该条（设计 §6.5 步骤 2） |
| `releaseReturnsAssignedToGroup` | `release(S2)` 后 S1/S2 都能再取到该条（`target` 复位） |
| `sweepResetsDeadTarget` | `sweep` 发现 `target` 订阅已消失 → `target = None`，仍可被其它匹配订阅取走 |
| `noMatchingSubscriberPausesGroup` | 组内没有匹配订阅者 → 该条保留未决、`committed` 不前进（「组内无人在线则暂停」） |
| `committedPersistsAndReloads` | ack 后重建 `GroupCursor`（同 `CursorStore`）→ `committed` 恢复到落盘值 |
| `restartRedeliversUnacked` | ack 1、不 ack 2、重建游标 → 2 及之后会被重新投递（at-least-once，设计 D7） |
| `newAppendVisibleAfterStreamReopen` | 打开流并读尽后再 `QueueLog.append`：不重开则读不到，重开后能读到（设计 §5.7 约定 3） |
| `deletedCommittedSegmentSkipsForward` | 人为删除 `committed` 所在的段（`removeById`）→ 恢复时记 WARN 并跳到现存最老段继续（设计 §6.5「位置失效」） |
| `referencesProtectsSegments` | `references(index)` 在游标还引用该段时为真，推进后为假（供 `LogCleaner`） |
| `concurrentNextAndAckAreSafe` | 4 线程交替 `next`/`ack` 1000 次：无重复投递同一位置的两个未确认副本、`committed` 单调 |

**Green**：按设计 §6.5 的四步算法实现；`entries` 用 `TreeMap<(Int64,Int64), DeliveryRecord>`。
**Refactor**：把「重投候选查找」「扫描推进」「committed 吞并」分成三个私有函数，各自可单测。

## 备注

- `fmq` 是 executable 模块。若 `cjpm test` 在 executable 模块下不可用，则把可测代码放在
  `fountain::fmq.*` 子包（子包可被测试模块引用），并新增一个 `fmq_test` 测试模块（`[test-dependencies]` 引用 `fmq`）
  或把纯逻辑下沉到 `f_mq`（共用 API）——**在 D2 之前先做一次 5 分钟的可行性验证**，避免到 F2 才发现测不了。
- 时间相关的用例（`ackTimeout`/TTL/批量 flush）一律通过**注入时钟**（`() -> DateTime` 或 `MonoTime`）来驱动，
  不使用 sleep 等真实时间。
- **存储层不要重复造轮子**：`SegmentedLog` 现在自带段元数据、按位置读、按编号/时间删段、重启自动开新段
  （`d72c87b0`，`f_io/README.md`）；本计划**没有**索引文件、没有目录扫描删段的步骤（E1 已改为「位置/读取适配」）。
  实现时若想再加一层索引/清理逻辑，先回看设计 D2/D4 的结论。
- 与旧实现的关键差异（不依赖 fleet、无主从/选举、无 Glob/Prefix 订阅、ACK 用 (subscribedId,index,offset)、
  filter 在服务端）已在设计 §8 与 `.autocode/mq.md` 的对照表中登记；实现时不要照搬旧代码。
