# FMQ 消息队列需求文档

> 基于 `.autocode/mq.md` 查漏补缺后的完整需求文档。

---

## 1. 概述

FMQ 是基于 fountain 框架的分布式消息队列，构建于 f_net（TCP 通讯）、f_protocol（应用协议）、f_codec（编解码）、fsync（元数据/集群管理）、f_io::SegmentedLog（消息持久化）之上。

- **代码路径**：`./fmq/src/{client,server,cli,common}/`
- **项目组织**：`fountain::fmq`，子包按端划分
- **性能追求**：极致性能，mmap 顺序读写，零拷贝优先
- **依赖关系**：fsync 是元数据服务，FMQ 是 fsync 的客户端

## 2. 消息模型

### 2.1 消息内容结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `topic` | `String` | 主题路径，UNIX 风格，如 `/order/create` |
| `labels` | `Array<String>` | 消息标识标签，可为空数组 |
| `data` | `Array<Byte>` | 消息负载（业务数据） |
| `id` | `MessageID` | 消息唯一 ID（pid + tid + time） |
| `producerId` | `String` | 生产者标识 |
| `timestamp` | `DateTime` | 生产时间 |
| `expireAt` | `?DateTime` | 可选：过期时间，None 表示永不过期 |

### 2.2 消息生命周期

```
生产者生产 → 写入 SegmentedLog（持久化） → 服务端分发 → 消费者确认 → 过期后删除
```

1. **生产**：生产者发送消息到服务端，服务端写入 SegmentedLog
2. **存储**：消息按队列文件存储，每个队列一个 SegmentedLog 实例
3. **分发**：服务端读取线程从队列头部读取消息，按消费者注册条件匹配
4. **消费**：消费者收到消息后处理，处理完发送 ACK
5. **确认**：服务端收到 ACK 后记录 offset 到 fsync
6. **过期清理**：后台线程定期清理过期消息和已确认的消息文件

### 2.3 消息可靠性语义

| 级别 | 行为 | 场景 |
|------|------|------|
| **AtMostOnce** | 消息最多投递一次，持久化，不等待 ACK | 日志/监控 |
| **AtLeastOnce（默认）** | 消息持久化，等待 ACK，超时重试 | 通用业务 |
| **ExactlyOnce** | 结合幂等消费者或分布式事务保证 | 金融级场景 |

> 复用 `fountain::f_protocol.QoS` 枚举定义。

## 3. 消息队列分区模型

### 3.1 主题与队列

| 概念 | 说明 |
|------|------|
| **Topic（主题）** | 消息的逻辑分类，UNIX 路径表示 |
| **Queue（队列）** | 主题下的分区，每个队列一个 SegmentedLog、一个读线程、一个写线程，实现并行消费 |
| **Partition（分区，即 Queue）** | 队列对消费者表现为分区，同分区内消息有序 |

- 一个主题可以有 N 个队列（队列数在创建主题时指定，默认 1）
- 队列数不能小于 1
- 队列数可以超过 MQ 主节点数（可通过环绕分布）
- **同一队列内消息保证 FIFO 顺序**
- **不同队列之间不保证顺序**

### 3.2 队列分布策略

```
queueIndex = CRC64(topic + ":" + queueIndex) % nodeCount   // 0号队列
queueIndex = (prevNodeIndex + 1) % nodeCount                // 后续队列依次向后排
```

实现步骤：
1. 对 `topic + ":0"` 计算 CRC64，取模确定 0 号队列所在主节点
2. 队列 1 在下一个主节点，队列 2 再下一个
3. 超过节点数则回绕到第一个主节点继续分布

## 4. 生产消息

### 4.1 生产者 API

```cangjie
// 生产者接口
public func produce(topic: String, labels: Array<String>, data: Array<Byte>): ProduceResult
public func produce(topic: String, labels: Array<String>, data: Array<Byte>, qos: QoS): ProduceResult
public func produceBatch(topic: String, messages: ArrayList<Message>): ArrayList<ProduceResult>

// 枚举：生产结果
public enum ProduceResult {
    | Success(MessageID)        // 成功，返回消息ID
    | TopicNotFound             // 主题不存在
    | MessageTooLarge           // 消息过大
    | NoAvailableBroker         // 无可用服务端
    | Timeout                   // 超时
    | Error(String)             // 其他错误
}
```

### 4.2 消息路由

1. 客户端根据主题名获取该主题的队列数（从本地缓存或 fsync）
2. 计算队列索引：`CRC64(topic + ":" + producerId) % queueCount`（按生产者 hash，保证同一生产者同一主题的消息顺序）
3. 根据队列索引定位消息发往的主节点
4. 如果该主节点不可用，自动重试到从节点或下一个可用节点

### 4.3 消息大小限制

| 项 | 限制 | 配置环境变量 |
|----|------|-------------|
| 最大消息体 | 4 MB | `mq_max_message_size`（默认 4194304） |
| 每条消息最大 labels 数 | 64 个 | `mq_max_labels_per_message`（默认 64） |
| 每个 label 最大长度 | 256 字节 | 硬限制 |

超过限制由服务端拒绝，返回 `MessageTooLarge`。

## 5. 消费消息

### 5.1 消费者组

- 同一消费者组内，同一主题的消息在组内消费者之间负载均衡（一条消息只被组内一个消费者消费）
- 不同消费者组的消费者各自独立消费同一条消息（广播语义）

### 5.2 消费者注册

消费者在 fsync 的 `/mq/consumes` 下注册订阅信息，数据结构：

| 字段 | 类型 | 说明 |
|------|------|------|
| `consumerId` | `String` | `${IP}:${processId}:${threadId}` |
| `groupId` | `String` | 消费者组名 |
| `topics` | `Array<String>` | 订阅的主题模式（支持 glob 模式，如 `/order/*`） |
| `matchMode` | `MatchMode` | 匹配模式（EXACT / GLOB / PREFIX） |
| `labels` | `?Array<String>` | 可选：消息必须包含的所有 label |
| `pathFilter` | `?f_data.path.PathPattern` | 可选：DataPath 过滤表达式 |

```cangjie
public enum MatchMode {
    | EXACT      // 严格路径相等
    | GLOB       // glob 模式匹配（如 /order/*）
    | PREFIX     // 前缀匹配（如 /order/ 匹配 /order/create、/order/update）
}
```

消费流程：
1. 服务端 watch fsync 的 `/mq/consumes`，获取消费者注册信息
2. 服务端持久化消费者 offset 到 fsync 的 `/mq/offset/<topic>/<queue>/<groupId>`
3. 匹配消息时，先按 topic 匹配（EXACT/GLOB/PREFIX），再按 labels 过滤，最后按 pathFilter 过滤
4. 确认后的 offset 由消费者主动发送 ACK 时更新

### 5.3 消费 API

```cangjie
// 注册消费者
public func subscribe(groupId: String, topicPattern: String, matchMode: MatchMode): Bool
public func subscribe(groupId: String, topicPattern: String, matchMode: MatchMode, labels: Array<String>): Bool
public func subscribe(groupId: String, topicPattern: String, matchMode: MatchMode, pathFilter: String): Bool

// 拉取消息（Pull 模式）
public func poll(timeout: Duration): ?Message

// 推送模式通过 Channel/回调接收消息
// 确认消费
public func ack(messageId: MessageID): Bool

// 批量确认
public func ackBatch(messageIds: ArrayList<MessageID>): Bool

// 取消订阅
public func unsubscribe(groupId: String, topicPattern: String): Bool
```

### 5.4 Offset 管理

| Key 路径 | 说明 |
|----------|------|
| `/mq/offset/<topic>/<queue>/<groupId>` | 消费者组的消费进度（Int64，已确认的最大 offset） |

- offset 以消息在 SegmentedLog 中的 `LogPosition.seq` 为准
- 新消费者首次加入时，offset 为 0（从头开始消费）
- 现有消费者加入时，offset 为上次持久化的值
- 支持重置 offset（管理端操作）

### 5.5 客户端重连和 offset 恢复

1. 客户端连接断开后立即重连
2. 重连成功后，向服务端发送当前 offset 信息
3. 服务端从断点处继续推送消息（at-least-once 语义下可能有少量重复）
4. 客户端端的业务层需实现幂等消费

## 6. 服务端设计

### 6.1 整体架构

```
┌─────────────────────────────────────────┐
│              MQ Server                    │
│  ┌─────────────────────────────────────┐ │
│  │  QueueManager                        │ │
│  │  ├── Queue 0: SegmentedLog + Reader + Writer  │ │
│  │  ├── Queue 1: SegmentedLog + Reader + Writer  │ │
│  │  └── Queue N: SegmentedLog + Reader + Writer  │ │
│  └─────────────────────────────────────┘ │
│  ┌─────────────────────────────────────┐ │
│  │  ConsumerMatcher                     │ │
│  │  ├── EXACT routing                  │ │
│  │  ├── GLOB routing                   │ │
│  │  └── PREFIX routing                 │ │
│  └─────────────────────────────────────┘ │
│  ┌─────────────────────────────────────┐ │
│  │  ReplicationManager                  │ │
│  │  ├── Data sync to slaves            │ │
│  │  └── Health check                   │ │
│  └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

### 6.2 队列文件（SegmentedLog）管理

- 每个队列一个 SegmentedLog，文件路径：`<data_dir>/<topic>/<queueIndex>/`
- 单文件最大 512 MB（环境变量 `mq_segment_max_size` 可配，默认 536870912）
- 文件名格式：`<topic>_<queueIndex>_<startSeq>.<fileExt>`
- 数据目录：环境变量 `mq_data_dir`（默认 `/var/fmq/data/`）

### 6.3 服务端队列线程

每个队列一个写线程和一个读线程：

**写线程：**
1. 接收生产者发来的消息
2. 写入 SegmentedLog
3. 同步到从节点（如有）
4. 向生产者返回写入结果

**读线程：**
1. 从 SegmentedLog 头部顺序读取消息
2. 根据消费者注册信息匹配投递目标
3. 将消息发送给匹配的消费者
4. 发送消息后记录投递记录（消息 ID + 消费者），启动超时计时器
5. 超时前收到消费者 ACK → 更新 offset，清理投递记录，继续下一条消息
6. 超时未收到 ACK → 执行重试策略
7. 无消费者匹配时，当前消息不退回到队列，等待后续消费者注册

#### 6.3.1 ACK 超时处理与重试策略

```
投递 → 等待 ACK（mq_ack_timeout_ms）
  ├── ✓ ACK 收到 → offset 推进 → 下一条
  └── ✗ 超时未 ACK → 重试
        ├── 重试次数 < maxRetry → 重新投递
        │     ├── 原消费者仍在线 → 重投原消费者
        │     └── 原消费者已离线 → 投递组内其他消费者
        └── 重试次数 ≥ maxRetry → 死信队列
```

**关键参数（环境变量）：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `mq_ack_timeout_ms` | 30000 | ACK 超时时间（毫秒） |
| `mq_max_retry_count` | 3 | 最大重试次数 |
| `mq_retry_interval_ms` | 1000 | 重试间隔（毫秒） |

**重试细节：**

1. 重试间隔采用固定间隔（`mq_retry_interval_ms`），不指数退避
   - 因为单个读线程顺序处理，退避会阻塞后续消息投递。若需退避，待后续引入独立重试队列后优化
2. 每次重试前检查原消费者是否仍在线：
   - 在线 → 重投原消费者（保证顺序，避免其他消费者重复）
   - 离线 → 从消费者组中选另一个在线消费者投递
   - 组内无在线消费者 → 暂停重试，等待组内有消费者上线后再投递
3. 重试计数为什么是 `maxRetry` 次，不是 `maxRetry` 秒
4. 读线程不因等待重试而阻塞整个队列——重试消息单独入重试队列，读线程继续处理后续消息

**死信队列（DLQ）：**

超过最大重试次数的消息移入死信队列，不再投递给消费者：

**存储：**
- 死信队列路径：`<data_dir>/<topic>/<queue>/dlq/`
- 死信消息保留时间：`mq_dlq_retention_hours`（环境变量，默认 168h = 7 天）
- 保留期满自动清理，不依赖人工介入

**处置策略（仅支持人工介入，不支持自动重驱）：**

```
死信消息入 DLQ → 告警日志 → 运维人员排查
  ├── 消费者 BUG → 修复 BUG → 手动 redeliver
  ├── 环境问题 → 恢复环境 → 手动 redeliver
  ├── 数据异常（业务拒绝） → 跳过/丢弃
  └── 可降级错误 → 无需处理，期满自动清理
```

- **不自动重驱**：防止根因未修复时死信循环，消费端反复崩溃
- 运维人员完成以下步骤后再执行手动重投：
  1. 排查消息失败原因（查看日志）
  2. 修复根因（消费者 BUG、环境问题等）
  3. 通过管理端命令 `redeliverDeadLetter` 将消息重新注入源队列
  4. 重投的消息重新走完整的重试策略（重试计数重置为 0）

**管理端命令：**

| 命令 | 参数 | 说明 |
|------|------|------|
| `listDeadLetters` | `--topic <topic>`, `--queue <queueIndex>` | 查看死信消息列表 |
| `redeliverDeadLetter` | `--topic <topic>`, `--queue <queueIndex>`, `--messageId <id>` | 重新投递指定死信 |
| `redeliverAllDeadLetters` | `--topic <topic>`, `--queue <queueIndex>` | 批量重新投递所有死信 |

### 6.4 服务端投递规则

同一队列的消息在读线程中按以下规则投递：
- **同组竞争**：同一消费者组内有多个消费者订阅该队列时，消息按轮询（Round-Robin）分发给其中一个消费者，同组内不重复
- **跨组广播**：不同消费者组都订阅了该队列时，每条消息分别投递给每个组的一个消费者
- 消费者不固定绑定到特定队列，由读线程在每次投递时按当前在线的消费者列表动态分配

### 6.5 消费者到队列的匹配

消费者通过 fsync 注册订阅信息的 `topics` 字段（支持 EXACT/GLOB/PREFIX）匹配消息：

1. 服务端读线程从当前队列读取消息后
2. 查询所有注册的消费者，按 `topics` 模式匹配当前消息的 topic
3. 汇总匹配的消费者，按消费者组分组
4. 每组选一个消费者（Round-Robin）投递
5. 跨组之间独立投递（广播）
- 消费者组数等于队列数时，可实现完全并行

后续可通过管理端变更分配策略。

### 6.6 主从架构

#### 主从角色
- Master：接收生产/消费请求，管理队列文件
- Slave：从 Master 同步消息数据，准备接管

#### 故障切换流程
1. 客户端通过 PING/PONG 心跳检测主节点状态（心跳间隔 5 秒，环境变量 `mq_heartbeat_interval_sec`）
2. 连续 3 次心跳失败（环境变量 `mq_healthcheck_max_retry`），客户端将当前主节点标记为不可用
3. 客户端尝试连接从节点
4. 从节点提升为临时主节点，开始服务
5. 原主节点恢复后，从临时主节点同步丢失的数据
6. 同步完成后，原主节点通知客户端切换回来

#### 数据同步
- 主节点每次写入 SegmentedLog 后，同步发送到从节点
- 从节点记录同步进度（确认的 seq）
- 主节点在从节点确认后才向生产者返回 ACK（可配置为 quorum，默认 1）
- 同步使用 f_net 的 SLAVEOF 命令

### 6.7 无效队列文件清理

后台线程（间隔 60 秒）：
1. 扫描所有队列文件
2. 删除已超过保留期（`mq_retention_hours`，默认 72 小时）的文件
3. 删除所有消息已确认且过期的文件
4. 保留至少最后 1 个文件（避免全空）

## 7. 元数据设计

### 7.1 fsync 命名空间

所有 MQ 元数据保存在 fsync 中：

| Key 路径 | 值类型 | 说明 |
|----------|--------|------|
| `/mq/topic/<topic>` | `TopicMeta` | 主题元数据 |
| `/mq/consumes` | `ConsumeRegistration` | 消费者注册表 |
| `/mq/offset/<topic>/<queue>/<groupId>` | `Int64` | 消费 offset |
| `/mq/brokers/<nodeId>` | `BrokerMeta` | MQ 节点信息 |
| `/mq/topics` | `Array<String>` | 所有主题索引（管理用） |
| `/mq/consumerGroups` | `Array<String>` | 所有消费者组索引（管理用） |
| `/mq/consumerGroups/<groupId>/topics` | `Array<String>` | 组的主题列表 |

```cangjie
// 主题元数据结构
public struct TopicMeta <: DataFields<TopicMeta> {
    queueCount: Int64 = 1
    consumerGroups: Array<String> = []
    createTime: DateTime = DateTime.now()
}

// MQ 节点信息
public struct BrokerMeta <: DataFields<BrokerMeta> {
    nodeId: String          // 节点 ID
    host: String            // IP
    port: Int64             // 端口
    isMaster: Bool          // 是否主节点
    partitions: Array<String>  // 管理的队列列表（"topic/queueIndex"）
}
```

## 8. 连接与会话管理

### 8.1 心跳机制

| 角色 | 心跳方向 | 间隔 | 超时判定 |
|------|----------|------|---------|
| Client → Server | PING 请求 | 5s（可配） | 连续 3 次失败 |
| Server → Client | PONG 响应 | 被动响应 | - |
| 主 ↔ 从 | SLAVEOF+PING | 3s | 连续 3 次失败 |

### 8.2 重连策略

1. 首次重连：立即尝试
2. 连续失败：指数退避（1s, 2s, 4s, 8s... 最大 60s）
3. 重连上限：无上限（持续尝试，直到进程退出）

### 8.3 闲置连接超时

- 30 分钟内无活动且无订阅/生产任务的连接，服务端主动关闭
- 环境变量：`mq_idle_timeout_minutes`（默认 30）

| `listDeadLetters` | `--topic <topic>`, `--queue <queueIndex>` | 查看死信消息 |
| `redeliverDeadLetter` | `--topic <topic>`, `--queue <queueIndex>`, `--messageId <id>` | 重新投递死信消息 |

### 9.3 实现

- 实现 `fountain::f_app.SubCommand`，子命令 `'mqcli'`
- 使用 `f_cmd` 或 `f_config` 解析命令行参数
- 创建临时 `f_net::Client` 连接到任意 mq 主节点执行管理操作

## 11. 服务端节点配置一致性

MQ 服务端启动时：
1. 读取 `mq_hosts` 环境变量
2. 将本机配置广播到其他节点
3. **检测各节点的 `mq_hosts` 配置是否一致**
4. 如果不一致，输出错误日志并退出进程
5. 一致的节点根据 `mq_hosts` 列表的顺序确定自身序号和职责

## 12. 网络协议命令

基于 f_protocol 现有命令扩展，MQ 服务端使用以下命令前缀（Command）：

| 命令 | 方向 | 用途 |
|------|------|------|
| `PUBLISH` | Client → Server | 生产消息 |
| `CONSUME` | Client → Server | 拉取/注册消费 |
| `SUBSCRIBE` | Client → Server | 订阅主题 |
| `UNSUBSCRIBE` | Client → Server | 取消订阅 |
| `RESP` | Server → Client | 响应结果 |
| `PING` | Client → Server | 心跳 |
| `ACK` | Client → Server | 消息确认 |
| `SLAVEOF` | Slave → Master | 从节点同步 |
| `ELECT` | Master ↔ Master | 选主 |
| `REGISTER` | Client → Server | 注册生产者 |
| `DEREGISTER` | Client → Server | 注销生产者 |

MQ 服务端处理流程：

```
客户端              服务端
  │                  │
  │── PUBLISH ──────→│  1. 接收消息
  │                  │  2. 写入 SegmentedLog
  │                  │  3. 同步到从节点（如有）
  │                  │  4. 投递给匹配消费者
  │                  │  5. 等待消费者 ACK
  │←───── RESP ─────│  6. 返回生产结果给生产者
```

## 15. 启动顺序

```
1. fsync 服务端（必须先启动）
2. fmq 服务端（连接 fsync 获取元数据，创建队列文件）
3. fmq 客户端（连接 fmq 服务端和 fsync）
4. fmqcli 管理端（可按需随时执行）
```

启动失败处理：
- MQ 服务端连接 fsync 失败：重试（指数退避，最大 60s），持续失败则退出
- MQ 客户端连接 MQ 服务端失败：重试（指数退避，最大 60s），不退出（后台持续尝试）

## 16. 待明确的问题（需产品决策）

> 以下问题记录设计分歧和未定事项，附可行性分析和选型建议供决策参考。

---

### 16.1 重试次数上限和死信队列

> ⚠️ **已在 §6.3.1 定案**：最大重试 3 次，超限入死信队列，保留 7 天，管理端 `listDeadLetters` / `redeliverDeadLetter`。

**可行性**：简单，基于内存重试队列 + 独立 DLQ 文件即可实现。

**建议**：v1 就引入 DLQ，否则消息静默丢失后排查困难。

---

### 16.2 消费者暂停/恢复消费

**需求**：消费者在不取消订阅的前提下，临时暂停某个主题的消费，后续再恢复。

**可行性分析**：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| **客户端侧 pause/resume**（推荐） | 低 | 消费者收到消息后不 ACK 也不处理，或直接丢弃。服务端无感 |
| **服务端侧 pause 标志** | 中 | 在 fsync 消费者注册信息中增加 `paused: Bool`，服务端读线程跳过该消费者 |

**建议**：
- v1 优先只在客户端侧实现 pause/resume（消费者暂不 poll 或注册临时 `paused` 状态到 fsync）
- 若需要服务端不再发送（节省带宽），v2 再加服务端 pause

---

### 16.3 延迟消息

**需求**：生产者指定消息在未来的某个时间点才开始投递，如 `produce(topic, data, delay: Duration)`。

**可行性分析**：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| **服务端定时器 + 延迟队列**（推荐） | 中高 | 服务端维护延迟队列，定时器到期后将消息移入正常队列。需要一个单独的时间轮（Timing Wheel）或最小堆管理到期时间 |
| **客户端延迟 poll** | 低 | 生产者本地 sleep 后再发送。缺点：生产者进程重启丢失延迟任务 |
| **f_ticktock 集成** | 中 | 利用 `f_ticktock` 的定时任务机制，到期后调 produce。适合延迟精度要求不高的场景 |

**建议**：
- v1 **不实现**。延迟消息会显著增加服务端复杂度（需要定时器管理、持久化延迟消息防止重启丢失）
- v2 考虑，优先级低于事务消息

---

### 16.4 事务消息

**需求**：生产者先发送"半消息"（prepare），业务操作完成后才 commit，确保业务操作和消息发送的原子性。典型场景：订单创建成功后才发消息。

**可行性分析**：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| **两阶段提交（2PC）**（推荐） | 高 | 类似 RocketMQ 的事务消息：prepare → 业务操作 → commit/rollback。服务端需维护事务状态表，后台线程回查未决事务 |
| **本地消息表 + 定时补偿** | 中 | 业务方自己写消息表，定时任务扫描未发送的消息。FMQ 不感知事务，但增加业务方复杂度 |

**架构影响**：
- 服务端需新增 `PREPARE` / `COMMIT` / `ROLLBACK` 协议命令
- fsync 中新增 `/mq/transactions/<txId>` 事务状态记录
- 后台回查线程：服务端定期回调生产者确认未决事务状态

**建议**：
- v1 **不实现**。2PC 引入的复杂度极高，且大多数场景可以通过"先执行业务再 produce"配合 at-least-once + 幂等消费者解决
- v2 视需求优先级而定

---

### 16.5 消息保留策略：按大小（保留最近 N GB）

**需求**：除了按时间（保留 N 小时），还支持按磁盘空间保留（保留最新的 N GB 数据）。

**可行性分析**：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| **双策略 AND**（推荐） | 中 | 时间和大小同时生效，满足任一条件即清理。清理时从最旧的文件开始删除 |
| **双策略 OR** | 中 | 时间和大小分别独立触发清理，先触发的先执行 |

**差异对比**：

| 按时间保留（已有） | 按大小保留（新增） |
|-------------------|-------------------|
| 保证消息在 N 小时内可消费 | 保证磁盘不爆 |
| 消息量少时浪费空间 | 消息量少时保留更长时间 |

**建议**：
- 两者不是二选一，应该**同时启用**——先满足哪个就触发清理
- 新增环境变量 `mq_retention_max_gb`（默认 0，表示不限制大小）
- v1 可以暂不实现，由运维通过磁盘监控 + 调小 `mq_retention_hours` 来间接控制

---

### 16.6 消费者重置 offset 到任意位置

**需求**：运维需要让消费者组从指定位置重新消费，用于数据修复或回溯。

**可行性分析**：简单。管理端直接修改 fsync 的 `/mq/offset/<topic>/<queue>/<groupId>` 即可。

**建议**：v1 直接支持，CLI 已设计 `resetOffset` 命令，只需实现即可。低风险，高价值。

---

### 16.7 批量消费

**需求**：消费者一次 poll 获取多条消息，提高吞吐。

**可行性分析**：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| **服务端批量返回**（推荐） | 中 | CONSUME 命令支持 `batchSize` 参数，服务端一次性返回多条消息，消费者批量 ACK |
| **客户端多次 poll 聚合** | 低 | 消费者内部缓存多次 poll 结果后批量处理，但网络往返不变 |

**建议**：
- v1 不在协议层支持批量（避免读线程复杂度爆炸）
- 消费者可在客户端侧做聚合 buffer，累积到一定数量或超时后逐条 ACK

---

### 16.8 消息压缩

**需求**：消息体较大时（>1KB）启用压缩，减少网络和磁盘开销。

**可行性分析**：

| 压缩算法 | 压缩比 | CPU 开销 | 延迟影响 |
|---------|--------|---------|---------|
| **zstd**（推荐） | 高 | 中 | 低 |
| **gzip** | 中 | 高 | 中 |
| **lz4** | 低 | 极低 | 极低 |

- 生产者侧压缩、消费者侧解压，服务端透传不做解压
- 消息元数据中增加 `compression: CompressionType` 字段

**建议**：
- v1 **不实现**。大多数业务消息 <1KB，压缩收益小且增加复杂度
- 若后续出现大消息场景，推荐 zstd

---

### 16.9 优先级队列

**需求**：高优先级消息优先被投递，即使它在低优先级消息之后到达。

**可行性分析**：
- FMQ 基于 SegmentedLog 顺序写，天然不支持乱序投递
- 要实现优先级，需要为每个优先级单独建队列，读线程按优先级顺序轮询
- **复杂度极高**，且破坏消息顺序语义

**建议**：**不实现**。优先级需求建议通过"不同主题 + 不同队列数"的方式解决：高优先级主题用更多队列保证更快消费。

---

### 16.10 消费暂停后的积压告警

**需求**：队列深度（未消费消息数）超过阈值时，触发告警通知运维。

**可行性分析**：简单。后台线程定期扫描 SegmentedLog 的当前写入位置和消费者 offset，计算 lag。

**建议**：v1 先只暴露 lag 指标到日志，不建告警系统。后续可集成 Prometheus 等监控。

---

### 决策优先级总结

| 功能 | v1 必要性 | 实现建议 |
|------|----------|---------|
| 重试 + 死信队列 | **P0（已定案）** | 按 §6.3.1 实现 |
| resetOffset | **P1** | CLI 命令已设计，简单直接实现 |
| 消费暂停 | **P2** | 先客户端侧实现，服务端侧 v2 |
| 积压 lag 指标 | **P2** | 先日志输出 |
| 批量消费 | **P3** | 客户端侧 buffer |
| 延迟消息 | **P4（v2）** | 结合 f_ticktock |
| 事务消息 | **P4（v2）** | 2PC 复杂度高 |
| 消息压缩 | **P4（v2 按需）** | 推荐 zstd |
| 按大小保留 | **P4（v2 按需）** | 与按时间保留并存 |
| 优先级队列 | **不做** | 用多主题方案替代 |
