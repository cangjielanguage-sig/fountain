## 2. 核心数据模型

### 2.1 消息（Message）

```cangjie
public struct Message {
    id: MessageID          // >=16 byte 唯一标识
    topic: String
    labels: ArrayList<String>
    payload: Array<Byte>   // 业务负载
    producerId: String
    timestamp: DateTime
    expireAt: ?DateTime    // None 永不过期
    qos: QoS               // AtMostOnce / AtLeastOnce / ExactlyOnce
    compression: CompressionType  // None / Zstd（暂保留，v1 恒为 None）
}
```

### 2.2 消息 ID

复用 `fountain::f_protocol.MessageID`：

```cangjie
public struct MessageID <: DataFields<MessageID> {
    pid: Int64        // 生产者进程 ID
    tid: Int64        // 线程内递增序号（单调递增）
    time: DateTime    // 生产时间
}
```

消息 ID 保证全局唯一：不同进程 pid 不同，同进程内 `(pid, tid)` 唯一。

### 2.3 队列（Queue）状态模型

```cangjie
public class Queue {
    let topic: String

    let log: SegmentedLog              // 消息文件存储

    let retryBuffer: ArrayList<RetryEntry>  // 重试消息缓冲区
    var onServers: ArrayList<BrokerNode>    // 所在主节点列表（主/备）
    var deadLetter: DeadLetterStore         // 死信存储
}
```

### 2.4 投递记录（DeliveryRecord）

```cangjie
public class DeliveryRecord {
    let messageId: MessageID
    let consumerId: String         // 投递目标消费者
    let groupId: String
    let deliverTime: DateTime      // 投递时间
```

## 3. 网络协议设计

### 3.1 协议封装

基于 `fountain::f_protocol.Message` 扩展，各端共用 `common/protocol.cj` 定义的封装方法。

**请求/响应结构：**

```
┌─────────┬──────────┬──────────────┬──────────┐
│ Command │ Flags    │  MessageID   │ Body     │
│  1 byte │  1 byte  │  ~20 bytes   │ 可变长度  │
└─────────┴──────────┴──────────────┴──────────┘
```

- **Command**：指令类型（PUBLISH / RESP / ACK ... 共 13 种）
- **Flags**：QoS（2bit）、DUP（1bit）、RETAIN（1bit）、ACK（1bit），其余保留
- **MessageID**：请求/响应关联标识
- **Body**：DefaultCodec 编码的消息体或结果数据

### 3.2 命令定义

| 命令 | Code | 方向 | body 内容 |
|------|------|------|----------|
| `PUBLISH` | 0x30 | C→S | `Message`（不含 id） |
| `RESP` | 0xB0 | S→C | `ErrorCode` + `MessageID`（生产/ACK 结果） |
| `SUBSCRIBE` | 0x80 | C→S | `ConsumerRegistration` |
| `UNSUBSCRIBE` | 0x90 | C→S | `ConsumerId` + `Topic` |
| `CONSUME` | 0xA0 | C→S | `ConsumerId` + `BatchSize` |
| `ACK` | 0xE0 | C→S | `MessageID` |
| `PING` | 0xC0 | C→S | 空（心跳） |
| `REGISTER` | 0x20 | C→S | `ProducerId` |
| `DEREGISTER` | 0xF0 | C→S | `ProducerId` |
| `SLAVEOF` | 0x10 | S→S | `NodeId` |
| `ELECT` | 0xD0 | S↔S | `NodeId` + `Term` |

### 3.3 CLI 协议

管理端不直接调用 f_net 消息，而是**通过 mq 服务端的 f_net Server 转发管理命令**：

```
mqcli → f_net::Client → 任意 MQ 节点 → 执行管理操作 → 操作 fsync → 返回结果
```

所有管理操作最终转变为对 fsync key 的读写。

## 4. 队列管理（QueueManager）

### 4.1 队列声明周期

```
Topic 创建 → QueueManager.distribute()
  → 按 CRC64 计算每个队列归属的节点
  → 在本节点创建 Queue 实例
  → Queue.init() → 打开/创建 SegmentedLog
  → 启动 QueueWriter 写线程
  → 启动 QueueReader 读线程
  → 记录 /mq/brokers/<nodeId> 到 fsync

节点故障 → 其他节点接管失效队列
  → QueueManager.reassign(failedNode)
  → CRC64 计算属故障节点的队列
  → 在健康节点重建 Queue 实例，启动 Writer/Reader
  → 接管期间生产者/消费者继续正常读写

节点恢复 → 其他节点归还队列
  → QueueManager.unreassign(restoredNode)
  → 接管队列置为 draining 模式
  → 恢复节点通过 CRC64 知悉队列归属，createQueues 在本地创建
  → 接管节点继续分发剩余消息直至 deliveryBuffer 空
  → drainCompleteCheck 移除排空完成的队列

Topic 删除 → QueueManager.destroy(topic)
  → 停止所有队列的 Reader/Writer 线程
  → 关闭 SegmentedLog
  → 删除 SegmentedLog 文件和数据目录
  → 清理 fsync 元数据
```

### 4.2 队列分布算法

```
// 输入：主题名 topic，队列总数 queueCount，节点列表 nodes（有序，按 mq_hosts 顺序）
func distribute(topic: String, queueCount: Int64, nodes: ArrayList<BrokerNode>): Int64 {
    // 0 号队列：CRC64 取模确定起始节点
    let startIndex = CRC64(topic + ":0") % nodes.size
    // 后续队列依次向后排列，超出节点数则环绕
    for (i in 0..queueCount) {
        let nodeIndex = (startIndex + i) % nodes.size
        assignQueueToNode(topic, i, nodes[nodeIndex])
    }
}
```

### 4.3 队列文件存储

```
<data_dir>/
  <topic_encoded>/                # topic 路径编码（/ → _）
    <queueIndex>/
      <filePrefix>_<startSeq>.log  # SegmentedLog segment 文件
      dlq/                         # 死信队列
        dlq_<startSeq>.log
```

- `mq_data_dir`：默认 `/var/fmq/data/`
- 每个队列的 SegmentedLog 配置：`LogConfig { dir, filePrefix, maxFileSize, syncInterval, startSeq, fileExt }`

## 5. 写线程（QueueWriter）

### 5.1 写流程

```
生产者 PUBLISH 到达
  ↓
CommandExecutor.handleProduce(request)
  ↓
queueManager.getQueues(topic) → 获取 Queue 实例
  ↓
queue.append(data)    → SegmentedLog.append（持久化）
queue.sync()          → fsync 刷盘
  ↓
向生产者返回 RESP(0, ack)
```

PUBLISH 走**同步写路径**，由 CommandExecutor 的 handler 直接调用 `queue.append()`，不经过 QueueWriter 的 inboundQueue。

### 5.2 Writer→Reader 管道

QueueWriter 后台线程负责**将消息推入读管道**，使消费者可拉取：

```
QueueWriter.run()  [后台线程 per-Queue]
  ↓
inboundQueue.remove()      → 从提交队列取出数据
  ↓
queue.append(data)         → SegmentedLog.writeImpl（mmap memcpy / file.write）
queue.sync()               → file.flush()
  ↓
queue.deliveryBuffer.add(data)  → 🔑 推入 LinkedBlockingQueue
  ↓
syncToSlaves(data)         → 并行通知所有从节点
```

关键设计：
- `deliveryBuffer` 是 `LinkedBlockingQueue<Array<Byte>>`（容量 1024），线程安全
- Writer 写 SegmentedLog 后立即 push 到 `deliveryBuffer`，Reader 侧可见
- `syncToSlaves` 是异步的，不阻塞生产流程

### 5.3 线程模型

```cangjie
public class QueueWriter {
    let queue: Queue
    let replicationManager: ReplicationManager

    public func run(): Unit {
        while (!closed) {
            if (let Some(data) <- inboundQueue.remove()) {
                queue.append(data)
                queue.sync()
                queue.deliveryBuffer.add(data)    // 推入读管道
                syncToSlaves(data)                // 同步从节点
            } else {
                sleep(Duration.millisecond * 10)  // 无数据时 yield
            }
        }
    }
}
```

### 5.4 同步到从节点

```cangjie
private func syncToSlaves(position: LogPosition): Unit {
    if (mq_sync_quorum == 1) { return }  // 仅主确认，无需等待

    let slaves = getOnlineSlaves()
    if (slaves.size == 0) { return }

    // 并行向所有从节点发送待同步数据
    let futures = ArrayList<Future<Bool>>()
    for (slave in slaves) {
        futures.append(spawn { sendToSlave(slave, position) })
    }

    // 等待至少 quorum - 1 个从节点确认
    var confirmed = 0
    for (f in futures) {
        if (f.get()) { confirmed += 1 }
        if (confirmed >= mq_sync_quorum - 1) { break }
    }
}
```

## 6. CONSUME 拉取协议（消费者读取）

FMQ 采用 Pull 模式：消费者主动发送 CONSUME 命令，服务端从 `deliveryBuffer` 取出消息返回。QueueReader 后台线程负责将消息从 SegmentedLog 推入 `deliveryBuffer`。

### 6.1 Server 端处理

```
Client → CONSUME(topic, groupId, batchSize) → f_net::Server
  ↓
CommandExecutor.handleConsume(request)
  ┌─ 解码请求体
  │   DefaultCodec.decode<String>(topic)
  │   DefaultCodec.decode<String>(groupId)
  │   DefaultCodec.decode<Int64>(batchSize)
  │
  ├─ queueManager.getQueues(topic) → 获取队列列表
  │
  ├─ 遍历所有队列:
  │    for each Queue:
  │      deliveryManager.getOffset(topic, q.index, groupId)
  │      → 获取该消费者组的偏移量
  │
  │      q.deliveryBuffer.tryRemove()
  │      → 🔑 非阻塞尝试取出消息
  │      → Some(data): recordDelivery() + 加入 consumed
  │      → None: 跳过（deliveryBuffer 空）
  │
  └─ 返回 RESP(bodyType="consume", encodeMessageList(consumed))
     → DefaultCodec.encode(count) + encode(data)×N
```

**关键设计**：
- `tryRemove()` 是非阻塞的——deliveryBuffer 为空时立即返回 `None`，不阻塞 CONSUME 请求
- 每次 CONSUME 返回所有队列中可用的消息，不超过 batchSize
- `recordDelivery()` 创建 DeliveryRecord 用于 ACK/超时追踪

### 6.2 Client 端处理

```
Consumer.poll<T>(timeout)
  ┌─ subscriber.getSubscriptions()
  │   → 本地缓存: (groupId, topic, dataFilter)
  │
  ├─ 遍历每个订阅:
  │    encodeConsumePayload(topic, groupId, 1)
  │    → DefaultCodec.encode(topic).encode(groupId).encode(1)
  │
  ├─ ProtocolMessage(Command.CONSUME(0), id, MqBody("consume", payload))
  │   client.transfer(id, req, timeout)
  │   → 🔑 超时返回 None（无消息时不阻塞调用方）
  │
  ├─ 收到 RESP:
  │    convert<MqBody>(r.data) → bodyType == "consume"
  │    decodeMessageList(body.payload)
  │    → decode<Int64>(count) + decode<Array<Byte>>(msg)×N
  │
  ├─ dataFilter 过滤（可选）:
  │    if (dataFilter != "" && !dataFilterMatch(dataFilter, msgData))
  │      continue  ← 跳过，拉取下一条
  │    dataFilterMatch:
  │      DefaultCodec.decodeData(buf) → Data 树
  │      DataPath.cache(filter).get(DataList(data)).next().isSome()
  │
  └─ 返回 Some(Message(topic, id, payload, labels))
```

### 6.3 Writer→Reader 管道详述

```
QueueWriter.append(data)           QueueReader.run() [后台]
  ↓                                   ↓
SegmentedLog.write(data)            deliveryBuffer.remove()
  ↓                                   ↓ (阻塞等待)
deliveryBuffer.add(data)            消息出队
  ↓                                   ↓
syncToSlaves(data)                  未来: ConsumerMatcher → 网络投递
```

| 组件 | 类型 | 容量 | 行为 |
|------|------|------|------|
| `deliveryBuffer` | `LinkedBlockingQueue<Array<Byte>>` | 1024 | Writer `add()` / Reader `remove()`（阻塞）/ CONSUME `tryRemove()`（非阻塞） |
| Writer `remove()` | 阻塞 | — | QueueReader 后台线程用，无消息时阻塞等待 |
| CONSUME `tryRemove()` | 非阻塞 | — | CommandExecutor handler 用，无消息立即返回空 |

### 6.5 消费者匹配算法

```cangjie
public class ConsumerMatcher {
    // 输入：消息的 topic
    // 输出：map[groupId → consumerId]
    public func match(message: Message): HashMap<String, String> {
        let result = HashMap<String, String>()
        let registrations = getRegistrations()  // 从本地缓存获取

        // 按消费者组分 group
        let groups = HashMap<String, ArrayList<ConsumerRegistration>>()
        for (reg in registrations) {
            if (matchesTopic(reg.matchMode, message.topic)) {
                groups.getOrPut(reg.groupId) { ArrayList() }.add(reg)
            }
        }

        // 每组的消费者间做 Round-Robin
        for ((groupId, consumers) in groups) {
            let selected = roundRobinSelect(consumers, message)
            result[groupId] = selected.consumerId
        }
        return result
    }

    private func matchesTopic(mode: MatchMode, topic: String): Bool {
        return match (mode) {
            case Exact(pattern) => pattern == topic
            case Glob(pattern) => PathPattern(pattern).matches(topic)
            case Prefix(pattern) => topic.startsWith(pattern)
        }
    }
}
```

### 6.6 投递与重试

```
投递消息 → 记录 DeliveryRecord → 等待 ACK
  │
  ├── ✓ 收到 ACK → 推进 offset → 从 DeliveryRecord 中移除 → 下一条
  │
  └── ✗ ACK 超时（mq_ack_timeout_ms）
        └── retryCount < mq_max_retry_count
              ├── 原消费者在线 → 重投原消费者
              ├── 原消费者离线 & 组内有其他消费者 → 重投其他消费者
              └── 组内无消费者 → 暂停重试（等消费者上线）
              → retryCount++ → schedule 到 retryBuffer
        └── retryCount ≥ mq_max_retry_count → 死信队列
```

### 6.7 offset 管理

```cangjie
// 读线程内部维护：
var readerOffset: Int64 = loadOffsetFromFsync()
// 每次 ACK 确认后推进 offset
func onAck(messageId: MessageID): Unit {
    let record = deliveryRecords.remove(messageId)
    if (record != None) {
        let Seq = extractSeqFromMessageId(messageId)
        if (Seq > readerOffset) {
            readerOffset = Seq
            persistOffsetToFsync(topic, queueIndex, groupId, readerOffset)
        }
    }
}
```

**关键设计**：offset 按消费者组独立管理。同一队列 N 个消费者组有 N 个独立的 offset 值，互不干扰。

## 7. 主从复制

### 7.1 角色定义

| 角色 | 职责 |
|------|------|
| **Master** | 接收生产/消费请求，管理 SegmentedLog，同步到 Slave |
| **Slave** | 从 Master 同步数据，不对外服务，准备接管 |

### 7.2 数据同步协议

```
Slave → Master: SLAVEOF(SlaveNodeId)
Master → Slave: 全量同步（SegmentedLog 当前文件列表）
                ↓
                增量同步（每次 append 后发送增量数据）
                ↓
Slave 确认已同步的 seq → Master 记录 Slave 同步进度
```

### 7.3 故障切换

```
客户端检测到 Master 心跳超时
  ↓
1. 客户端从 BrokerManager 获取该 Master 对应的 Slave 列表
2. 尝试连接 Slave，发送 NEW_MASTER 候选请求
3. Slave 收到多数派节点的确认后提升为 Master
4. 提升后的 Master 更新 /mq/brokers/<nodeId> 的 isMaster=true
5. 客户端切换到新 Master
6. 旧 Master 恢复后自动降级为 Slave
```

### 7.4 切回

```
旧 Master 恢复 → 作为 Slave 连新 Master → 同步缺失数据
  ↓
新 Master 确认数据一致 → 主动发起切回
  ↓
新 Master → 旧 Master: 通知准备接管
旧 Master 提升为 Master → 更新 fsync
旧 Master → 客户端: Master 已恢复，请切换
客户端 → 旧 Master: 验证连通性
客户端切换回原始 Master
```

### 7.5 队列接管与排空（Queue Draining）

当节点故障时，其队列由健康节点接管。恢复后接管节点启动排空流程，确保未消费消息继续被分发，而非立即关闭或复制。

#### 7.5.1 接管流程

```
健康节点通过 BrokerManager 检测到节点 N 故障
  ↓
QueueManager.reassign(N)
  ↓
遍历所有已知主题的 topicQueues
  ↓
CRC64 计算各队列编号的归属节点
  ↓
如果归属 == 故障节点 N 且队列未在本地创建：
  → new Queue(topic, index, dataDir, segmentSize)
  → 加入本地 topicQueues 列表
  → QueueManager.startAll() 自动启动 Writer/Reader 线程
  ↓
生产者/消费者通过正常的 CRC64 路由持续使用队列
```

接管队列完全工作在本地 SegmentedLog 上，不需要远程复制即可提供服务。

#### 7.5.2 排空流程（Drain）

```
恢复节点上线后，其原有队列在接管节点上仍在运行。
接管节点调用 unreassign(restoredNode)
  ↓
遍历 topicQueues，CRC64 查找应属恢复节点的队列
  ↓
设置 q.draining = true
  ↓
┌─────────────────────────────────────────────┐
│             排空队列生命周期                    │
├─────────────────────────────────────────────┤
│ 阶段 1：标记排空                              │
│   q.draining = true                          │
│   q 仍留在 topicQueues 中                    │
│                                              │
│ 阶段 2：继续分发（接管节点）                      │
│   append()      → 抛出 MqException（拒绝写入）  │
│   CONSUME 读取  → deliveryBuffer.tryRemove()   │
│   QueueReader   → 持续分发直到 buffer 空       │
│                                              │
│ 阶段 3：排空完成                               │
│   deliveryBuffer 空且无未确认的 Delivery       │
│   tryFinishDrain() → close() → return true    │
│                                              │
│ 阶段 4：清理                                  │
│   drainCompleteCheck() 扫描所有排空队列         │
│   检测到 draining=true + isClosed()           │
│   → 从 topicQueues 移除                       │
└─────────────────────────────────────────────┘
```

#### 7.5.3 恢复节点的重新接管

恢复节点启动后，正常调用 `QueueManager.createQueues`：

```
for (i in 0..queueCount) {
    let ownerIndex = CRC64(topic + ":" + i) % nodeCount
    if (ownerIndex == this.nodeIndex) {
        new Queue(topic, i, ...)    // 队列归回本节点
    }
}
```

接管节点上相同编号的队列处于排空状态，排空完毕后会自动移除。接管期的数据写入到接管节点的 SegmentedLog，不被复制回恢复节点——未消费的消息留在接管节点上分发直到消费完毕。

#### 7.5.4 并发安全

| 资源 | 保护策略 |
|------|----------|
| `Queue.draining` | 单一线程设置（unreassign），读取方（append/close）不做 CAS，因状态转换方向单一（正常→排空→关闭） |
| `topicQueues` 修改 | drainCompleteCheck 与 unreassign 串行化（调用方保证外部同步） |
| `deliveryBuffer` | LinkedBlockingQueue 线程安全，Writer 一侧停止 add，Reader 侧持续 tryRemove |

### 8.4 消费循环

```cangjie
// 后台线程：Pull 模式，T 为消息数据类型
private func startConsumeLoop<T>(groupId: String, matchMode: MatchMode): Unit where T <: DataFields<T> {
    let dataFilter = getDataFilter(groupId)  // 从注册信息中获取 DataPath 表达式
    spawn {
        while (!closed) {
            // 从服务端拉取消息
            let result = client.send(CONSUME(consumerId, batchSize=1))
            match (result) {
                case Some(msg) =>
                    // labels 过滤 + 边解码边用 DataPath 过滤消息数据
                    if (labelsFilter(msg) && dataFilterMatch<T>(msg.payload, dataFilter)) {
                        onMessage(groupId, msg)     // 回调业务层
                        client.send(ACK(msg.id))    // 手动 ACK
                    } else {
                        client.send(ACK(msg.id))    // 不匹配也 ACK，继续下一条
                    }
                case None => sleep(Duration.millisecond(100))  // 无消息时短暂等待
            }
        }
    }
}

// 边解码边过滤：使用 f_codec 将 Array<Byte> 解码为 T，同时用 DataPath 匹配
private func dataFilterMatch<T>(payload: Array<Byte>, filter: ?String): Bool where T <: DataFields<T> {
    if (filter == None || filter.value == "") { return true }
    let decoder = DefaultCodec.getDecoder()
    // 流式解码 + 并行 DataPath 匹配（伪代码示意）
    let data = decoder.decodeFromBytes<T>(payload)
    return PathPattern(filter.value).test(data)
}
```

## 10. dataFilter 执行位置分析

### 9.1 当前设计：客户端侧过滤

消费者注册时可选的 `dataFilter`（DataPath 表达式）默认在**客户端侧**执行：

```
服务端投递消息 → 客户端收到需解码
  → dataFilterMatch<T>(payload, dataFilter)
    → DefaultCodec.decode<T>(payload)     // 解码为类型 T
    → PathPattern(dataFilter).test(data)   // DataPath 匹配
  → 匹配则 poll() 返回，不匹配则 ACK 后丢弃
```

### 9.2 服务端侧过滤可行性

#### 核心障碍

服务端保存的消息体是 `Array<Byte>`（opaque blob），而 `dataFilter` 需要解码为结构化数据才能匹配。消费者的泛型参数 `<T>` 是编译时类型，服务端不感知。

```
poll<Order>(...)   // poll 时指定 T
            ↑
        T = Order 是客户端编译时类型，服务端无此信息
```

#### 可行方案：无类型解码为泛化 Data 树

不依赖具体 `<T>`，直接读取字节流中的类型标记，构建 `f_data::Data` 树：

```
Array<Byte> → DefaultCodec.decodeToGeneric() → Data(Dict)
  → f_data.path.PathPattern.test(data) → Bool
```

`decodeToGeneric()` 流程：

```
读取 DataFields 编码的元数据
  → 根据类型标记（string/bool/int/float/list/map/object...）
  → 递归构建 DataString / DataReal / DataBool / DataArray / DataDict ...
  → 返回 Data
```

- 依赖 `f_codec` + `f_data.path`（服务端已引入）
- 需在 `f_codec` 新增约 200 行 `decodeToGeneric()` 方法
- 不需要客户端上传类型信息

#### 方案对比

| 维度 | 客户端侧过滤（当前） | 服务端侧过滤（方案） |
|------|---------------------|---------------------|
| 网络带宽 | 所有消息都发送 | 只发送匹配消息 |
| 服务端 CPU | 0 | 每条消息 × 每个有 dataFilter 的消费者组做一次解码+DataPath |
| 客户端 CPU | 解码+过滤 | 只处理匹配消息 |
| 实现复杂度 | 低 | 中（需 `decodeToGeneric`） |
| 下游典型场景 | 过滤率 < 50% 时无收益 | 过滤率 > 90% 时大幅节省带宽 |

#### 建议

**v1 保持客户端侧过滤**，在消费循环中实现：

```
labelsFilter(msg) && dataFilterMatch<T>(msg.payload, dataFilter)
```

服务端侧过滤作为 v2 优化点预留。两端切换不影响 API 签名——`subscribe()` 和 `poll<T>()` 接口保持一致，仅修改消费者循环内部实现。

若 v2 实现服务端过滤，可选择性地为高过滤率消费者组开启，低过滤率组继续使用客户端过滤。

```
│    for (e in expired) {          │     │       }                             │
│      retry(e) ?? dlq(e)          │     │     }                               │
│    }                             │     │   }                                 │
│  }                               │     │                                     │
└──────────────────────────────────┘     └─────────────────────────────────────┘
```

**Reader 与 Writer 之间没有直接的数据通道**。Writer 只写文件，Reader 直接从 SegmentedLog 读取。

## 13. 启动流程

### 12.1 MQ 服务端启动

```
1. loadConfig() → 解析环境变量
2. 初始化 fsync::Client（连接 fleet_hosts）
3. 读取 /mq/topics → 获取所有主题列表
4. 读取 /mq/brokers → 获取所有节点信息
5. 检测 mq_hosts 一致性（各节点配置对比）
6. 确定自身角色（根据 mq_hosts 顺序 + ELECTION 结果）
7. QueueManager.init() → 为分配到本节点的队列创建 Queue 实例
8. 启动 QueueWriter 和 QueueReader 线程
9. 启动 f_net::Server（监听 mq_hosts 中本节点的端口）
10. 启动 ConsumerMatcher 刷新线程（watch fsync /mq/consumes）
11. 启动 DeadLetter 清理线程
12. 注册 BrokerMeta 到 fsync: /mq/brokers/<nodeId>
```

### 12.2 MQ 客户端启动

```
1. loadConfig() → 解析环境变量
2. 初始化 f_net::Client，连接 mq_hosts 所有节点
3. 初始化 fsync::Client，连接 fleet_hosts
4. MqClient 注册到各 MQ 节点（REGISTER）
5. 等待用户调用 subscribe / produce
```

### 12.3 MQ CLI 启动

```
1. loadConfig() → 解析环境变量
2. 解析命令行参数
3. 创建临时 f_net::Client 连接任意 MQ 节点
4. 发送管理命令
5. 打印结果，退出
```

## 14. 错误码

| 码值 | 名称 | 说明 |
|------|------|------|
| 0 | `SUCCESS` | 成功 |
| 1 | `TOPIC_NOT_FOUND` | 主题不存在 |
| 2 | `TOPIC_EXISTS` | 主题已存在 |
| 3 | `GROUP_NOT_FOUND` | 消费者组不存在 |
| 4 | `GROUP_EXISTS` | 消费者组已存在 |
| 5 | `MESSAGE_TOO_LARGE` | 消息超过大小限制 |
| 6 | `TOO_MANY_LABELS` | 标签数超过限制 |
| 7 | `BROKER_NOT_AVAILABLE` | 服务端不可用 |
| 8 | `PERMISSION_DENIED` | 权限不足 |
| 9 | `ACK_TIMEOUT` | ACK 超时 |
| 10 | `INVALID_TOPIC_FORMAT` | 主题名格式不合法 |

```cangjie
// common/error.cj
public enum MqErrorCode {
    | SUCCESS = 0
    | TOPIC_NOT_FOUND = 1
    | TOPIC_EXISTS = 2
    | GROUP_NOT_FOUND = 3
    | GROUP_EXISTS = 4
    | MESSAGE_TOO_LARGE = 5
    | TOO_MANY_LABELS = 6
    | BROKER_NOT_AVAILABLE = 7
    | PERMISSION_DENIED = 8
    | ACK_TIMEOUT = 9
    | INVALID_TOPIC_FORMAT = 10
}

}
```
