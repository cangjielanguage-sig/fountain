### [x] P1-4: Queue.tryReadFromLog() logStream 无保护 ✅ 已完成

- **问题等级**: P1
- **问题描述**: logStream 延迟创建且无同步，并发初始化泄漏流；close() 与 tryReadFromLog 竞态
- **修复方案**: Mutex(streamLock) 保护 logStream 初始化、清理、关闭
- **实施难度**: 低

#### 经验总结
- `synchronized(streamLock)` 保护三处：
  - `tryReadFromLog()` 中 logStream 的延迟初始化（check→create→assign）
  - `tryReadFromLog()` 中流耗尽时的关闭+置空

### P2 — 中等问题

#### P2-1: SyncRegistry 心跳 jitter 是确定性的，不防 thundering herd ✅ 已完成

- **问题等级**: P2
- **问题描述**: `client/sync_registry.cj:50` `config.heartbeatIntervalSec * 37 % 100` 是一个纯确定函数。所有客户端若配置相同的 `heartbeatIntervalSec`（默认 5），得到的 jitter 值完全相同（5*37%100=85ms）。jitter 的意图是分散客户端心跳请求防止 thundering herd，但确定性的"抖动"等同于无抖动。
  - 此 jitter 是从第 5 轮审查 P4-4 修复而来，原始提议是 "±0~99ms pseudo-random jitter"
  - 当前的实现是确定性的，只偏移了固定的 85ms，所有客户端仍对齐
- **触发条件**: 大量客户端同时启动时仍产生 thundering herd
- **改进方案**: 引入真正的随机值（`std.random` 或基于进程 ID 的伪随机），确保不同进程的 jitter 不同
- **实施难度**: 低

#### 经验总结
- 确定性公式 `c * 37 % 100` 对于相同 c 产生相同结果，无法达到"分散突发"的目的
- 应使用进程级随机源或 `Random` 生成 jitter 偏移
- **修改**: `sync_registry.cj` 新增 `import std.random.*`，jitter 计算改为 `Random().nextInt64(100)`，确保各实例独立随机偏移

#### P2-1: Consumer.poll() dataFilter ACK 响应被丢弃（ACK 静默丢失） ✅ 已完成

- **问题等级**: P2
- **问题描述**: `consumer.cj:67` `client.transfer(ackReq.id, ackReq, Duration.second * 5)` 的返回值被完全丢弃，不检查 ACK 是否成功。当网络波动或服务端繁忙时，ACK 可能失败，导致：
  - 消息被客户端过滤掉（dataFilter 不匹配）
  - ACK 未被服务端接收
  - 服务端视为"未确认"，超时后重新投递给其他消费者

- **触发条件**: dataFilter 过滤消息 + 网络不稳定

#### 经验总结
- `consumer.cj:67` 的 `client.transfer(ackReq.id, ackReq, Duration.second * 5)` 返回值未检查

- ConsumerLoop 的 ACK 丢弃是故意的（fire-and-forget，失败下次回调会更新 offset），但 poll() 模式中丢失 ACK 意味着消息永久丢失"被消费"记录
- **修改**: `consumer.cj:67` 新增 `let ackResp = ...` 并使用 `if (ackResp.isNone()) { log.warn{...} }`

### P0 — 严重 BUG

#### P0-1: Queue.close() 并发 SIGSEGV（testConcurrentReadAndClose） ✅ 已完成

- **文件**: `server/queue.cj:114-123`
- **问题等级**: P0
- **问题描述**: `close()` 不获取 `streamLock` 直接关闭 SegmentedLog，与 `tryReadFromLog()` 中正在执行的 `dec.decode` 并发。decode 内部调用 `f_base::mcopy` 从 mmap 区域拷贝数据时，`log.close()` 可能 `munmap` 该内存 → **SIGSEGV**。此竞态间歇触发（第15轮偶发，第16轮未复现）。
- **修复方案（方案 B）**: `close()` 先获取 `streamLock` → 设置 `closed` 标志 + 关闭 `logStream` → 确保无 reader 在锁内执行 decode → 释放锁 → 锁外关 SegmentedLog
- **实施难度**: 低

#### 经验总结
- **修改文件**: `server/queue.cj:114-123`
- **新增测试**: `QueueTest.testConcurrentReadAndCloseStress` — 20 轮并发读+关闭压力测试
