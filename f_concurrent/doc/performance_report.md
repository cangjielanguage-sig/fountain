### Random 线程安全修复详情

- **问题**：原实现使用 `Random()` 实例，多线程并发调用 `nextFloat64()` 存在数据竞争
- **解决方案**：使用 `AtomicInt64` 作为种子，通过 `fetchAdd(1)` 保证并发安全，结合 XorShift64 算法生成伪随机数
- **代码变更**：
  ```cangjie
  // 移除：private let random = Random()
  // 新增：
  var seed: AtomicInt64   // 实例级别种子
  private static let seedGen = AtomicInt64(0)  // 全局种子生成器

  @OverflowWrapping
  private func xorShift64(): Int64 {
      var x = seed.fetchAdd(1)
      x ^= (x << 13)
      x ^= (x >> 7)
      x ^= (x << 17)
      return x
  }
  ```

### clear() 原子性修复详情

- **问题**：原 clear() 分两步执行（非原子）：headRef.store() + size_.store(0)，并发 add/remove 可能导致 size_ 不一致
- **解决方案**：引入 epoch 代际计数器
  1. `clear()` 先递增 `epoch`
  2. `add()`/`remove()` 在修改 `size_` 前检查 `epoch` 是否变化
  3. 若 epoch 变化，跳过 `size_` 修改或补偿（回滚已修改的 size）
- **代码变更**：
  ```cangjie
  var epoch: AtomicInt64  // 新增代际计数器

  // clear() 先递增 epoch，使并发操作检测到代际变化
  public func clear(): Unit {
      epoch.fetchAdd(1)
      headRef.store(Node<K, V>.createHead(MAX_LEVEL))
      size_.store(0)
  }

  // add/remove 在 size_ 修改前检查 epoch
  if (epoch.load() != curEpoch) {
      // 跳过 size_ 修改或补偿
  }
  ```

## WSL2 环境波动说明

本报告数据与历史版本存在差异，这是 WSL2 环境的特征：

- **CPU 调度**：WSL2 在 Windows 宿主调度下，vCPU 亲和性和频率波动大
- **内存/cache**：跨 OS 边界的内存操作延迟不稳定
- **I/O 开销**：仓颉运行时的 GC 和内存分配路径在 WSL2 下开销偏高

### 2. 操作复杂度

| 操作 | 期望复杂度 | 说明 |
|------|-----------|------|
| get | O(log n) | 纯查找，无 CAS |
| add (新key) | O(log n) | findNode + 多层 CAS 插入 |
| add (更新key) | O(log n) + validateNode | findNode + CAS + O(1) 前驱验证 |
| remove | O(log n) | findNode + 逻辑删除 CAS + 物理删除 |
| removeIf | O(n) | 遍历全部节点 |

| clear | O(1) | 替换 head 引用 + epoch 递增 |
