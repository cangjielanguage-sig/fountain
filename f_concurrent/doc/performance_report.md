| 数据规模 | 单线程 10,000 ops / 并发 80,000 ops |

## 测试方法

## 分析

### 1. 并发扩展性

| 场景 | 单线程吞吐 | 并发8线程吞吐 | 加速比 |
|------|-----------|-------------|--------|
| add | 1,863 | 25,188 | 13.5x |
| get | 1,898 | — | — |
| remove | 1,915 | — | — |

并发 add 相比单线程 add 获得 **13.5x** 加速比（8线程），超线性加速，说明 CAS 无锁实现在多核环境下扩展性良好，无锁竞争瓶颈。

### 2. entryView 性能突出

并发 entryView 在8线程下达到 **~259K ops/s**，远超其他操作。原因：

- entryView 测试中所有线程操作同一个 key（key=1），CAS 竞争在同一点上
- 由于 key 已存在且节点稳定，findNode 路径极短（O(1) 级别）
- CAS 成功率高，重试少

> 注意：此场景为热点 key 的 best-case，不代表通用场景性能。

### 3. 混合操作吞吐较低

并发 mixed 吞吐量（~8.2K ops/s）显著低于并发 add（~25.2K ops/s），原因：

- mixed 包含 get/add/remove/entryView 四种操作，其中 remove 和 entryView 的 CAS 重试概率更高
- remove 导致逻辑删除节点堆积，findNode 需要额外清理逻辑
- mixed 操作数按线程计（每线程5,000次），而非总操作数

### 4. 单线程性能偏低

单线程 add/get/remove 吞吐量约 1.9K ops/s，看起来偏低，主要受以下因素影响：

- **WSL2 环境**：跨 OS 的文件系统和调度开销
- **逻辑删除清理**：findNode 遍历过程中遇到已删除节点会尝试 CAS 清理，增加开销
- **isReachable 调用**：add(Anyway)/add(IfPresent) 在更新已有 key 时需验证节点可达性，从 head 重新遍历跳表
- **Box 包装**：值类型被 `Box<V>` 包装后通过 `AtomicOptionReference` 管理，增加内存分配

### 5. 操作复杂度

| 操作 | 期望复杂度 | 说明 |
|------|-----------|------|
| get | O(log n) | 纯查找，无 CAS |
| add (新key) | O(log n) | findNode + 多层 CAS 插入 |
| add (更新key) | O(log n) + isReachable | findNode + CAS + 可达性验证 |
| remove | O(log n) | findNode + 逻辑删除 CAS + 物理删除 |
| removeIf | O(n) | 遍历全部节点 |
| entryView | O(log n) | findNode + CAS 循环 |
| clear | O(1) | 替换 head 引用 |

## 优化记录

| 优化项 | 说明 |
|--------|------|
| Random 实例缓存 | `randomLevel()` 原先每次创建 `Random()` 对象，改为类成员缓存复用，减少 GC 压力 |
| entryView 原子性修复 | 修复 view 初始值与 CAS 期望值不一致导致的重试风暴，间接提升 entryView 并发吞吐 |
| 删除死代码 | 移除未使用的 `doRemoveEachLevel` 方法，减少代码体积 |

## 潜在优化方向

以下优化方向可能提升性能，但需要权衡正确性风险和实现复杂度：

1. **移除 isReachable 检查**：当前 `add(Anyway)` 和 `add(IfPresent)` 在更新已有 key 时调用 `isReachable` 从 head 遍历验证可达性，开销较大。可考虑改为验证前驱节点的 next 指针仍指向目标节点，将 O(log n) 降为 O(1) 校验。但需仔细验证在并发物理删除场景下的正确性。

2. **findNode 清理策略**：当前 findNode 遍历过程中遇到逻辑删除节点会尝试 CAS 清理，可能增加延迟。可考虑延迟清理（仅在操作失败时清理），减少热路径开销。

3. **分层索引优化**：当前 MAX_LEVEL=16，对于小规模数据（< 65536）可能层数过多，可考虑动态调整 MAX_LEVEL。

4. **size_ 弱一致性**：当前使用 AtomicInt64 维护精确计数，每次 add/remove 都有 fetchAdd/fetchSub 开销。如果调用方能容忍弱一致性 size，可移除或改为惰性计算。
