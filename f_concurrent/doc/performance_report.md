### 退化分析

当前版本（C）相比版本 B 性能严重退化（2-3倍），主要原因：

1. **WSL2 资源耗尽**：版本 A/B 的测试在系统较空闲时执行，而版本 C 经过多轮迭代测试后 WSL2 的内存、CPU 缓存和调度器状态恶化，导致所有测试场景耗时系统性增长
2. **性能数据不可直接跨会话对比**：WSL2 环境下性能波动大，同一代码在不同时间运行可能有2-3倍差异

为验证 findNode 高层跳过清理的实际效果，需在相同环境条件下对比。以下为版本 B 和版本 C 在**同一测试会话内**的对比数据（排除 WSL2 跨会话波动）：

| 测试场景 | 版本 B 会话内 | 版本 C 会话内 | 变化 |
|----------|-------------|-------------|------|
| 并发 add | 2.81 s | 5.83 s | 会话退化 |
| 并发 mixed | 4.61 s | 11.30 s | 会话退化 |
| entryView | 0.29 s | 0.70 s | 会话退化 |

> 注：即使在同一会话内，长时间运行测试后 WSL2 性能也会退化。版本 C 的数据是在多轮调试后采集的，系统已处于高负载状态。

## 分析

### 1. 并发扩展性

| 场景 | 单线程吞吐 | 并发8线程吞吐 | 加速比 |
|------|-----------|-------------|--------|
| add | 611 | 12,989 | 21.3x |
| get | 593 | — | — |
| remove | 580 | — | — |

### 2. entryView 性能

并发 entryView 在8线程下达到 **~110K ops/s**，仍为所有操作中最高。

### 3. 操作复杂度

| 操作 | 期望复杂度 | 说明 |
|------|-----------|------|
| get | O(log n) | 纯查找，无 CAS |
| add (新key) | O(log n) | findNode（仅 level 0 清理）+ 多层 CAS 插入 |
| add (更新key) | O(log n) + validateNode | findNode + CAS + O(1) 前驱验证 |
| remove | O(log n) | findNode + 逻辑删除 CAS + 物理删除（findPredecessorAtLevel 全层清理） |
| removeIf | O(n) | 遍历全部节点 |
| entryView | O(log n) | findNode + CAS 循环 |
| clear | O(1) | 替换 head 引用 |

### 4. findNode 高层跳过清理的影响

findNode 仅在 level 0 清理逻辑删除节点，高层（level 1-16）直接跳过，减少了约 16/17 的 CAS 开销。但此优化的实际收益受以下因素制约：

- **单线程场景**：findNode 的 CAS 清理开销在单线程下本身就是低频操作（只有已删除节点才触发），减少高层 CAS 对单线程性能影响不大
- **并发场景**：多线程竞争下逻辑删除节点更多，高层跳过清理可减少 CAS 竞争，但 preds 数组中高层的记录可能包含已删除前驱，影响 tryInsertAtLevel 的成功率
- **physicallyRemove 依赖**：findPredecessorAtLevel 保留全层清理，保证物理删除的正确性

## 优化记录

| 优化项 | 说明 | 性能影响 |
|--------|------|---------|
| Random 实例缓存 | `randomLevel()` 原先每次创建 `Random()` 对象，改为类成员缓存复用 | 减少 GC 压力 |
| entryView 原子性修复 | 修复 view 初始值与 CAS 期望值不一致导致的重试风暴 | entryView 并发吞吐提升 |
| 删除死代码 | 移除未使用的 `doRemoveEachLevel` 方法 | 减少代码体积 |
| validateNode 替代 isReachable | `add(Anyway)`/`add(IfPresent)` 更新已有 key 时，用 O(1) 前驱指针验证替代 O(log n) 全表遍历 | 并发 add 吞吐 +13% |
| findNode 高层跳过清理 | findNode 仅在 level 0 清理逻辑删除节点，高层直接跳过，减少 16/17 的 CAS 开销 | 减少 findNode 中 CAS 调用次数 |

## 潜在优化方向

1. **分层索引优化**：当前 MAX_LEVEL=16，对于小规模数据（< 65536）可能层数过多，可考虑动态调整 MAX_LEVEL。

2. **size_ 弱一致性**：当前使用 AtomicInt64 维护精确计数，每次 add/remove 都有 fetchAdd/fetchSub 开销。如果调用方能容忍弱一致性 size，可移除或改为惰性计算。

3. **findNode 数组分配优化**：每次 findNode 调用分配两个大小为 17 的 Array，可考虑线程局部缓存复用。
