## WSL2 环境波动说明

本报告数据与早期版本（单线程 ~1.9K ops/s、并发 add ~28K ops/s）存在显著差异。经过对比验证，同一代码在不同时间段运行性能差异可达 2-3 倍，这是 WSL2 环境的特征而非代码退化：

- **CPU 调度**：WSL2 在 Windows 宿主调度下，vCPU 亲和性和频率波动大
- **内存/cache**：跨 OS 边界的内存操作延迟不稳定
- **I/O 开销**：仓颉运行时的 GC 和内存分配路径在 WSL2 下开销偏高

为便于横向对比，以下保留早期版本在系统较空闲时的基准数据。

### findNode 高层跳过清理实验结论

在相同环境条件下对比测试，findNode 高层跳过清理（仅 level 0 清理）与全层清理版本性能无显著差异，但会增加 tryInsertAtLevel 重试率（高层 preds 包含已删除前驱）。已回退此优化，保留全层清理策略。

## 分析

### 1. 并发扩展性

| 场景 | 单线程吞吐 | 并发8线程吞吐 | 加速比 |
|------|-----------|-------------|--------|
| add | 590 | 12,559 | 21.3x |
| get | 612 | — | — |
| remove | 665 | — | — |

### 2. entryView 性能突出

并发 entryView 在8线程下达到 **~121K ops/s**，远超其他操作。原因：

- entryView 测试中所有线程操作同一个 key（key=1），CAS 竞争在同一点上
- 由于 key 已存在且节点稳定，findNode 路径极短（O(1) 级别）
- CAS 成功率高，重试少

> 注意：此场景为热点 key 的 best-case，不代表通用场景性能。

### 3. 操作复杂度

| 操作 | 期望复杂度 | 说明 |
|------|-----------|------|
| get | O(log n) | 纯查找，无 CAS |
| add (新key) | O(log n) | findNode + 多层 CAS 插入 |
| add (更新key) | O(log n) + validateNode | findNode + CAS + O(1) 前驱验证 |
| remove | O(log n) | findNode + 逻辑删除 CAS + 物理删除 |
| removeIf | O(n) | 遍历全部节点 |
| entryView | O(log n) | findNode + CAS 循环 |
| clear | O(1) | 替换 head 引用 |

## 优化记录

| 优化项 | 说明 | 效果 |
|--------|------|------|
| Random 实例缓存 | `randomLevel()` 改为类成员缓存复用 | 减少 GC 压力 |
| entryView 原子性修复 | 修复 view 初始值与 CAS 期望值不一致 | entryView 并发吞吐提升 |
| 删除死代码 | 移除未使用的 `doRemoveEachLevel` | 减少代码体积 |
| validateNode 替代 isReachable | O(1) 前驱验证替代 O(log n) 全表遍历 | 并发 add +13%（空闲时基准） |
| findNode 高层跳过清理 | 仅 level 0 清理，高层跳过 | 实验后回退：无显著收益，增加重试率 |

## 潜在优化方向

1. **分层索引优化**：当前 MAX_LEVEL=16，对于小规模数据可考虑动态调整。

2. **size_ 弱一致性**：每次 add/remove 的 fetchAdd/fetchSub 有开销，可改为惰性计算。

3. **findNode 数组分配优化**：每次分配两个大小 17 的 Array，可考虑线程局部缓存复用。

4. **findNode 中 value.load() 合并**：当前遍历时每个节点都做 `node.value.load().isNone()` 检查，在低删除场景下多数检查多余。可考虑延迟检查。
