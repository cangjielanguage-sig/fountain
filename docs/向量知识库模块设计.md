## 1. 组件能力核查

### 1.1 f_store

**完整公开 API**（`f_store/src/Store.cj` 实读）：

```
Store(path: String)
add(key: Array<Byte>, value: Array<Byte>): ?Array<Byte>
add(key, value, expireAt: DateTime) / add(key, value, expire: Duration)
get(key: Array<Byte>): ?Array<Byte>
contains(key: Array<Byte>): Bool
remove(key: Array<Byte>): ?Array<Byte>          // 写 tombstone
ttl(key, expireAt | expire): Unit
prefix(prefix: Array<Byte>): PrefixIterator
syncWAL(): Unit
close(): Unit
isClosed(): Bool
levelSummary(): String
```

**能力矩阵**

| 特性 | 状态 | 对知识库的意义 |
|---|---|---|
| key/value 为 `Array<Byte>` | ✅ | 向量直接存字节，无序列化框架依赖 |
| 按 key 字节序排序 | ✅ | 前缀即表，天然分库 |
| 无锁并发 | ✅ | 在线查询与后台导入可并行 |
| WAL + 崩溃恢复 | ✅ | 不用自己做持久化 |
| 前缀迭代（独立 File 句柄） | ✅ | 全量扫描不阻塞点查询 |
| TTL | ✅ | 支持临时/过期文档 |
| 批量写 | ❌ | 单条 add，导入靠循环 |
| 事务 | ❌ | 需要两阶段写 |
| 范围扫描 | ❌ | 所有检索必须走前缀 |

**value 大小：实测结论**

读 `SSTable.cj` 与 `WAL.cj` 的序列化代码：

```
SSTable 记录: keyLen(Int64) valueLen(Int64) sequence(Int64) expireAt(Int64) key value
WAL    记录: sequence(Int64) kLen(Int64) vLen(Int64) expireAt(Int64) crc(UInt32) key value
```

- **长度字段是 Int64，没有 4GB 或 2GB 的限制**
- 但有 `static let MAX_SSTABLE_SIZE: Int64 = 64 * 1024 * 1024`（单 SSTable 文件 64MB）

这意味着：

| 单条 value | 每 SSTable 条数 | 评价 |
|---|---|---|
| 4 KB（dense 向量） | ~16,000 | ✅ 健康 |
| 64 KB | ~1,000 | ✅ 可接受 |
| **1 MB** | **~64** | ⚠️ 能存，但文件会非常碎 |

**结论：1MB 技术上可以，但不建议。** 单个 SSTable 只装 64 条会让 compaction 频率和写放大显著上升。大对象（整篇文档原文）应该分块：`c:{chunkId}:{partNo}`，每块 ≤ 64KB。

### 1.2 仓颉性能实测

融合开发引擎（7 核 Cortex-A53，`cjc -O2`）：

```
1024 维 Float32 点积        1.35 μs
全扫 20000 条               27 ms
外推 100000 条              135 ms
外推 1600 条                2.16 ms
```

约 1.5 GFLOPS 单线程。主流 x86 上还能快 5~8 倍。**纯仓颉标量循环够用。**

### 1.3 仓颉生态能力盘点（影响文档解析）

| 能力 | 有/无 | 说明 |
|---|---|---|
| `stdx.compress.zlib` | ✅ | `CompressInputStream` / `CompressOutputStream`，支持 `DeflateFormat` / gzip / zlib |
| ZIP 容器解析 | ❌ | 需自己写（格式简单，约 200~300 行） |
| XML 解析 | ❌ | 标准库与 stdx 都没有 |
| 正则 `f_regex` | ✅ | 可用于轻量标签提取 |

**这三条直接决定了文档解析的策略**：ZIP 能解（deflate 有了），但 XML 树要自己处理——建议不建树，直接按标签做流式文本抽取。

## 2. 可行性判定

| 环节 | 可行性 | 依据 / 风险 |
|---|---|---|
| 向量存储 | ✅ | 4KB/条，SSTable 装 16000 条 |
| IVF-Flat | ✅ | 实测 4.2 ms @ 10万 |
| IVF-PQ | ✅ | 需自写码本训练 + ADC，中等工作量 |
| 稀疏倒排 | ✅ | 前缀遍历天然适配 |
| colbert 重排 | ✅ | 走服务端 `/score`，仓颉侧不算 |
| HNSW | ❌ | **不实现**（量化对比见 6.6） |
| 批量导入 | ⚠️ | 无 batch API，40 万次单条 add |
| 一致性 | ⚠️ | 无事务，两阶段写 |
| **文档解析** | ✅ | 走外部工具链（pandoc + poppler），仓颉侧只做进程调用 |
| **PDF 解析质量** | ⚠️ | 多栏/无 ToUnicode 字体的 PDF 仍有风险，见 7.3 |

> 注：1.3 列出的"无 ZIP / 无 XML"能力缺口，因为改成外部工具链而**不再是问题**。

## 3. 三路向量的正确用法

> **"用上三路向量" ≠ "给三路都建索引"。**

| 向量 | 原始用途 | 应该怎么用 |
|---|---|---|
| **dense**（1024 维） | 语义召回 | ✅ 一级召回索引（IVF 系列） |
| **sparse**（token→权重） | 词面精确匹配 | ✅ 一级召回索引（倒排） |
| **colbert**（每 token 一个 1024 维） | 细粒度重排 | ❌ **不建索引**，只对候选现算 |

### 为什么 colbert 不能建索引

10 万块，每块 150 token：

| 数据 | 单条 | 10 万条 |
|---|---|---|
| dense | 4 KB | **400 MB** |
| sparse | ~480 B | 48 MB |
| **colbert（原始）** | 307 KB | **30 GB** ❌ |
| colbert（池化到 4 个） | 16 KB | 1.6 GB ⚠️ |

30 GB 塞进 LSM，compaction 会打满 IO。

### 检索流程

```
query
  ├─▶ dense  → IVF top-100 ──┐
  └─▶ sparse → 倒排 top-100 ──┤
                              ├─▶ 融合去重 → top-50
                              └─▶ [可选] colbert 重排 → top-K
```

colbert 单次重排成本：32 query token × 128 doc token × 1.35 μs ≈ 5.5 ms/条；top-20 约 110 ms。

**默认关闭**（已定）。开启后走服务端 `/score`，仓颉侧不持有矩阵。

## 5. 存储设计

### 5.1 key 布局（带命名空间）

所有 key 统一加命名空间前缀，为多库隔离留出空间：

```
{ns}:m:ver                        索引格式版本
{ns}:m:cfg                        维度 / nprobe / 簇数 / 当前索引类型
{ns}:m:cent:{clusterId}           簇心向量
{ns}:m:pqcodebook:{subspace}      PQ 码本（切到 IVF-PQ 后才有）

{ns}:d:{docId}                    文档元数据
{ns}:d:{docId}:ready              就绪标记（两阶段写的第二阶段）
{ns}:c:{chunkId}                  块正文
{ns}:c:{chunkId}:{partNo}         大块分片（> 64KB 时）

{ns}:v:d:{chunkId}                dense 原始向量 4KB
{ns}:v:s:{chunkId}                sparse 向量
{ns}:v:pq:{chunkId}               PQ 码（m 字节）

{ns}:i:t:{len2}{token}:{chunkId}  倒排 posting
{ns}:i:c:{clusterId}:{chunkId}    IVF 桶成员
```

### 5.2 多知识库隔离：两个方案

| 维度 | 单 Store + key 前缀 | 多 Store 实例 |
|---|---|---|
| 磁盘布局 | 一个目录，共用 SSTable | 每库独立目录 |
| 内存 | 一份 MemTable | 每库一份 MemTable + Bloom + 索引缓存 |
| 后台线程 | 一组 compaction 线程 | **每库一组**，库多时线程爆炸 |
| 查询定位 | 前缀过滤，天然可用 | 直接定位到实例 |
| 隔离性 | 弱：compaction 互相影响 | 强 |
| 删库 | 逐 key 写 tombstone，靠 compaction 回收 | 删目录，秒级 |
| 备份/迁移单库 | 难（要前缀导出） | 易（拷目录） |
| 跨库检索 | 天然支持（去掉 ns 前缀即可） | 需要上层合并 |
| 实现复杂度 | 低 | 中（生命周期管理） |

**结论：默认单 Store + key 前缀。**

理由：

1. f_store 没有"库"的概念，多实例等于多套 WAL + compaction 线程 + Bloom 过滤器，资源线性增长
2. LSM 的 compaction 本来就是全量重写，多库混在一起对写放大影响有限
3. 前缀隔离在查询侧几乎零成本（`prefix()` 直接跳过其他库）
4. 跨库检索在单 Store 下是免费的，多实例要上层写合并逻辑

**但有两个场景应该改用多 Store：**

- 需要**独立备份/迁移**某个库（比如把"产品文档"库单独导出去）
- 需要**严格资源隔离**（一个库导入时不能拖慢另一个库的查询）

这两种情况建议做成配置项 `isolation: prefix | store`，默认 `prefix`。

### 5.3 三个编码细节

**① token 变长会让前缀撞**

`{ns}:i:t:的:` 与 `{ns}:i:t:的确:` —— 后者被前者包含。必须加长度前缀：

```
{ns}:i:t: <2 字节大端长度> <token 字节> : <chunkId 8 字节大端>
```

**② chunkId 定长大端**

保证同一前缀下 posting 按 id 有序，便于归并和分页。

**③ Float32 → Byte**

仓颉不能把 `Array<Float32>` 直接当字节。用 `Float32.bitCastUInt32()` 拆 4 字节，直接写进预分配的 `Array<Byte>(dim*4)`，小端序（与 aarch64/x86 一致）。**避免中间数组**，这是导入 10 万条时的热点。

### 5.4 一致性：两阶段写

```
1. 写 c:{chunkId}          块正文
2. 写 v:d / v:s            向量
3. 写 i:t / i:c            索引项
4. 最后写 d:{docId}:ready  就绪标记
```

查询只返回 `ready` 存在的文档。崩溃留下的孤儿数据由后台 GC 按"没有 ready"回收。

### 5.5 存储估算

10 万块（300 字/块），前缀隔离下：

| 数据 | 体积 |
|---|---|
| 块正文 | ~100 MB |
| dense 原始向量 | **400 MB** |
| sparse | 48 MB |
| 倒排 posting | ~96 MB |
| IVF 桶成员 | ~2 MB |
| **合计（IVF-Flat）** | **≈ 650 MB** |
| **合计（切到 IVF-PQ 后）** | **≈ 260 MB**（dense 从 400MB 降到 6.4MB） |

预留 1.5 GB 磁盘（含 compaction 峰值）。

## 6. 索引设计

### 6.1 抽象接口

```cangjie
public enum IndexKind <: Equatable<IndexKind> {
    | BruteForce
    | IvfFlat
    | IvfPq
    // Hnsw 保留占位，本期不实现（见 6.6）
}

public interface VectorIndex {
    func kind(): IndexKind
    func size(): Int64

    // 构建与维护
    func build(samples: Iterator<(Int64, Array<Float32>)>): Unit
    func rebuild(): Unit

    // 增量
    func add(chunkId: Int64, vec: Array<Float32>): Unit
    func remove(chunkId: Int64): Unit

    // 查询
    func search(q: Array<Float32>, topK: Int64): Array<Hit>

    // 持久化
    func flush(): Unit
}
```

关键是把 **粗量化器** 抽成独立对象，这是 IVF-Flat 与 IVF-PQ 能平滑切换的基础：

```cangjie
public class CoarseQuantizer {
    func train(samples: Array<Array<Float32>>, k: Int64): Unit
    func assign(vec: Array<Float32>): Int64
    func nearestClusters(q: Array<Float32>, nprobe: Int64): Array<Int64>
    func centroid(id: Int64): Array<Float32>
}
```

### 6.2 三种实现与选型阈值

| 实现 | 适用规模 | 查询 @10万 | 存储/条 | 增删 | 实现量 |
|---|---|---|---|---|---|
| `BruteForceIndex` | < 2 万 | 27 ms | 4 KB | 极易 | ~100 行 |
| `IvfFlatIndex` | 2 万 ~ 50 万 | 4.2 ms | 4 KB | 易 | ~400 行 |
| `IvfPqIndex` | 50 万 ~ 1000 万 | ~0.7 ms | 64 B（m=64） | 中等 | ~700 行 |

**默认策略**

```
n < 20_000        → BruteForce   （100% 召回，代码最简单）
n < 500_000       → IvfFlat      ← 默认起点
else              → IvfPq
```

阈值可通过初始化参数覆盖，也可以 `policy: fixed` 关掉自动切换。

（原计划中的 `HnswIndex` 已决定不实现，理由见 6.6。）

### 6.3 自动切换机制

用户要求"随数据量增加自动置换索引实现"。实现方式：

```
每次 ingest 结束后检查 n：
  若 n > 当前实现的阈值上限：
    1. 写 {ns}:m:rebuild:target = 目标类型
    2. 后台线程构建新索引（读旧索引 + 双写新结构）
    3. 完成后原子写 {ns}:m:cfg.indexKind = 目标类型
    4. 后台清理旧结构
```

**三个安全约束**

| 约束 | 说明 |
|---|---|
| 读不阻塞 | 重建期间查询继续用旧索引 |
| 写要暂存 | 重建窗口内的新数据进入"增量队列"，切换后回放 |
| 失败可回退 | 切换是单 key 原子写，失败则保持旧索引，不丢数据 |

**保守建议**：自动切换放在"导入会话结束时"触发，而不是每条 add 都检查——避免在导入中途触发重建导致严重的双写开销。

### 6.4 IVF-Flat ↔ IVF-PQ：能不能平滑切换

**结论：能，而且是所有索引切换里最平滑的一对。**

原因：两者共享同一个**粗量化器 + 分桶结构**，只有"桶内怎么编码向量"不同。

```
IVF 索引 = 粗量化器(K 个簇心) + 分桶({ns}:i:c:*) + 桶内编码
             ↑ 完全复用            ↑ 完全复用      ↑ 唯一差异
```

| | IVF-Flat | IVF-PQ |
|---|---|---|
| 桶内存储 | 原始向量 `v:d:`（4×d 字节） | PQ 码 `v:pq:`（m 字节） |
| 距离计算 | 精确点积（1024 次乘加） | ADC 查表（m 次加法） |
| 索引结构的 key | 完全相同 | 完全相同 |

**切换步骤（不需要重新聚类）**

```
1. 复用已有簇心，不重训粗量化器
2. 采样一部分向量的残差，训练 PQ 码本
   （m 个子空间 × 256 码字；m=64, d=1024 → 每子空间 16 维）
3. 全量扫描：算残差 → 编码成 m 字节 → 写 v:pq:{chunkId}
4. 原子切 {ns}:m:cfg.indexKind = IvfPq
5. 验证召回达标后，可选删除 v:d:
```

**平滑性评估**

| 维度 | 评价 |
|---|---|
| 索引结构是否要重建 | ❌ 不需要，分桶完全复用 |
| 是否需要重新聚类 | ❌ 不需要 |
| 一次性转换成本 | 10 万条编码约 1~3 分钟（可后台） |
| 转换期间可否服务 | ✅ 可以，双读旧新 |
| 是否可回滚 | ✅ 保留 `v:d:` 即可回退 |
| 召回影响 | ⚠️ 有损，nprobe 需调大 1.5~2 倍补偿 |

**两个必须注意的点**

1. **PQ 是在残差上做的，不是原始向量上。** 所以编码时必须知道该向量属于哪个簇——这个信息分桶里已经有了，直接复用。
2. **码本会随数据分布漂移失配。** 如果后续数据分布变化大（比如新导入了一个完全不同领域的文档集），需要重训码本并重新编码。建议在 `m:cfg` 里记录训练时的样本统计量，漂移超阈值时告警。

**顺带一个反直觉的收益**：PQ 不只是省存储，**查询也更快**。

- IVF-Flat：3120 候选 × 1024 次乘加 ≈ 4.2 ms
- IVF-PQ：建表 64×256×16 次乘加（约 0.35 ms）+ 3120 × 64 次查表加法（约 0.3 ms）≈ **0.65 ms**

所以数据量上来后切 IVF-PQ 是双赢，只有召回要付代价。

### 6.5 IVF-Flat → HNSW 能平滑切换吗

**不能。**

| | 说明 |
|---|---|
| 结构不同 | HNSW 没有"桶"，是多层图，无法复用 IVF 的分桶 |
| 必须全量重建 | 每个点要重新插入图并连边 |
| 重建耗时 | 10 万条约 2~3 分钟（估算），比 PQ 编码慢 |
| 重建期间 | 只能读旧索引，写入需要队列 |
| 删除行为不同 | IVF 删桶成员即可，HNSW 会破坏图 |

**所以 HNSW 只能作为"一次性重建"路径**，不能像 PQ 那样增量迁移。这也是为什么默认不走 HNSW：一旦上了，后续所有增删都要按图的规则处理。

### 6.6 HNSW vs IVF-PQ：几百万 / 千万量级

#### 量化对比

按现代服务器 CPU（16 核、AVX-512）估算，1024 维点积约 0.1 μs；PQ 查表约 2 ns。

| 规模 | HNSW 内存 | IVF-PQ 内存 | HNSW 延迟 | IVF-PQ 延迟 | 延迟倍数 |
|---|---|---|---|---|---|
| 100 万 | 4.1 GB | **64 MB** | 0.05 ms | 1 ms | 20× |
| 500 万 | 20.6 GB | **320 MB** | 0.06 ms | 2.5 ms | 40× |
| 1000 万 | **41 GB** | **640 MB** | 0.07 ms | 5 ms | 70× |

内存差 **64 倍**，延迟差 **20~70 倍**，方向相反。

#### 关键判断：千万级 HNSW 不是"更快"，是"跑不动"

1000 万条 1024 维向量，HNSW 需要 **41 GB 内存**（40 GB 向量 + 1.3 GB 图）。这个量级下：

- 单机必须配 64 GB 以上内存
- 内存一满就 swap，延迟直接崩到毫秒级甚至秒级，HNSW 的优势瞬间消失
- 而 IVF-PQ 只要 640 MB，任何机器都放得下

**这也是业界的主流选择**：Faiss 对十亿级的官方推荐是 IVF-PQ，DiskANN 也是基于 PQ 的磁盘索引。纯 HNSW 基本只用在千万以下、内存充裕的场景。

HNSW 当然也可以叠加 PQ 压缩（HNSW+PQ），但那就接受了同样的量化损失，图遍历带来的低延迟优势也被压缩后的距离计算稀释——等于绕回了 PQ 的老路。

#### 但真正决定性的是端到端

| 场景 | embedding | 检索（IVF-PQ @100万） | 端到端 |
|---|---|---|---|
| 当前（远程 bge-m3） | 50~200 ms | 1 ms | 51~201 ms |
| 本地 GPU bge-m3 | ~11 ms | 1 ms | ~12 ms |
| 本地 GPU + HNSW | ~11 ms | 0.05 ms | ~11 ms |

即使把 bge-m3 挪到本地 GPU，HNSW 相对 IVF-PQ 也只省下 **不到 1 ms**（约 8%）。

**结论：延迟上的 20~70 倍差距，在端到端里被 embedding 吃掉。**

#### 最终建议：不实现 HNSW

三个理由，按权重排序：

1. **内存代价是反向的**：HNSW 在千万级要 41 GB，IVF-PQ 只要 640 MB。到了真正需要它的规模，它反而成了最大障碍。
2. **延迟优势被端到端淹没**：省 1 ms，占 8%。
3. **实现与运维成本高**：800~1500 行；删除要标记或全量重建；仓颉没有 `PriorityQueue`；召回不达标时难以定位。

**按你的标准（"差很多就都实现"），孤立指标上确实差很多（20~70 倍）；但按端到端看差别可忽略，且内存方向上 HNSW 更差。所以我建议只做 IVF 路线。**

如果将来确实需要极限延迟（比如 QPS 上千的在线服务），正确方向不是手写 HNSW，而是：
- IVF-PQ + 原始向量重排（先粗排 100，再用精确向量重排）
- 或者引入成熟的 C++ 库（但有 NAPI 垫片问题）

**决策记录：首版只实现 `BruteForce` / `IvfFlat` / `IvfPq` 三种，HNSW 不实现。**

## 7. 文档解析：格式范围与工具选型

### 7.1 支持的格式（已定稿）

| 格式 | 处理方式 |
|---|---|
| `docx` `pptx` `xlsx` | pandoc → Markdown |
| `html` `rtf` `epub` `odt` | pandoc → Markdown |
| `tsv` `csv` | pandoc → Markdown 表格 |
| `txt` `md` | **直存** |
| `pdf` | `pdftotext`（主）/ `mutool`（备） |
| **其他**（`doc` `ppt` `xls` `wps` `et` `dps` …） | **不支持**，明确报错 |

**一个必须先说清的前提：pandoc 读不了 PDF。**

查 pandoc 官方 `--list-input-formats`：PDF 只出现在**输出**侧（"PDF → 通过 pdflatex、wkhtmltopdf、weasyprint"），输入格式列表里根本没有 pdf。所以 PDF 必须走 poppler/MuPDF。

**这个取舍的副产品**：不再需要 LibreOffice。依赖从 3~4 个降到 2 个（pandoc + poppler），部署简单很多。

### 7.2 pandoc 调用

```bash
# 统一用 gfm 输出，保留表格和标题层级
pandoc -f docx -t gfm --wrap=none -o out.md in.docx
pandoc -f pptx -t gfm --wrap=none -o out.md in.pptx
pandoc -f xlsx -t gfm --wrap=none -o out.md in.xlsx
pandoc -f html -t gfm --wrap=none -o out.md in.html
pandoc -f rtf  -t gfm --wrap=none -o out.md in.rtf
pandoc -f epub -t gfm --wrap=none -o out.md in.epub
pandoc -f odt  -t gfm --wrap=none -o out.md in.odt
pandoc -f tsv  -t gfm --wrap=none -o out.md in.tsv
pandoc -f csv  -t gfm --wrap=none -o out.md in.csv
```

要点：

- **`--wrap=none`** 必须加，否则 pandoc 会按 72 列硬折行，把正文切碎，直接影响分块质量
- **版本要求**：`pptx` / `xlsx` 读取需要 pandoc **≥ 3.1**；2.x 只能读 docx。不少发行版仓库里还是 2.x，部署时要验证
- xlsx 会转成多个表格，需要保留"哪个 sheet"的信息（可先 `pandoc -f xlsx -t markdown` 看输出结构再决定后处理）
- `csv` / `tsv` 输出统一为 Markdown 表格，与 xlsx 行为一致，不再有"直存 vs 转表格"的形态差异

### 7.3 PDF：pdftotext vs mutool

#### 逐项对比

| 维度 | `pdftotext`（poppler-utils） | `mutool draw`（MuPDF） |
|---|---|---|
| 安装包 | poppler-utils | mupdf-tools |
| 可得性 | 绝大多数发行版预装或一条命令装好 | 需单独安装 |
| 阅读顺序 | **三种模式可选**：默认（PDF 内部顺序）/ `-layout`（物理版面）/ `-raw`（内容流原始顺序） | 自有布局引擎自动重排，**无模式开关** |
| 多栏版面 | `-layout` 多数可用；复杂版面会左右栏交错 | 布局引擎通常更好，但出问题时无法换策略 |
| 连字符断词 | 不处理，`inter-\nesting` 会留在输出里 | `-dehyphenate` 内置 |
| 表格 | `-table` 表格检测（较新版本） | 支持表格检测选项 |
| 结构化输出 | `-bbox` 输出带坐标的 XHTML | `-F stext` 输出 XML（坐标 + 字体 + 字号），信息更全 |
| 文字编码 | 需显式 `-enc UTF-8`，部分系统默认非 UTF-8 | 默认 UTF-8 |
| 页范围 | `-f` / `-l` | `-p 1,3,5` |
| 速度 | 快 | 更快，大文件差距明显 |
| 容错 | 一般 | 更好，对损坏/非规范 PDF 更宽容 |
| 无文本层（扫描件） | 输出空 | 输出空（两者都救不了，需要 OCR） |

#### 优缺点小结

**pdftotext 的优势**：可得性最好；三种模式可选，能针对文档类型换策略；选项丰富；社区资料最多。
**pdftotext 的短板**：复杂多栏会交错；不处理连字符；表格能力弱；编码要显式指定，漏了就出乱码。

**mutool 的优势**：布局引擎质量更好；内置去连字符；速度更快；对损坏文件更宽容；`stext` 结构化输出信息最全。
**mutool 的短板**：要额外装；**没有可选模式**，一旦它的引擎判断错了，你没有退路；行为不如 poppler 透明。

一句话概括：**pdftotext 给你旋钮，mutool 给你更好的默认值。**

#### 建议：主 pdftotext，质量不达标回退 mutool

```
pdftotext -layout -enc UTF-8 in.pdf out.txt
   ↓ 质量检测
不合格 → mutool draw -F txt -dehyphenate -o out.txt in.pdf
   ↓ 仍不合格
判定为不可解析，明确报错
```

#### 自动质量判定

| 信号 | 阈值 | 判定 | 动作 |
|---|---|---|---|
| 每页平均字数 | < 50 | 疑似扫描件 / 无文本层 | **直接失败**，报"需要 OCR" |
| 非可打印字符占比 | > 10% | 字体编码 / ToUnicode 缺失 | **直接失败**，换工具也没用 |
| 平均行长 | < 8 字且行数异常多 | 版面被切碎（多栏交错） | **回退 mutool** |
| 连续重复行 | 出现 ≥ 3 次 | 页眉页脚 | 不换工具，清洗即可 |

**这个区分很重要**：只有"版面问题"值得换工具；"编码问题"和"空白"换工具也救不回来，应该直接失败。盲目回退会让失败变慢，而不是变成功。

### 7.4 其他格式：一律不支持

`doc` / `ppt` / `xls` / `wps` / `et` / `dps` 全部放弃，理由：

| 格式 | 放弃原因 |
|---|---|
| `doc` `ppt` `xls` | OLE2 复合文档 + 各格式私有结构。要支持必须引入 LibreOffice（300 MB+ 依赖），且转换保真度不可控 |
| `wps` `et` `dps` | 金山自有格式，LibreOffice 支持情况因版本而异、资料互相矛盾，无法保证成功率 |

**处理方式**：`kb_ingest` 收到这些扩展名时直接返回明确错误：

```
不支持的格式：.doc
请先用 WPS / Office 另存为 .docx，或导出为 PDF
```

比"转换成功但内容残缺"要好得多——**静默降质比明确失败更危险**，因为用户会以为知识库里已经有了这份文档。

### 7.5 失败处理

| 失败情况 | 检测 | 处理 |
|---|---|---|
| 工具未安装 | 启动时探测 `pandoc --version` / `pdftotext -v` | 该格式标记不可用，ingest 时明确报错 |
| pandoc 版本 < 3.1 | 解析版本号 | pptx/xlsx 禁用，docx 仍可用 |
| 转换超时 | 子进程超时（默认 60 s） | 终止进程，记录失败文件 |
| 输出为空/过短 | 文本长度 < 阈值 | 视为解析失败，不写入索引 |
| PDF 版面质量差 | 见 7.3 判定表 | 回退 mutool，仍差则失败 |
| 扫描版 PDF | 抽出文本近乎空 | 明确报错"需要 OCR"，不静默写入空文档 |
| 不支持的扩展名 | 白名单校验 | 明确报错，提示另存 |

**启动自检**应在服务起来时跑一次，把结果缓成能力表（`{docx: ok, pptx: ok, pdf: ok, ...}`），避免每次 ingest 都探一遍。

### 7.6 解析器接口（不变）

```cangjie
public interface DocumentParser {
    func supports(ext: String): Bool
    func parse(path: String): ParsedDoc
}

public struct ParsedDoc {
    let title: String
    let markdown: String
    let blocks: ArrayList<Block>   // 由 Markdown 解析出标题层级
    let metadata: HashMap<String, String>
}
```

`blocks` 从 pandoc 产出的 Markdown 里解析标题层级（`#` / `##`），保持"按标题分块"的能力。

## 8. 导入管线

```
文件
 ├─▶ 格式识别（扩展名 + magic number 双校验）
 ├─▶ Parser.parse → ParsedDoc(blocks)
 ├─▶ 分块
 │    · 优先按标题层级切（h1/h2 作为边界）
 │    · 长段按 512 字窗口 + 64 字重叠
 │    · 表格行单独成块
 │    · 每块记录 parentDocId + 序号 + 标题路径
 ├─▶ chunkId = hash(docId + 序号 + 正文前 64 字)
 │    （内容不变则 id 不变 → 幂等）
 ├─▶ bge-m3 /embed 批量（32 条/批）→ dense + sparse
 ├─▶ 两阶段写 f_store
 └─▶ 每 500 块 syncWAL()
```

**幂等**：重新导入同一文档时，先按 `d:{docId}` 删掉旧 chunk，再写新的。

**大文档**：单块正文超过 64KB 时按 `c:{chunkId}:{partNo}` 分片。

## 9. 查询流程与性能

### 9.1 流程

```
1. bge-m3 /embed(query) → dense + sparse          （HTTP 50~200 ms）
2. dense 检索：粗量化器取 nprobe 个簇 → 扫桶 → top-100   （0.7~4.2 ms）
3. sparse 检索：前缀拉 posting → 权重累加 → top-100      （2~5 ms）
4. 融合：归一化 + 加权 + 去重                            （< 1 ms）
5. [可选] colbert /score 重排 top-20                    （HTTP ~100 ms）
6. 配额 + 截断 → 返回
```

### 9.2 性能汇总

| 索引类型 | dense 检索 @10万 | 端到端（colbert 关） |
|---|---|---|
| BruteForce | 135 ms | 190~340 ms |
| **IvfFlat** | **4.2 ms** | **57~207 ms** |
| IvfPq | 0.7 ms | 53~203 ms |
| Hnsw | 0.4 ms | 53~203 ms |

**结论：IvfFlat → IvfPq 的 3.5 ms 差异，在端到端里几乎看不出来。** 切 PQ 的主要动机是**存储**（400MB → 6.4MB），不是速度。

这也解释了为什么不需要急着上 HNSW。

### 9.3 导入性能

| 阶段 | 10 万块 |
|---|---|
| 解析（docx/xlsx） | 1~5 分钟 |
| bge-m3 embedding（3125 批） | GPU 约 5 分钟 / CPU 1~3 小时 |
| 向量字节化 + 写 f_store | 2~5 秒 |
| IVF 聚类（256 中心，10 轮） | 约 34 秒 |

**瓶颈全在 embedding，仓颉侧不是瓶颈。**
