## §0 总览与设计原则

**需求**：字节码世界与宿主仓颉闭包的**双向互操作**——① **接收并调用**：字节码/机器码在执行期**接收**宿主仓颉闭包做实参，并在字节码世界内**调用**它（§1–§10）；② **返回并承接**：字节码世界内产生的闭包（内部闭包值 12）**跨桥返回**宿主，由宿主侧承接为可调用包装（CFunc / `JitFunction` 包装实例）并调用（§14；**仅返回方向**——参数方向与存容器仍禁）。

**继承**：M1 全部硬不变式（I1–I8）原样生效——ID 形态（冻结决策 ④：宿主闭包对象同样只以整数 ID 进入字节码世界）、fail-fast（错误写槽即终止）、封闭白名单（本次按 §13.3 规则**扩展**白名单：激活 `CALL_HOST` + 新增 H63，构成 M2 的白名单增量）。

**核心设计决策（本文的支点）**：

> **CALL_HOST 在机器码层面 = "目标运行期确定的 helper 调用"。**
> 转发器 H63 是一个**普通仓颉 helper**（@C 薄入口 + 普通 Cangjie 实现），复用 M1 helper 的全套基础设施：trampoline ABI（`rdi=ctx, rsi=&args, rdx=n, ret rax=cell`）、错误转码写槽、窗口登记、自动尾随 `CHECK_ERR`（I3）、GC/异常/重入边界。

由此，M1 §6 议题清单的八项困难中，①③⑤⑦四项被**机制归一**消解（见 §5/§6），剩余项（②④⑥⑧）由显式语义规则覆盖（§6）。**不引入任何新执行机制**——这是本方案"可行"的根本：需要新写的只有 H63 的仓颉实现体与 Marshal 验签逻辑。

**新增概念一览**：

| 概念 | M1 对应 | 增量 |
|---|---|---|
| HostClosure 类型 | 内部闭包值（token 9 / LocalType 12） | token 10 / LocalType 13（句柄型） |
| 验签 | 无（M1 闭包不跨桥，签名是静态知识） | Marshal 运行期签名核对（§4） |
| 错误码 21 | 99 = 实现缺陷 | 21 = 宿主闭包执行期异常（正常程序流，与 99 语义严格区分） |
| CALL_HOST 激活 | M1 汇编期 `ERR_NOT_IMPL` | 0x79 重定义为 `u8 argc` |
| H63 转发器 | helper 白名单 H01–H62 | +H63 `host_call_trampoline` |
| HostObject（v0.3 增篇） | 宿主自定义类一律 19 拒收（M1 §8.2.1） | token 11 / LocalType 14；引用传递（§11） |
| 成员访问增量（v0.4–v0.5 增篇） | HostObject 仅不透明传递（§11） | 包装模式（零机制）+ 实例字段读写（H64/H65）+ 成员访问语法糖（§12） |
| 逃逸闭包回桥（v0.8.8 增篇） | 内部闭包值 12 仅限 CALL_FUNC 链内（M1 逃逸禁令） | **跨桥返回**（仅返回方向）：原地提升 + 提升组三规则 + 包装器 close / 单元弱语义 19（§14） |

## §1 HostClosure 表示

**运行时表示**：句柄表条目 `{tag=10, cb: HostCallback}`；`HostCallback = {fn: 仓颉函数值, sig: SignatureDescriptor}`。

- `fn` 是**宿主仓颉闭包对象本身**（GC 托管）——句柄表条目持强引用，调用期间对象不可能死亡（与 List/Map pin 同一保活模型，M1 §8.1 决策 ④ 的直接复利：**无需任何"函数指针→稳定地址"的运行时 API**）。
- `sig: SignatureDescriptor` = 参数类型序列 + 返回类型（按 §11.7 LocalType 编码）。由 Marshal 验签（§4）一次性产出并缓存于条目——**CALL_HOST 执行期零验签**。
- **LocalType 13 = HostClosure**（句柄型，空安全规则同 §3.2 M1：恒非 0）。可声明为**参数槽与局部槽**，权限与内部闭包值（12）相同：可赋值、可在 `CALL_FUNC` 链内传递（参数槽 13）、链内返回。
- **不可为常量**：闭包不可序列化（M1 §8.4 已冻结），HostClosure 不新增常量 kind（**kind 11 由 M3 JSON 字面量使用**，见 `jit-bytecode-m3.md`），宿主闭包只能经**桥 Marshal（B 路径）**进入，或在字节码世界内经 `CALL_FUNC` 传递。字节码内**没有构造 HostClosure 的指令**（无 `hostclosure_new`）：它的唯一来源是宿主。

**逃逸边界**（与内部闭包值 12 对称，仅方向相反）：

| 通道 | 内部闭包值（12，M1） | HostClosure（13，M2） |
|---|---|---|
| 跨桥实参（call\<T\>） | ✗（Marshal 无行） | **✓（本文核心）** |
| 跨桥返回 | **✓（§14 增篇，v0.8.8——经提升组；仅返回方向；参数与存容器仍禁）** | **✓（对称）**：解包表 `get` 原样带回仓颉闭包引用——对象本属宿主，零拷贝零转换 |
| 存入容器 | ✗ | ✗（同 M1：窗口重置 → 悬空 ID） |
| CALL_FUNC 链内传递/返回 | ✓ | ✓（参数槽 13 / retType=13） |
| 作常量 | ✗ | ✗ |

> 返回方向一并支持的原因：实现是平凡的（`get` 逆操作），且与实参方向共享全部验签/生命周期机制；只做单向反而造成不对称的认知负担。高阶（闭包的 T/R 又是函数类型）仍禁止，见 §6。**内部闭包（12）的跨桥返回自 v0.8.8 起开放——见 §14（提升组方案）。**

## §2 字节码与格式变更（verMajor 2）

| 项 | M1（verMajor 1，verMinor 7） | M2（verMajor 2，verMinor 0） |
|---|---|---|
| `.fbc` 头 verMajor | 1 | **2**；M1 加载器遇 verMajor 2 → 加载期拒绝（18）；M2 加载器兼容 verMajor 1（按 verMajor 分派校验规则集） |
| LocalType | 0–12 | **+13 = HostClosure、+14 = HostObject**（均句柄型；**15–255** 仍拒绝——12 内部闭包、13 宿主闭包、14 不透明宿主对象均有定义） |
| 类型 token | 1–9 | **+10 = HostClosure、+11 = HostObject**（`IS_TYPE/GUARD_TYPE/H19` 与句柄槽 `tag` 可用） |
| `CALL_HOST`（0x79） | 汇编期 `ERR_NOT_IMPL`（M1 从未产出该 opcode——重定义不破坏任何 M1 产物） | 操作数 **`u8 argc`**（M1 预留的 `u16 fid` 编码废弃——fid 形态属第一档"编译期注册回调"，本文范围外），栈布局 `[h_fn, a1..an]`；`CAT_CALL` |
| 错误码 | 0–20 / -1 / -2 / 99 | **+21 `ERR_HOST_CALLBACK`**：宿主闭包执行期抛出异常且未回译；`cause` 附原始异常描述（与 99 的 cause 通道同构，M1 §8.2.3）；`site` = `CALL_HOST` 指令的字节码偏移（定位到调用点） |
| 19 `ERR_CALL_CONTRACT` | 参数长度/元素类型/返回 T 不符/调用已卸载单元 | **+验签失败**（§4，site=-1） |

**不变项**：ctx 布局（64 B 整数标量）、帧布局（§3.1）、全部 M1 指令语义、fail-fast（I3/I4）、窗口与逃逸机制（§8.1/§9.6）、W^X 与 IBT（§12.3）。

## §3 前端语言面

**类型记法**：参数/局部可声明函数类型 `name: (T1, T2) -> R`——T/R ∈ LocalType 0–8/10–11（9=Regex 与 **12/13 函数类型均不合法**）；**禁高阶**（冻结，沿 M1 §8.6 决策）：T/R 不得为函数类型——高阶链属第三档（§10）。无参形式 `() -> R`。（注意区分：**JIT 函数自身的参数槽**可以是 13——这是本文核心；受禁的是"闭包签名的 T/R 为函数类型"。）

**调用解析**（M1 §8.4 名字解析顺序的扩展）：

```
recursive → user helper（静态 hid，§8.4）→ HostClosure 形参/局部（静态类型驱动）→ 未定义异常
```

HostClosure 分支按**声明类型**静态判定（编译期已知是 13 型 ⇒ 发射 CALL_HOST 而非 CALL_CLOSURE/CALL_FUNC）——无运行期查找。

**边界（沿 M1 形参遮蔽规则）**：HostClosure 形参/局部与已注册 user helper **同名** → **编译错误**（禁止静默择一；M1 T23"形参遮蔽调用 → 拒绝"先例的扩展）；上述解析顺序仅在无名字冲突时生效。

**降低**：`fn(a1, a2)` = 实参表达式从左到右入栈 → `LOADL fn`（句柄压栈底）→ `CALL_HOST 2` + 汇编器自动尾随 `CHECK_ERR`（I3）。与内部闭包调用（`LOADL 0` + `CALL_CLOSURE`）完全平行。

**实参来源封闭**：HostClosure 值只能来自桥 Marshal（宿主传入）或 `CALL_FUNC` 链内传递——字节码内不可构造。因此"闭包从哪来"的答案永远是宿主代码，字节码世界对它是**纯消费者**。

## §4 Marshal 与验签（§8.2.1 的 M2 行）

**Marshal 表新增行**：

| 签名参数类型 | 接受的 `Any` 实际类型 | 转换 | 失败 |
|---|---|---|---|
| `(T1..Tn) -> R`（HostClosure） | 仓颉函数值 | **运行期验签**（下）→ 回调表登记（`pin` 路径 B，tag=10）→ ID | 19 |

**验签流程**（Marshal 时一次性执行，产物缓存）：

1. **函数类型判定**：仓颉函数类型是类型系统一等公民，`is` 对函数类型按 std 语义判定（实现前提 P1，见 §9.1）；不是函数值 → 19。
2. **参数个数**核对（与声明签名逐位一致）→ 不符 → 19。
3. **逐参类型**核对（T1..Tn）→ 不符 → 19。
4. **返回类型**核对（R）→ 不符 → 19。
5. 产出 `SignatureDescriptor` 存入句柄条目；**禁高阶复检**（R 不得为函数类型）→ 违反 → 19。

**解包表新增行（返回方向，对称）**：

| 签名返回类型 | 解包 | T 校验 |
|---|---|---|
| `(T1..Tn) -> R` | `get` → 原样返回仓颉闭包引用 | `T` == 对应函数类型 |

**生命周期**：HostClosure 条目属 **B pin 路径**（M1 §8.1）——调用结束随 try/finally 清理释放（§8.2 M1 既有机制，零新逻辑）；CALL_FUNC 链内传递期间由被调帧窗口存活（同参数槽 12 规则）。**单元卸载（M1 §8.7）无交互**：HostClosure 是 per-call 资产，不挂单元。

## §5 CALL_HOST 执行语义（H63 转发器）

**lowering**：与 `CALL_HELPER` 同款——`call H63` + 自动 `CHECK_ERR`。机器码无任何新模式（I8 自动满足）。

**H63 `host_call_trampoline`**：普通仓颉 helper（@C 薄入口；三引擎共用同一实现 → I7 结构性成立）。执行流程：

```
1. fetch 栈底句柄 → HostCallback{fn, sig}          // tag≠10 → 8（类型不符）
2. 按 sig 逐参 cell → 仓颉值                        // 句柄型 get / 值型原值（解释性 marshal）
3. 调用 fn（普通仓颉调用）
     ├─ 可能触发 GC      → 与 M1 helper 同一边界（§6）
     ├─ 可能抛出仓颉异常 → catch-all → 21 + cause     // fail-fast：写槽返回，CHECK_ERR 短路
     └─ 可能重入 JIT     → 合法，见下
4. 返回值 → cell
     └─ R 为引用型 → 窗口登记新槽（分配型语义：登记 1 槽；R 编译期已知，§9.6）
     └─ R 为值型   → 原值返回，不登记
```

**与 user helper（§8.4）的关系：并存，按需选择**：

| | user helper | HostClosure + CALL_HOST |
|---|---|---|
| 目标确定时机 | 编译期（注册表静态 hid） | 运行期（每次调用的实参） |
| 验签 | 无（注册时签名即契约） | Marshal 时一次性 |
| 调用开销 | 零间址（静态 trampoline） | fetch + 描述符遍历（§8） |
| 适用 | 目标编译期已知 | 目标按次调用不同（回调/策略注入） |

**重入语义（冻结）**：宿主闭包体内调用 JIT 产物**合法**——走正常 `call` 路径开**新 ctx**（M1 §9.7：ctx 随调用栈分配、各调用窗口 `[hwBase, hwTop)` 互不重叠、句柄表槽追加有同步保护）。嵌套调用是**独立事务**：独立 errCode/site/fnId/窗口，内层 fail-fast 不影响外层错误槽；深度受宿主线程栈限制（同自递归，M1 §8.0）。实现者须知：桥的重入路径 = 既有 `call` 代码本身，无新机制，但**测试必须覆盖**（T31）。

**取消边界**（沿 M1 §8.3）：宿主闭包执行期间不可中断（-2 仅 `LOOP_BACK` 回边产生）；`CALL_HOST` 点不设安全点——取消感知延迟上界 = 闭包剩余执行时长。已在 M1 成文的边界，本文引用不重复论证。

## §6 安全模型（继承 + 增量）

| 机制 | 语义 |
|---|---|
| **deopt** | 含 `CALL_HOST` 的函数 → `FuncEntry.flags.bit0`（被调闭包体静态不可知，黑盒——与 `CALL_CLOSURE`/预定义 helper 同一 §9.15 模式）→ **deopt 源汇编期禁令**；运行期防御性 -1 → 99 不重放。宿主闭包的副作用（若有）绝不会被重放重复执行 |
| **纯度** | 宿主闭包副作用黑盒；"可重复调用结果一致"的前提 = 闭包自身行为确定——**注册者自担**（§8.4 既有原则的延伸：宿主向 JIT 世界提供什么行为，责任在宿主侧） |
| **fail-fast** | 21 写槽即终止本次调用，经 `CHECK_ERR → BAIL` 收敛 epilogue（I3/I4 原样）；宿主闭包异常不穿越机器码（helper 边界"绝不抛出"合同原样适用） |
| **GC** | 转发器是仓颉函数——内部分配可触发 GC、GC 栈扫描穿过 JIT 帧 = **M1 helper 已接受并已文档化的同一边界**（保守扫描 + 窗口强引用保活）；闭包对象由句柄条目持强引用，调用期间恒存活。无新边界，仅需测试覆盖（T32） |
| **W^X / IBT** | H63 是编译期静态布局的机器码入口（单元 code buffer 内），`endbr64` ✓；无运行期代码页修改 ✓ |
| **卸载** | 无交互（§4）；单元资产（含 H63 机器码）按 M1 §8.7 正常回收 |
| **禁高阶** | 双重强制：前端声明处编译期拒绝（§3）+ Marshal 验签复检（§4）；运行期无高阶链 ⇒ 签名描述符深度恒 1 |

**八项困难 × 本文消解方式**（对照 M1 §6 议题清单）：

| # | 困难 | 消解 |
|---|---|---|
| ① 调用通道缺位 | CALL_HOST 激活 + H63 转发器（复用 helper 全套机制） |
| ② 静态性丧失 | 静态性**下沉到类型层**：调用点按声明类型静态发射；运行期只有一次表取值（无需运行期回调注册表——句柄表即回调表） |
| ③ 签名校验/禁高阶 | Marshal 一次性验签 + 缓存；禁高阶双重强制（§4） |
| ④ 输入等价性 | 差分口径改列"转发语义一致"（§7）；纯度责任划归注册者（§8.4 原则） |
| ⑤ 异常语义错位 | 独立错误码 21（业务异常 ≠ 99 实现缺陷）+ cause 通道 |
| ⑥ 重入 | 合法化 + 独立事务语义（§5）；机制零新增（ctx 每调用独立已是 M1 §9.7 现状） |
| ⑦ GC 栈边界 | 归一为 M1 既有 helper 边界（无新边界） |
| ⑧ 序列化 | HostClosure 不入 `.fbc`（不可为常量，§1）——分发世界零交互 |

## §7 三引擎一致性（I7）

- H63 为**共用仓颉实现**；转发序列（取参顺序、逐参转换、错误转码、返回登记）确定且单实现 ⇒ 三引擎行为**结构性一致**（与 M1 helper 的 I7 论证同构）。
- **差分测试口径**：黄金基准由测试用例提供的**确定性宿主闭包**充当（同 M1 T23 对 user helper 的做法）；断言 = 结果/错误码/site 三引擎逐位一致。宿主闭包自身的非确定行为不在 JIT 的证明义务内（注册者自担）。

## §8 性能

- 每次调用成本：句柄 fetch + 描述符遍历逐参转换（解释性）+ 一次仓颉间接调用——估算为 user helper 调用的 1.5–3×（转换参数越多越接近上限）。
- **M2.1 优化展望**（不在本文）：验签后按 `SignatureDescriptor` 缓存 **per-signature 特化 trampoline**（消除描述符遍历）；热路径单态化。正确性优先，特化不得改变可观察语义（差分同 T30–T36）。
- **窗口登记**：CALL_HOST 返回引用型时登记 1 槽（R 编译期已知）——§9.6 初始容量（默认 128）、扩容兜底照旧。

## §11 不透明宿主对象通道（HostObject，v0.3 增篇）

**需求与定位**：宿主仓颉 **class** 实例以**不透明载荷**方式进出字节码世界——**仅在仓颉侧声明**、仅含**公共实例成员变量**、**仅用来传递数据**：字节码对它的全部能力 = 持有、转发、返回；**零字段访问、零构造、零方法调用、零比较，从不解引用**（**v0.4 增篇 §12** 在此基线上开放实例字段读写——仍经 helper 受控访问，机器码零解引用（I2）不变；方法与属性访问经 §12.1 宿主包装模式）。典型用途：宿主把 DTO/上下文对象交给编译函数转发给宿主注册函数（§8.4），或经返回值带回。

**为什么选 class（设计理由）**：① **引用语义** ⇒ 传递零拷贝 O(1)、`Any` 通道免装箱（对照方案：struct 需 copy-on-mutate 应对值语义、每次字段写占 1 槽并撞"窗口只增不减"的 16 压力，且在不透明前提下同样无收益）；② 字节码零解引用 ⇒ 无值语义映射、无成员逃逸规则、无 §9.15 耦合；③ 未来透明化（字段访问）时，class 引用语义使"原地变更"语义自然（变更型 helper/§9.15 模式现成），无值语义障碍——本通道是可持续升级的底座。

**类型与表示**：

- token 11 = HostObject；LocalType 14 = HostObject（句柄型，恒非空，§3.2 空安全规则同）。
- 条目 `{tag=11, obj: 宿主类实例引用}`——与 List/Map 同款"引用保活"模型；pin 语义照 §8.1（同表内同对象复用同 ID——class 有对象身份，本语义自然成立）。
- **宿主纪律（规范要求；桥不机械校验，沿 §8.4"准入责任自担"原则）**：通道所用类须为**纯数据类**（仅公共实例成员变量）——① 字段读写增量（§12.2）与后续透明化路径依赖该约定；② 传递共享语义可预测。

**能力面（冻结）**：

| 能力 | 支持 | 说明 |
|---|---|---|
| 推断局部（`let o = hostFn()`，LocalType 14） | ✓ | 类型从预定义调用结果推断（沿 `let fn = {…}` 推断先例） |
| 预定义函数（§8.4）参数 / 返回 | ✓ | 签名编码扩展：14 型槽的具体类 = 注册时提供的 Cangjie 类型（静态知识外置，List 元素类型同款模式） |
| 作为实参转发给另一预定义函数 | ✓ | 本通道核心用途 |
| JIT 函数返回值（retType=14） | ✓ | `call<User>` 交付：解包表 get → 宿主类实例引用；`T` 校验由 call\<T\> 单态化适配器承担（T = 具体类） |
| 实例字段读写 | △（v0.4 起，§12.2） | get_field/set_field（H64/H65，变更型路由复用 §9.15）；本表其余行为为基线 |
| 构造 / `==` | ✗ | 构造与 `==` 不开放；方法/属性经 §12.1 包装模式；实例成员直接语法见 §12.4（v0.5） |
| 常量化 | ✗ | 宿主类型不可序列化（同 HostClosure，§1） |
| `call<T>` 实参方向（源入口形参） | ✗（本基线） | 需宿主类型注册表；列入 §13 |
| CALL_FUNC 跨函数形参（参数槽 14） | ✗（本基线） | 需源语言 opaque 形参语法；列入 §13 |

**Marshal 与边界校验**：

- 解包表（§8.2.2）新增行：`retType=14 → get → 宿主类实例引用`（引用原样返回，零拷贝）。
- **边界型别校验（本通道唯一新增校验点）**：预定义调用转发前，桥核对 `fetch(id).obj is <注册签名中的声明类>` → 不符 → 19；沿用 §4 验签的"静态知识外置 + 边界一次性核对"模式。
- **null 策略**：pin/交付遇 null → 19（与句柄恒非空不变式一致，§3.2）。
- **实施注记**：M1 §8.2.1"不接受的对象类型（无类型 token，如宿主自定义类）→ 19"行在 M2 实施时更新为——**经本通道接受的宿主类实例例外（token 11）**；其余对象仍 19。

**生命周期与安全（全部继承既有机制，零增量）**：

- 句柄路径：B pin / C 窗口（预定义结果 wrap 为分配型语义）/ D 逃逸——try/finally 清理（§8.2）、保活矩阵与逃逸规则（§8.1）照旧。
- deopt：字节码零解引用、零副作用 ⇒ 重放安全；不触发 flags.bit0（除既有 §6 CALL_HOST 规则）。
- GC：条目强引用保活 ✓；并发：宿主在调用期间不得并发修改被传递的共享对象（§8.3 只读契约精神；字节码侧零风险）。
- 卸载（§8.7）：句柄为 per-call/窗口资产、无常量——无交互。

**性能**：传递 O(1)（引用拷贝）、`Any` 通道零装箱、无任何载荷拷贝；JIT 执行层与既有句柄型零差异。

**测试**：T34（§10）。

## §12 成员访问增量（v0.4–v0.5 增篇）：包装用法模式 · 实例字段读写 · 成员访问语法糖

**定位**：在 §11 不透明通道之上推进两步——**第 0 步**（零规范变更）：方法/属性/静态成员的"宿主包装"用法模式（今天即可用）；**第 1 步**（小增量）：实例字段**直接读写**（H64/H65 + 字段表注册；写入走 §9.15 变更型既有路由）。**排除项冻结**（§12.3）。

### §12.1 第 0 步：宿主包装用法模式（零机制变更）

成员访问按"**包装为预定义函数**"（§8.4）表达——M1/M2 无任何格式或 helper 变更：

| 成员 | 包装方式（宿主注册） | JIT 源示例 |
|---|---|---|
| 实例方法 `u.save(t)` | `(User, String) -> Unit`，实现体调用 `u.save(t)` | `save(u, "v1")` |
| 实例只读 prop / `let` `u.name` | `(User) -> String`（getter） | `name(u)` |
| 实例 `mut prop` 读 / 写 | `(User) -> Int64` + `(User, Int64) -> Unit` | `age(u)` / `setAge(u, 18)` |
| 静态方法 `User.parse(s)` | `(String) -> User`（可返回 HostObject，retType=14） | `parse(s)` |
| 静态 `let` / 只读 prop `User.version` | `() -> Int64`（纯读） | `version()` |
| 静态 `var` / `mut prop` | **不提供包装指引——冻结排除**（§12.3） | —— |

规则（全部继承既有机制）：

- 传参/返回 HostObject 走 §11 通道；返回值属宿主类 → retType=14 ✓
- 含此类调用 → 黑盒 → 函数 `flags.bit0` + deopt 源禁令（§9.15：预定义 helper 同一判定）；
- **异常语义指引**：预定义通道内未捕获异常 → 99 + cause（M1 T23 现状）；如需"业务异常"语义（21，CALL_HOST 通道），改用 HostClosure 表达（§5），或包装体内以返回值表达业务失败——两通道不对称的适用性见 §13 开放问题 ⑥。

### §12.2 第 1 步：实例字段读写（小增量）

**前提：字段表注册（新增最小注册协议）**

- 宿主向 `Compiler` 注册类的字段表（快照语义同 §8.4）：`PublicField(name: String, type: LocalType, index: UInt16, mutable: Bool, typeRef: ?String)` × n（`mutable` = Cangjie `var`/`let` 标志；`typeRef` = 14 型字段的目标类名——供语法糖的类型解析与链式访问，§12.4）；
- 字段类型范围：LocalType **0–8、10–14**（9=Regex 排除——M1"仅常量"约束未解除）；具体类/元素类型为宿主静态知识（外置，§11 模式）；
- 编译期：字段名 → `index` 解析在前端完成（访问未注册类的字段 → 编译错误）；**字节码只见 index 与类型码**。

**helper（M2 实施时登记，编号接 H63）**：

| H | 名称 | 签名 | 语义 | 失败 |
|---|---|---|---|---|
| H64 | `host_get_field` | `(obj, i64 index) → cell` | 读字段：值型直取原值；**句柄型 marshal 为句柄**（对宿主对象做 pin 语义 ⇒ **对句柄型字段为条件分配型**——窗口登记 1 槽；值型不登记，编译期由字段类型可判） | 8, 99 |
| H65 | `host_set_field` | `(obj, i64 index, cell) → 0` | 写字段（**变更型**）：值型直存；句柄型 fetch 后存对象引用；**防御性 `mutable` 校验 → 19**（v0.5；语法糖编译期为主防线，§12.4） | 8, 19, 99 |

- **变更型路由（§9.15 全规则原样适用）**：① 常量禁写——HostObject 不可常量化（§11）⇒ 自然满足；② **deopt 禁令**——含 H65 的函数禁止全部 deopt 源（汇编期；§7 校验 11 触发清单 + `host_set_field`）→ `flags.bit0`；③ 防御兜底——防御性 -1 → 99。
- **语义正确性**：class 引用语义 ⇒ **原地变更即正确**（§11 选型动因兑现——无值语义障碍）；写入对宿主可见（同一对象，调用返回后宿主观测到修改）。
- **可重复性口径**：对象状态属"输入"前提（§9.15 既有口径）——"同输入同输出"以"输入对象状态相同"为准；宿主并发修改纪律照 §11（§8.3 精神）。
- **读的语义**：值型字段读 = 纯读（确定性）；句柄型字段读 = 对对象**引用**的 pin（宿主对象图不受影响；句柄在窗口/逃逸机制下管理，照 §8.1）。
- **防御**：obj tag≠11 → 8（既有 fetch 语义）；字段 index/类型由注册表 + 前端双重校验，运行期防御命中（理论不可达）→ 99。

**降级糖**：实例成员直接语法 `u.f` / `u.f = v` / `u.m()` 已立 **§12.4（v0.5）**——降级到本篇 helper 与 §12.1 包装调用，语义零新增。

### §12.3 排除项（冻结）

| 成员 | 处置 | 理由 |
|---|---|---|
| `static var` / `static mut prop` | **不做**（永久排除该形态的**访问**） | **隐藏全局态不属于调用输入**——违反纯度约束（§8.3"helper 读写跨调用可见的可变态 → 破坏可重复调用结果一致"）、使差分测试黄金基准失效，且跨线程天然共享（**完整论证：附 B**） |
| `public static let` / 只读 prop | ✓ 经 §12.1 包装可用 | 初始化后不变 ≡ 常量语义（纯读无代价） |
| 构造 / `==` | 不开放 | 非"传递 + 访问"必需；维持 §11 基线的数据胶囊语义边界 |

### §12.4 第 2 步：成员访问语法糖（v0.5）

**定位**：把 §12.1 包装模式与 §12.2 字段读写**降级为直接语法**——`u.f`（读）、`u.f = v`（写）、`u.m(args)`（调）。**语义零新增**：每种糖都有既定的等价手写形式（降级表），差分测试断言"**糖路径 ≡ 手写路径**"。**依赖：类注册表最小子集**——即 §13 开放问题 5①"完整宿主类型注册表"的**成员解析部分**（继承解析、opaque 形参、`call<T>` 实参方向仍留后续）。

**类注册表（最小形态；Compiler 实例内，快照语义同 §8.4）**：

```
registerClass(desc: ClassDescriptor)
ClassDescriptor { name: String, fields: [PublicField], methods: [PublicMethod] }
PublicField  { name, type: LocalType, index: UInt16, mutable: Bool, typeRef: ?String }  // §12.2（v0.5 扩展）
PublicMethod { name: String, bind: PredefinedFunction }  // 首参固定为该类：签名 (C, T…) -> R
```

- **方法表**：`u.m(a…)` 绑定到注册的预定义函数（首参 = 宿主对象）——`bind` 即 §12.1 包装模式的**显式登记**，不新设调用机制；
- **字段解析**：`u.f` 查 §12.2 字段表（name → index/type/mutable）；14 型字段的 `typeRef` 支撑链式解析（`u.a.b`）；
- **类型跟踪（前端）**：HostObject 表达式携带"具体类"静态知识（沿 List 元素类型外置模式）——来源：预定义调用结果的注册签名、字段 `typeRef`、局部推断；与 §11 边界校验互为**双重**（前端静态匹配 → 编译期错误；运行期防御不变）。

**语法与求值（冻结）**：

- `.` 仅接成员标识符；**仅对静态已知为某注册类**的 14 型表达式合法（其余 → 编译错误）；词法按 "`. + 标识符`" 识别（与数字字面量点号消歧；`.` 此前未使用，不影响既有文法）；
- **求值顺序：左到右**（`u.m(a1,a2)`：u → a1 → a2；`u.f = v`：u → v）——与 M1 调用实参/多重赋值口径一致；
- 链式与嵌套：`u.a.b`、`u.m().f` 合法（每层类型由注册表/签名提供）；13 型字段读取后按既有闭包调用语法使用（签名外置，不受影响）；
- **静态成员不参与语法糖**（`User.version` 经 §12.1 包装函数）；**继承成员不解析**（仅本类声明成员；未注册基类成员 → 编译错误）。

**降级表（糖 ≡ 手写，语义零新增）**：

| 糖 | 降级 | 备注 |
|---|---|---|
| `u.f`（值型字段） | `get_field(u, idx)`（H64） | 纯读、零登记 |
| `u.f`（句柄型 / 14 / 13 字段） | `get_field(u, idx)` | 条件分配型（§12.2） |
| `u.f = v`（`var` 字段） | `set_field(u, idx, v)`（H65） | 变更型全路由（§9.15）+ 含它函数 deopt 禁令 |
| `u.f = v`（`let` 字段） | **编译错误**（`mutable=false`）；裸 H65 防御 → 19 | 双防线（v0.5） |
| `u.m(a…)` | 预定义调用 `m(u, a…)`（§12.1 包装，hid 由方法表解析） | 同一路径；黑盒判定不变 |

**编译期拒绝集（错误消息含类名/成员名）**：对非 HostObject 表达式用 `.`；未注册类；未知字段/方法；`let` 字段写；方法签名实参不匹配（静态签名已知）。

**测试**：T36（§10）。

## §14 逃逸闭包回桥——返回嵌套闭包（v0.8.8 增篇）

**定位**：内部闭包值（LocalType 12 / token 9）**跨桥返回**——宿主侧承接为可调用包装（CFunc / `JitFunction` 包装实例）。与 §0 主线（宿主闭包进字节码，13）方向相反、机制对偶，补齐"完整双向互操作"的**回程轴**；与"高阶"（函数类型作 T/R 传递）保持独立。**开放范围仅"跨桥返回"方向——跨桥实参（参数 Marshal 表）与存容器维持禁止**。

**路线定稿**：(a) **原地提升**（三选一对比后定稿——与 M1 机制最同构；备选 (b) 真引用重挂 / (区间 + 改址) 留档于 §14.3 末）。

### §14.1 提升机制（核心动作）

交付边界（unbox，**执行完成之后、窗口重置之前**），桥对「闭包自身槽 + 全部句柄型捕获所指数组」执行 **D 路径式原地提升**（M1 §8.1 规则 1 从"一个返回槽"推广为"提升组"）：**迁出窗口记账、表项保留、ID 不变、gen 不变、不参与任何后续分配重用**。

- **不复制、不改址**：编号不变 ⇒ 一切已分发副本自动续命、无"同对象两编号"分叉；`LOAD_CAP` 语义零变化；提升时机与 deopt 重放正交。
- **捕获描述符**：哪些捕获为句柄型由前端**静态捕获描述符**给出（同"签名是静态知识"模式）。

### §14.2 提升组三规则

1. **清单与幂等**：桥为每个逃逸闭包记录**提升组清单**（闭包槽 + 捕获槽）；重复提升（多闭包共享捕获）幂等、计数 +1；
2. **释放链**：释放 = `close(包装器)` 遍历清单计数 −1、归零释放（gen +1 可复用）——**调用 try/finally 清理豁免提升槽**（唯一释放路径 = close）；
3. **常量不入组**：**路径 A 常量槽不入组、不释放**（释放点仅单元卸载）。

### §14.3 宿主承接与包装器

- **返回解包表（M1 §8.2.2）开放 Closure 行**——解包为宿主值 **CFunc**（承接逃逸闭包 ID）；**参数 Marshal 表（M1 §8.2.1）不加行**——实参方向不开放；

## 附 B：`static var` / `static mut prop` 排除理由（冻结依据）

**结论**：`static var` 与 `static mut prop` 的**访问**永久排除（§12.3）；`static let` / 只读 prop 不受影响（经 §12.1 包装可用）。**这不是实现性问题**——static 访问与实例访问的实现难度相同（helper 读类型元数据即可）。排除是**契约纪律**的选择，依据按破坏深度排列：

**① "可重复调用"的输入等价性无法定义（根本原因）。** M1 的口径：可重复调用结果一致，以"输入对象状态相同"为前提（§9.15）。实例字段的状态**就是输入的一部分**——对象是调用者交进来的东西，两次调用给它同一对象状态即可复现。静态状态不属于任何输入：同一份参数、同一份对象状态下，两次调用可因隐藏全局态而结果不同——且该状态**不可枚举、不可快照**（任何宿主代码都能修改它）。一句话：**instance 写 = 修改输入；static 写 = 修改"世界"**——前者有等价性可言，后者没有。

**② 差分测试黄金基准失效 + 三引擎串扰。** T2 的口径是"同一 `.fbc` + 同一输入 → 三引擎逐位相等"。静态状态使"同一输入"失去定义；更直接的是——三引擎在同一进程内并行跑差分时，一个引擎的执行改变静态变量会**串扰**另两个引擎的结果，直接破坏并行差分。

**③ 并发纪律无从落实。** 实例对象至少可以约定"同一对象别并发碰"（§8.3 精神——可操作的纪律）；static 是**进程级共享单例**：任何线程都能经任何路径碰到它，"别并发碰"这条纪律连表述都做不到。与 §9.7 线程模型（各调用窗口独立、禁止跨线程共享写）直接冲突。

**④ 隐式非确定性侵蚀体系纪律。** user helper（§8.4）允许副作用——因为它是**显式扩展点**：注册表一眼可见，注册者按"准入责任自担"明确承接非确定性。而 static 访问藏在"看起来像普通字段读取"的语法背后，**把非确定来源伪装成普通数据**——"读个静态变量而已"的误认会侵蚀封闭白名单体系的纪律。这是体系性坏味道，不是单个功能的取舍。

**对照（为什么 `static let` / 只读 prop 放行）**：初始化后不变 ≡ 常量语义 ≡ 纯读确定——不触碰上述任何一条。

**安全替代路径（推荐序）**：

1. **状态放进 HostObject 实例字段**——状态随对象成为输入的一部分（可重复性/差分/并发纪律全部有解）；
2. **必须用显式非确定状态 → 经 user helper 显式包装**（§8.4：显式注册、责任自担——"要非确定性就明说"）；
3. **值恒定 → 注册时注入**（等价 `static let` 语义）。

**重议条件（三者缺一不可）**：若未来确需重议，必须同时满足——① 静态状态集合**可枚举且可快照/复位**（测试框架能构造"同输入"）；② 给出全局共享可变状态的**并发纪律**；③ 以"注册制静态访问描述符"**显式化**（而非普通成员语法），消除隐式性。满足后方可作为独立增量重新立项。
