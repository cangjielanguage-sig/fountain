## 发现

### [一般][存量] 同一个模块里并存两套配置生效语义，且都没有在 README 层面统一说明

- **位置**：`f_llm/src/config/LLMConfig.cj:48-102`（每次调用都 `Config.getValue` / `Config.getString`，即**逐次读取**）、`f_llm/src/llm/LLMConfsHolder.cj:73-76`（DB 快照，首次访问装载 + 60s 惰性 TTL 刷新，刷新失败保留旧快照）
- **来源**：存量（快照模式无基线）
- **判据**：review-checklist §11（契约一致性）、§14（配置项语义可理解性）
- **证据**：静态确定 —— 一类配置（`llm_auto`、`llm_channels`、`llm_confRefreshSeconds` 等）通过 `f_config` 每次现取；另一类（模型/渠道配置）由 `LLMConfsHolder` 持有快照并按 TTL 整体替换；两类都不在启动期一次性冻结
- **描述**：运维改 `f_config` 的值可以立刻影响下一次 `LLMConfig.getX()`，但改数据库里的模型配置要等最多 60s 且只在「下一次访问」时生效；反过来，有些 f_config 项（如 `llm_confRefreshSeconds` 自己）改了只影响后续的 TTL 判定。三套时机（立即 / 惰性 TTL / 下次访问）叠加，文档若没写清，排障时会出现「改了没生效 / 生效了但另一半没生效」
- **建议**：在 README 里给出一张「配置项 → 生效时机」表；或在 `LLMConfig` 顶部注明「逐次读取、无缓存」这一事实

### [一般][存量] `EmailChannel` 的附件落盘命名靠「逐个 exists 探测」，目录条目多时退化为 O(n²)

- **位置**：`f_llm/src/channel/EmailChannel.cj:125-142`（`while (true) { candidate = '${stem}-${index}${ext}'; if (!exists(...)) return candidate; index++ }`）
- **来源**：存量
- **判据**：review-checklist §6.4（低效算法）、§11（边界）
- **证据**：静态确定 —— 每个候选名都发一次 `exists` 系统调用；同名文件已存在 N 个时要发 N 次，批量收邮件时是 O(总文件数 × 单目录探测次数)
- **描述**：收件目录里同名附件积累到几千个时，每封邮件都要扫几千次 `stat`；`index` 是 `Int64`，实际不会溢出，但探测成本随目录规模线性上升且没有上限（目录不清理就一直涨）
- **建议**：改用「时间戳/UUID + 原名」命名，或一次性 `list` 目录建集合再自增

### [一般][存量] `close()` 静默吞掉客户端关闭失败

- **位置**：`f_llm/src/channel/EmailChannel.cj:376-383`、`f_llm/src/balance/BalanceUnits.cj:44`
- **来源**：存量
- **判据**：review-checklist §3（静默吞异常）
- **证据**：静态确定 —— `try { value.close() } catch (_: Exception) {}` 后立刻 `client = None`
- **描述**：SMTP/IMAP 连接关闭失败（服务端已断、TLS 关闭异常）时无痕迹，连接泄漏只能靠抓包或服务端日志发现；对一个「周期性收发邮件」的渠道，泄漏会累积到 fd 上限
- **建议**：`catch` 里 `warn` 一条带渠道名的日志

### [轻微][存量] `LLMConfsHolder` 的刷新失败只保留旧快照，缺少「快照年龄」指标

- **位置**：`f_llm/src/llm/LLMConfsHolder.cj:73-76`（注释声明的语义）
- **来源**：存量
- **判据**：review-checklist §11（可观测性）
- **证据**：静态确定 —— 刷新失败保留旧快照并记 error，但没有对外暴露「当前快照装载时间 / 连续失败次数」
- **描述**：DB 长时间不可用时，服务会一直用旧模型配置跑，日志里只有一串 error；运维无法判断「当前生效的是哪一版配置」
- **建议**：暴露 `snapshotAge` / `refreshFailures` 两个计数器

## 总评

本轮只抽查了 4 个文件，**不能代表 368 个 .cj 的整体质量**。就看到的这几处：配置语义是最大的隐患（三套生效时机并存且没有一张总表），邮件渠道的附件命名在目录变大后会退化。`LLMConfsHolder` 的设计（整体替换快照、在途请求继续用旧快照、刷新失败保留旧值）是正确的并发取舍。存量 4 条（一般 3 / 轻微 1），是否纳入修复待用户决定。
