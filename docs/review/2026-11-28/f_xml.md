## 发现

### [一般][存量] 实体溢出文件（spill）的删除失败被静默吞掉，异常退出时无人清理

- **位置**：`f_xml/src/ExpandSink.cj:252-269`（`close()` 里 `try { removeIfExists(path) } catch (_: Exception) {}`）、`f_xml/src/ExpandSink.cj:371-384`（公开 `close()` 同型）
- **来源**：存量（快照模式无基线）
- **判据**：review-checklist §11（资源清理）、§3（静默吞异常）
- **证据**：静态确定 —— 两处删除都是空 catch；`createFileFrom`（`:61-77`）在默认位置创建临时文件，`spillDir` 未显式配置时落在系统临时目录
- **描述**：实体展开量超过内存阈值时会把内容溢写到临时文件（这是防实体炸弹的正确做法）。但进程被 `SIGKILL`、OOM 杀死或 `close()` 未被调用时，这些临时文件会留在 `/tmp`；`removeIfExists` 失败（目录权限、文件被占用）时连一条日志都没有。长期运行 + 频繁解析大 XML 的进程会慢慢把 `/tmp` 填满，且从日志里查不到任何线索
- **建议**：删除失败记 `debug`/`warn`（带路径）；`createFileFrom` 生成的文件名带上 pid + 启动时间，便于外部清理；或在启动时清理「本进程遗留」的旧文件

### [轻微][存量] `ExpandSink.createFileFrom` 的候选回落把真实原因丢掉了

- **位置**：`f_xml/src/ExpandSink.cj:61-77`
- **来源**：存量
- **判据**：review-checklist §3（异常信息丢失）
- **证据**：静态确定 —— 循环里 `catch (_: Exception) { continue }`，最后统一抛「无法创建实体溢出文件，请显式指定 spillDir」
- **描述**：逐个候选失败的原因（目录只读、磁盘满、路径不是目录）全被丢弃；运维看到的是「请显式指定 spillDir」，而真实原因可能是「磁盘满」，按提示改配置也不会好
- **建议**：把每个候选的失败原因收敛到最终异常（`addSuppressed` 或拼进 message）

### [轻微][存量] `EntityLimits.maxDepth` 与 `XmlOptions.maxElementDepth` 默认值相差 256 倍，文档未说明两者关系

- **位置**：`f_xml/src/XmlOptions.cj:103-105`（`maxExpandedPerEntity` 64 KB、`maxExpandedTotal` 8 MB、`maxDepth` 16）、`f_xml/src/XmlOptions.cj:136-153`（`maxElementDepth` 默认 4096）、`f_xml/src/DoctypeParser.cj:124`（`maxDepth` 16）
- **来源**：存量
- **判据**：review-checklist §14（配置项可理解性）
- **证据**：静态确定 —— 两套 `maxDepth` 语义不同（实体递归 vs 元素嵌套），但命名相同、默认值差 256 倍
- **描述**：调参的人很容易把两个 `maxDepth` 当成同一个概念；把元素深度调到 4096 时并不会放宽实体递归，反之亦然
- **建议**：README / `XmlOptions` 注释里并列写清两者语义与默认值

## 总评

防线上做得比多数 XML 解析器扎实：解析是迭代式（不靠递归吃栈）、元素嵌套与参数实体递归各有独立深度上限、实体展开有「单实体 / 总量 / 硬上限」三级预算、超量后溢写磁盘而不是继续堆增长、写侧转义统一走 `Escaper`。本轮没找到严重或一般级的安全缺陷，问题集中在「溢写文件的清理与错误信息」这一类运维可见性上。**注意覆盖有限**：72 个 .cj 里只定向读了 7 个，`Lexer` / `RuneSource`（46 KB / 27 KB）未读，因此本报告的「无严重项」只对已读范围成立。存量 3 条（一般 1 / 轻微 2），是否纳入修复待用户决定。
