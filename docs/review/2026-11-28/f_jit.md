## 发现

### [一般][存量] `CompileCache.awaitReady` 用墙钟空转做退避，等待者多时是纯 CPU 燃烧

- **位置**：`f_jit/src/CompileCache.cj:128-150`（`:143-144` `let t = MonoTime.now(); while ((MonoTime.now() - t).toNanoseconds() < backoffNs) {}`）
- **来源**：存量（快照模式无基线）
- **判据**：review-checklist §6.4（忙等）、§12.1（并发退避）
- **证据**：静态确定 —— 两次检查之间的退避是**紧循环读时钟**，没有 `sleep`/`park`；注释自陈「旧实现自旋 500 万次、每轮取全局锁，实测 187 µs/次；改成墙钟退避后个位数 µs」，说明作者是**用测量数据**换掉了锁竞争，但没消掉 CPU 空转
- **描述**：同一 key 的等待者越多，空转的核越多；JIT 冷启动阶段大量并发首调同一函数时，最坏情形是 N 个线程各自 30 s 内空转（超时上限 `awaitTimeoutNs` 默认 30 s）。在容器 CPU 配额受限时，这会把「等待编译」放大成「抢不到 CPU 编译不完」，形成正反馈
- **建议**：退避后半段改用 `sleep(µs)`（柯颉 `std.sync` 的定时等待或 `Thread.sleep`），或改成条件变量/事件通知；已有的测量数据表明「不取锁」是关键，`sleep` 同样不取锁

### [轻微][存量] 失败缓存只能靠 `invalidateFailures()` 全量清空，没有单 key 失效

- **位置**：`f_jit/src/CompileCache.cj:110-118`
- **来源**：存量
- **判据**：review-checklist §11（缓存失效粒度）
- **证据**：静态确定 —— 注释自陈「失败单元没有 `close`…『先编译 → 失败 → 补注册类/函数 → 重试』会永久复述旧的『未注册』错误」，修法是提供一个全量 `clear()`
- **描述**：补注册一个类之后要清空**所有**失败记录，其它不相关的失败会被重新计算一遍（多花编译时间）；反过来若调用方忘记调用，失败会一直被复用
- **建议**：提供 `invalidateFailure(key)`；或在注册类/函数时按依赖关系自动失效
