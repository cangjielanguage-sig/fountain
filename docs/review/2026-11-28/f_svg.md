## 发现

### [一般][存量] `CssCalc.parsePrimary` 在错误分支漏减 `depth`，一次非法 `calc()` 会毒化后续解析

- **位置**：`f_svg/src/CssCalc.cj:179-201`（`depth++` 在 `:188`，`depth--` 只在成功路径 `:199`；`:192` 与 `:196` 两条 `return None` 均跳过递减）
- **来源**：存量（快照模式无基线）
- **判据**：review-checklist §11（错误路径的状态回滚）、§4（递归深度计数失真）
- **证据**：静态确定 —— 进入 `(` 分支先 `this.depth++`；内层 `parseExpression()` 返回 `None` 时直接 `return None`，括号不匹配时同样直接返回，两处都没有 `this.depth--`
- **描述**：`depth` 是**实例字段**（`private var depth: Int64 = 0`，`:81`），同一个 `CssCalc` 实例通常被整份样式表复用。一旦有个值写成 `calc(1px + )` 或 `calc((1px)`，`depth` 就永久 +1；再错 16 次后 `depth >= CSS_CALC_MAX_DEPTH`，此后**所有** `calc()`（哪怕完全合法）都返回 `None`，表现为「文档后半部分的 calc 全部失效」——错误与症状完全对不上，且不可恢复
- **建议**：`depth++` 之后用 `try/finally` 或在每条 `return None` 前递减；更稳的做法是把 `depth` 作为参数传递（纯函数式），避免实例状态

### [轻微][存量] 三套嵌套上限的命名相近、默认值相差 16 倍，缺少集中说明

- **位置**：`f_svg/src/CssCalc.cj:21`（`CSS_CALC_MAX_DEPTH = 16`）、`f_svg/src/SvgExternalDocument.cj:33`（`SVG_EXTERNAL_MAX_DEPTH = 4`）、`:41`（`SVG_USE_MAX_DEPTH = 64`）、`f_svg/src/SvgRenderTree.cj:817`（嵌套 svg 深度 64，硬编码在判断里）
- **来源**：存量
- **判据**：review-checklist §14（配置/常量可理解性）
- **证据**：静态确定 —— 三个常量分散在两个文件，嵌套 svg 的 64 直接写在条件里而不是常量
- **描述**：调上限时容易只改一处（或误以为它们联动）；`SvgRenderTree.cj:817` 的 64 与 `SVG_USE_MAX_DEPTH` 数值相同但语义不同，靠读代码才能区分
- **建议**：集中到一个 `SvgLimits`（或至少在 README 列一张表），嵌套 svg 的 64 也提成常量

## 总评

抽样到的防护面比预期扎实：`use` 链、嵌套 svg、外部文档引用三条递归路径都有显式上限（64 / 64 / 4），CSS `calc()` 也有深度上限（16），说明作者把「恶意/畸形 SVG 递归」当成了正经威胁在防。发现 1 恰好是这个防护自身的缺陷——**上限计数在错误路径不回滚**，把「防递归」变成了「一次语法错就永久失效」。**必须强调覆盖极低**：301 个 .cj 里只读了 4 个的部分段落（约 1.5%），文本渲染、滤镜、路径解析、渐变等大头完全没看，本报告不能代表 f_svg 整体。存量 2 条（一般 1 / 轻微 1），是否纳入修复待用户决定。
