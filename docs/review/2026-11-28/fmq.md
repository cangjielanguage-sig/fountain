## 发现

### [严重][存量] `flushOnce` 发送抛异常时整批备份丢失，与「不能凭空丢批次」的注释相反

- **位置**：`fmq/src/cluster/BackupReplicator.cj:139-158`（`batch = pending; pending = 新表` 在 143-152，`let retry = sendBatch(batch)` 在 153，无 try/catch）
- **来源**：存量（快照模式无基线）
- **判据**：review-checklist §11（数据丢失路径）、§3（失败不可观测）
- **证据**：静态确定 —— 批次在 `synchronized(lock)` 内被整体摘出并清空 `pending`，随后 `sendBatch(batch)` 不在任何 try/catch 里；只有它**正常返回**时才会 `requeue(retry)`。同文件 `:165` 的注释明确写「单节点：没有副本可发，不算失败（**不能凭空丢批次**）」
- **描述**：`sendBatch` 内部会调用 `transport.successors(backup)`、序列化、网络发送——任何一处抛异常（节点列表刷新失败、连接异常、编码异常），控制流直接跳出 `flushOnce`，`batch` 里所有 `BackupItem` 既不重入 `pending` 也不落盘，**这一批备份数据永久消失**，且调用方（定时器/主循环）只会看到一个异常。这是「备份链路在故障时最需要可靠」的反例
- **建议**：`try { retry = sendBatch(batch) } catch (e) { requeue(batch); throw/warn }`；`requeue` 本身也应有上限与丢弃日志

### [一般][存量] `pending` 待发队列没有上界，对端长期不可达时无界增长

- **位置**：`fmq/src/cluster/BackupReplicator.cj:86`（`private var pending = ArrayList<BackupItem>()`）、`:134`（`pending.add(...)`）、`:238-260`（`requeue` 合并回队）
- **来源**：存量
- **判据**：review-checklist §5（无界容器 → OOM）
- **证据**：静态确定 —— 入队与重入队都没有 `maxSize` 判断；`oldestEnqueuedMs` 只用于延迟统计
- **描述**：备节点长时间不可达（维护、网络分区）时，每个写入的 `record` 都会复制一份进 `pending`（`BackupItem` 持有 `record` 本体），内存随写入量线性增长直到 OOM；OOM 发生在**主节点**上，把「备节点故障」升级为「主节点崩溃」
- **建议**：给 `pending` 设条数/字节上限，超限时按策略处理（丢弃最旧 + 计数告警、或拒绝写入并返回明确错误）；把「积压条数与最旧条龄」暴露成指标

### [一般][存量] 批次内「已成功目标」的记账依赖分组结构，异常路径下无法回滚已完成部分

- **位置**：`fmq/src/cluster/BackupReplicator.cj:161-215`（`sendBatch` / `statesOf`）
- **来源**：存量
- **判据**：review-checklist §11（部分成功的一致性）
- **证据**：静态确定 —— `sendBatch` 按「待发目标集合」分组后逐组发送；某组抛异常时，前面已成功的组既不返回 `retry` 也不更新 `remainingTargets`（异常直接向上抛，`retry` 列表丢失）
- **描述**：与发现 1 同根因（缺 try/catch），但影响面不同：即使外层补了 `requeue(batch)`，整批重发会让**已成功的目标**收到重复副本（至少在「去重键」缺失时）。当前实现既没有「部分成功」的结果类型，也没有幂等键说明
- **建议**：`sendBatch` 返回 `(sentTargets, retryItems)` 并把异常转成 retry，配合下游按 `(topic, queueIndex, position)` 幂等

### [轻微][存量] 备份开关关闭时 `flushOnce` 直接返回，`pending` 里的旧条目不会清空

- **位置**：`fmq/src/cluster/BackupReplicator.cj:140-142`
- **来源**：存量
- **判据**：review-checklist §11（状态残留）
- **证据**：静态确定 —— `if (backup <= 0) { return }`，没有清空或告警
- **描述**：运行期把副本数改为 0 后，此前积压的 `pending` 永久驻留内存（直到进程退出），既不再发送也不释放
- **建议**：关闭时清空并记一条「丢弃 N 条积压备份」的日志

## 总评

读到的这条备份链路思路是对的（按目标分组、只重发未成功的目标、批次与网络分离、把「单节点无副本」判为成功），但**异常路径没兜住**：批次一旦被摘出队列，`sendBatch` 抛异常就是整批丢失，而同一文件的注释恰恰写着「不能凭空丢批次」。再加上 `pending` 无上界，备节点故障会先吃掉主节点内存、再由异常吃掉备份数据。**覆盖严重不足**：69 个 .cj 只精读 1 个，元数据存储、队列、日志清理都没展开，本报告不能代表整个 fmq。存量 4 条（严重 1 / 一般 2），是否纳入修复待用户决定。
