# f_mq 详细设计

> 需求来源：`.autocode/mq.md`（第 8–99、145–148 行：模块定义、编解码/通讯/核心功能、`f_mq` 配置）。
> 本文只覆盖 `f_mq`；服务端 `fmq` 见 `../../fmq/doc/详细设计.md`。
> 开发顺序见同目录 `开发计划.md`。

## 0. 术语

| 术语 | 含义 |
| --- | --- |
| 记录（record） | 一条消息的线上/落盘字节：`codec(TOPIC) + codec(TAGS) + codec(MESSAGE_ID) + codec(BODY)`，见 §3.2 |
| 节点（node） | 一个 `fmq server` 进程；节点集合与顺序由 `mqClient_hosts` 决定，下标从 0 开始 |
| 队列（queue） | 主题下按编号 0..queueNum-1 的逻辑队列；每个队列在**唯一一个**节点上有一份 SegmentedLog |
| 订阅（subscription） | 客户端一次 `subscribe` 产生的订阅实体，标识为 UUID 字符串 `subscribedId` |
| 订阅组（subscribe group） | 主题下的消费组；组内多个订阅者不重复消费；游标按组维护 |
| 所有者（owner） | 队列所在节点；主题的所有者集合 = 该主题各队列 owner 的并集 |

## 1. 模块定位

- 编译目标：**动态链接库**（`cjpm.toml: output-type = "dynamic"`），包名 `fountain::f_mq`。
- 使用方：
  1. 业务应用（仓颉应用/被 fboot 加载的模块）作为 MQ 客户端；
  2. `fmq` 服务端与 `fmq manager` 管理端（复用共用 API：数据模型、记录编解码、协议载荷与命令封装）。
- 依赖模块（`cjpm.toml`）：

| 模块 | 用途 |
| --- | --- |
| `f_base` | 异常基类 `BaseException`、退出回调 |
| `f_codec` | 记录编解码（`DefaultCodec`）、`Array<Byte>` 原始字节块编码 |
| `f_config` | 读取 `mqClient_hosts` |
| `f_data` | `Data`/`DataAny`/`DataObject<T>`、`f_data.path`（过滤器） |
| `f_io` | `f_io.ByteBuffer`（记录拼装） |
| `f_log` | 日志 |
| `f_net` | `Client<T>`、`MultiClient`、`MessageFuture`、`SocketBuffer` |
| `f_protocol` | `Message`/`MessageID`/`Command`（帧与命令；实现都在子包 **`fountain::f_protocol.default`**，`fountain::f_protocol` 本身只有 `Protocol`/`MessageCopier` 接口） |
| `f_time` | 超时/时间戳（`MonoTime`、`DateTime` 扩展） |
| `f_util` | `computeBytes`（字节量解析）、`UUID` |

## 2. 包级设计

| 包 | 意义 | 依赖（本模块内） | 依赖（模块外） |
| --- | --- | --- | --- |
| `fountain::f_mq` | 门面：`public import` 重导出 `base`/`client`/`exception` 的常用声明，业务侧只需 `import fountain::f_mq.*` | base, client, exception | — |
| `fountain::f_mq.base` | 共用 API：数据模型、记录编解码、协议载荷与命令封装、过滤器、错误码、主题名校验 | — | f_codec, f_data, f_protocol, f_util, f_log |
| `fountain::f_mq.client` | 客户端：`MQClient`（发布/订阅/消费/确认）、节点连接池、主题所有权缓存 | base, exception | f_net, f_config, f_log, f_time |
| `fountain::f_mq.exception` | 异常族：连接类、服务端错误类 | — | f_base |

依赖方向（箭头 = 依赖）：

```
exception ──> f_base
base ──> f_codec / f_data / f_protocol / f_util / f_log
client ──> base / exception / f_net / f_config / f_time
fountain::f_mq（门面） ──> base / client / exception
```

`fmq` 模块依赖 `f_mq` 的 `base`/`exception`（服务端与管理端不依赖 `client`；`fmq manager` 只依赖 `base` + `f_net`）。

## 3. 协议与记录格式（与规格逐条对齐）

### 3.1 命令映射

规格的 8 条命令 1:1 复用 `f_protocol` 已有命令（`f_protocol/src/default/constants.cj:113-129`，命令号 0–15 已被占满，**不新增命令**）：

| MQ 命令 | `f_protocol.Command` | 方向 | 载荷 |
| --- | --- | --- | --- |
| register（主题） | `REGISTER` | manager → 节点；节点 ↔ 节点 | `MQTopicMeta`；转发/同步用 `MQInternalMessage` |
| register（订阅组） | `REGISTER` | manager → 节点；节点 ↔ 节点 | `MQSubscribeGroupMeta`；同上 |
| deregister | `DEREGISTER` | manager → 节点；节点 ↔ 节点 | `MQDeregisterPayload` |
| publish | `PUBLISH` | 客户端 → 节点；节点 → 节点（备份） | `Array<Byte>`（记录）；备份用 `MQInternalMessage` |
| subscribe | `SUBSCRIBE` | 客户端 → 节点 | `MQSubscribePayload` |
| unsubscribe | `UNSUBSCRIBE` | 客户端 → 节点 | `MQUnsubscribePayload` |
| consume | `CONSUME` | 客户端 → 节点 | `MQConsumePayload` |
| ack | `ACK` | 客户端 → 节点 | `MQAckPayload` |
| error | `ERROR` | 节点 → 客户端 | `MQResult`（`code != 0`） |
| （响应） | `RESP` | 节点 → 客户端 / 节点 ↔ 节点 | 按请求而定，见 §3.3 |

> **约束（来自源码）**：`Command` 枚举的 16 个编号已全部占用且 `REGISTER`/`SUBSCRIBE` 等不带标志位参数
> （`f_protocol/src/default/constants.cj:113-155`），因此 MQ 不能在协议层新增命令或给这些命令加子类型标志；
> 「同一命令的不同用途」一律通过**载荷类型**区分（§3.4）。
>
> **与 f_net 内建行为的相容性**：`f_net` 的服务端读循环只截获「PING」与「id 匹配本连接在飞 ping 的 ACK」
> （`f_net/src/server/server.cj:150-156`），客户端的读循环只截获「PING」（`f_net/src/client/client.cj:62-64`）；
> MQ 的 `ACK` 由客户端用**全新的 `MessageID`** 发出，不会命中服务端的 ping id，因此能正常进入业务分发。

### 3.2 publish 记录字节布局

```
record = codec(TOPIC:String) ‖ codec(TAGS:Array<String>) ‖ codec(MESSAGE_ID:String) ‖ codec(BODY:T)
```

- 四部分**各自独立编码**、在网络流中连续排列（规格第 48–53 行）；`f_codec` 的编码自描述（每值带类型头与长度），
  因此接收侧可用同一个 `DefaultCodec` 依次 `decode<String>` / `decode<Array<String>>` / `decode<String>` / `decodeData` 逐段解出，
  不需要额外长度前缀（`f_codec/src/default/DefaultCodec.cj:141-220, 740-975`）。
- `MESSAGE_ID` 是 `fountain::f_protocol.MessageID` 的字符串表示（`MessageID.toString()`，格式
  `pid_tid_hostId_yyyyMMddHHmmssSSS`，`f_protocol/src/default/MessageID.cj:39-41`）。它与帧自带的 `Message.id` **是两条信息**：
  帧头里的 `MessageID` 用于请求/响应配对，记录里的字符串用于 MQ 侧标识与排障；客户端生成一次 `MessageID`，
  两者取同一个值（`Message.build<Array<Byte>>(command, id, record)`）。
  > `hostId` 来自配置项 `protocol_hostId`（**必填**，`f_protocol/src/default/ProtocolConfig.cj:24-33`）：
  > 未配或配 0 时构造 `MessageID` 抛 `IllegalArgumentException`。它同时是 `MessageID` 身份的一部分
  > （`(pid, tid, 时间戳)` 跨机器会重复），也是记录里 MESSAGE_ID 的节点维度。
  > 客户端发布时显式传入（`f_mq/src/client/MQClient.cj` 的 `publish`），保证帧 id 与记录标识带同一个主机号。

落盘时，`record` 由服务端 `QueueLog` 追加一层 `[4 字节大端长度][record]` 边界头（长度不含头部），
用于顺序读取定界；详细格式与跨版本约束见 `fmq/doc/详细设计.md` §5.8「记录格式」。该前缀不改变本节的
record 内部布局，也不出现在网络帧里。
- BODY 支持：任意基本类型、`String`、`Decimal`、`DateTime`、`Duration`、`@DataAssist[props fields]` 类，以及它们的
  `Array`/`ArrayList`/`HashSet`/`TreeSet`/`HashMap`/`TreeMap`（规格第 52 行）。这些类型在 `f_codec` 中均有
  `encode`/`tryFromData` 路径（`f_codec/src/default/DefaultCodec.cj:141-220` + `f_data/src/base/CollectionData.cj`、
  `MapData.cj`、`NumberData.cj`）。
- **记录进帧**：`Message` 的载荷字段是**单个** `Data`（`f_protocol/src/default/Message.cj:262` 依次编码
  `time/pid/tid/hostId/data`）。记录是「一串编解码值」，承载方式是把整串字节装进 `Array<Byte>` 作为载荷：
  `DefaultCodec.encode(data: Data)` 对 `DataCollection<Array<Byte>, Byte>` 有专门分支，走
  `encode(value: Array<Byte>)` 的**原始字节写出**（`f_codec/src/default/DefaultCodec.cj:150-151, 539-546`），
  解码侧对应返回 `array.toData()`（同文件 `:950-975`），即帧的 data 区内容 = 记录字节本身（外加一个长度头）。
  这样服务端拿到的 `Array<Byte>` 就是「从网络流接收到的字节序列」，可以**原样**写进 SegmentedLog（规格第 53 行）。
- **超过 4096 字节的记录会走临时文件（重要约束，验证时新发现）**：`DefaultCodec` 的解码侧有 `fileThreshold`
  （默认 4096，取值等于 `setBytesPool(arraySize:)`，`f_codec/src/default/DefaultCodec.cj:51, 70-75`）：声明长度
  ≤ 阈值 → 返回 `Array<Byte>`；**否则把载荷写进 `/tmp/tmpFile<UUID>/` 临时文件**并返回 `File` 包装的
  `DataInputStream`（同文件 `:962, 994-1035`）。因此 MQ 侧一律用 **`MQBytes.fromData(data: Data): ?Array<Byte>`**
  （§5.5）取记录字节：两种形态都支持，临时文件读回后要清理；**绝不能**直接把载荷当 `Array<Byte>` 转换——
  `convert` 的 SILENCE 语义会把它静默变成空数组，从而把「大消息」误判成「无消息」。
  进程若希望常用尺寸的消息不落临时文件，可在启动早期调用 `DefaultCodec.setBytesPool(arraySize: N)`
  （进程级静态设置、会影响同进程其它模块，需评估；见 §7 Q6）。

### 3.3 各命令载荷（`f_mq.base` 内的 @DataAssist 类）

| 命令 | 载荷类型 | 字段 |
| --- | --- | --- |
| register 主题 | `MQTopicMeta` | `topic: String`, `queueNum: Int64`, `delayingMs: Int64`（规格第 37–42 行给定前两项，`delayingMs` 为扩展） |
| register 订阅组 | `MQSubscribeGroupMeta` | `topic: String`, `subscribeGroup: String`, `revision: Int64`, `origin: Int64` |
| register 响应 | `MQTopicAssignment` / `MQResult` | 主题：分配结果；订阅组：`MQResult(0, "ok")` |
| deregister | `MQDeregisterPayload` | `kind: String`（`"topic"`/`"group"`）、`topic: String`、`subscribeGroup: String` |
| publish | `Array<Byte>` | 记录字节（§3.2） |
| subscribe | `MQSubscribePayload` | `subscribedId: String`（客户端生成的 UUID）、`topic: String`、`subscribeGroup: String`、`tags: Array<String>`、`filter: String`、`autoAck: Bool` |
| subscribe 响应 | `MQResult` | 0 = 成功 |
| unsubscribe | `MQUnsubscribePayload` | `subscribedId: String` |
| consume | `MQConsumePayload` | `subscribedId: String` |
| consume 响应 | `MQConsumeResult` | `queueIndex: Int64`、`segmentedIndex: Int64`、`segmentedOffset: Int64`、`record: MQBlob`（**空 blob = 本次没有消息**） |
| ack | `MQAckPayload` | `subscribedId: String`、`queueIndex: Int64`、`segmentedIndex: Int64`、`segmentedOffset: Int64` |
| ack 响应 | `MQResult` | 0 = 成功；`ACK_UNKNOWN` = 该位置不属于该订阅 |
| error | `MQResult` | `code != 0`，见 §3.5 |
| 内部消息 | `MQInternalMessage` | `kind: String`、`payload: MQBlob`（内部子载荷的编码字节） |
| 内部子载荷 | `MQMetaSyncRequest` / `MQMetaSnapshot` / `MQTopicAssignment` / `MQSubscribeGroupMeta` / `MQMetaTombstone` / `MQBackupPayload` / `MQBackupState` / `MQBackupCursor` | 见 §3.4.2 与 `fmq/doc/详细设计.md` §6 |

> 规格第 33、35 行要求 register 的载荷「以 `f_codec` 编码、解码为 `MQTopicMeta` / `MQSubscribeGroupMeta` 对象」——上表即按此落地。

### 3.4 载荷分派规则

接收侧一律用中性类型接收（`Server<DataAny>` / `Client<DataAny>`，理由见 `fmq` 文档 §6.1），随后按下表分派：

| 载荷形态（运行时 `Data` 子类型） | 解释 |
| --- | --- |
| `DataCollection<Array<Byte>, Byte>` | 记录字节（publish 的用户消息） |
| `SimpleDataObject`，`typeInfo` = `MQTopicMeta` / `MQSubscribeGroupMeta` / `MQDeregisterPayload` / `MQSubscribePayload` / … | 对应的命令载荷 |
| `SimpleDataObject`，`typeInfo` = `MQInternalMessage` | 内部消息：再按 `kind` 解出 `payload` 字节，按内部类型解码 |
| `DataNone` | 无载荷（如 `Message.ping()`） |

`SimpleDataObject.typeInfo` 是公开属性（`f_data/src/base/DataObject.cj:45-52, 102-106`），因此按类型分派是稳定且可测的。
`MQInternalMessage.kind` 目前有三种：`"metaSync"`（元数据同步请求/应用/快照）、`"backup"`（备份推送）
与 `"stats"`（指标查询）；子载荷用同一套 `f_codec` 编码为 `Array<Byte>`（自描述、可逐部分编码）。
`metaSync` 的子载荷有五种：`MQMetaSyncRequest`（请求快照）、`MQTopicAssignment`（主题分配）、
`MQSubscribeGroupMeta`（组变更）、`MQMetaTombstone`（删除墓碑）与 `MQDeregisterPayload`（旧版删除广播，
仍需兼容解码）；对应 `MQProtocol` 的五个 `metaSync` 重载。

### 3.5 错误码（`MQErrorCode` 常量）

| 码 | 名称 | 触发场景（规格） |
| --- | --- | --- |
| 0 | `OK` | 成功 |
| 1 | `TOPIC_NOT_EXIST` | publish/subscribe 的主题不存在（规格第 54、96 行） |
| 2 | `TOPIC_ALREADY_EXIST` | 重复注册主题 |
| 3 | `GROUP_NOT_EXIST` | 使用未注册的订阅组订阅（规格第 58–59 行，「必须报错」） |
| 4 | `GROUP_ALREADY_EXIST` | 重复注册订阅组 |
| 5 | `INVALID_TOPIC` | 主题不是合法绝对路径（规格第 97 行） |
| 6 | `INVALID_GROUP` | 订阅组名非法 |
| 7 | `SUBSCRIBE_NOT_EXIST` | unsubscribe/consume/ack 用了未知的 `subscribedId` |
| 8 | `NOT_OWNER` | 该节点没有此主题的任何队列（客户端据此换节点重试，见 §6.2） |
| 9 | `ACK_UNKNOWN` | ack 的位置与该订阅不匹配 |
| 10 | `FILTER_UNSUPPORTED_BODY` | filter 非空、但 BODY 的对象类型在本进程不可解码（§7 Q3） |
| 11 | `INTERNAL` | 其他内部错误 |

错误一律用 `Message.error(id: 请求id, data: MQResult)` 回给请求方（规格第 96 行）。

### 3.6 与帧的关系

```
f_protocol 帧: [version 1B][command 1B][len 4B BE][payload][crc32 4B]
payload      : codec(time) codec(pid) codec(tid) codec(hostId) codec(data)
data         : 见 §3.3（记录 / 载荷对象 / 空）
```

帧长度与 CRC 由 `f_protocol` 负责（`Message.cj:261-308, 351-386`）；`protocol_maxFramePayload` 默认 1GB，
由 `ProtocolConfig` 在**首次使用时**读取（`f_protocol/src/default/ProtocolConfig.cj`），因而不受包初始化顺序影响。

### 5.3 `MQMessage`（规格给定 + 约束细化）

```cj
@DataAssist[props fields]
public class MQMessage {
    private var topic: String = ''              // 订阅的 topic
    private var tags: Array<String> = []        // 消息 tags
    private var body: ?DataAny = None           // 消息内容（中性 Data）
    private var queueIndex: Int64 = 0           // 主题内的队列编号
    private var segmentedIndex: Int64 = 0       // 消息在 SegmentedLog 的段索引
    private var segmentedOffset: Int64 = 0      // 段内偏移

    /** 严格转换：空/异类 BODY 返回 None，绝不返回「字段全默认对象」（A04） */
    public func get<T>(): ?T where T <: DataFields<T>
    public func toData(): Data    // @DataAssist 生成
}
```
- **相对规格的调整（决策 D1）**：规格片段写作 `DataObject<T>.populate(body.data)`，其约束是
  `T <: ObjectData<T> & DataFields<T>`（`f_data/src/base/DataObject.cj:194-224`），只能取 `@DataAssist` 类，
  取不了 `Int64`/`String` 这类标量；而规格允许 BODY 是任意基本类型。改用严格 `convert<T>`（`f_data/src/base/DataFields.cj:46`）
  可同时覆盖两类，语义一致（`DataObject<T>.populate` 是它的一条特例路径）。同时把泛型约束显式写全（规格片段缺约束，无法编译）。
- `get<T>` 的判定顺序：BODY 为 `None`/`DataNone`/空字节 → `None`；对象 BODY 的 `typeInfo.qualifiedName`
  与 `T` 不符 → `None`；其余走严格转换，异常折回 `None`。
- `queueIndex` 与两个位置字段一起由 `consume` 填充，`ack` 必须原样带回；缺了 `queueIndex` 会确认到错误的队列。
- `body` 为空（`None`）表示消息 BODY 是 `DataNone`（例如发布 `None`）。

### 5.5 `MQMessageRecord`

```cj
public class MQMessageRecord {
    /** 逐部分编码：codec(topic) ‖ codec(tags) ‖ codec(messageId) ‖ codec(body) */
    public static func encode<T>(topic: String, tags: Array<String>, messageId: String, body: T): Array<Byte>
        where T <: ToData
    /** 完整解码；结构损坏返回 None（截断/多余字节都被判为损坏） */
    public static func decode(record: Array<Byte>): ?MQMessageContent
    /** 只解出 TOPIC（服务端路由用，不碰 BODY） */
    public static func topic(record: Array<Byte>): ?String
    /** 只解出 TAGS（服务端 tags 匹配用） */
    public static func tags(record: Array<Byte>): ?Array<String>
    /** 只解出 BODY 的 Data（服务端 filter 求值用；BODY 之后的字节不计入） */
    public static func body(record: Array<Byte>): ?DataAny
    /** 解出 MESSAGE_ID 字符串（排障/日志用） */
    public static func messageId(record: Array<Byte>): ?String
}
```
- 实现要点：
  - 编码：`DefaultCodec()` 连续 `encode` 后 `finish().copy(to: f_io.ByteBuffer)`，再取 `bytes()`；
    收尾必须 `release()`（`f_codec/src/default/DefaultCodec.cj:675-688`）。
  - 解码：把 `record` 包成 `f_io.ByteBuffer`（`f_io/src/ByteBuffer.cj:22-152`），用同一个 `DefaultCodec` 顺序解码；
    `decodeData` 只消费一个自描述值，因此「只解前几段」不会越界。
  - 损坏判定：`decode` 要求四个部分全部解出且**恰好消费完 `record.size` 字节**；判定用 `ByteBuffer.readOffset`
    与入参长度比较（`ByteBuffer` 没有 `size` 属性，`f_io/src/ByteBuffer.cj:41-58`），**不要依赖「读不满自动归零」**：
    `ByteBuffer.read` 读不满时会 `clear()` 把读写偏移归零（同文件 `:59-65, 119-134`），会把截断伪装成「恰好用尽」。
- **`MQBytes` / `MQBlob`（记录的字节层工具，同属本层）**：`MQBytes.fromData(data: Data): ?Array<Byte>` ——
  把载荷还原为字节：字节块形态（`DataCollection<Array<Byte>, Byte>`）直接返回；临时文件形态
  （`DataInputStream` 包 `File`，见 `f_codec/src/default/DefaultCodec.cj:962, 994-1035`）读回后删除文件与父目录；
  其它形态返回 `None`（宁可失败也不返回空数组）。
  `MQBlob` 是载荷字段类型（`DataFields<MQBlob>`）：`tryFromData` 覆盖同一套形态矩阵，读取临时文件后
  `close` → 删文件 → 删父目录；`toData()` 与 `Array<Byte>.toData()` 字节完全一致，因此不改变线格式。
  字段为 `MQBlob` 的载荷必须用 `record.copyBytes()` / `record.size()` 读取，构造仍保留 `Array<Byte>` 重载。
- 调用关系：`MQClient.publish` → `encode`；`fmq` 的 publish 分发 → `topic`；tags 匹配 → `tags`；filter → `body`；
  客户端 `consume` → `decode`；`MQProtocol.asRecord`/`asConsumeResult`/`asInternal` 与 `fmq` 的 publish 分发 → `MQBytes.fromData`。

### 5.8a 名称字符集与长度上限

四类名字的合法集与长度上限，客户端与服务端共用同一实现（`MQTopic` / `MQGroup` / `MQTags` +
`MQChars.containsBlankOrControl`），不合法时客户端本地失败（`INVALID_TOPIC` / `INVALID_GROUP` /
`INVALID_TAGS`），服务端再校验一次作为权威：

| 项 | 常量 | 上限 | 字符集 |
| --- | --- | --- | --- |
| 主题 `MQTopic` | —（无显式长度上限） | — | 以 `/` 开头、不以 `/` 结尾、无 `//` 空段；不含空白与控制字符（按 Unicode 码点） |
| 组名 `MQGroup` | `MQGroup.MAX_LENGTH = 255` | 255 字节 | 空串合法（默认组）；不含空白/控制字符；不含 `/` `\` `:` `%`；不以 `.` 开头或结尾 |
| tags 数量 `MQTags` | `MQTags.MAX_COUNT = 64` | 64 个 | — |
| 单个 tag `MQTags` | `MQTags.MAX_LENGTH = 128` | 1..128 字节 | 非空；不含空白与控制字符（按 Unicode 码点） |
| 单条记录 `QueueLog` | `MAX_RECORD_SIZE` / `effectiveMaxRecord` | `min(MAX_RECORD_SIZE, maxFileSize - 4)` | 记录不得跨段；零长度头视为损坏段 |

- 组名会直接成为 `metas/groups/<escaped>.meta` 与 `cursors/<escaped>.cursor` 的文件名，因此路径与转义字符必须在入口挡下。
- 单条记录上限由段上限派生（`fmq` 侧）：段上限配得比记录上限小时，实际上限取 `maxFileSize - 4`；超限由
  `LogRecordTooLargeException` 在写入前拒绝，不会产生越界写。

### 5.11a 统计与延迟辅助

- `MQProtocol.stats(topic)`：`REGISTER` + `MQInternalMessage{kind="stats"}`，子载荷为 `String`；

  TTL 常量 `ownershipTtl = Duration.minute`（超时后重新探测，覆盖节点扩容/主题重分配）。

## 6. 客户端行为设计

### 6.1 初始化

1. `MQClientConfig.hosts` → 节点表（下标 = 顺序）；
2. 建 `MQNodePool`（懒连接：首次用到某节点才 `Client` 建连）；
3. 建 `MQOwnershipCache`、订阅表。
- 初始化不主动连任何节点（连不上不在启动期爆错，而在首次调用时报 `MQConnectionException`）——避免「一个节点抖动导致客户端无法启动」。

### 6.2 publish 路由

1. `topic` 合法性与 `tags` 校验；
2. 目标节点 = `MQOwnershipCache.ownersOf(topic)` 的第一个可用节点；缓存未命中 → 按节点顺序尝试；
3. `transfer(publishMsg, publishTimeout=5s)`：
   - `RESP`/`MQResult(0)` → 成功；
   - `ERROR` + `NOT_OWNER` → 标记该节点不是 owner（缓存并集修正），换下一个节点重试；
   - `ERROR` + `TOPIC_NOT_EXIST` → 抛 `MQServiceException`（规格第 54 行）；
   - 超时/连接异常 → 换下一个节点，全部失败抛 `MQConnectionException`。

### 6.3 subscribe

1. 生成 `subscribedId = UUID.random().toString()`（规格第 65 行「用 UUID 表示」）；
2. `MQFilter.compile(filter)` 预编译（本地快速失败）；
3. **向所有配置节点**发送 `SUBSCRIBE`（各带 `subscribedId`），收集响应：
   - `MQResult(0)` → 该节点是所有者，加入 `owners`；
   - `NOT_OWNER` → 跳过；
   - `TOPIC_NOT_EXIST` / `GROUP_NOT_EXIST` → 中止并向已接受的节点补发 `UNSUBSCRIBE`（回滚），抛 `MQServiceException`
     （规格第 58–59 行要求对未注册的订阅组报错）；
   - 连接失败 → 记录，若最终 `owners` 为空则抛 `MQConnectionException`；
4. `owners` 写入订阅与所有权缓存。
- 说明：客户端**不做注册/删除主题**——只有 `fmq manager` 可以（规格第 30、35、45、47 行），客户端 API 里没有对应入口。

### 6.4 consume

1. 取订阅，按 `cursor` 轮转 `owners`（每轮对每个 owner 发一次）；
2. 对 owner 发 `CONSUME(subscribedId)`，`transfer(..., consumeTimeout=1s)`：
   - `MQConsumeResult.record` 非空 → 解码记录（`MQMessageRecord.decode`）→ 组 `MQMessage`（填位置）→
     记录 `deliveries[(index,offset)] = node` → 返回；
   - `record` 为空 → 下一个 owner；
   - `ERROR` + `SUBSCRIBE_NOT_EXIST` → 抛 `MQServiceException`（订阅已失效，需重新 subscribe）；
3. 全部 owner 都空 → `sleep(consumePollInterval)` 后重试（**阻塞直到拿到消息**）。

### 6.5 ack

1. 按 `deliveries` 查投递来源节点（命中即删）；
2. 未命中（例如进程重启后重放）→ 向所有 owner 广播 `ACK`，忽略 `ACK_UNKNOWN`；
3. `autoAck = true` 的订阅：服务端在投递时已推进游标（规格第 64 行），客户端**不需要**调用 `ack`；
   此时 `deliveries` 不记录（省内存），`ack` 被显式调用时按第 2 条广播处理。

### 6.6 unsubscribe / close

- `unsubscribe`：向所有 `owners` 发 `UNSUBSCRIBE`；本地删除订阅与 `deliveries`；`SUBSCRIBE_NOT_EXIST` 忽略（幂等）。
- `close`：`MQNodePool.close()`（`Client.close()` 幂等）→ 清空订阅表 → 标记关闭。

### 6.7 线程安全

- `MQClient` 的所有公开方法可并发调用：订阅表/`deliveries`/所有权缓存用 `ConcurrentHashMap`；
  `MQClient.close()` 与其它方法之间用 `f_net` 的 `Client` 语义兜底（关闭后 `transfer` 抛异常）。
- `consume` 的唯一认领：同一 `(queueIndex, index, offset)` 不会被两个线程同时取出——用 `deliveries.addIfAbsent`
  原子占位，未抢到则继续下一个 owner；`ack` 成功后才删除映射，失败时保留以便重试。

## 7. 关键设计决策与开放问题

### 决策

| 编号 | 决策 | 理由 / 依据 |
| --- | --- | --- |
| D1 | `MQMessage.get<T>()` 用 `convert<T>` 且显式写全泛型约束 | 规格片段无法编译且只覆盖 `@DataAssist` 类；见 §5.3 |
| D2 | filter 的「结果为 true」在 MQ 侧定义：空迭代 = false；首元素 `DataBool(b) → b`；`DataNone → false`；其它 → true | `f_data.path` 只公开 `get()`，布尔判定入口是 `internal` |
| D3 | 客户端 `publish<T>(topic, body, tags!)` 形态 | 规格只给了协议格式；客户端必须有一个入口（可随用户意见调整） |
| D4 | `consume` 阻塞直到取到消息；服务端单次 `CONSUME` 立即返回「有/无」 | 规格返回类型非可空；长轮询放在客户端循环，服务端不需要挂起请求 |
| D5 | `subscribedId` 由**客户端**生成并携带 | 订阅跨多个 owner 节点，需要同一 id；规格只要求「用 UUID 表示」 |
| D6 | 不新增 `f_protocol` 命令，同一命令的多用途靠载荷类型区分 | 命令号 0–15 已满、`REGISTER` 等不带标志位；见 §3.1 |
| D7 | 记录在帧内以 `Array<Byte>` 原始字节块承载 | `f_codec` 对 `DataCollection<Array<Byte>,Byte>` 有原始字节分支，服务端可原样落盘（规格第 53 行） |
| D8 | 服务端元数据同步/备份等内部消息用 `MQInternalMessage` 信封 | 无法新增命令；内部消息不污染用户载荷语义 |
| D9 | 记录字节一律经 `MQBytes.fromData` 还原（兼容「字节块」与「>4KB 落临时文件」两种载荷形态），失败返回 `None` 而不是空数组 | `DefaultCodec` 的 4096 阈值会改变解码结果的 Data 形态（`f_codec/src/default/DefaultCodec.cj:962, 994-1035`）；静默空数组会把大消息误判成「无消息」 |

### 开放问题（需用户裁决；未裁决时按「建议」实现）

| 编号 | 问题 | 建议 |
| --- | --- | --- |
| Q1 | 服务端节点表从哪个配置项读？规格只在 `## f_mq` 一节给了 `mqClient_hosts`，但服务端也要知道「所有服务节点」 | 服务端与管理端同样读 `mqClient_hosts`（本机身份按 `mqServer_port` 端口匹配，见 fmq 文档 §6.1） |
| Q2 | filter 的布尔判定规则（D2 的「存在即真」）是否符合预期？ | 先按 D2 实现，规则独立成 `MQFilter`，改规则只动用例 |
| Q3 | BODY 为对象类型（`@DataAssist` 类）时，服务端**无法解码**（该类型未在 fmq 进程注册，`f_codec/src/default/DefaultCodec.cj:921-937` 直接抛 `CodecException`）⇒ 服务端 filter 对这类 BODY 不可用 | 方案 A（本期）：订阅带非空 filter 时，publish 遇到对象 BODY 回 `FILTER_UNSUPPORTED_BODY` 错误（不丢、不误投）；方案 B：仅当 BODY 类型在 fmq 进程也存在时可用现成的 `DefaultCodec.registerType<T>()`（`f_codec/src/default/DefaultCodec.cj:76-86`）显式登记，**任意客户端自定义类型仍无解**，根治要 f_codec 支持「未知对象类型的兜底解码」（或配一个类型声明操作） |
| Q4 | `consume` 是否需要带超时的重载（`consume(id, timeout!)`），以及是否需要非阻塞版 `tryConsume` | 建议后续加非破坏性重载，本期只按规格签名实现 |
| Q5 | 是否需要客户端级的「主题元数据查询」API（列出主题/分配） | 规格未要求；`fmq manager listTopics` 已覆盖运维需求，本期不加 |
| Q6 | 是否在进程启动时调用 `DefaultCodec.setBytesPool(arraySize: N)` 把记录的解码阈值从 4096 提高（避免常用尺寸的消息落 `/tmp` 临时文件）？ | 该设置是**进程级静态**的（会影响同进程的 f_rpc 等其它模块），建议先按默认 4096 + `MQBytes` 兼容两种形态落地，等有实测数据再决定是否调大 |
